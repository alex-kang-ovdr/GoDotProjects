# 12. 산소·화재·균열·수리 시스템

> 범위: FTL 본편 및 AE, 모드 제외. 확인일: 2026-11-13. [확인]은 공개 자료의 규칙, [해석]은 설계 의미, [재구성안]은 독립 구현 모델이다. 특히 산소 유동식과 화재 확산식은 원작 코드의 복원이 아니다.

## 1. 시스템 목적

이 시스템은 피격을 단일 체력 감소에서 공간 문제로 바꾼다. 같은 선체 피해라도 무기실 화재, 산소실 균열, 조종실 고립은 서로 다른 대응을 요구한다. 수리하는 동안 다른 일을 할 수 없다는 인력 비용이 피해의 장기 효과를 만든다.

**[해석]** 환경 위험은 전투가 잠시 멈춘 순간에도 이미 받은 피해의 결과를 남긴다. 따라서 승패 판정 뒤에 모든 방을 자동 정리하면 살아남았지만 함선이 위험한 FTL의 상태를 재현하지 못한다. 실제 위험 종료 조건과 안전 상태로의 전이는 [01](01_core_loop_run_state.md), 승무원 작업은 [10](10_crew_species_and_training.md)과 연결한다.

| 상태 | 영향을 받는 대상 | 대표 해결 수단 |
|---|---|---|
| 저산소·진공 | 산소를 필요로 하는 승무원, 화재 | 산소 공급 복구, 문 연결·격리 |
| 화재 | 승무원, 설비, 산소, 주변 타일 | 직접 진화, 산소 차단, 배기 |
| Hull Breach | 해당 방 산소, 설비 작업 접근 | 균열 봉합 |
| 시스템 손상 | 설비 용량·작동 | 승무원·수리 드론 등 |
| 선체 손상 | 함선 전체 생존 | 상점·이벤트·선체 수리 수단 |

## 2. 선체와 균열의 구분

**[확인]** Hull Breach는 방의 산소가 빠지는 상태이며, 균열이라는 부가 효과가 생겼다는 이유로 선체 피해가 추가되는 것은 아니다. 균열을 고치는 행위와 감소한 선체 HP를 복구하는 행위도 서로 다르다. 같은 방의 시스템 수리·조작에는 균열 처리가 영향을 준다. [E01]

**[재구성안]** 피해 이벤트를 아래처럼 분해한다.

```text
DamageResult
  hullDelta
  systemDamageByRoom
  crewDamageByEntity
  igniteTiles
  createBreachTiles
  ionStatus
```

`createBreachTiles`를 적용하는 함수에서 `hullDelta -= 1` 같은 추가 피해를 관성적으로 넣지 않는다. 폭발 무기·드론·이벤트마다 상위 피해 데이터가 실제 선체 피해를 결정한다.

## 3. 방별 산소

**[확인]** 산소는 방마다 다르고, 전체 함선 산소 표시만으로 각 방의 안전성을 판단할 수 없다. 산소 시설, 열린 문, 우주로 열린 에어록, 균열, 화재, Lanius가 영향을 준다. 질식은 해당 방 산소가 5% 이하일 때 발생하며, 함선 평균 산소가 25% 미만이면 저산소 경고가 나타난다. 일반 승무원 질식 피해는 자료상 초당 6.4 HP다. [E02]

| 경계값 | 확인된 의미 | 잘못된 해석 |
|---|---|---|
| 방 산소 ≤5% | 질식 위험 | 전체 평균이 높으면 해당 방도 안전 |
| 방 산소 <10% | 화재가 소멸하는 방향으로 진행 | 임계값 통과 순간 모든 불 즉시 삭제 |
| 함선 산소 <25% | 전체 경고 | 모든 방이 똑같이 25%라는 의미 |

**[해석]** 전체 게이지는 거시적 경보이고 방 색상은 즉시 행동을 위한 미시 정보다. 두 표현은 중복이 아니라 서로 다른 범위의 상태를 설명한다.

### 3.1 공급과 유출

**[재구성안]** 방을 노드, 문과 에어록을 연결로 보는 저비용 시뮬레이션이 적합하다. 매 틱 각 방의 공급·흡수·유출을 누적한 뒤 함께 적용한다. 아래 식은 설계 설명용이며 원작 수식이 아니다.

$$
O_r^{t+\Delta t}=\operatorname{clamp}\left(O_r^t+\Delta t\left(P_r-C_r-L_r+\sum_j F_{j\rightarrow r}\right),0,1\right)
$$

- `P`: 산소 시설에 의한 공급.
- `C`: 환경·종족 등 산소 소비·흡수.
- `L`: 균열·외부 개방에 따른 손실.
- `F`: 열린 연결을 통한 방 사이 교환.

방 간 교환은 한쪽에서 뺀 양과 다른 쪽에 더한 양을 맞춰야 한다. 같은 연결을 양쪽 방 갱신에서 두 번 적용하면 산소가 생성·소멸하는 오류가 생긴다. 실제 원작의 확산 속도·방 크기 보정·에어록 처리 순서는 별도 실측 대상이다.

### 3.2 배기는 공간 전체를 사용하는 명령

**[해석]** 에어록과 여러 문을 열면 위험 방을 고립시키는 대신 그 경로의 공간을 포기하게 된다. 수리가 필요한 방과 안전한 이동 통로가 동시에 줄어드는 점이 비용이다. “불이 있는 방만 산소를 0으로 만들기” 같은 직접 명령으로 대체하면 레이아웃과 문 시스템의 의미가 사라진다.

## 4. 화재

**[확인]** 화재는 타일에 생성되고 다른 타일·방으로 퍼질 수 있다. 불은 산소를 소비하고 승무원·시설에 지속 피해를 주며, 시설을 완전히 태워 파괴하면 선체 손실로 이어질 수 있다. Rockman과 선내 드론 등에는 화재 피해 면역이 있다. 강화된 문은 방 간 전파에 영향을 준다. [E03]

### 4.1 화재의 상태 모델

**[재구성안]** 타일 화재와 방 화재 집계를 함께 관리한다.

```text
FireTile
  tileId, roomId
  intensityOrHealth
  spreadTimer
  oxygenStarvationTimer
  activeExtinguishers
```

같은 타일에 여러 발의 무기가 적중했을 때는 화재 인스턴스를 무한 중첩하지 않는다. 원작의 중첩·확률 처리 규칙을 확인하여 강도 갱신 또는 생성 무효로 처리한다. 화재가 없는 타일과 이미 불타는 타일에 대한 확률은 별도 데이터로 검증한다.

### 4.2 피해와 작업 중단

**[해석]** 화재는 직접 피해, 산소 저하, 시설 파괴, 인력 강제 이동이라는 서로 다른 비용을 결합한다. 한 항목의 피해율이 낮더라도 다른 작업을 중단시키면 가치가 커진다. 화재 무기의 밸런스를 선체 DPS만으로 비교할 수 없는 이유다.

**[검증 필요: 출처 충돌]** 커뮤니티 Wiki의 `Boarding` 문서는 불 하나의 대인 피해를 1.2 HP/s, `Fires` 문서는 2.128 HP/s로 다르게 서술한다. 본 문서는 어느 값도 확정 상수로 채택하지 않는다. 원작 버전, 피해 판정 주기, 방 안 불 개수, 승무원 위치를 고정한 실험으로 검증해야 한다. 숫자를 적당히 평균내지 않는다. [E03, E04]

## 5. 균열과 복구 순서

**[해석]** 균열은 추가 피해원인 동시에 작업 방해물이다. 산소를 빼내므로 장시간 수리할 인원의 체력이 줄고, 시스템 복구에 앞서 별도 작업을 요구할 수 있다. 피해량은 같아도 균열이 있는 방이 더 오래 마비되는 구조다.

**[재구성안]** 방의 복구 일을 다음처럼 서로 다른 작업으로 등록한다.

| 작업 | 완료 시 바꾸는 값 | 완료해도 복구되지 않는 값 |
|---|---|---|
| 균열 봉합 | 균열의 존재·유출 | 이미 줄어든 산소, 선체 HP |
| 진화 | 불의 존재·강도 | 시스템 손상, 선체 HP |
| 시스템 수리 | 사용 가능한 시스템 막대 | 선체 HP, 다른 방 위험 |
| 선체 복구 | 전체 함선 HP | 실내 위험·손상 모두를 자동 복구하지 않음 |

작업자는 매 프레임 모든 작업을 동시에 수행하는 만능 수리원이 아니다. 적의 존재, 화재, 균열, 고장, 조작 가능성에 따라 작업이 선택되어야 한다. 정확한 원작 우선순위가 미확정인 조합은 테스트 케이스로 남긴다.

## 6. 승무원·드론·종족 연동

종족 수치의 기준은 [10](10_crew_species_and_training.md)이며 여기서는 조합의 의미만 분석한다.

| 조합 | [해석] 얻는 이점 | 남는 제약 |
|---|---|---|
| Rockman + 화재 방 | 진화 중 화재 피해를 받지 않음 | 산소가 고갈되면 별도 질식 위험 |
| Engi + 여러 고장 | 빠른 수리로 연쇄 장애 시간 축소 | 진공·적의 공격에는 안전하지 않음 |
| Lanius + 균열 방 | 산소 부족 환경에서 작업 지속 | 다른 종족의 합류를 어렵게 할 수 있음 |
| 수리 드론 + 위험 방 | 생물 승무원 노출 감소 | 전력·드론 제어 상태와 자동 목표에 의존 |
| 의료실 + 저산소 | 회복과 환경 피해가 동시에 발생 | 산소 문제 자체가 해결된 것은 아님 |

**[재구성안]** 면역을 `environmentImmune=true` 하나로 저장하지 않는다. `immuneToFire`와 `needsOxygen`, 질식 피해 배율, 회복 가능 여부를 분리해야 Rockman과 Lanius의 차이를 재현할 수 있다.

## 7. 대표 연쇄 상황

### 상황 A: 산소실에 균열이 발생한 경우

1. **[해석]** 시스템 피해로 공급이 약해지고 균열로 해당 방 산소가 빠진다.
2. 수리 인원을 보내면 낮은 산소가 체력 비용을 발생시킨다.
3. 문을 열어 주변 방의 산소를 공유할지, 다른 방을 보호하기 위해 격리할지 선택한다.
4. 균열을 막고 시스템을 복구해도 이미 줄어든 산소는 다시 채워져야 한다.
5. 체력이 낮은 인원은 복구 완료 전 교대하거나 안전한 방으로 철수해야 할 수 있다.

### 상황 B: 화재 방을 배기한 뒤 산소를 재공급

**[해석]** 문을 열어 진공으로 만들었다고 즉시 다음 작업자를 투입하는 것은 별도 위험이다. 불의 소멸, 에어록 폐쇄, 산소 회복, 이동 경로 확보는 서로 다른 시점에 완료된다. UI에서 “불 없음”과 “안전함”을 같은 색으로 표시하면 잘못된 명령을 유도한다.

## 8. 재구성 갱신 순서

아래 순서는 결정적 재생과 테스트를 위한 **[재구성안]**이다. 원작의 업데이트 순서를 확인했다는 의미가 아니다.

1. 이번 틱 입력과 문·전력 상태 변경을 적용한다.
2. 방별 산소 변화량을 이전 스냅샷 기준으로 계산한다.
3. 산소를 동시에 갱신한다.
4. 화재의 피해·확산·소멸 후보를 계산한다.
5. 승무원 환경 피해와 작업 진행을 갱신한다.
6. 완성된 수리·진화·봉합을 처리한다.
7. 시스템 파괴에 따른 선체 손실과 승무원 사망을 한 번씩 확정한다.
8. 경고·오디오·방 색상을 결과 상태에서 갱신한다.

동일 틱에 불이 꺼지고 수리가 끝나는 경우가 실행 플랫폼마다 달라지지 않도록 동률 규칙을 정한다. 일시정지에서는 이 루프의 시뮬레이션 시간이 진행되지 않아야 한다.

## 9. QA 및 수용 기준

| ID | 조건 | 기대 결과 |
|---|---|---|
| ENV-01 | 선체 피해 없이 균열만 생성 | 선체 HP 그대로, 방 산소만 관련 규칙으로 변화 |
| ENV-02 | 균열 봉합 | 유출은 멈추지만 선체 HP 자동 회복 없음 |
| ENV-03 | 평균 산소 높고 방 하나만 저산소 | 그 방 인원에게 질식 적용 |
| ENV-04 | 닫힌 방에 Lanius·Human 동시 배치 | 서로 다른 환경 반응 |
| ENV-05 | Rockman을 저산소 화재 방에 배치 | 화재 면역과 질식 피해를 별도로 적용 |
| ENV-06 | 시스템 완전 파괴 순간 여러 불 존재 | 선체 손실 사건 중복 발행 방지 |
| ENV-07 | 프레임 속도를 바꿔 같은 배기 시나리오 | 초 단위 결과가 허용 오차 내 일치 |
| ENV-08 | 문을 열고 닫기를 반복 | 산소가 경계값을 초과하거나 음수가 되지 않음 |
| ENV-09 | 일시정지 상태에서 배기 명령 | 명령은 기록해도 산소·화재 시간이 진행되지 않음 |
| ENV-10 | 전투 승리 순간 화재·균열 잔존 | 무조건 실내 초기화하지 않음 |

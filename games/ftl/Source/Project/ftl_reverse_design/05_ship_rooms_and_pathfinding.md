# 05. 함선 구조·방·문·승무원 이동 역기획

> 대상: FTL: Faster Than Light PC 기본 게임 + Advanced Edition(AE). 확인일: 2026-11-13.\
> [확인]은 공개 자료로 확인한 게임 동작, [해석]은 설계 분석, [재구성안]은 재현용 제안이다. 원본 엔진의 코드·자료구조를 열람한 문서가 아니다.

## 1. 시스템의 목적과 경계

FTL의 함선은 화면에 그려진 우주선 이미지와 별도로, **방·타일·출입문으로 연결된 전술 공간**으로 작동한다. 우주 공간에서 함선을 직접 조종하는 대신 내부 인력을 이동시켜 운용·수리·방어를 수행한다. 따라서 내부 평면도는 외형 장식이 아니라 성능의 일부다.

[확인] 시스템은 함선별로 정해진 방에 설치된다. 상점에서 시스템을 구입해도 원하는 방에 자유 배치하거나 기존 방 위치를 바꾸는 건설 방식은 아니다.[S1]

| 입력 | 처리 | 출력 |
|---|---|---|
| 승무원 선택·목적 방 지정 | 도달 가능 경로와 도착 위치 결정 | 이동 명령·예약 위치 |
| 문 개폐 명령 | 문 상태 및 방 연결 갱신 | 통행 가능성·산소 교환 변경 |
| 탑승·귀환·정신 지배 | 소속·체류 함선·점유 상태 변경 | 아군/적군의 이동 권한 변경 |
| 해킹·크리스탈 봉쇄·문 파괴 | 연결 조건 변경 | 우회·문 공격·대기 상태 |
| 방에 도착 | 할 일과 작업 위치 선택 | 운용·수리·진화·백병전 |

승무원 피해와 수리 속도는 [10장](10_crew_species_and_training.md)·[11장](11_boarding_and_personal_combat.md), 산소와 화재는 [12장](12_atmosphere_fire_breach_repair.md)을 참조한다.

## 2. 공간을 구성하는 객체

### 2.1 방과 타일

[확인] 일반적인 플레이어 함선 내부는 작은 타일 단위의 방들로 나뉜다. 방마다 시스템 유무, 승무원이 서는 자리, 연결된 문이 달라진다. 의료실처럼 설비가 자리를 차지하는 방은 보이는 바닥 타일 수와 실제 정지 가능한 인원 수가 같지 않을 수 있다.[S2]

[재구성안] 다음 항목을 분리해야 방과 타일의 기능을 혼동하지 않는다.

| 객체 | 보유 정보 | 잘못 합쳤을 때의 문제 |
|---|---|---|
| ShipLayout | 방 배치, 연결, 시스템 설치 위치 | 함선 이미지와 판정이 불일치 |
| Room | 산소량, 시스템 ID, 타일 목록 | 타일 하나의 불이 방 전체 불로 처리됨 |
| Tile | 화재, 균열, 정지 위치, 통행 좌표 | 위치에 따라 달라지는 피해를 표현 불가 |
| Door | 양쪽 방 또는 외부 우주, 상태, 통행 권한 | 환기와 통행이 항상 동일하다고 오판 |
| Station | 운용 콘솔의 위치·방향 | 방에 있는 것과 운용하는 것을 혼동 |
| CrewPosition | 현재 위치·목표 위치·이동 진행 | 일시정지 중 연속 명령이 중복 배치됨 |

### 2.2 함선의 체력과 방의 상태

[확인] 선체 내구도(Hull), 시스템 손상, 승무원 체력은 서로 다른 자원이다. 방을 피격해도 모든 내부 상태를 하나의 방 HP로 환산하지 않는다. 빈 방을 맞아도 선체 피해를 받을 수 있고, 시스템만 파괴하는 공격도 있다.

[재구성안] 방에는 일반적인 통합 HP를 두지 않고, 선체 피해는 Ship, 시스템 피해는 System, 인원 피해는 Crew, 화재·균열은 Tile로 보낸다. 같은 공격이 이 경로 중 여러 개를 동시에 발생시킬 수 있다.

## 3. 문 제어와 통행

### 3.1 기본 규칙

[확인] 문 제어 시스템이 정상이라면 플레이어는 자기 함선의 문을 원격으로 열고 닫을 수 있다. 강화된 문은 침입자의 이동을 지연시키지만 아군의 정상 이동을 같은 방식으로 방해하지 않는다. 문 제어 운용은 문 성능을 높이는 수단이다.[S3]

[해석] 문은 다음 세 가지 자원을 바꾼다.

- **시간:** 침입자가 다음 방으로 넘어오기 전까지 확보되는 지연.
- **산소:** 어느 공간을 우주에 연결해 질식·진화를 유도할지 결정.
- **접근성:** 부상자 퇴각, 수리 인력 투입, 승무원 분리의 난이도.

### 3.2 통행 가능성과 기밀 유지의 분리

[재구성안] 다음 두 판단을 별도로 수행한다.

1. CanCrewPass(crew, door): 이 승무원이 지금 통과할 수 있는가?
2. DoesAirFlow(door): 현재 이 문을 통해 산소가 교환되는가?

강화문을 아군이 지나갈 수 있다고 해서 항상 열린 환기 통로로 취급하면 안 된다. 반대로 파괴되어 열린 문은 원하지 않는 공간까지 감압시킬 수 있다.

### 3.3 비정상 문 상태

| 상태 | 게임에서의 의미 | 재구성 시 주의 |
|---|---|---|
| 정상 닫힘 | 통행 권한에 따라 자동 통과·문 공격 | 아군 이동과 적 공격을 구분 |
| 정상 열림 | 방 연결이 환기에 참여 | 문이 열리자마자 산소가 모두 같아지는 단순화 금지 |
| 공격으로 개방 | 침입 경로 확보 | 시스템 업그레이드만으로 즉시 완전 복구시키지 않음 |
| 해킹 잠금 | 해킹된 방 출입을 해당 함선 승무원에게 제한 | 소유 함선과 통행 허용 진영을 별도 보관 |
| 크리스탈 봉쇄 | 일정 시간 방의 출입 제한 | 문 제어 개폐 명령과 독립적인 효과 |
| 문 시스템 무력화 | 원격 문 조작의 제약 | 기존 열림/닫힘 상태가 어떤 상황에서 유지되는지 검증 |

[확인] 해킹된 시스템 방의 문은 침입자에게 유리한 방향으로 통행 권한이 바뀐다. 이는 일반적인 “적 문은 항상 적에게 유리하다” 규칙으로 처리할 수 없는 사례다.[S4]

## 4. 승무원 이동 명령

### 4.1 플레이어가 의도하는 명령 단위

[해석] 기본 조작은 “정확한 픽셀로 이동”보다 “이 방으로 이동해 그 방의 문제를 처리”에 가깝다. 다중 선택은 그룹 이동을 쉽게 하지만, 도착 후 전투·수리·진화·운용 전환을 이해할 수 있도록 결과가 예측 가능해야 한다.

[재구성안] 이동 요청은 다음 단계로 처리한다.

1. 명령 시점의 소속과 현재 함선을 확인한다.
2. 목적 방에서 예약 가능한 정지 위치를 찾는다.
3. 이미 명령받은 다른 승무원의 예약을 고려한다.
4. 잠긴 연결은 통과·공격·불가 중 하나로 분류한다.
5. 경로를 생성하고 즉시 명령 피드백을 표시한다.
6. 이동 중 상태 변화가 발생하면 경로를 재평가한다.
7. 도착하면 방의 작업 규칙에 인계를 한다.

### 4.2 일시정지 중 예약

[재구성안] 일시정지 중에도 명령은 변경할 수 있으므로, **현재 점유 위치와 최종 예약 위치를 분리**하는 편이 안정적이다.

예시:

- 방 A에 2명이 있고 방 B에 2자리가 있다.
- A의 2명에게 B 이동을 명령한다.
- 시간이 흐르기 전 다른 1명에게 B 이동을 명령한다.
- 현재 위치만 검사하면 3명 모두 B에 들어갈 수 있다고 잘못 판단한다.
- 예약을 검사하면 이미 사용될 2자리를 제외하고 명령을 조정한다.

이 예약 모델은 원작 내부 구현을 확인한 결과가 아니라 같은 사용자 경험을 재현하기 위한 제안이다.

### 4.3 경로 선택과 작업 자동화

[검증 필요] 동일 길이 경로의 우선순위, 문 앞 대기 순서, 승무원이 이동 중 서로 교차하는 미세 규칙은 공개 설명만으로 완전히 확정할 수 없다. 이런 사항은 원작 영상·직접 플레이로 프레임 단위 검증해야 한다.

[재구성안] 초기 구현은 방 그래프에서 연결 경로를 찾고 방 내부에서 정지 타일까지 이동시키는 2단계 방식으로 충분하다. 다만 다음 사항은 별도 정책으로 둔다.

- 위험한 방을 자동으로 피할지, 플레이어의 최단 이동 명령을 우선할지.
- 문 공격 중 다른 길이 열리면 즉시 우회할지.
- 목표 인원이 사망·퇴각하면 해당 자리를 재사용할지.
- 운용 중 승무원에게 이동을 내리면 즉시 운용 보너스를 제거할지.

원작의 자동 행동을 재현하려면 “안전한 경로 탐색”을 임의로 추가하지 않아야 한다. 편의 기능처럼 보이더라도 진화·감압·탑승의 위험 계산을 바꿀 수 있다.

## 5. 배치가 만드는 기획적 차이

| 배치 특성 | 이점 | 대가 |
|---|---|---|
| 주요 시스템이 가까움 | 수리 인원 공유가 쉬움 | 화재·침입 대응이 한 구역에 집중 |
| 의료실이 중앙 | 부상자의 왕복 시간이 짧음 | 환기 경로 설계가 까다로움 |
| 외부 문이 주요 방 가까이 있음 | 진화·침입자 감압이 쉬움 | 아군의 이동 구역도 빠르게 감압 |
| 긴 통로·분리 구역 | 위험 확산을 늦추는 문 수가 많음 | 수리와 치료 복귀가 느림 |
| 큰 텔레포터 방 | 한 번에 전개할 병력이 많음 | 승무원 채용·회복 수요가 커짐 |

[해석] 같은 장비를 가진 두 함선도 수리 동선과 환기 가능성 때문에 생존력이 달라진다. 따라서 함선 밸런스는 무기·전력만 비교해서는 완성되지 않는다.

## 6. 대표 상황 흐름

### 상황 A: 산소실에 화재가 발생

1. 일시정지하고 산소실 연결·인원·주변 방을 확인한다.
2. 수리팀 투입과 감압 중 하나를 선택한다.
3. 감압한다면 부상자와 이동 경로를 먼저 분리한다.
4. 문을 열어 외부까지 연속 경로를 만든다.
5. 불이 사라졌다고 즉시 안전한 것은 아니다. 방 산소 회복을 기다린다.
6. 산소실 수리와 시스템 재가동을 완료한다.
7. 열린 문을 복구하고 지정 위치로 복귀한다.

### 상황 B: 무기실 해킹과 침입이 겹침

1. 해킹된 방을 단순한 “닫힌 방”이 아닌 통행 권한이 뒤집힌 공간으로 인식한다.
2. 안에 갇힌 승무원의 생존 시간과 외부 구조 시간 비교.
3. 공격·정신 지배·해킹 대응·적 함선 파괴 중 탈출 경로 선택.
4. 해킹 효과 종료와 문 복구를 별도 사건으로 기록.
5. 전투가 끝났더라도 내부 위험이 남으면 자동으로 안전 상태에 진입시키지 않는다.

## 7. 재구성용 데이터 예시

~~~json
{
  "layoutId": "example_layout",
  "rooms": [
    {"id": 0, "tiles": [0, 1], "systemSlot": "piloting", "stationTile": 0},
    {"id": 1, "tiles": [2, 3, 4, 5], "systemSlot": "weapons", "stationTile": 2}
  ],
  "doors": [
    {"id": 0, "roomA": 0, "roomB": 1, "isAirlock": false},
    {"id": 1, "roomA": 1, "roomB": null, "isAirlock": true}
  ],
  "reservedDestinations": {}
}
~~~

이 데이터는 **설명용 가상 함선**이며 특정 원작 함선의 좌표를 복원한 값이 아니다. 표시 좌표와 논리 연결을 분리해 그림이 바뀌어도 통행 판정이 유지되도록 한다.

# STARWARD v7 — 2D·3D 전투 화면과 그래픽 스타일

## 1. 하나의 시뮬레이션, 두 표시 방식

`Game`은 함선·타일·승무원·투사체·전력·난수·시간을 소유한다. `app.js`는 입력을 공개 명령으로 변환하고 전투 시간을 한 곳에서 진행한다. 2D SVG와 3D 렌더러는 그 상태를 읽어 표시한다. 3D는 WebGL을 우선 사용하고, 사용할 수 없으면 Canvas2D에 실제3D 기하를 투영하는 호환 출력을 사용한다.

2D/3D 전환으로 새 `Game`을 생성하거나 전투를 다시 시작하지 않는다. 선체, 자원, 승조원 체력과 위치, 충전, 날아가는 탄, 조준, 일시정지와 선택 상태를 유지한다. 그래픽 설정은 항해 저장과 분리한 브라우저 설정이다.

## 2. 화면 선택과 조작

격납고와 전투 화면에 2D/3D 선택과 그래픽 스타일 선택을 제공한다. 3D에서도 승무원 목록·체력·전력·무기·능력·설치 화면은 사용할 수 있다. 기존 Space 정지/재개와 숫자 무기 선택을 유지한다.

| 조작 | 2D | 3D |
|---|---|---|
| 타일 지정 | SVG 사각 셀 클릭 | 깊이와 카메라를 반영한 실제 타일 피킹 |
| 승무원 선택 | 도면 또는 목록 | 3D 승무원 또는 목록 |
| 적 승무원 공격 | 적 선택과 공격 명령 | 같은 명령 라우터 |
| 무기 조준 | 적 방의 타일 | 적 방의 3D 타일 |
| 문 | 문 표식 또는 목록 | 3D 문 또는 목록 |
| 시점 | 고정 평면 | 드래그 회전, 휠 확대·축소, 카메라 초기화 |

카메라를 움직이는 드래그를 타일 클릭으로 처리하지 않는다. 화면의 시점만 바뀌며 게임 좌표를 쓰지 않는다. 2D 모드이거나 브라우저 문서가 비활성 상태(`document.hidden`)이면3D 렌더링을 멈춘다. 스크롤로 화면 밖에 있거나 모달에 가려진 경우까지 별도로 감지하지는 않는다.

## 3. 실제 3D 렌더링

외부 엔진·CDN·모델 파일 없이 classic script `render3d.js`를 사용한다. 기본 출력은 WebGL 1이다. 선체 바닥·방·문·시설·승무원은 높이와 깊이가 있는 기하로 만든다. 모델·뷰·원근 투영 행렬과 깊이 검사를 사용한다. GPU가 없는 환경의 호환3D도 같은3D 정점과 카메라 행렬을 사용하고, 투영된 면의 깊이를 정렬해 Canvas2D에 그린다.

게임 평면의 x/y는 3D 월드 X/Z에, 높이는 Y에 대응한다. 양측 함선을 같은 장면에 배치하며 실제 레이아웃 크기에 맞춰 위치와 카메라 범위를 계산한다. 바닥 타일은 정수 격자와 일치하고, 벽은 승조원과 시설을 볼 수 있도록 절개 형태로 표시한다.

승무원의 보간 위치와 이동 경로, 문 열림·파손, 시설 손상·화재·균열·은폐·해킹·정신 지배, 실제 발사체와 빔은 엔진 상태에 연결한다. 공격 애니메이션이 자체 피해 계산을 하지 않는다.

## 4. 세 그래픽 스타일

| ID | 표시명 | 표현 방향 |
|---|---|---|
| `stellar` | 현대 SF | 어두운 금속 선체, 밝은 전력선과 패널, 청록 아군·주황 적군 |
| `lowpoly` | 로우폴리 | 단순한 입체 모델, 면이 드러나는 명암, 밝은 재질 대비 |
| `blueprint` | 청사진 | 남색 바탕, 밝은 구조선·타일선, 단순한 기술 도면 표현 |

2D에서도 배경·바닥·타일·승무원·시스템 표현에 스타일을 반영한다. 선택·적대·피격·산소 위험을 구분하는 의미 색상과 명령 결과는 유지한다.

## 5. 렌더러 인터페이스

```js
const renderer = Starward3D.create({
  canvas,
  onPick(selection) { /* app 공통 명령 라우터 */ },
  onUnavailable(message) { /* 사용자 안내와 2D 복귀 */ }
});
renderer.render(game, UI);
renderer.setStyle('stellar');
renderer.resetCamera();
renderer.resize();
renderer.destroy();
```

피킹 결과는 함선·방·정수 타일 좌표 또는 승무원/문 ID를 반환한다. 화면 픽셀을 게임 좌표로 오인하지 않는다. WebGL에서는 별도 색상 ID 버퍼와 깊이 검사로 현재 보이는 대상의 ID를 얻는다. 호환3D에서는 투영된 삼각형과 클릭점의 포함 관계·깊이를 검사해 동일한 선택 payload를 반환한다. 입력 대상이 없는 우주 공간을 클릭하면 이동 명령을 보내지 않는다.

`render(game, UI)`는 상태를 읽기만 한다. DOM 갱신은 기존 주기를 유지하고, 3D 렌더는 매 화면 프레임 호출한다. 포인터를 누르는 동안 DOM 재생성을 막는 기존 보호와 3D 카메라 드래그가 충돌하지 않도록 렌더 루프를 분리한다.

## 6. 수명·성능·실패 처리

캔버스를 반복해서 DOM에서 제거하지 않는다. 창 크기와 표시 영역에 맞춰 출력 크기·투영·피킹 버퍼를 함께 갱신하고 DPR을 제한한다. 렌더러 폐기 시 GPU 버퍼·프로그램·입력 리스너를 정리한다.

WebGL 초기화가 불가능하면 같은 캔버스의2D 출력으로 호환3D를 시도하고 화면 제목에 구분한다. WebGL 컨텍스트 손실은 안내와2D 복귀로 처리한다. 사용할 출력 수단이 모두 없을 때도2D로 이어간다. 게임 상태를 초기화하지 않는다. 호환3D는 장면 복잡도와 렌더 빈도를 제한한다. 기기별 프레임률이나 모든 GPU 호환을 측정 없이 보장하지 않는다.

## 7. 오프라인 패키지와 기술 근거

파일 로드 순서는 `data.js → engine.js → campaign.js → render3d.js → app.js`이다. 오프라인 빌더는 다섯 스크립트와 CSS를 한 HTML로 인라인한다. 그래픽 모드나 스타일을 바꾸기 위해 외부 파일을 요청하지 않는다.

기본 렌더링 구조는 [MDN의 모델·뷰·투영 설명](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_model_view_projection)과 [Khronos WebGL API 명세](https://registry.khronos.org/webgl/specs/latest/1.0/)를 참고한다. 세 행렬은 물체의 위치·카메라·원근을 분리하고, WebGL 컨텍스트는 캔버스의 3D 출력과 GPU 상태를 소유한다. 실제 성능·입력·외형은 이 프로젝트의 브라우저 검증 결과로 별도 기록한다.

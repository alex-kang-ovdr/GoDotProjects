# STARFORGE 다음 단계: 함선 기하·연결 / 승무원·물류 개선 설계

작성 2026-11-18 · 제안 대상 v5 · 원작 정확한 게임 빌드 미확인

이 문서는 공개 원작 자료를 보완하고 STARFORGE v4 다음 구현 범위를 결정하기 위한 설계안이다. **원작 확인**은 공식 위키 또는 명시된 개발자 패치 당시의 관측이다. **제안**은 새 프로토타입의 구현 계약이며 원작 엔진 알고리즘을 복원했다는 뜻이 아니다. 기존 게임 코드와 v1 원본 데이터는 변경하지 않았다. 추가 채택 후보는 support_proposals.json에 출처별로 기록했다.

이번 개선의 목표는 큰 모듈의 공간 비용, 작업자의 자리 점유, 문과 통로가 만드는 운송 시간을 실제 선택으로 만드는 것이다. 신규 부품 수를 늘리기 전에 배치·통행·운송·저장 복원에서 같은 좌표와 자원 원장을 사용해야 한다. 기존 6/12/18 전력 운반 상한 등 프로토타입 조정값을 원작 단위로 다시 해석하지 않는다.

## A. 함선 기하·연결

### A1. 복원한 사실과 남은 자료

**원작 확인.** 문은 방실 사이 승무원 통행과 화재 전파에 관여한다. 문이 놓일 수 있는 위치는 공개 모딩 문서에서 AllowedDoorLocations라는 별도 목록으로 설명된다. 해당 문서는 회전 전 좌상단 기준, 오른쪽·아래쪽 양의 축, 부품 바깥의 인접 셀 좌표를 설명한다. 이 설명만으로 특정 원작 부품의 문 좌표를 만들어서는 안 된다. [문](https://cosmoteer.wiki.gg/wiki/Door), [문 위치 정의](https://cosmoteer.wiki.gg/wiki/Door_Locations)

**원작 확인.** 모딩 문서에는 corridor와 conveyor가 비벽체(IsWalled=false) 예로 제시된다. 일반 비벽체 이웃은 문 없이 접근하는 예외가 있으므로 “모든 부품 경계에 문 필요”라는 요약만으로 통행 그래프를 만들면 잘못된다. 같은 문서는 물리 영역과 이동 제한 필드도 따로 다룬다. 다만 작성 중인 문서이며 특정 현재 빌드의 원본 파일 검사는 아니다. [공개 데이터 필드](https://cosmoteer.wiki.gg/wiki/Modding/Data_fields)

**원작 확인.** 개발자 0.29.0 공지는 코일·하이퍼코일·프로세서 공장의 모든 저장 타일 옆에 문을 허용한 변경을 명시한다. 추가 JSON은 이 관계만 보존한다. 저장 타일의 실제 좌표를 확보하지 않았으므로 문 좌표 배열은 만들지 않는다. [0.29.0 개발자 공지](https://store.steampowered.com/news/posts/?appids=799600&enddate=1753322128&feed=steam_community_announcements)

복구된 너비·높이는 형상의 경계를 정하는 자료다. **점유 마스크, 충돌 모양, 보행 셀, 문 포트, 조작석, 배기 금지영역을 모두 확정하는 자료는 아니다.** 표에서 값이 없는 것과 원본 .rules에서 필드를 생략한 것은 서로 다르다. 특히 문 위치 목록 생략 시의 모딩 기본 동작을 위키의 정보 누락에 적용하면 안 된다.

### A2. 정의와 배치 상태를 분리한다 — 제안

모듈 정의에는 출처 정보와 프로토타입 형상을 함께 두되 출처 상태를 구분한다. 실제 개체에는 정의 ID, 기준 셀, 회전, 손상, 재고만 저장한다. 처음에는 원자로·조종실·저장고·레이저를 대상으로 제작자가 검수한 작은 형상 집합을 만든다. 원작 크기를 참고해 직사각형 보행 영역을 그리더라도 그것은 authored_prototype 값이다.

~~~json
{
  "definitionId": "prototype.reactor_medium.v1",
  "sourceRecordId": "medium_reactor_core",
  "geometryAuthority": "authored_prototype",
  "bounds": {"width": 3, "height": 3},
  "occupiedCells": [[0,0],[1,0],[2,0]],
  "walkCells": [[0,0],[1,0]],
  "ports": [{"id":"west-0","cell":[0,0],"normal":[-1,0],"kind":"door"}],
  "workstations": [],
  "clearanceRegions": [],
  "geometryVersion": 1
}
~~~

이 축약 예시의 좌표는 **설명용 제안**이다. 완성 부품 데이터도, 원작 원자로의 실제 셀 목록도 아니다. 모든 배열은 검수된 정의 파일에 명시하며, 빈 배열은 “없음”, null은 “미확인”으로 구분한다. 미확인 원작 값을 사용하려면 별도의 프로토타입 정의가 필요하다.

anchor는 회전된 경계 상자의 좌상단 **셀 인덱스**다. 셀 중심을 정수 좌표로 취급하면 v4의 중심 좌표 체계와 연결하기 쉽다. 각 개체의 고유 ID는 회전이나 위치 변경에도 유지한다. 문은 두 모듈 ID와 두 포트 ID를 참조하며 좌표만으로 소유자를 추정하지 않는다.

### A3. 네 방향 회전과 포트 — 제안

회전 전 크기를 w×h, 내부 셀을 (u,v), 시계 방향 회전을 r이라 한다. 화면의 x는 오른쪽, y는 아래쪽이다.

| r | 회전 셀 Rr(u,v) | 회전 후 크기 |
|---:|---|---|
| 0 | (u,v) | (w,h) |
| 1 | (h−1−v,u) | (h,w) |
| 2 | (w−1−u,h−1−v) | (w,h) |
| 3 | (v,w−1−u) | (h,w) |

배치 셀은 anchor+Rr(u,v)다. 포트의 바깥 법선은 평행이동 없이 같은 회전만 적용한다. r=1에서는 (dx,dy)→(−dy,dx)이다. 포트가 맞닿으려면 두 포트의 셀이 변을 공유하고 법선이 반대여야 한다. 내부 자원 출입점과 조작석도 동일 변환을 사용한다.

회전 편집은 선택한 기준 셀을 고정하고 결과 점유 영역 전체를 미리 보여준다. 사용자가 보는 그림, 충돌 검사, 통행 위치가 같은 변환 함수를 사용해야 한다. 편집기의 미러링은 단순 회전과 분리하며 비대칭 문 위치까지 함께 변환한다.

### A4. 점유와 세 종류의 연결 — 제안

| 구조 | 노드와 연결 | 판단하는 것 |
|---|---|---|
| 구조 연결 | 살아 있는 모듈과 허용 접촉변 | 선체 분리와 몸체 귀속 |
| 승무원 통행 | 보행 셀과 통행 가능한 공유변 | 도달 가능성과 운송 시간 |
| 열 연결 | 해당 장치의 검수된 열 포트 | 열 전달 여부 |
| 배치 금지 | 셀/영역과 금지 레이어 | 추진기·무장 주변의 배치 허용 |

장갑이 두 방을 물리적으로 연결해도 승무원 경로가 생기지는 않는다. 반대로 문 하나를 철거한다고 선체가 곧바로 분리되어서는 안 된다. 벽체 사이에는 합법적인 문 연결이 필요하고, 일반 통로류의 비벽체 공유변은 직접 연결한다. 화재 전파가 문을 통과할 수 있다는 사실을 모든 열 전달에 같은 그래프를 써도 된다는 의미로 확대하지 않는다.

공개 모딩 자료는 추진기·무장 금지영역을 Prohibits, ProhibitedBy, ProhibitRects 등의 별도 정의로 설명한다. [배치 금지영역](https://cosmoteer.wiki.gg/wiki/Modding/Data_fields/Part_placement_blocking) **제안:** v5는 occupiedCells와 clearanceRegions를 독립 검사하고 금지 레이어를 필터링한다. 원작 배기 거리와 사각형을 확인할 때까지 자체 금지영역임을 표시한다. 모듈을 붙이기 전에 기존 금지영역에 새 선체가 들어가는지와 새 금지영역에 기존 선체가 들어가는지를 양방향 검사한다.

### A5. 한 번의 편집 트랜잭션 — 제안

previewRefit은 원본을 복제하고 작업 취소·화물 정산·모듈 재사용·회전·문 연결을 같은 순서로 계산한다. 결과에는 비용, 재고 이전·매각, 사라지는 문, 새로 고립된 장치, 승무원 도달 불가 목록이 포함된다. applyRefit은 동일 계획의 원본 리비전이 유지될 때만 커밋한다. 생산이나 화물 이동으로 원장이 변했다면 새 견적을 제시한다.

설계의 중간 단계는 비합법적일 수 있어도 최종 상태로 검증한다. 이는 원작 청사진 모드의 공개 설명과 부합한다. [Ship Editor](https://cosmoteer.wiki.gg/wiki/Ship_Editor) 단, 제안하는 견적 토큰·리비전·원자 커밋은 프로토타입 구현 방법이다. 자동 문 배치는 합법 포트끼리만 생성하며 기존 문을 추측해서 복원하지 않는다.

## B. 승무원·물류

### B1. 조작과 운송을 서로 다른 작업으로 만든다

**원작 확인.** 승무원은 장치 조작, 전력 전달, 자원 이동, 탄약 장전을 수행한다. 조작 인원과 보급 우선순위는 따로 점검되는 항목이다. [Crew](https://cosmoteer.wiki.gg/wiki/Crew), [고장 점검 가이드](https://cosmoteer.wiki.gg/wiki/Guides_Hub/Troubleshooting) 0.27.2 개발자 공지는 센서의 기본 조작 우선순위 9와 전지 보급 우선순위 8을 각각 명시한다. [0.27.2 개발자 공지](https://store.steampowered.com/news/posts/?appids=799600&enddate=1732681972&feed=steam_community_announcements)

**제안:** 운송은 완료되는 작업이고 조작은 자리를 유지하는 작업이다. operate는 지정 조작석에 도착하고 슬롯을 점유해야 효력을 낸다. deliver는 공급원 도착, 픽업, 이동, 전달, 잔여 화물 처리로 끝난다. 같은 승무원이 같은 시간에 두 작업의 효과를 낼 수 없다. 수리·소화는 기존 서비스 작업으로 남기며 긴급 정책이 전환을 요청할 수 있다.

조종실처럼 조작 인원이 확인된 장치부터 도입한다. 공장 인원이 null인 자료를 “0명 필요”로 바꾸지 않는다. 기존 자동 생산을 유지할 경우 factoryOperatorRequirement=0은 별도 프로토타입 조정값이다. 조작석 좌표도 제작자가 정한 위치라는 사실을 표시한다.

### B2. 역할 정책의 두 축 — 제안과 근거

**원작 확인.** 0.24.0에는 역할별 Hiring Priority 1~10, 높은 역할 우선 충원, 낮은 역할에서 자동 충원하는 옵션, 낮은 역할부터 전출하는 규칙이 추가되었다. 이는 고용·충원 정책이며 매 작업을 고르는 점수와 동일하지 않다. [0.24.0 개발자 공지](https://store.steampowered.com/news/posts/?appids=799600&enddate=1696087490&feed=steam_community_announcements)

**제안:** Role은 hiringPriority, taskWeights, allowedModules, allowedSources, reserveOperators를 가진다. 기존 balanced/power/ammo는 역할 프리셋으로 이관한다. repairPolicy는 화재·수리 긴급도의 상위 정책으로 유지한다. 작업별 숫자 범위·동률 처리·선점 임계치는 자체 튜닝으로 표시한다.

~~~json
{
  "crewId":"crew_17",
  "roleId":"power_team",
  "homeModuleId":"part_4",
  "location":{"moduleId":"part_9","cell":[1,0]},
  "job":{"kind":"operate","targetModuleId":"part_9","stationId":"console-0","leaseId":"lease_52"},
  "cargo":null
}
~~~

출발 전 작업자가 부족한 조종실·무장을 표시하고 “인원을 늘리라”는 단일 경고 대신 부족한 역할과 접근 불가 이유를 보여준다. 임무 수행 중에는 이미 조작 중인 사람이 작은 점수 차이로 계속 자리를 바꾸지 않도록 최소 유지시간과 선점 비용을 둔다. 이 안정화는 제안 알고리즘이며 원작 수치가 아니다.

### B3. 시간 비용으로 경로를 고른다 — 제안

**원작 확인.** 이동 보도 문서는 역방향 보도를 걷는 대신 별도 반환 경로를 선택할 수 있다고 설명한다. [Moving Walkway](https://cosmoteer.wiki.gg/wiki/Moving_Walkway) 다음 구현은 최단 칸 수 대신 예상 이동 시간을 비교해야 한다.

각 유향 통행변의 기본 비용을 이동 거리/(기본 속도×방향·방실 계수)로 둔다. 출발 셀과 도착 셀 중 어느 계수를 쓰는지는 프로토타입 계약으로 고정한다. 정적인 방향 비용은 Dijkstra 또는 A*에 사용하고, 실시간 혼잡은 짧은 구간 이동에 적용한다. 혼잡이 통로를 완전히 막는 물리 충돌로 변하지 않도록 한다.

물류 왕복 비용에는 작업자→공급원, 공급원→수요처, 픽업·전달 시간이 포함된다. 가장 가까운 공급원이 재고 부족이면 다른 합법 공급원을 평가한다. 도달 가능성을 검사하기 전에 상위 몇 개 수요만 자르면 이전에 수정한 공급 기아 문제가 재발한다. 자원별 공급 연결이 지정되었다면 그 범위 안에서만 후보를 고른다.

### B4. 배터리·축전기·저장 타일

**원작 확인.** 축전기는 큰 입력 배터리를 단위 크기로 바꾸며, 주변 장치로 보내는 데도 승무원이 필요하다. 일반 모드의 축전기는 파괴 시 원자로처럼 폭발하지 않는 것으로 설명된다. [Power Capacitor](https://cosmoteer.wiki.gg/wiki/Power_Capacitor) **제안:** 축전기를 발전기가 아닌 유한 중계 재고로 모델링한다. 운송과 에너지 보존을 먼저 구현하고 저장량·비용은 별도 어댑터로 결정한다.

**원작 확인.** 위키는 전지 보급 요청 시 전체 팩을 가져오는 것으로 서술한다. [Batteries](https://cosmoteer.wiki.gg/wiki/Batteries) v4의 6/12/18은 최대 적재량이고 부분 운반이 가능하므로 동일한 규칙이 아니다. v5는 이 차이를 명시적으로 유지하거나 팩 단위와 잔여 에너지 처리까지 함께 변경해야 한다. 소형 충전시간 충돌을 임의 선택해서 처리 지연에 넣지 않는다.

원작 저장고는 타일별 한 자원 종류와 지정·공급 연결을 가진다. 명시적 공급 연결은 연결되지 않은 목적지로의 공급을 제한한다. [Storage Bay](https://cosmoteer.wiki.gg/wiki/Storage_Bay) **제안:** 슬롯별 resourceId, amount, capacity, designation을 저장한다. 현재 탄약 240과 황 20의 독립 버퍼는 legacy 저장 형식으로 보존하고, 새 저장 모델 전환 견적에서만 슬롯을 재배치한다.

### B5. 예약과 순환을 방지한다 — 제안

각 운송 예약은 자원, 수량, 공급 모듈, 목적 모듈, 소유 승무원, 두 모듈의 revision을 가진다. 예약은 미래 수량을 잠글 뿐 실제 재고가 아니다. 픽업 순간 공급원에서 빼고 화물에 더하며, 전달 순간 화물에서 빼고 목적지에 더한다. 실패한 목적지 예약은 풀되 운반 화물은 해당 사람에게 남긴다.

축전기 A→B→A 같은 순환은 단순한 거리 점수로 막을 수 없다. 전력 중계 노드에 공급 단계 또는 명시적인 방향 연결을 두고, 같은 팩을 직전 공급원으로 자동 재수송하지 않는다. 도크에서의 반환은 별도 정산 이벤트다. 제조에서는 소비된 입력을 activeBatch라는 별도 소유 상태로 보관하고, 한 배치에 completionId를 부여해 완료를 한 번만 처리한다.

진단에는 수요율, 실제 전달률, 평균 왕복 시간, 공급원 대기, 문/통로 대기, 조작석 부족, 생산 중단 원인을 분리한다. “발전량 충분”이어도 전달률이 낮아 무기가 멈추는 상황을 설명해야 한다. 목표 화면은 총 승무원 숫자보다 어느 경계와 역할에 시간이 쓰이는지 보여준다.

## C. 저장 v5 이관과 갱신 비용 — 제안

### C1. v4를 즉시 크게 늘리지 않는다

v4의 단일 셀 함선에 새 크기를 곧바로 덮으면 모듈이 겹치고 진행 중 경로가 끊어진다. v5 저장은 geometryProfile과 definitionVersion을 필수로 가진다. 구형 저장은 먼저 legacy-v4 형상으로 감싸서 기존 전투·재고·좌표를 그대로 재개한다. 전체 함선을 새 형상으로 바꾸는 작업은 도크의 명시적인 변환 견적에서 진행한다. 구형 형상을 새로운 원작 기하로 표시하지 않는다.

변환 계획은 oldModuleId→newModuleId, 이전 셀→새 보행 셀, 이전 문→새 포트 쌍의 매핑을 포함한다. 같은 부품을 재사용하면 ID와 손상·재고·활성 배치를 유지한다. 조작석이나 문 매핑이 불가능하면 자동 생성했다고 숨기지 않고 계획을 거부하거나 미해결 항목으로 표시한다.

### C2. 커밋 순서와 불변조건

1. 원본 저장을 검증하고 해시·revision을 고정한다.
2. 분리된 상태에서 도크 작업을 정산하고 형상·문·슬롯을 매핑한다.
3. 점유·금지영역·구조·통행을 재구축하고 승무원 위치·역할을 검증한다.
4. 모든 자원의 이전/매각/손실 기록과 배치 완료 기록을 비교한다.
5. 견적과 같은 계획을 한 번만 커밋하고 이전 저장을 복구용으로 남긴다.

도크에서 인원을 새 숙소 내부로 재배치하는 것은 명시된 작업장 동작이다. 비행 중 화물이나 승무원을 순간 이동시키는 대체 처리로 사용하지 않는다. 알려진 값보다 작은 새 저장 공간에 재고가 들어가지 않으면 이전·매각 수량을 견적에 표시하고, 설명 없는 절삭은 금지한다.

자원 불변식은 **함내 재고+승무원 화물+이미 재고에서 차감한 미완료 배치 투입량=실제 보유량**이다. 여기서 운송 예약은 중복 계상하지 않는다. 생산 후에는 입력 소비와 출력 생성이 같은 원장 이벤트에 기록되어야 한다. 에너지와 일반 물자를 합산하지 않으며, 건조 환급·거래 크레딧도 별도 원장으로 검증한다.

### C3. 무효화와 성능 목표

모듈 설치·회전·제거·파괴는 geometryRevision을 올린다. 문 변경은 walkRevision, 이동 보도 회전은 routeCostRevision, 역할·공급 연결 변경은 assignmentRevision을 올린다. 재고량 변경만으로 구조 그래프를 다시 만들지 않는다. 예약이 참조한 모듈/포트가 사라지면 해당 작업만 재평가하고, 분리된 컴포넌트가 다른 함선으로 귀속되면 소유 참조를 함께 갱신한다.

제안 기준 부하는 함선 2척, 총 모듈 320개, 승무원 120명, 함선당 보행 셀 4096개 이하이다. 정적 회전 마스크는 정의별로 캐시하고 경로는 revision별로 재사용한다. 목표는 60Hz 시뮬레이션에서 보급 스케줄링 평균 2ms 이하, 구조 변경 재구축 10ms 이하이다. 이는 측정 전 성능 목표이며 현재 달성했다고 주장하지 않는다. 순회 횟수·경로 계산 수·캐시 적중·작업 취소 원인을 계측하고 모바일 기준 기기에서 재조정한다.

## E. 다음 구현 순서

첫 단계는 기하 정의·네 회전·점유·금지영역과 문 편집이다. 이 단계에서는 기존 물류량과 전투 수치를 보존하고, 셀과 모듈 ID의 일관성만 검증한다. 다음 단계에서 시간 가중 통행과 조작석 작업을 도입하며 기존 역할 프리셋을 연결한다. 마지막으로 축전기 중계와 타일별 저장을 넣고 원정 밸런스를 조정한다.

완료 판정은 부품이 크게 보이는 것에 그치지 않는다. 같은 문·셀·포트를 편집기, 승무원, 전투 판정, 저장 복원이 함께 사용해야 한다. 확인되지 않은 원작 좌표는 계속 미확인으로 남기고, 작성한 프로토타입 형상과 수치는 별도 버전의 실행 정의로 제공한다.

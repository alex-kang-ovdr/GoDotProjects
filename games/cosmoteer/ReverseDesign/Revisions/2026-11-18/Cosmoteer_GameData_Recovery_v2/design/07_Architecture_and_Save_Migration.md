# 상태 구조·틱·저장 전환 개선

이 문서의 런타임 구조와 알고리즘은 **STARFORGE 다음 버전 제안**이다. 원작 엔진 구현을 복원한 것으로 해석하지 않는다. 현재 v4의 실제 구조는 [추출 JSON](../data/starforge_v4.json)의 `construction.geometry`, `crew.task_model`, `combat.shields`, `thermal.model`, `persistence.version`에서 확인한다.

## 1. 데이터와 인스턴스의 분리

정적 `PartDefinition`에는 점유 셀, 벽·문 후보, 작업장, 외부 금지 영역, 자원 저장 슬롯, 장치 성능을 둔다. 런타임 `PartInstance`에는 기준점·회전·HP·재고·작업 상태만 둔다. 점유 셀은 인스턴스 ID를 참조하는 공간 색인이다. 같은 장치가 6칸을 차지해도 HP와 재고는 한 인스턴스에 한 번만 저장한다.

| 엔터티 | 영속 상태 | 파생 상태·캐시 | 변경 책임 |
| --- | --- | --- | --- |
| 함선 | 기준 위치·자세·속도·소유자 | 질량 중심·관성·경계 상자 | 이동 및 구조 시스템 |
| 부품 | ID·정의 ID·앵커·회전·손상·장치 상태 | 점유 셀·활성 연결 | 건조·피해 시스템 |
| 문 | 두 셀·방향·설치/파괴 상태 | 통행 edge | 편집·피해 시스템 |
| 승무원 | 위치·역할·작업 ID·운반물 | 경로·작업 점수 | 작업 관리자 |
| 재고 원장 | 보유량·예약·제작 중 투입량 | 가용량·예상 도착량 | 물류·제작·거래 |
| 실드 발생기 | 전지·가동 상태·OC 모드 | 월드 호·충돌 후보 | 전력·방어 |
| 열망 | 부품별 열량·밸브·연결 설정 | 네트워크 ID·용량 합계 | 열 시스템 |
| 임무 | 상태·목표 진행·보상 수령 ID | 지도 표식 | 커리어 시스템 |

`planning/runtime_contract.schema.json`은 위 계약 중 문서 예제의 구조를 검사하는 제안 스키마다. 원작 `.rules` 스키마나 완성된 게임 저장 스키마가 아니다.

## 2. 그래프와 변경 번호

구조 그래프는 부품 간 지지 관계를, 통행 그래프는 승무원이 실제 지나갈 수 있는 셀과 문을, 열 그래프는 방향과 연결 설정을 갖는 포트를 표현한다. 하나의 연결 배열을 세 용도로 재사용하지 않는다. 각 그래프에 `revision`을 부여하고, 캐시는 계산에 사용한 revision과 함께 저장한다.

부품 제거는 먼저 하나의 변경 집합에 모은다. 연쇄 폭발 중 매번 전 함선을 재구축하지 않고, 해당 틱의 파괴 사건을 안정적인 순서로 처리한 후 구조를 갱신한다. 그 결과 분리된 부품과 승무원·운송 작업에 취소 또는 소유권 변경 사건을 발생시킨다. 변경 번호가 바뀐 경로는 다음 이동 전에 유효성을 확인한다. 예약은 경로 캐시가 사라졌다는 이유만으로 중복 반환하지 않는다.

## 3. 틱과 사건 순서

v4는 고정 시뮬레이션 스텝을 사용한다. 다음 구현에서도 같은 입력·시드·카탈로그 해시에 대한 재현 가능성을 유지하는 것을 목표로 한다. 아래는 **제안 순서**이며 원작 내부 순서를 주장하지 않는다.

1. 명령 수집과 사전 검증: 틱 번호, 명령 ID, 사용 규칙 세트, 예상 revision 확인.
2. 전 틱에서 예약한 거래·건조·도착의 커밋: 실패하면 원자적으로 취소하고 원장을 복원.
3. 작업 선택과 이동: 전용 운용 슬롯, 서비스 작업, 운송 작업을 동일한 인력 풀에서 배정.
4. 장치 운용: 전지 생성, 실드 전지 유지비, 실제 운용 가능한 공장의 진행, 무기 사격 요청 계산.
5. 이동·발사체·실드·부위 충돌: 후보를 시간과 안정 ID로 정렬하고 피해 사건을 생성.
6. 피해·화재·폭발·열: 자원별 손실 원인을 기록하고 연쇄 사건을 제한된 큐로 처리.
7. 구조·통행·열망 갱신과 작업 재검증: 파괴된 목적지의 도착을 승인하지 않음.
8. 통계·표시 스냅샷: 플레이어 화면은 커밋된 상태만 읽음.

동일 틱에서 파괴와 배송이 겹칠 때는 사건 순서로 한 결과만 허용한다. '도착 표시'와 '자원 커밋'을 다른 시스템에서 각각 실행하지 않는다. 한 수치가 두 곳에서 권위 값을 갖지 않도록 실드 전지, 생산 중 재료, 운반물이 각각 책임자를 갖는다.

## 4. 거래·작업의 원자성

모든 예약에는 `reservationId`, 자원, 수량, 출발·도착, 소유 작업, 상태를 둔다. 같은 `commitId`를 두 번 수신하면 첫 결과를 반환한다. 사용자 화면의 예상 비용은 상태를 수정하지 않는 quote 함수에서 만들고, 실제 커밋은 예상 revision을 다시 확인한다.

제작에는 `inputHeld`, `progressWork`, `outputPending`을 구분한다. 입력을 배치 시작 시 소비하는 정책을 선택한다면, 정지·전력 부족은 `progressWork`를 보존한다. 취소 시 입력 반환 여부는 레시피 정책으로 결정하며, 파괴는 손실 원장에 남긴다. 출력 공간을 예약하지 않고 제작이 완료된 경우에는 생산물을 사라지게 하거나 초과 적재하지 않고 출력 대기 상태에 둔다. 여기서 정책은 웹 게임 제안이며, 원작의 내부 처리 시점은 별도 확인 대상이다.

## 5. 저장 전환: v4 → 제안 v5

**자동 크기 확대를 금지한다.** v4에서 발전기·실드·공장은 모두 한 칸이다. 이를 불러오는 즉시 원작 치수로 늘리면 인접 부품이 겹치고 동선이 끊긴다. 가격·재료 체계를 함께 바꾸면 같은 파일에서 임의 보상·재고도 생성될 수 있다.

권장 전환 절차는 다음과 같다.

1. 원본 세이브를 읽기 전용으로 보관한다. v4 유효성 검사와 해시를 기록한다.
2. `rulesetId=starforge.v4`, `catalogueHash`, `migrationState=legacy`를 붙인 호환 상태에서 복원한다. 전투 중 파일은 같은 규칙으로 전투를 마친 후 전환한다.
3. 도크에서 전환 초안을 만든다. 새로운 다칸 부품은 자동 배치하지 않고 충돌·문·운용 슬롯·비용·재고 차이를 표시한다. 기존 함선은 초안의 실패와 무관하게 유지한다.
4. 승무원 운반물과 제작 중 입력을 원장으로 정산한다. 이미 소비된 황을 저장고에 중복 생성하지 않는다. 기존의 빈 재고를 원작 기본 보급량으로 채우지 않는다.
5. 점유·문·구조·통행·열망·재고 상한·임무 보상 원장을 모두 검사한다. 미확정 문 좌표를 요구하는 부품은 실제 지원 카탈로그가 준비되기 전까지 전환 대상으로 채택하지 않는다.
6. 유효한 초안만 새 파일로 저장한다. 성공한 결과에 `migrationId`, 원본 해시, 대상 카탈로그 해시를 기록한다. 같은 migrationId의 재실행은 재보상을 발생시키지 않는다.

| 원래 상태 | 처리 제안 | 실패 시 결과 |
| --- | --- | --- |
| 도크·재고 보유 | 전환 초안으로 원장 정산 | 원본 그대로, 초안 오류 목록 |
| 생산 중 | 소비된 입력과 작업 진행을 명시적 변환 | 입력 수량 판정 불가 시 전환 차단 |
| 전투·발사체 존재 | v4 호환 규칙으로 재개 | 전투 중 강제 카탈로그 교체 금지 |
| 최신 미지원 버전 | 읽기 거부 + 파일 보존 | 불완전한 기본값으로 로드하지 않음 |
| 중복 ID·음수·NaN | 검증 거부 | 기존 활성 게임 상태 유지 |

## 6. 관측과 성능

매 프레임 전체 부품을 다시 순회하는 경로 탐색·네트워크 재구축을 피하고 변경 영역과 revision에 따라 재사용한다. 초기 웹 구현 목표는 160개 부품 인스턴스, 64명 승무원, 2척 동시 교전을 먼저 안정화하는 것이다. 이는 제안 검증 규모이며 원작 한계나 측정된 성능이 아니다. 실드 후보·동일 틱 연쇄 폭발·캐시 재탐색 수에 카운터를 두고 실제 브라우저의 P95 시뮬레이션 시간과 작업 취소 수를 기록한다. 성능 목표의 채택은 기준 기기·브라우저·해상도를 명시한 측정 이후에 한다.

런타임에 필요한 원본 계수와 표시용 설명을 분리한다. null인 핵심 데이터가 있는 카탈로그는 시작 단계에서 오류를 내고 지원 가능한 부품 목록을 보여준다. 전투 도중 임의의 0·1 계수를 대입해 조용히 실행하지 않는다.

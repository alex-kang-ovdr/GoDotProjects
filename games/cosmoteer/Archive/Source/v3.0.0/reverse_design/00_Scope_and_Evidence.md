# 00. 분석 범위와 근거 관리

[전체 목차](README.md)

| 항목 | 기준 |
| --- | --- |
| 대상 | Cosmoteer: Starship Architect & Commander, Steam 상용판 |
| 작성일 | 2026-11-13, 한국 시간 |
| 문헌 기준선 | 조사에서 확인한 배포 공지 0.30.5 및 0.30.5a |
| 기본 플레이 | 모드 없는 Career와 공통 함선 시뮬레이션 |
| 보조 범위 | Creative, 협동, PvP, 설계 공유, 모딩 |
| 문서 성격 | 공개 자료를 바탕으로 한 시스템 역기획과 독립적인 재구현 설계 |

## 1. 이 문서 묶음의 목적

플레이어에게 무엇을 할 수 있는지 설명하는 공략과, 개발팀에게 무엇을 만들어야 하는지 설명하는 명세 사이를 연결한다. 부품의 이름을 나열하는 데서 끝내지 않고 **입력 → 제약 검사 → 상태 변화 → 다른 시스템에 전달되는 결과 → 플레이어가 읽는 피드백**을 추적한다.

대상 독자는 시스템 기획자, 게임플레이 프로그래머, 시뮬레이션 프로그래머, UI 기획자다. 실제 제작에 활용할 수 있도록 상태, 데이터 소유권, 예외, 검증 시나리오를 포함한다. 다만 제안한 클래스, 필드, 수식, 틱 순서가 원작 소스 코드와 같다는 뜻은 아니다.

## 2. 기준 버전과 포함 범위

**[확인]** 공식 공지 피드에서 0.30.5, 0.30.5a 및 Career 2.0 개발 현황을 확인했다. 이번 문서의 현행 규칙은 이 배포 공지들을 기준으로 정리한다. 이후 공지가 없다는 절대적 보장이나 로컬 설치 빌드를 검사했다는 의미는 아니다. [P02]

| 범위 | 처리 원칙 | 주로 읽을 문서 |
| --- | --- | --- |
| 현행 상용판의 함선·승무원·전투 | 시스템 분석의 중심 | 02–12 |
| 현행 Career의 탐사·경제·명성 | 현재 플레이 흐름으로 분석 | 13–17 |
| Meltdown 이후 열·냉각·오버클럭 | 독립 시스템으로 포함 | 11 |
| Career 2.0 | 개발 중 항목으로만 표시 | 16, 19, 23 |
| Cosmoteer Classic | 역사적 기술 설명에만 제한 사용 | 19, 20 |
| 데모 제한 | 정식판 규칙과 혼합하지 않음 | 필요 시 검증 목록 |
| 모드 추가 부품·경제 | 기본 게임에서 제외 | 19의 확장 정책 |
| 내부 AI·물리·네트워크 구현 | 공개 설명과 제안 구조를 분리 | 20 |

공식 개발 공지에 따르면 Career 2.0은 아직 개발 중이며, 다중 섹터와 임무 구성 방식의 개편을 다룬다. 이를 현재 플레이의 필수 규칙으로 채택하지 않는다. 향후 계획이 변경될 수 있으므로 본문에는 구현 확정일이나 출시일을 추정하여 넣지 않는다. [P02]

## 3. 문장에 붙이는 네 가지 근거 수준

| 표기 | 의미 | 읽는 방법 |
| --- | --- | --- |
| **[확인]** | 공식 공지 또는 식별 가능한 문서에서 확인한 게임 규칙 | 실제 실행 확인과는 구분한다 |
| **[해석]** | 확인된 규칙이 만들어 내는 선택·전략·설계 의도에 대한 분석 | 개발자의 직접 발언으로 인용하지 않는다 |
| **[제안]** | 비슷한 게임을 구현하기 위한 데이터·알고리즘·UI·테스트 설계 | 원작의 내부 구현 명세로 취급하지 않는다 |
| **[검증 필요]** | 자료 충돌, 최신 값 누락, 조건 불분명 | 실기기 또는 해당 버전 데이터로 확인 후 확정한다 |

절 전체가 `[제안]`이면 그 안의 표와 코드도 제안이다. `[가정 예시]`는 제안 또는 해석을 설명하기 위해 만든 수치다. 실제 부품 가격, 피해량, 인원, 속도와 혼동하지 않도록 가정을 계산 바로 앞에 적는다.

### 3.1 확인이라는 표현의 제한

이번 작업에서는 게임을 직접 실행하거나 설치된 `.rules` 파일을 읽지 않았다. 그러므로 `[확인]`은 **문헌에서 확인**했다는 뜻이다. 수용 테스트는 재구현 또는 후속 실측에 사용할 절차이며, 이미 실행해 통과한 테스트 목록이 아니다.

### 3.2 공식 위키의 취급

공식 홈페이지가 연결하는 Wiki는 유용한 규칙 자료지만, 모든 항목이 최신 패치에 맞춰 동시에 갱신되지는 않는다. 개별 페이지의 수치가 최신 개발자 공지와 충돌하면 공지를 우선한다. 직접 열기에서 403이 발생한 문서는 검색 색인에 표시된 본문만 근거로 삼았으며, 보이지 않는 표나 문장을 읽었다고 간주하지 않았다.

## 4. 출처의 우선순위와 충돌 해결

| 우선순위 | 자료 | 사용 범위 |
| --- | --- | --- |
| 1 | 해당 버전 개발자 정식 패치 공지 | 새 기능·변경 수치·버그 수정의 판정 |
| 2 | 공식 홈페이지와 개발자 기술 글 | 제품의 의도, 공개적으로 설명한 기술 이력 |
| 3 | 공식 Wiki의 개별 규칙·부품·모딩 문서 | 공지에 없는 지속 규칙, 개념, 운영 조건 |
| 4 | 과거 문서·과거 공지 | 도입 이력과 변경 전 상태의 이해 |
| 별도 | 사용자 제공 나무위키 URL | 직접 열람 실패를 기록하고 참고 진입점으로만 보존 |

충돌이 나면 “최근에 검색되었다”는 이유만으로 최근 규칙이라고 판단하지 않는다. 검색 수집일과 규칙 변경일은 다르다. 특히 Release Candidate와 정식 공지는 구분한다. 정식판이 RC의 수치를 다시 조정했으면 정식판을 적용한다.

**처리 절차 [제안]**

1. 서로 다른 주장에 동일한 대상·조건·버전이 적용되는지 확인한다.
2. 정식 패치에 명시된 변경이면 그 버전 이후의 규칙으로 채택한다.
3. 텍스트 설명 오류인지 실제 성능 변경인지 분리한다.
4. 여전히 해결되지 않으면 수치나 조건을 단정하지 않고 검증 항목으로 남긴다.
5. 규칙을 소유한 문서 한 곳을 수정하고 다른 문서는 상대 링크로 연결한다.

## 5. 규칙 소유권

서로 다른 문서가 같은 규칙을 조금씩 다르게 정의하지 않도록 다음처럼 책임을 둔다.

| 규칙 | 주 문서 | 다른 문서의 사용 방법 |
| --- | --- | --- |
| 배치·설계 적용·청사진 | 02 | 경제 문서는 비용과 해금 조건만 참조 |
| 선체 연결·분리 | 03 | 전투 문서는 분리 결과를 호출 |
| 승무원 작업 선택 | 04 | 물류 문서는 운송 작업의 수요를 생성 |
| 운송·공급망 | 05 | 전력과 탄약은 각기 운송할 항목을 제공 |
| 전지 생성·저장·소비 | 06 | 공통 전력망으로 오해하지 않도록 구분 |
| 추력과 이동 명령 | 07 | 전술 문서는 목표 위치·방향을 제공 |
| 무기·방어·피해 | 08–10 | 서로 독립된 단계를 계약으로 연결 |
| 열·오버클럭 | 11 | 화재와 구분하고 연결 규칙을 여기서 정의 |
| 전술 명령 | 12 | 전투 AI의 의도와 실제 장치 작동을 분리 |
| 탐사·자원·경제·진행 | 13–17 | 보상, 재고, 명성, 해금을 별개 상태로 관리 |
| 표시·편집·진단 | 18 | 시뮬레이션 상태를 읽고 명령을 제출 |
| 모드·확장·공유 | 19 | 공통 시뮬레이션 위의 정책으로 정리 |
| 제안 데이터와 처리 순서 | 20 | 다른 문서의 의사코드를 통합하는 기준 |
| 제작 단계·통합 검증 | 21 | 게임 실측과 개발 테스트를 구분 |

## 6. 단위와 수식 사용 규약

| 표현 | 이 문서에서의 의미 | 주의점 |
| --- | --- | --- |
| 타일 | 함선 배치·내부 이동의 공간 단위 | 세계 거리 m와 자동으로 동일시하지 않는다 |
| 초, cycle | 시간 또는 작업 주기 | 게임 배속과 실제 벽시계 시간을 구분 |
| 전지·배터리 | 운반되는 전력 자원과 그 저장량 | 팩 개수와 전력량의 변환을 명시해야 한다 |
| 처리율 | 시간당 운반·소비·생산량 | 용량과 다른 값이다 |
| 열량·열 상태 | 게임에서 다루는 열 관련 상태 | 근거 없이 섭씨·줄로 변환하지 않는다 |
| 명성 | Fame | 세력별 관계 또는 크레딧과 별도 축 |
| 유효 DPS | 선택한 관측 구간의 실제 피해/시간 | 툴팁 DPS와 혼동하지 않는다 |
| 예산 | 재구현의 시간·메모리·개발 범위 제약 | 실제 Cosmoteer의 성능 수치가 아니다 |

수식이 나오면 최소한 입력의 단위, 계산 목적, 적용 조건을 같이 적는다. 예를 들어 `실효 처리율 = min(생산율, 운송율, 소비 가능율)`은 병목을 설명하는 정상상태 근사이며, 게임의 실제 이벤트 처리나 과도 구간을 완전히 재현하지 않는다.

## 7. 후속 실측 기록 양식 [제안]

| 필드 | 기록할 내용 |
| --- | --- |
| ExperimentId | 중복되지 않는 실험 이름 |
| Build / Mods | 정확한 빌드 문자열, 활성 모드와 설정 |
| ShipDesign | 설계 파일과 변경 이력 |
| InitialState | 승무원, 전지, 탄약, 열, 피해, 명령 |
| Variable | 한 번에 변경한 독립 변수 |
| Observation | 초 단위 시점과 관측값 |
| Result | 문헌과 일치·불일치·판정 불가 |
| UpdateTarget | 수정할 문서와 규칙 ID |

같은 설계를 비교하더라도 초기 탄약이 가득 찬 경우와 생산부터 시작한 경우는 다른 실험이다. 포격 성능을 비교할 때에는 사거리·상대 자세·방어 상태·전투 시간도 고정해야 한다.

## 8. 자료 이용 및 읽기 안내

문서는 공개 정보를 한국어로 재구성한 독립적인 분석이다. 이미지·코드·게임 데이터의 원본 재배포를 포함하지 않는다. Mermaid는 원작 화면을 복제한 것이 아니라 관계를 설명하기 위해 새로 작성한 다이어그램이다. 한국어 부품명은 이해를 돕기 위한 번역이며 영문 게임 명칭을 함께 확인해야 한다.

전체 구조는 [01](01_Core_Loop_and_System_Map.md), 실무 구현 구조는 [20](20_Technical_Architecture_and_Data_Model.md), 확인되지 않은 항목의 통합 목록은 [23](23_Sources_and_Fact_Check.md)에서 읽을 수 있다.

# STARFORGE — Drydock v4

**함선을 조립하고, 황을 운반해 탄약을 생산하며, 승무원의 보급·화재 진압·현장 수리를 운영하는 JavaScript 우주 함선 게임입니다. 세 구간의 작전을 완수하고 보상을 다음 설계에 투자합니다.**

Cosmoteer의 함선 제작·승무원 물류·부품별 전투에서 출발한 독자적인 실험입니다. v4는 복구한 분석 데이터 중 확인 가능한 원자로 등급 관계, 황→탄약 제조 비율, 승무원 이동 관계를 실행 데이터로 연결합니다. 원작 관측값과 웹 게임용 조정값을 별도로 기록합니다. 원작 바이너리·내부 코드·전체 콘텐츠를 복원한 버전은 아닙니다.

## 실행

빌드 단계나 패키지 설치가 필요하지 않습니다. **dist 폴더의 파일을 함께 유지한 상태에서 dist/index.html을 브라우저로 열면 됩니다.** index.html만 다른 곳으로 옮기면 함께 사용하는 스크립트와 스타일을 불러올 수 없습니다.

로컬 HTTP 서버를 사용하려면 프로젝트 폴더에서 다음 명령을 실행합니다.

```sh
cd dist
python3 -m http.server 8000
```

이후 [http://localhost:8000](http://localhost:8000)을 엽니다. Windows에서 python3 명령이 없고 Python이 설치되어 있다면 python 또는 py로 실행할 수 있습니다.

런타임은 외부 패키지 없이 작성한 JavaScript입니다. 게임 파일을 받은 이후에는 로컬 실행을 위해 외부 서비스나 계정이 필요하지 않습니다.

### 단일 HTML로 내보내기

Node.js가 있다면 다음 명령으로 CSS와 JavaScript를 하나에 포함한 실행 파일을 만듭니다. 생성된 HTML은 별도 폴더나 웹 서버 없이 브라우저에서 열 수 있습니다.

```sh
node scripts/export-offline.cjs
```

기본 출력은 `exports/starforge.html`입니다. 다른 경로를 명령의 마지막 인수로 지정할 수도 있습니다. 브라우저가 로컬 파일의 자동 저장을 제한하면 게임 메뉴의 JSON 내보내기로 진행을 보관하세요.

## v4에서 바로 체험하기

1. **청사진(B) → FORGE / 생산형**을 적용합니다. 시작 자금으로 선택할 수 있으며, 중포와 탄약 공장을 함께 운용합니다.
2. **생산·기술·정비 보급(U)**에서 황 재고와 공장 상태를 확인합니다. 새 원정의 기본 저장고에는 황 6이 있고 구형 저장을 가져오면 황을 새로 구매합니다.
3. 황·전지는 승무원이 공장까지 운반합니다. 공장은 황 1을 투입해 전력을 공급받는 작업 시간 10초 동안 탄약 20발을 만듭니다.
4. 생산된 탄약을 승무원이 중포 또는 저장고로 옮깁니다. 공장의 완제품 공간이 차거나 황·전지가 없으면 생산을 기다립니다.
5. 승리 후 황을 회수하고 저장 공간을 넘는 분량은 정거장 매각액으로 정산합니다. 중형·대형 원자로와 통로 재설계로 운반 병목을 개선합니다.

작업 중인 공장을 선택하면 개별 정지·재개할 수 있습니다. 함선 전체 일시정지와 공장 정지는 별개입니다.

## 분석 데이터의 적용 범위

| 항목 | 원작 복구 관측 | STARFORGE 실행값 |
| --- | --- | --- |
| 원자로 발전 단계 | 소형 1.5 / 중형 4.5 / 대형 13.5 | 10.5 / 31.5 / 94.5 에너지/s |
| 원자로 전지 크기 | 1 / 2 / 3 | 승무원 1회 운반 상한 6 / 12 / 18 |
| 원자로 저장량 | 8 / 16 / 24 | 100 / 200 / 300 에너지 |
| 황→탄약 | 황 0.05당 탄약 1, 출력 2/s | 황 1 → 탄약 20, 작업 10초 |
| 방실 이동 | 기본 3.2, 통로 ×1 / 방실 ×0.5 | 동일한 타일/s 관계 적용 |
| 황 가격 | 20 C | 2 C, 게임용 가격 배율 0.1 |

발전량·운반량·버퍼에는 서로 다른 조정 배율을 적용했습니다. 하나의 물리 단위 환산이라고 해석하면 안 됩니다. 원작의 정확한 생산 배치 크기·주기는 미확인 상태이며 1→20/10초는 확인된 비율과 생산율을 보존하도록 정한 게임 작업 단위입니다. 모든 부품은 한 격자를 점유하며 원작 다칸 크기를 구현하지 않습니다. 거리는 화면에서 **칸**, 내부 운동 단위는 **u**로 표시합니다.

실행 모듈 [dist/data.js](dist/data.js)는 출처·확인 상태를 보관한 [data/analysis-snapshot.json](data/analysis-snapshot.json)에서 생성합니다. 출처가 없거나 충돌하는 값은 null 상태를 유지하며 readKnown()은 이를 런타임 확정값으로 읽지 않습니다. 기존 레이저·중포·실드의 독자적인 전투 조정값을 원작 수치로 표기하지 않습니다. 자세한 필드별 근거는 [분석 데이터 어댑터](docs/systems/04_analysis_data_adapter.md)에 있습니다.

## 플레이 흐름

1. **도크에서 조립합니다.** 부품을 직접 배치하거나 기본 청사진을 선택합니다. 대칭 배치와 되돌리기를 이용해 무장, 추진기, 통로를 조정합니다. 청사진을 바꿀 때에는 재사용할 부품과 필요한 차액을 먼저 확인합니다.
2. **보급과 발사 방향을 확인합니다.** 승무원이 도달할 수 있는 통로가 필요합니다. 앞에 자기 함선의 부품이 있으면 무기가 사격하지 못하며, 추진기 방향에 따라 낼 수 있는 기동력이 달라집니다. 기술 창에서 개량과 정비 자재의 예산도 확인합니다.
3. **작전을 선택해 출격합니다.** 출격 버튼에서 해당 구간의 세 작전 중 하나를 고릅니다. 위험과 보상을 확인한 다음 출격을 확정합니다. 전투에서는 전술과 공격 표적을 조절하고, 화재가 발생하면 정비 정책과 우선 작업 대상을 바꿉니다.
4. **회수하고 복귀합니다.** 승리 후 보상을 회수하고 도크로 돌아갑니다. 귀환 시 전투 전 설계에 맞춰 선체를 복구하고, 필요한 승무원 충원을 포함해 복구비를 정산합니다. 살아남은 탄약·황·생산 진행·정비 자재와 구매한 기술은 유지합니다. 탄약·황·정비 자재의 추가 보충은 별도로 구매합니다. 같은 승리의 보상을 반복해서 받을 수는 없습니다.
5. **보상을 다음 설계에 투자합니다.** 부품을 늘리기 전에 사선, 승무원 경로, 추진 방향을 확인합니다. 세 번째 구간을 끝내면 원정 완료입니다. 패배하거나 긴급 철수하면 같은 구간에서 다시 준비하며, 복구비가 부족할 때에는 구난 지원으로 재출격을 돕습니다.

승리 화면에서는 **잔해 회수 → 조선소 귀환 → 수리·보충 → 다음 출격** 순서로 진행합니다.

## 조립과 청사진

대칭 모드는 중앙 축을 기준으로 반대편 칸을 함께 편집합니다. 중앙 축에 있는 부품은 한 번만 배치하고 비용도 한 번만 냅니다. 두 부품을 설치할 자금이 부족하거나 반대편 칸이 이미 차 있다면 전체 배치가 취소됩니다. 일부만 설치된 채 비용이 빠지는 동작은 허용하지 않습니다.

편집 이력은 최근 24개 작업까지 유지합니다. 배치·철거·회전·청사진 적용은 되돌릴 수 있으며, 철거를 되돌리면 해당 부품과 재고, 환불 전 자금도 돌아옵니다. 출격하거나 다른 원정을 불러온 뒤에는 이전 편집 이력을 이어 사용하지 않습니다. 화재·내구도·정비 상태가 진행된 경우에도 오래된 편집 이력을 무효화해 진압과 피해를 되돌리지 않습니다.

기본 청사진은 **균형형, 중포형, 레이저형, FORGE 생산형** 네 종류입니다. 사용자 청사진에는 부품 종류·위치·방향을 보관합니다. 현재 함선에서 같은 종류의 부품을 재사용하고, 없는 부품은 구매하며, 남는 부품은 내구도에 비례해 환불합니다. 재사용하는 부품의 손상과 재고를 유지하므로 청사진을 다시 적용하는 것만으로 수리되거나 탄약이 생기지 않습니다. 수리는 수리 버튼으로, 탄약 보충은 보충 버튼으로 진행합니다.

## 전투에서 달라지는 선택

### 무장과 추진

무기는 사거리, 회전 방향에 따른 사격 범위, 자기 함선의 가림 여부를 확인한 뒤 발사합니다. 보급이 충분한데 쏘지 못한다면 무장 앞에 장갑이나 다른 부품이 있는지, 선택한 표적이 발사 가능한 방향에 있는지 확인합니다. 전술 오버레이와 선택한 부품의 정보를 함께 살펴보면 원인을 찾기 쉽습니다.

추진기는 방향과 설치 위치에 따라 이동과 선회에 기여합니다. 배기 바로 뒤 칸을 비워야 하며, 한 방향의 추진기만 늘린 설계는 다른 방향으로 움직이거나 돌아서는 능력이 부족할 수 있습니다. 작동하는 추진기가 없으면 이동·선회 명령만으로 새 가속도가 생기지 않습니다. 기동력은 함선 질량과 전지 공급의 영향도 받습니다.

### 전술과 표적

| 선택 | 용도 |
| --- | --- |
| 균형 | 기본 교전 거리를 유지하며 싸웁니다. |
| 돌격 | 더 가까이 접근하는 교전을 선택합니다. |
| 거리 유지 | 거리를 벌리는 교전을 선택합니다. |
| 위치 고정 | 자동 접근을 멈추고 현재 위치에서 대응합니다. |

자동 표적 우선순위는 **무장 / 원자로 / 조종실 / 실드** 중에서 고릅니다. 적 부품을 직접 선택하면 그 표적에 집중하며, **지정 해제**를 누르면 다시 우선순위에 따라 대상을 고릅니다. 장갑 뒤의 핵심 부품을 지정해도 탄체는 앞에 놓인 부품과 충돌할 수 있습니다.

오버클럭은 순간 화력을 높이는 대신 전력 수요와 발열을 늘립니다. 승무원 정책의 균형·전력 우선·탄약 우선은 운반 작업의 우선순위를 바꿉니다. 무기를 추가한 뒤 화력이 늘지 않으면 공급 경로와 열을 먼저 살펴봅니다.

## 화재와 현장 정비

피격과 높은 열은 화재를 일으킬 수 있습니다. 불은 추가 피해를 주고 인접 모듈로 번집니다. 승무원은 목표 모듈이나 바로 옆 통로까지 실제로 걸어가 소화한 뒤 손상을 수리합니다. 구조에 연결된 부품이라도 장갑에 막혀 작업 장소까지 갈 수 없으면 현장 작업을 할 수 없습니다.

소화는 정비 자재를 소비하지 않습니다. 현장 수리는 작업자 한 명당 초당 최대 8 HP를 회복하며, 자재 1당 4 HP를 수리합니다. 자재가 없으면 수리를 멈추며 파괴된 부품은 도크에서 복구합니다. 수동 우선 지정에도 같은 경로·자재·정책 제한이 적용됩니다.

| 정비 정책 | 현장 인력 한도 | 선택의 영향 |
| --- | --- | --- |
| 균형 | 승무원의 25%를 내림, 인원이 있으면 최소 1명 | 정비와 보급을 함께 유지 |
| 생존 우선 | 승무원의 60%를 내림, 인원이 있으면 최소 1명 | 손상 복구에 더 많은 인력을 사용 |
| 보급 집중 | 소화 1명, 현장 수리 중지 | 전지·탄약 운반 인력을 확보 |

12명인 기본 함선에서는 균형이 최대 3명, 생존 우선이 최대 7명을 사용합니다. 이 인력은 보급 승무원과 공유하므로 복구에 집중하면 무장 공급이 줄어들 수 있습니다. 자세한 화재 수치와 작업 조건은 [화재·현장 정비 문서](docs/systems/01_fire_and_field_maintenance.md)에 있습니다.

## 기술 개량과 정비 자재

**U** 또는 **기술 개량·정비 보급**에서 현재 자금과 다음 단계 가격을 확인합니다. 구매는 도크에서 가능하며, 기술은 이번 원정 동안 유지합니다.

| 기술 | 단계당 효과 | 1 / 2 / 3단계 가격 |
| --- | --- | --- |
| 원자로 효율 | 실제 발전량 +10% | 350 / 650 / 1,000 C |
| 함내 작업 동선 | 승무원 이동 속도 +8% | 300 / 550 / 850 C |
| 추진 제어 개량 | 실제 추력 +10% | 300 / 550 / 850 C |

최대 3단계이며 효과를 기본값에 합산합니다. 새 원정에서는 레벨이 0으로 돌아갑니다. 기술은 생산·이동·추진을 개선하며, 막힌 통로나 사선·배치 방향은 조립에서 해결해야 합니다.

정비 자재는 초기 80, 상한 240입니다. 한 번에 최대 80을 160 C에 보급하며, 상한 근처에서는 남은 공간만 구매합니다. 실제 비용은 구매량 × 2를 올림합니다. 예를 들어 237.25가 남아 있으면 2.75를 6 C에 보충합니다. 함선 내 공유 재고로 계산하며 자재를 따로 운반하는 단계는 구현하지 않았습니다. [기술·자재 경제 문서](docs/systems/02_technology_and_maintenance_economy.md)

## 단순화한 부분

이 프로토타입은 제작·물류·전투의 연결을 설명하는 데 집중합니다. Cosmoteer 전체를 대체하는 시뮬레이터나 모드 도구로 사용하지 않습니다.

- 원작의 부품별 실제 성능표, 다중 타일 부품, 전체 무장·열 부품 목록을 복제하지 않았습니다.
- 은하 탐험, 진영 관계, 거래 시장, 대규모 함대와 여러 형태의 Career 임무는 범위에 포함하지 않습니다.
- 승무원, 탄약, 전력, 열, 기동과 피해는 이 게임에 맞춘 단순화된 모델입니다.
- 원작 함선 디자인이나 원작 저장 파일을 가져오는 형식이 아닙니다.
- 온라인 협동·PvP, 계정 간 동기화, 서버 저장은 포함하지 않습니다.

완전한 물리 엔진이나 원작의 정확한 내부 규칙을 검증하는 용도로는 적합하지 않습니다. 각 설계 변경이 공급과 전투 결과에 어떤 영향을 주는지 비교하는 작은 실험으로 사용하면 좋습니다.

## 저장 파일

현재 원정과 사용자 청사진 목록은 같은 브라우저의 localStorage에 저장됩니다. 다른 브라우저나 다른 주소로 이동할 때는 이 저장이 함께 이동하지 않으므로, **저장 메뉴의 JSON 내보내기**를 사용합니다. 앱에서 내보내는 파일에는 원정과 사용자 청사진 목록이 함께 들어 있습니다. 가져오기에 실패한 데이터는 현재 원정과 목록을 변경하지 않습니다.

**새 원정은 현재 함선·자금·구간 진행·기술 레벨을 초기화하며, 저장한 사용자 청사진 목록은 유지합니다.** 정비 자재도 초기량으로 돌아갑니다. 현재 함선의 손상·재고까지 포함한 원정을 남기려면 새 원정을 시작하기 전에 JSON을 내보냅니다. 브라우저의 사이트 데이터 삭제는 원정과 청사진 목록 모두를 지울 수 있으므로, 장기 보관에는 내보내기 파일을 사용합니다.

저장 형식 v4는 이전 배포판의 v1·v2·v3 원정을 가져올 수 있습니다. 황은 0으로 시작하고 기존 전력·탄약·개량을 보존합니다. 예전 파일에 없는 기술은 0단계, 정비 상태는 기본값으로 시작하며 구매했던 부품·자금·진행은 유지합니다. 사용자 청사진 목록이 없으면 현재 목록을 유지합니다. 이전 설계에도 새 규칙이 적용되므로 불러온 뒤 출격 전 방향·차폐·정비 상태를 확인합니다. 알려지지 않은 저장 버전이나 잘못된 데이터는 거부합니다. 상세 계약과 고정한 과거 저장 표본은 [저장 v4 문서](docs/systems/06_save_v4_and_inventory.md)에 정리했습니다.

**v4 전투 저장은 황·공장 진행·원료 투입 상태와 부품 손상·재고·화재, 승무원의 운반·소화·수리 작업, 정비 자재·정책·기술, 비행 중 탄체·최근 피격·회수 잔해까지 보관합니다.** 순수 장식용 파편과 짧은 시각 효과는 복원하지 않습니다. v1 파일에는 탄체 정보가 없으므로 그 파일을 가져올 때에는 당시 날아가던 탄체를 복구할 수 없습니다. 저장 기능은 진행 복구용이며 전투를 프레임 단위로 똑같이 재생하는 리플레이 도구는 아닙니다.

## 테스트

Node.js가 설치되어 있다면 프로젝트 폴더에서 실행합니다.

```sh
node --test tests/*.test.cjs
```

테스트는 다음 사용자 결과와 상태 불변 조건을 확인합니다. Canvas API 계약 검사는 실행 중 예외·비정상 좌표·상태 변조를 확인하며 브라우저 화면 검수를 대신하지 않습니다.

- 기본 함선의 출격 가능 여부와 승무원 보급 진행.
- 잘못된 배치가 거부될 때 Credits와 부품이 유지되는지.
- 전투 자원이 음수가 되지 않는지.
- 부품 제거·표적 피해·조종실 제한이 일관되는지.
- 기본 첫 교전을 끝낼 수 있는지와 회수 보상의 중복 지급 방지.
- 도크 복귀, 다음 구간 진행, 패배 후 회복.
- 저장 왕복과 잘못된 저장 데이터의 원자적 거부.
- 고정한 이전 배포판 v1·v2·v3 저장의 마이그레이션.
- 운반 중인 탄약을 포함한 복구·재조립의 재고 보존.
- 탄약고가 가득 찬 상태의 운반 재고 보존과 수용할 수 없는 승무원실 철거의 원자적 거부.
- 보급할 수 없는 외부 장치가 정상 공급까지 막지 않는지.
- 대칭 편집의 원자성, 환불·재고를 포함한 되돌리기, 기본 청사진 출격.
- 실제 가속 방향과 무추진 상태, 자기 함선에 가려진 무기의 발사 차단.
- 전술에 따른 교전 거리, 직접 표적 해제와 작전별 보상의 저장·중복 지급 방지.
- 비행 중 탄체를 포함한 전투 저장과 실제 모듈 파괴 직후 복원.
- 실제 승리 보상으로 두 차례 증설·탄약 구매를 거쳐 세 구간을 완주하는지.
- 화재의 지속 피해·확산과 실제 현장 도착 후의 소화·수리.
- 막힌 작업 경로, 소수 자재 고갈, 파괴 부품의 비재생과 정책별 인력 경쟁.
- 정비 자재의 부분 구매, 기술의 가격·최대 단계·실제 발전·배달·가속 효과.
- 이동 중·작업 중 서비스 저장과 화재 진행 뒤 조립 Undo의 롤백 방지.
- 황·탄약의 제조 전후 물질 보존과 전력·원료·공간 부족 상태.
- 분석 데이터의 출처·확인 상태·단위와 결정적 어댑터 생성.
- 생산 중 저장·개별 정지·철거 및 운반 재고를 포함한 견적과 실제 결제 일치.

**2026-11-18, Node.js v24.22.1에서 80개 테스트를 모두 통과했습니다.** 첫 구간의 기본 승리, 지정 모듈 피해, 대체 작전의 승리와 세 구간 순찰 캠페인 완주는 실제 전투 업데이트로 검증합니다. 완주 검사에서는 추가 자금을 주거나 적 내구도를 바꾸지 않고, 기술 0단계에서 보상으로 두 차례 각 1,940 C의 증설과 탄약을 실제 구매합니다. 구간 사이 저장·불러오기도 거칩니다. 이는 검증된 한 가지 진행 경로이며 모든 설계·전술 조합의 승리를 보장하지 않습니다.

화재·손상·자금 경계를 정확하게 만들기 위한 일부 검사는 해당 상태를 직접 준비하며, 주석에 구분합니다. 이후 이동·작업·소비·구매는 실제 시뮬레이션으로 진행합니다. 기존 불량 저장 입력 15종과 v3 입력 14종을 원자성 테스트에서 확인합니다. 이전 저장 호환성 검사는 현재 코드에서 새로 만든 데이터 대신 실제 배포 커밋에서 동결한 v1·v2·v3 표본 여덟 개를 사용합니다.

Node 테스트는 시뮬레이션 계약의 검증입니다. 이번 환경에서는 미리보기 브라우저의 연결 거부로 신규 화면의 실제 입력·터치·DOM 배치를 검수하지 못했습니다. Canvas 렌더러 출력은 별도로 확인했습니다. [상세 검증 기록](docs/VERIFICATION.md)을 참조하세요.

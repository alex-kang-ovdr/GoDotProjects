# 04. 분석 데이터 연결과 생산 코어

## 목적과 적용 범위

STARFORGE v4는 공개 자료에서 확인한 원자로 단계별 차이, 승무원 이동 계수, 황과 탄약의 생산 비율을 게임 계산에 연결한다. `dist/data.js`가 제공하는 실행 상수를 시뮬레이션이 사용하며, 어떤 값이 원작 관측이고 어떤 값이 STARFORGE 조정인지 함께 조회할 수 있다.

원자료는 2026-11-17에 관측한 `cosmoteer_public_reconstruction_v1`의 선별본이다. 설치된 Cosmoteer의 데이터 파일을 추출한 결과가 아니며 정확한 게임 빌드는 확인되지 않았다. `exactGameBuild`는 계속 `null`이다. Classic 수치, Career 2.0 계획, STARFORGE 기존 수치를 원작 확인값으로 섞지 않는다.

선별본은 `data/analysis-snapshot.json`에 있다. 기존 11종과 새 원자로 2종·탄약 공장을 합친 **14개 게임 부품 연결**, 보조 규칙·자원·보류 사례를 포함한 **23개 관측 레코드**, **28개 출처**를 담는다. 연결 목록에 있는 모든 부품의 전투 수치가 원작 값으로 바뀌는 것은 아니다. 변경되는 계산만 아래 변환표와 `MAPPINGS`로 명시한다.

## 원작 관측과 게임 조정

| 항목 | 원작 관측 | STARFORGE 실행값 | 적용 방식 |
|---|---|---|---|
| 소·중·대 원자로 전지 묶음 | 1 / 2 / 3 power | 6 / 12 / 18 에너지 운반 | 묶음 수치 ×6 |
| 원자로 발전량 | 1.5 / 4.5 / 13.5 power/s | 10.5 / 31.5 / 94.5 에너지/s | 발전량 ×7 |
| 원자로 내부 전력량 | 8 / 16 / 24 power | 100 / 200 / 300 | 버퍼 ×12.5 |
| 원자로 가격 | 25,000 / 50,000 / 75,000C | 350 / 700 / 1,050C | 원자로 가격 전용 ×0.014 |
| 원자로 질량 | 4 / 9 / 16t | 4.2 / 9.45 / 16.8 | 원자로 질량 ×1.05 |
| 원자로 내구도 | 각 4,000HP | 각 230HP | 내구도 ×0.0575 |
| 승무원 기본 이동 | 3.2타일/s | 3.2격자/s | 수치와 상대 계수 채택 |
| 통로 / 일반 방 이동 계수 | 1 / 0.5 | 1 / 0.5 | 관계를 직접 적용 |
| 황 기본가격 | 20C/개 | 2C/개 | 황 거래 전용 ×0.1 |

전지 묶음, 발전량, 버퍼의 계수가 다르다. 이는 개별 밸런스 매핑이며 원작 power를 STARFORGE 에너지로 변환하는 보편적인 물리 단위 공식이 아니다. 기존 전투 규모에 맞추면서 원자로 간 1:2:3 운반량과 1:3:9 발전량 차이를 유지하려는 선택이다.

원자로 출처: [소형](https://cosmoteer.wiki.gg/wiki/Small_Reactor_Core), [중형](https://cosmoteer.wiki.gg/wiki/Medium_Reactor_Core), [대형](https://cosmoteer.wiki.gg/wiki/Large_Reactor_Core). 승무원 계수 출처: [Crew](https://cosmoteer.wiki.gg/wiki/Crew). 가격 출처: [Sulfur](https://cosmoteer.wiki.gg/wiki/Sulfur).

## 황→탄약 생산

관측된 제작 비율은 황 0.05개→탄약 1개다. 같은 비율을 정수로 표현하면 **황 1개→탄약 20개**다. 자료의 표시 출력률은 초당 2개이며 전력 소비는 초당 0.08 power다. 원작의 정확한 배치 크기와 배치 시간은 확인되지 않았다. [Cannon Ammo Factory](https://cosmoteer.wiki.gg/wiki/Cannon_Ammo_Factory)

STARFORGE는 이를 **황 1개를 사용하는 10초 생산 작업**으로 구현한다. 20÷10=2로 표시 출력률과 일치하지만, 10초가 원작의 실제 배치 시간이라는 뜻은 아니다. 공장 전력은 별도 조정으로 초당 0.48 에너지를 소비한다. 공장 비용 420C, 전력 버퍼 24, 완성 탄약 버퍼 60은 프로토타입 운영 규모다. 공장 황 버퍼 5는 공개 자료에서 확인한 용량을 사용한다.

생산 시작 때 황을 작업 중 재료로 전환하며, 작업이 끝날 때 탄약을 만든다. 중간 정지·전력 부족·저장은 진행 중 재료를 유지한다. 정상 철거와 파괴는 서로 다른 결과를 가진다. 정상 철거는 작업 중 황을 포함해 회수 가능한 재료를 다른 저장 위치로 돌려보낸다. 공간이 부족하면 명시된 프로토타입 판매 계수로 자동 매각한다. 전투에서 공장이 파괴되면 그 공장에 있던 재료가 손실될 수 있다. 이 손실을 정상 거래나 저장 불러오기의 소실로 혼동하지 않는다.

저장고는 기존 탄약 외에 황 20개를 담는다. 새 원정은 저장고당 황 6개로 생산을 시험할 수 있다. v1~v3 저장을 불러올 때는 새 황을 지급하지 않는다. 황의 구매·판매·보관 한도와 제조 작업은 저장에 포함한다. 강철과 탄약의 원작 단가는 출처 조회용으로 보존하며, 이번 버전에 별도의 강철 채광·거래 체계가 추가됐다고 표시하지 않는다.

황 거래 견적은 `getProductionQuote('sulfur', amount)`가 반환하는 수량·가격·창고 용량·현재량·여유량으로 확인한다. `buyResource('sulfur', amount)`는 검증한 양만 구입하며, 잘못된 자원 ID나 수량, 부족한 자금으로 실패하면 원래 상태를 유지한다. 개별 공장은 `setFactoryEnabled(partId, enabled)`로 중단·재개할 수 있다. `getStats().factories`는 진행 시간, 작업 중 재료 여부, 원료·탄약 재고, 대기 이유를 제공한다.

## 자료를 실행값으로 바꾸는 경계

`readKnown(recordId, field, expectedUnit)`는 다음 조건을 모두 만족하는 필드만 반환한다.

1. 해당 레코드와 필드가 실제로 존재한다.
2. 값이 `null`이 아니다.
3. 상태가 `wiki_snapshot` 또는 `patch_confirmed`다.
4. 출처 ID가 있고 선별본의 출처 목록으로 연결된다.
5. 호출자가 단위를 지정했다면 단위가 일치한다.

불충분한 값에 0이나 비슷한 값을 넣지 않는다. 소형 원자로의 충전시간은 관측 간 충돌이 있으므로 실행 매핑에 사용하지 않는다. 침실 가격, 체인건 재료, 강철 제작 입력, 고폭 미사일의 불완전 소비율 표 역시 보류 사례로 남는다. 기존 게임의 `bunk`는 충돌 있는 2인 침실이 아닌, 확인된 6인 `crew_quarters`를 참조한다.

`getEvidence()`로 원문 값·단위·상태·출처·충돌 관측을 조회하고, `getMapping()`으로 게임에 적용된 계수와 조정 이유를 확인한다. 원작 관측 객체는 수정할 수 없도록 동결돼 있다. 게임 저장 파일에는 임의의 새 부품 정의나 출처 코드를 주입하지 않는다.

## 실행 API

브라우저에서는 `globalThis.StarData`, Node에서는 `require('./data.js')`로 같은 객체를 받는다. 브라우저는 `data.js`를 `sim.js`보다 먼저 로드해야 한다. 런타임 네트워크 조회는 없다.

| API | 용도 |
|---|---|
| `PART_OVERRIDES` | 원자로 3종, 황 저장고 확장, 탄약 공장의 실행 정의 |
| `INDUSTRY` | 생산 비율·주기·전력·황 가격·운반·회수 조정 상수 |
| `CREW_MOVEMENT` | 기본 이동 속도와 통로·방 계수 |
| `PART_REFERENCES` | 게임의 14개 부품 유형→자료 레코드 연결 |
| `getPartReference(type)` | 해당 부품의 관측 자료와 실행 매핑 |
| `getEvidence(id, field)` | 단일 필드의 원값·상태·출처·관측 이력 |
| `readKnown(id, field, unit?)` | 검증을 통과한 원작 필드만 반환 |
| `getMapping(target)` | `parts.reactor_medium.batteryPack` 등 실행값의 변환 근거 |

생성 명령은 `node scripts/build-game-data.cjs`다. 입력은 검토된 저장소 내 JSON뿐이며, 같은 입력으로 같은 `data.js`를 만든다. 생성물의 `SNAPSHOT_DIGEST`와 원본 복구 JSON의 해시를 구분해 기록한다. 원본 해시는 출처 파일 식별용이며 게임 빌드 확인을 뜻하지 않는다.

`node scripts/build-game-data.cjs --check`는 파일을 쓰지 않고 생성 결과가 최신인지 확인한다. 브라우저 테스트나 다른 Node 검사와 함께 실행해도 배포 스크립트를 중간에 다시 쓰지 않는다.

## 검증 대상

데이터 검사는 null·충돌 필드의 실행 거부, 단위 오용 거부, 출처 외래키, 14개 부품 연결, 독립적인 매핑 계수, 브라우저/Node 동일성, 원자료 불변성과 결정적 재생성을 확인한다.

생산 통합 검사는 실제 승무원의 원료·탄약 운반, 원료와 완성품의 보존, 부족전력·일시정지·출력 포화 처리, 작업 중 저장 왕복, 잘못된 자원 저장의 원자적 거부, 원자로 단계별 실제 운반, 공개 배포 v3 저장의 호환성을 확인한다. 기존 3구역 완주 검사를 유지해 새 생산 선택이 기본 진행을 막지 않는지도 확인한다.

2026-11-18 검증에서 `tests/data.test.cjs`의 7개와 `tests/industry.test.cjs`의 16개, 합계 **23개 신규 검사**가 통과했다. 산업 검사의 보존식은 도크에서 `모든 탄약 + 20 × (창고 황 + 운반 중 황 + 작업 중 황)`이 일정하다는 조건이다. 전력·황·탄약·출력 버퍼를 동시에 검사해, 생산 완료 시점에만 보이는 총량 오류를 놓치지 않도록 했다. 기존 배포 코드로 동결한 v3 도크·전투 저장을 사용했으며 현재 엔진으로 과거 저장을 다시 만들지 않았다.

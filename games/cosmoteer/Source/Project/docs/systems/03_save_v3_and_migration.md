## 1. 저장의 역할

저장은 함선 모양뿐 아니라 현재 원정의 자금·진행·손상·재고·승무원 작업을 복원한다. 기술 개량과 정비도 원정 상태이므로 같이 보존한다. 앱의 JSON 내보내기에는 사용자 청사진 목록도 함께 담는다.

`Game.exportSave()`는 객체를 반환하고, `Game.importSave()`는 객체 또는 JSON 문자열을 받는다. 가져오기는 성공·실패와 설명 메시지를 반환한다. 알 수 없는 저장 버전이나 잘못된 작업을 정상 상태처럼 조용히 적용하지 않는다.

현재 저장은 `VERSION: 3`, `version: 3`, `game: "starforge-drydock"`를 기록한다. 검증의 형식 식별자는 VERSION과 game이다.

## 2. v3에서 추가한 상태

| 위치 | 필드 | 의미 |
| --- | --- | --- |
| 게임 | `repairPolicy` | balanced / survival / supply |
| 게임 | `serviceTargetId` | 현장 우선 대상의 모듈 ID 또는 null |
| 게임 | `upgrades` | reactor / logistics / drive의 정수 레벨 0~3 |
| 게임 | `fireClock` | 다음 화재 주기 판정까지 이어갈 누적 시간 |
| 함선 | `repairStock` | 0~240의 공유 정비 자재 |
| 모듈 | `fire` | 0~1의 화재 강도 |
| 통계 | `firesExtinguished` | 승무원이 진압한 화재 수 |
| 통계 | `hullRepaired` | 승무원이 현장에서 회복한 HP |
| 통계 | `repairStockUsed` | 현장 수리에 소비한 자재 |
| 승무원 작업 | 서비스 작업 구조 | 소화·수리의 현장, 경로, 작업 진행 |

기존의 도크·전투 상태, 구간, 크레딧, 부품 HP·에너지·탄약·열, 승무원 화물·보급 작업, 선택 작전·전술·표적 우선순위, 보상 회수 이력도 유지한다. 부품 ID는 살아 있는 작업과 표적을 연결하므로 중복 없이 복원해야 한다.

## 3. 현장 작업 형식

아래는 구조를 보여 주기 위한 예시다. 실제 ID·좌표·경로는 해당 함선에 존재하는 값이어야 한다.

```json
{
  "kind": "repair",
  "phase": "service",
  "sourceId": null,
  "targetId": "part_12",
  "site": { "x": 1, "y": -3 },
  "path": [
    { "x": 1, "y": -2 },
    { "x": 1, "y": -3 }
  ],
  "pathIndex": 1,
  "amount": 0,
  "work": 0.1,
  "effectAmount": 0.8
}
```

`kind`는 repair 또는 extinguish이며 phase는 service다. 전지·탄약 운반 작업과 달리 sourceId는 null, amount는 0이다. 서비스 작업자는 운반 중인 화물을 동시에 보유하지 않는다. site는 대상 자체 또는 상하좌우의 실제 걸을 수 있는 작업 칸이다.

pathIndex는 다음에 따라갈 경로 위치다. 이동이 끝나면 승무원 실제 좌표가 site에 도달해야 효과를 낸다. work와 effectAmount는 작업 효과를 일정 간격으로 표시하기 위한 누적 값이다. work가 0.35초가 될 때까지 수리를 시작하지 않는 대기 타이머로 해석하지 않는다.

복원 검사는 현장에 가는 도중과 실제 작업 중의 두 상태를 모두 다룬다. 표적·자재·정책·경로·작업 누적을 보존하고, 원본과 복원본을 같은 시간 더 진행했을 때 같은 작업 결과를 내는지 확인한다.

## 4. 가져오기 검증과 원자성

가져오기는 데이터를 읽어 임시 Game 상태를 만들고 검증을 마친 뒤 현재 게임에 적용한다. 파싱 초기에 실패하거나 경로 검사처럼 늦은 단계에서 실패해도 기존 원정을 부분적으로 바꾸지 않는다.

주요 검증은 다음과 같다.

- 버전·게임 식별자, 유효한 모드·정책·작전·기술 종류.
- 유한한 수치, 자금·자재·화재의 범위, 기술의 정수 레벨 0~3.
- 함선당 최대 160개 모듈·60명 승무원, 좌표 범위와 중복 칸·ID.
- 부품의 살아 있는 상태, 화물 종류·양과 보급 작업의 일치.
- 서비스 작업의 sourceId=null, amount=0, 무화물 상태.
- 대상과 작업 장소의 인접성, 활성 통로 여부, 경로 칸의 연결.
- 승무원 현재 위치에서 다음 경로 칸까지의 실제 거리, 마지막 경로와 목적지의 일치.
- 선택한 현장 우선 대상의 존재와 연결.

서비스 work는 현재 표시 주기 범위 안이어야 하고 effectAmount도 해당 작업의 표시 누적 범위 안이어야 한다. 문자열 입력에는 600,000자 상한이 있다. 객체 입력도 각 배열·필드의 상한과 연결 관계를 검증한다.

자동 검사는 음수·초과·무한대 fire, 음수·초과 자재, 잘못된 정책·기술 레벨, 없는 우선 대상, 떨어진 작업 장소, 화물을 든 서비스 작업, 잘못된 sourceId·amount·work 등 v3 불량 입력 14종을 확인한다. 각 실패 전후 exportSave 전체가 같은지 비교한다. 기존 형식의 불량 입력 15종 검사도 유지한다. [원자성 테스트](../../tests/service.test.cjs)

## 5. 이전 저장의 이관

| 입력 | 유지하는 상태 | 누락된 새 상태의 초기값·한계 |
| --- | --- | --- |
| v1 | 기존 함선·자금·구간·물류·회수 이력 | 기술 0, 균형 정비, 우선 대상 없음, fire 0, 플레이어 자재 80·적 자재 60. 원래 저장하지 않은 탄체는 복원할 수 없음 |
| v2 | 기존 상태에 더해 작전·전술·자동 표적·탄체 등 | 누락된 정비·기술 상태에 동일한 v3 초기값 적용 |
| v3 | 화재·현장 작업·자재·기술까지 복원 | v3 필드와 작업 관계를 검증 |

이전 저장을 읽어도 구매했던 모듈이나 크레딧을 초기화하지 않는다. 이미 회수한 승리 보상도 다시 지급하지 않는다. 이관 뒤에는 새 게임 규칙으로 진행하므로 이전 버전과 이후의 전투 결과가 항상 같다는 의미는 아니다.

호환성 검사는 현재 코드로 예전 형식처럼 꾸민 객체를 만드는 방식 대신 실제 배포 커밋에서 고정한 표본을 사용한다.

| 표본 | 출처 | 포함 상태 |
| --- | --- | --- |
| [legacy-v1.cjs](../../tests/fixtures/legacy-v1.cjs) | dcb17c2 | 도크, 진행 중 전투, 회수 완료 승리 |
| [legacy-v2.cjs](../../tests/fixtures/legacy-v2.cjs) | 424bd7a | 탄체 1개가 비행 중인 포격 작전, 회수 완료 승리, 실제 보상으로 1,940 C 증설을 구입한 2구간 도크 |

v2 도크 표본은 이미 지출한 자금과 추가 승무원·모듈을 포함한다. 이 표본으로 새 원정만 열리는 수준을 넘어 실제 진행이 유지되는지 확인한다. 고정 표본은 앞으로 현재 구현으로 다시 생성하지 않는다.

## 6. 복원하는 효과와 생략하는 효과

v2·v3 저장에는 비행 중 탄체, 최근 피격 기록, 회수 잔해가 들어간다. v3에서는 화재 주기와 현장 작업의 누적 상태도 이어 간다. 이미 발사된 탄체를 없애서 진행 중인 교전을 유리하게 바꾸는 방식으로 복원하지 않는다.

순수 장식용 파편과 짧은 시각 효과는 저장하지 않는다. 불러오는 순간 화면의 잔광이나 장식 파편이 달라질 수 있다. 이 저장은 진행 복구를 위한 것이며 버전·브라우저·입력 시점이 달라도 모든 프레임을 동일하게 재생하는 도구를 제공하지 않는다.

실제 모듈이 파괴된 바로 그 업데이트의 저장도 검사한다. 파괴된 자동 표적 참조는 불러올 때 정리할 수 있지만, 이 과정에서 부품을 치료하거나 승무원을 무료로 충원하거나 화물을 지우지 않아야 한다.

## 7. 앱 저장과 사용자 청사진

코어 원정 저장과 사용자 청사진 목록은 역할이 다르다. 앱은 JSON 내보내기에 `designLibrary`를 덧붙여 둘을 함께 이동시킨다. 가져오기는 목록 형식도 확인한 뒤 원정 가져오기가 성공했을 때 목록을 적용한다. 잘못된 원정 또는 목록 때문에 둘 중 하나만 바뀌지 않아야 한다.

청사진 목록이 없는 옛 파일을 가져오면 현재 목록을 유지한다. 새 원정은 원정 진행·기술·자재를 초기화하고 저장한 사용자 청사진 목록은 유지한다. 자동 저장은 같은 브라우저·주소의 localStorage를 사용하므로 다른 환경으로 옮길 때에는 JSON을 내보낸다.

## 8. 운영·검증 범위

재현할 때에는 원본 저장을 보관하고 테스트 복사본을 사용한다. 버전 번호만 바꾸어 호환된 것처럼 만드는 작업은 이관이 아니다. 새로운 필드를 도입할 때에는 이전 실제 배포 표본과 현재 진행 중 작업의 저장을 함께 검사한다.

현재 자동 검증에는 v1·v2 표본 여섯 개, v3 소화·수리의 이동·작업 중 왕복, 잘못된 입력의 원자성, 실제 파괴 직후 저장, 탄체 보존, 구간 사이 저장을 거치는 실제 세 구간 완주가 포함된다. 앱의 화면 조작과 청사진 목록을 포함한 혼합 가져오기는 별도 브라우저 검증 범위다.

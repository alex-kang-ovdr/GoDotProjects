# 21. 재구현 제작 단계와 통합 수용 기준

[전체 목차](README.md) · 문서 ID: PLAN-21 · 작성: 2026-11-13 · 기준: 0.30.5a 문헌

> 전체가 **[제안]**이다. 원작의 실제 제작 순서·인력·일정·내부 QA 계획을 추정한 문서가 아니다. 아래 테스트는 작성된 절차이며 게임 실행 또는 구현 코드로 수행한 결과가 아니다.

## 1. 제작 목표의 정의

재구현에서 먼저 증명할 것은 부품 수나 은하 크기가 아니라 **설계 변경이 운용을 바꾸고, 운용이 전투 결과를 바꾸며, 그 결과가 다음 설계의 이유가 되는가**다. 이 연결이 성립한 뒤 무기·부품·임무를 늘린다.

최소 기능 검증과 원작 동등 재현을 다른 완료 기준으로 둔다. 작은 프로토타입에서 열·협동·모든 무기를 생략할 수는 있지만, 그 상태를 0.30.5a 전체 재현 완료라고 부르지 않는다.

## 2. 단계별 산출물과 통과 조건

| 단계 | 구현 범위 | 산출물 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- | --- |
| M0 규칙·데이터 | ID, 단위, 상태 소유권, 기준 버전 | 데이터 사전·검증 도구 | 수치·참조·콘텐츠 버전이 일관됨 |
| M1 함선 기초 | 격자 배치, 연결, 문, 저장·로드 | 작은 함선 편집기 | 편집·파괴·복원 후 구조 무결성 |
| M2 운용 시뮬레이션 | 승무원, 작업, 전지·탄약 운반 | 공급 병목이 보이는 실험 | 동선 변경이 공급률에 반영됨 |
| M3 전투 수직 단면 | 이동, 무기 2종, 방어, 부위 파괴 | 반복 가능한 소규모 교전 | 손상으로 기능·경로·기동이 변함 |
| M4 손상·열 확장 | 화재, 냉각, 열 영향, 오버클럭 | 지속 교전과 복구 실험 | 초기 비축·열·손상을 따로 설명 가능 |
| M5 커리어 단면 | 탐사, 임무, 회수, 거래, 해금·명성 | 짧은 성장 루프 | 성과가 다음 설계 변경으로 연결됨 |
| M6 함대와 콘텐츠 | 다함선, 역할 분업, 다양한 장치 | 역할별 함대 실험 | 단일 함선 가정이 남지 않음 |
| M7 공유·멀티플레이 | 모드 정책, 설계 공유, 동기화 | 재현·협동·경기 기록 | 버전·권한·동시 명령이 일관됨 |

이 순서는 위험을 빨리 드러내기 위한 제안이다. 락스텝을 최종 목표로 삼는다면 결정론 기반은 M0부터 적용해야 한다. M7에서 네트워크 기능을 연결하더라도 시뮬레이션 전체를 그때 처음 결정론으로 바꾸는 계획은 피한다.

## 3. 첫 수직 단면의 구체적인 범위

### 3.1 포함할 장치 [가정한 제작 범위]

통로·문·선체 연결 부품, 승무원 거처, 제어 장치, 하나의 전력원, 저장 공간, 기동 장치, 에너지 무기, 탄약 무기, 장갑을 사용한다. 이름은 실제 부품 카탈로그를 확정하는 것이 아니라 필요한 기능 범주다.

소규모 교전에 상대 함선 하나와 회수 가능한 잔해를 배치한다. 플레이어가 장치를 추가했을 때 전력·탄약·인력이 함께 필요해지는 관계를 확인한다. 표적 부위를 파괴하면 장치 작동과 이동 경로가 바뀌어야 한다.

### 3.2 처음부터 필요한 진단 화면

| 진단 화면 | 필요한 이유 |
| --- | --- |
| 부품별 작동 불가 사유 | 전투 결과가 왜 달라지는지 설명 |
| 승무원 작업·목적지 | 인력 부족과 잘못된 배정을 구분 |
| 자원 원장·예약 | 중복 사용·유실을 찾음 |
| 구조·통행 그래프 | 연결과 통행의 불일치를 찾음 |
| 장치 발사·중단 기록 | 순간 성능과 지속 성능을 구분 |
| 시뮬레이션 틱 비용 | 규모 확장 전에 비싼 부분을 찾음 |

진단 기능은 사용자에게 항상 복잡한 화면으로 노출할 필요는 없지만, 개발 중에는 결과를 설명할 수 있어야 한다.

## 6. 불변 조건과 회계 검증

재고는 다음처럼 분해해서 확인한다. 각 항목의 정의는 원장 설계에 맞춰 상호 배타적으로 구성한다.

$$
Initial + Produced + Acquired = Stored + InTransit + FloatingOwned + Consumed + Sold + Lost
$$

이 식은 자원 유형별로 적용한다. 생산에 투입한 원료는 해당 유형의 Consumed에, 만들어진 산출물은 산출 유형의 Produced에 기록한다. FloatingOwned는 소유권을 유지한 채 외부에 떠 있는 물량이며 운반 중 물량과 중복 계산하지 않는다. 예약은 보유 자원의 사용 권리이므로 위 물량 식에 별도 자원처럼 더하지 않는다. 예약량은 `예약 가능한 실물량`을 넘지 않는다는 제약으로 검사한다. 거래 중인 자원은 소유권 이전 시점에 따라 Acquired/Sold와 물리 위치를 일관되게 기록한다.

다른 불변 조건은 다음과 같다.

- 파괴된 부품 ID를 활성 작업이 유효 목적지로 계속 사용하지 않는다.
- 하나의 승무원이 동시에 두 조작 슬롯의 확정 담당자가 되지 않는다.
- 함선에 속한 부품은 한 연결 집합과 하나의 소유 함선에 귀속된다.
- 부품 설정 변경으로 인한 비용·자원 소모는 성공한 확정 단계에만 반영된다.
- 상태 복구 후 예약의 소유 작업과 원장 항목이 서로 연결된다.

## 7. 실측과 밸런스 비교의 분리

### 7.1 규칙 실측

목표는 원작이 어떤 조건에서 어떻게 작동하는지 확인하는 것이다. 대상 빌드·모드·설계·초기 자원·배속·명령을 기록하고 하나의 변수를 바꾼다. 문헌의 미확인 수치를 확정하는 실험은 [23](23_Sources_and_Fact_Check.md)의 확인 항목과 연결한다.

### 7.2 재구현 검증

목표는 채택한 명세를 새 구현이 만족하는지 확인하는 것이다. 원작 수치와 다르게 정한 경우에는 “원작과 다름”과 “내 명세를 위반함”을 구분한다. 특히 실험 편의를 위해 단순화한 경로·열·피해 모델을 원작 오류로 설명하지 않는다.

### 7.3 밸런스 비교

가격, 인력, 부품 수, 초기 재고, 전투 조건을 통제한다. 한 설계가 이겼다는 결과만으로 부품이 과도하게 강하다고 결론 내리지 않는다. 상대 설계·거리·초기 방향·전술 정책을 바꿔 우세 조건을 찾는다.

## 8. 성능 부하 시나리오

| 부하 유형 | 변화시키는 독립 변수 | 측정값 |
| --- | --- | --- |
| 대형 함선 | 부품 수·내부 경로 길이 | 틱 시간·그래프 메모리 |
| 다함선 | 함선 수·교전 관계 | 충돌 후보·AI 평가 비용 |
| 인력 집중 | 승무원 수·동시 작업 요청 | 작업 검색·대기·경로 갱신 |
| 탄막 | 투사체 수·요격 장치 수 | 충돌·표적 탐색 비용 |
| 구조 파괴 | 한 번에 끊기는 연결 수 | 가장 느린 틱·재계산 범위 |
| 열 확산 | 활성 부품·네트워크 수 | 열 단계 비용·전달 오차 |
| 편집·저장 | 설계 규모·변경 수 | 입력 응답·저장·로드 시간 |

목표 수치는 초기 플랫폼과 최소 사양을 정한 뒤 수립한다. 대표 장면의 평균 수치만 보고 통과시키지 말고 구조 파괴·함선 분리·대규모 경로 무효화 직후의 지연을 별도로 기록한다.

## 9. 완료 정의

### 규칙 문서 완료

입력·조건·상태·결과·예외·출처·불확실성이 있고, 다른 문서와 용어가 일치한다. 제안 구조가 실제 원작 규칙처럼 쓰이지 않는다.

### 기능 구현 완료

정상 상황과 취소·파괴·경로 변경 상황을 처리하고, 저장·로드 후 상태가 일관되며, 실패 원인이 사용자 또는 개발자에게 보인다.

### 전체 재구현 완료

선택한 기준 버전의 기능 범위를 별도 목록으로 확정하고 모두 검증한다. 현재 묶음은 그 작업을 시작하기 위한 역기획서이며, 모든 부품의 정확한 값이 입력된 데이터베이스나 이미 검증된 복제품을 제공하는 것은 아니다.

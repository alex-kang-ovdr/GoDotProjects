# 06. 발전·전지·전력 분배 시스템 역기획

[전체 목차](README.md)

| 항목 | 내용 |
| --- | --- |
| 문서 ID | SYS-06 |
| 기준 | 상용 Cosmoteer 0.30.5a 공개 공지, 2026-11-13 |
| 검증 방식 | 문헌·검색 색인 교차 확인. 원작 실행·게임 데이터 추출 없음 |
| 표기 | **[확인]** 문헌 규칙, **[해석]** 설계 의미, **[제안]** 재구현 명세, **[검증 필요]** 미확정 수치·경계 동작 |

## 1. 핵심 역할

**[해석]** 전력 시스템의 핵심 자원은 발전량만이 아니다. 발전·저장·운반·소비의 네 단계가 모두 충족되어야 무기·방어·추진 기능이 유지된다. 발전소를 늘리는 해결과 운반 경로를 줄이는 해결은 서로 다른 병목에 작용한다.

**[확인]** 원자로는 전지를 생성하며 승무원이 이를 필요한 부품으로 나른다. 전지는 일반 자원 창고에 저장하지 않고 Power Capacitor 같은 전력 전용 설비에 저장한다. 소비 부품은 자체 에너지가 부족하면 기능을 유지하지 못한다. [S-SC06-1]

따라서 전선을 연결하면 모든 부품이 하나의 공용 전력망에서 즉시 전기를 쓰는 모델로 역기획해서는 안 된다. 기관실을 통한 인접 추진기 공급 같은 예외는 [기동·추진](07_Propulsion_and_Maneuvering.md)의 별도 계약으로 다룬다.

## 2. 생산·운반 단위·저장을 구별한다

| 개념 | 의미 | 흔한 오해 |
| --- | --- | --- |
| 발전률 | 시간당 새로 만들어지는 에너지 | 발전량만 충분하면 모든 부품이 항상 작동 |
| 전지 운반 단위 | 한 번 픽업하여 옮기는 에너지 묶음 | 전지 개수와 에너지 총량이 항상 같은 단위 |
| 원자로 내부 재고 | 아직 가져가지 않은 에너지 | 내부 재고가 많으면 모든 구역도 충전됨 |
| 축전기 저장량 | 전력 운반을 위한 지역 완충 재고 | 가까운 부품에 무선으로 자동 공급 |
| 소비처 저장량 | 부품이 자체적으로 사용할 수 있는 에너지 | 공급원 재고와 공유하는 하나의 수치 |
| 소비률 | 대기·작동·피격·발사 등의 조건별 소모 | 모든 소비가 일정한 초당 값 |

**[확인]** 공개 위키는 기본 소형·중형·대형 원자로의 전지 크기를 각각 단일·이중·삼중 용량으로 설명한다. 큰 묶음은 한 번의 운반에 더 많은 에너지를 실을 수 있지만 픽업 과정도 고려해야 한다. [S-SC06-1], [S-SC06-3]

**[검증 필요]** 정확한 픽업 시간은 자료 사이에 불일치가 있다. Batteries 요약표와 Small Reactor Core 개별 표가 소형 원자로의 충전 시간에 다른 값을 제시하므로, 현재 빌드에서 관찰하기 전에는 단일 확정값을 사용하지 않는다. [S-SC06-1], [S-SC06-2]

## 3. 축전기의 역할과 최신 기준

**[확인]** Power Capacitor는 생산자가 아니라 전력 저장·재분배 거점이며, 저장된 전지도 승무원이 운반한다. 일반 상태에서는 큰 전지 묶음이 단일 단위로 나뉘어 나오는 방식으로 설명되어 있다. [S-SC06-4]

**[확인]** 0.30.5의 오버클럭 축전기 용량은 48로 변경되었고, 0.30.5a는 용량이 3배라는 잘못된 설명을 수정했다. 과거의 “3배”를 현재 규칙으로 사용하지 않는다. [S-SC06-5]

**[해석]** 축전기는 세 가지 선택을 만든다. 첫째, 소비처 앞에 짧은 마지막 운반 구간을 만들 수 있다. 둘째, 순간적인 수요 상승을 저장분으로 흡수할 수 있다. 셋째, 원자로를 전방에 직접 배치하는 것과 다른 위험 분포를 만들 수 있다. 그러나 재충전 인력과 추가 공간이 필요하며, 긴 전투에서 발전 자체가 부족하면 축전기도 결국 소진된다.

오버클럭의 발열과 파괴 시 열 피해는 [열·오버클럭](11_Heat_and_Overclocking.md)에서 다룬다. 기본 축전기의 과거 설명을 모든 동작 모드의 안전성 보장으로 확장하지 않는다.

## 4. 입력·상태·출력

| 구분 | 항목 |
| --- | --- |
| 입력 | 부품 활성 토글, 발전 모드, 공급망 지정, 승무원 역할, 사격·추진·피격 이벤트 |
| 지속 상태 | 원자로·축전기·소비처 에너지, 전지 운반 중량, 출고·입고 예약, 열 상태 |
| 출력 | 작동 가능 여부, 전력 부족 알림, 운반 작업, 열 발생, 기능 성능 변화 |
| 교차 의존 | 조작 인력, 문·통로, 구조 손상, 제조 입력, 지휘 상태, 냉각 |

**[제안]** 에너지 값과 “배터리 객체 개수”를 서로 다른 필드로 둔다. 에너지 단위를 내부 정수로 정규화하고, 운반 단위는 출처·모드의 정책으로 결정한다. 문서·UI에 표시하는 단위 환산을 통일하여 `power`, `battery`, `energy per shot`이 다른 의미인데 같은 숫자로 보이는 문제를 막는다.

## 5. 소비 패턴 분류

**[확인]** 공개 전지 문서는 시간 경과, 발사, 생산, 방어막 피격 등 서로 다른 에너지 소모 조건을 구분한다. [S-SC06-1] 세부 부품별 소모량은 고정 표를 전재하지 않고 대상 버전 데이터로 검증한다.

| 분석상 소비 유형 | 시간 패턴 | 설계에 미치는 영향 |
| --- | --- | --- |
| 기저 소비 | 비교적 연속적 | 최소 발전·기본 보급 수요 |
| 지속 작동 소비 | 추진·지속 기능 사용 시간에 비례 | 조작 상태와 병행 부하 평가 필요 |
| 발사·생산 소비 | 이벤트마다 발생 | 일제 실행 시 순간 수요 집중 |
| 피격 소비 | 적의 공격에 따라 급증 | 평시 테스트로 예측하기 어려움 |
| 특수 상태 변화 | 점프·전력 교란 등 | 재충전과 회복 지연 검토 |

분류표는 **[해석]**이며 실제 원작 코드의 소비 컴포넌트 종류를 의미하지 않는다. 한 부품이 둘 이상의 패턴을 동시에 가질 수 있다.

## 6. 전력 예산의 세 가지 조건

아래 수식은 **[제안]**이며 원작의 실제 계산식을 복원한 것이 아니다.

### 6.1 장기 에너지 조건

\[
P_{generation}\geq\overline{P}_{demand}
\]

지속 평균 수요보다 발전률이 작으면 저장량이 아무리 커도 충분히 긴 시간에는 고갈된다. 반대로 이 조건이 맞아도 수송이 늦으면 소비처가 멈춘다.

### 6.2 지역 배송 조건

\[
P_{delivery,j}=\sum_{k\in route(j)}\frac{N_k E_{useful,k}}{T_{trip,k}}
\]

소비처 또는 소비처 묶음 `j`가 실질적으로 받을 수 있는 공급량을 따로 본다. 운반 인력을 중복 집계하지 않아야 하며, 같은 인원이 무기·방어·추진을 번갈아 공급한다면 각 기능에 전 인원을 배정한 것으로 계산할 수 없다.

### 6.3 순간 버팀 조건

\[
E_{local}\geq\int_{t_0}^{t_1}\max(0,P_{demand}(t)-P_{arrival}(t))dt
\]

소비처와 주변 완충 재고가 재보급 지연 동안의 부족분을 감당할 수 있어야 한다. 평균 발전률이 같아도 짧고 강한 일제사격과 길고 완만한 사격은 요구 저장량이 다르다.

### 가정 계산

**[제안 예시]** 소비가 3에너지/초이고 지역 배송이 2에너지/초, 사용 가능한 저장량이 10이라면 단순 모델에서는 약 10초 후 고갈된다. 배송이 3 이상으로 회복되면 감소가 멈추지만, 저장량이 즉시 최대치로 복구되는 것은 아니다. 이는 실제 부품 수치가 아니라 발전·운반·저장의 관계를 설명하는 가정이다.

## 7. 중앙 집중과 분산 전원의 선택

| 설계안 | 강점에 대한 해석 | 약점에 대한 해석 | 검증할 관찰 |
| --- | --- | --- | --- |
| 큰 중앙 전원 | 생산과 인력 집약 | 긴 운반·주요 지점 손상 영향 | 끝단 소비처 고갈 빈도 |
| 여러 지역 전원 | 짧은 공급 경로·구역 자립 | 부품·방호·인력 중복 | 같은 총비용에서 지속 작동률 |
| 중앙 전원+지역 축전 | 순간 대응과 전원 배치 분리 | 중계 운반·재충전 경합 | 첫 전투와 연속 전투 차이 |
| 특정 기능 전담 공급 | 결과 예측과 튜닝 용이 | 다른 구역 여유량 활용 제한 | 공급원 상실 후 복구 가능성 |

**[해석]** 원자로는 에너지원인 동시에 우선 보호 대상이 된다. 전방에 가까워질수록 수송에는 유리할 수 있지만 공격에 노출될 가능성도 커진다. “최대한 가까이”와 “최대한 안전하게”를 모두 만족할 수 없어서 배치 문제가 생긴다.

**[확인]** 소형 원자로 문서에도 파괴 시 폭발이 명시되어 있다. [S-SC06-2] 실제 폭발 반경·차폐 효과·최신 화재 강도는 [피해·파괴](10_Damage_Fire_and_Destruction.md)에서 별도로 관리한다. 오래된 폭발 예시를 모든 원자로·모드에 적용하지 않는다.

## 8. 상태 갱신 제안

```text
제안: UpdateEnergy(part, dt)
    generated = GenerationPolicy(part.mode, part.state, dt)
    part.energy = min(part.capacity, part.energy + generated)

    continuousNeed = ContinuousDemand(part, dt)
    events = GatherConsumptionEvents(part)
    for demand in [continuousNeed] + events:
        if CanPay(part.energy, demand):
            ApplyDemandAndEffect(part, demand)
        else:
            ApplyInsufficientPowerPolicy(part, demand)

    if NeedsResupply(part.energy, part.reservedIncoming, part.mode):
        PublishEnergyDemand(part)
```

실제 원작의 갱신 순서가 아니라 구현상의 질문을 드러내는 의사코드다. 같은 프레임에 전지가 도착하고 발사 요청이 발생했을 때 어느 것을 먼저 처리하는지 결정해야 한다. 모든 시스템이 동일한 안정적인 단계 순서를 사용해야 재현성이 유지된다.

**[제안]** 전력 부족 때문에 기능을 끄는 상황에서 재충전 즉시 켜짐과 꺼짐이 반복되면 작은 임계값 차이를 둘 수 있다. 그러나 실제 게임에 같은 히스테리시스가 존재한다고 주장하지 않는다. 소비처별 재보급 임계값과 작동 가능 임계값은 개별 데이터로 관리한다.

## 9. 진단 순서

전력 부족의 원인을 다음 순서로 분리한다.

1. **[제안]** 필요한 소비처가 실제로 전력 부족 상태인지 확인한다. 조작자·탄약·사거리 문제를 제외한다.
2. 공급원에 에너지가 있는지 확인한다. 비어 있다면 생산량 또는 수요 집중 문제를 의심한다.
3. 공급망 지정과 문·통로를 확인한다. 재고가 있어도 허용된 출처가 아닐 수 있다.
4. 운반 가능한 역할의 인원이 있는지 확인한다. 다른 고우선 작업에 묶여 있을 수 있다.
5. 실제 배송 주기와 소비처 저장량을 비교한다. 평균 발전량보다 지역 공급 지연이 문제일 수 있다.
6. 전투·추진·방어를 동시에 실행해 피크 수요를 확인한다. 평시 충전 상태만으로 합격시키지 않는다.

이 순서로도 설명이 안 되면 오버클럭·특수 모드·에너지 교란 등 상태별 규칙을 확인한다. 전력과 열은 서로 영향을 주지만 같은 수치를 다른 이름으로 표현하는 시스템이 아니다.

## 10. 데이터와 버전 관리

| 데이터 | 주요 필드 | 검증 주의점 |
| --- | --- | --- |
| EnergySourceDefinition | generationRate, packetSize, pickupTime, modes | 위키 요약과 개별 부품의 불일치 |
| EnergyStore | current, capacity, incomingReserved, outgoingReserved | 일반·오버클럭 모드 용량 구분 |
| ConsumptionProfile | idle, active, perEvent, perDamage | 표시 단위와 실제 이벤트 시점 |
| ResupplyPolicy | threshold, allowedSources, preferredRegion | 공급망 제한과 우선순위 구분 |
| FailurePolicy | insufficientPowerBehavior, destroyedEffect | 정지·재시작·파괴 효과 구분 |

모두 **[제안]** 필드다. `base`와 `overclocked` 데이터를 다른 레코드 또는 명확한 모드 변형으로 보관한다. 출처가 바뀌면 정적 표의 숫자만 수정하지 말고, 해당 수치를 사용한 예제와 테스트 조건도 함께 갱신한다.

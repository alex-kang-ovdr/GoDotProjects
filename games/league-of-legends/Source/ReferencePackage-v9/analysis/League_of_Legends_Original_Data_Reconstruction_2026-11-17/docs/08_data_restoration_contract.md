# 08. 원작 데이터 복원 범위와 데이터 계약

**기준:** 2026-11-17 KST / PC LoL / 공식 패치 표기 26.22 / 정적 데이터 빌드 16.22.1. 이 문서의 테이블 설계와 검증 절차는 재구성 제안이다. Riot의 내부 테이블 구조를 확보한 것으로 해석하지 않는다.

## 1. 복원의 단위를 먼저 고정한다

원작을 재현하려면 공개된 이름과 수치를 수집하는 단계, 규칙을 명세하는 단계, 실제 판정을 구현하는 단계를 분리해야 한다. 이번 데이터팩은 첫 단계의 기계 데이터와 두 번째 단계의 근거·실행 계약을 제공한다. 전 챔피언의 내부 스크립트나 서버 원본 소스는 포함하지 않는다.

| 층 | 실제 산출물 | 완료로 판단할 조건 |
|---|---|---|
| 공개 데이터 관측 | `raw/`에 보존한 필드, 응답 해시, 출처 매니페스트 | 고정 URL·빌드·지역·언어·수집 시각을 추적할 수 있음 |
| 정규화 | `data/`의 CSV와 JSON | 식별자·부모 참조·랭크 배열·조합 그래프를 검증하고 원문 포인터로 되돌아갈 수 있음 |
| 패치 복원 | 공식 패치별 규칙 장부 | 도입·수정·삭제·충돌을 구별하며 최신 확인 시점을 명시 |
| 실행 설계 | 시스템별 MD·수용 시나리오 | 비용 소비, 취소, 대상 필터, 중복 보상을 결정할 규칙이 있음 |
| 원작 동작 일치 | 향후 클라이언트 관측·재현 실험 | 같은 조건에서 입력·중간 상태·결과가 일치함. 이번에는 수행하지 않음 |

`DataDragon에 필드가 있다`는 사실과 `그 필드만으로 게임이 실행된다`는 판단은 다르다. 특히 텍스트용 표시 사거리, 설명에서 계산되는 효과, 내부 대체 스킬, 아이템 고유 효과는 별도 검증 대상이다.

## 2. 버전과 식별자

### 2.1 버전 묶음

분석 단위는 다음 튜플로 고정한다.

```text
RulesetKey = (product=LoL_PC, patch_label, ddragon_build, region,
              map_id, queue_id_or_scope, mode_namespace, observed_at)
```

이번의 `26.22`와 `16.22.1`은 각각 패치 표기와 Data Dragon 빌드다. 문자열의 첫 숫자를 임의로 같게 바꾸지 않는다. `versions.json`의 가장 앞 값만으로 한국 서버의 실행 버전을 단정하지 않고, `realms/kr.json`의 데이터 항목도 확인한다. 공식 문서 역시 데이터 갱신 지연과 지역 차이를 설명한다.[D01][D02][D03]

직전 데이터 비교는 별도의 `16.21.1 → 16.22.1` 묶음이다. 정규화 필드 차이는 **정적 파일의 관측 차이**이며, 원작의 모든 변경이나 핫픽스가 그 차이에 들어 있다는 뜻이 아니다.

### 2.2 키 규칙

| 자료 | 권장 기본 키 | 피해야 하는 키 |
|---|---|---|
| 챔피언 | 빌드 + 모드 + 숫자 `key`; 문자열 `id`도 별도 보관 | 번역 이름·배열 순번 |
| 챔피언 스킬 | 챔피언 키 + Q/W/E/R 슬롯 + 공개 spell ID | 스킬의 번역 이름만 사용 |
| 패시브 | 챔피언 키 + 공개 패시브 식별 정보 | 패시브 이름이 다른 챔피언과 항상 유일하다고 가정 |
| 아이템 | 빌드 + 모드 + item ID | 가격·아이콘 파일명 |
| 룬 | 빌드 + path ID + slot + rune ID | UI의 현재 정렬 순서만 사용 |
| 주문 | 빌드 + 숫자 key + 문자열 ID | D/F 키 자체 |
| 큐·맵 상수 | 데이터 종류 + 공식 ID + 관측 스냅샷 | 같은 맵이면 같은 규칙이라고 합침 |

표준 챔피언과 Classic 등 모드 변형은 다른 namespace로 다룬다. 이번 전 챔피언 분모는 기본 `champion.json`이며, 모드 전용 변형을 함께 추출했다고 표시하지 않는다.[D01]

## 3. 값의 상태를 숫자와 함께 저장한다

실행용 명세를 만들 때 다음 상태를 사용한다. 이는 본 데이터팩에서 제안하는 검토 체계이며, 모든 원본 파일에 같은 문자열이 존재한다는 뜻은 아니다.

| 상태 | 의미 | 실행 데이터 반영 |
|---|---|---|
| `observed_static` | 고정 빌드 JSON에서 직접 관측 | 해당 필드의 의미 범위 안에서 사용 |
| `documented_at_patch` | 특정 패치 노트가 명시 | 이후 변경 확인 여부를 별도 표시 |
| `documented_current` | 현재 공식 지원 문서의 설명 | 지역·모드와 문서 내 충돌 확인 |
| `derived` | 명시한 입력과 식에서 계산 | 계산식과 단위, 입력의 출처를 유지 |
| `unresolved` | 필요한 의미·계수·규칙을 확보하지 못함 | 검토 필요. 0이나 기본값으로 자동 대체하지 않음 |
| `conflict` | 같은 범위의 근거가 충돌 | 후보를 보관하고 자동 승인하지 않음 |
| `custom` | 사용자 요구 또는 독립 프로토타입 설계 | 원작 규칙과 별도 ruleset에 저장 |

`null`, 빈 배열, 누락된 키, 숫자 0은 서로 다르다. 예를 들어 소모량 배열이 0이어도 체력 비용·충전 소비·조건부 비용이 따로 존재할 수 있다. `effect[1]`이 0이라고 피해가 0이라고 확정하지 않는다. 공개 데이터의 보조 변수나 다른 표현 계층을 함께 확인해야 한다.[D01]

## 4. 데이터 파일의 사용 목적

| 파일군 | 사용할 수 있는 정보 | 자동으로 얻을 수 없는 정보 |
|---|---|---|
| `champions`, `champion_stats` | 이름 연결, 기본 스탯·성장 입력, 태그 | 권장 포지션 확정, 모든 성장 예외·패시브 보정 |
| `champion_spells`, `spell_ranks` | 공개 QWER와 랭크별 쿨다운·비용·표시 사거리 | 시전 시간, 타격 반경, 모든 판정 단계, 변신 후 전체 스킬 |
| `spell_effect_arrays` | 원문 효과 인덱스와 수치 배열 | 인덱스가 피해·시간·회복 중 무엇인지의 무조건적 판정 |
| `spell_template_tokens` | 템플릿 변수의 해결 여부 | 누락된 계수나 내부 계산 함수의 생성 |
| `items`, `item_stats` | 가격·판매가·공개 정적 스탯·조건 필드 | 설명에만 있는 모든 고유 효과의 실행 |
| `item_recipes` | 공개 재료 관계 | 일반 구매 외 무료 변환·특수 업그레이드의 모든 절차 |
| `item_map_flags`, `items_sr_shop_candidates` | 맵 플래그와 구매 후보 필터 | 모든 챔피언·역할·상점 상황에서 실제 구매 가능하다는 보증 |
| `rune_paths`, `runes` | 룬 경로·슬롯·식별자 | 룬의 전체 수치, 발동 빈도 제한, 중첩 규칙 |
| `summoner_spells` | 공개 주문 목록·쿨다운·레벨·모드 표기 | 강화·퀘스트·아이템 적용 후 최종 쿨다운 |
| `official_*`, `ddragon_maps` | API의 맵·큐·모드 식별자 | 해당 큐가 지금 특정 지역에서 운영 중이라는 보증 |

실제 파일의 열 정의와 건수는 `data/data_dictionary.json`, `data/coverage_report.json`을 기준으로 한다. 문서의 예시 스키마와 추출 CSV의 실제 헤더를 혼동하지 않는다.

## 5. 아이템 그래프의 복원

조합은 `(완성품, 재료, 개수, 관계 종류)`의 그래프로 다룬다. 재료 ID가 반복될 수 있으므로 집합으로 바꾸어 수량을 잃지 않는다. `from`과 `into`의 역관계가 완전히 일치하지 않으면 보정값을 만들어 넣지 말고 검증 경고를 남긴다.

일반 구매의 검산 후보는 `총 가격 = 재료 총 가격 + 조합 비용`이다. 다만 무료 변환·특수 레시피·역할 또는 챔피언 전용 아이템은 일반 규칙의 예외가 될 수 있다. 이 등식의 불일치는 조사 신호이며 무조건 잘못된 원본이라는 결론이 아니다.

구매 시점의 권장 검증 순서는 **아이템 존재 → 적용 모드 → 소유자 조건 → 거래 위치 → 슬롯·유일 조건 → 재료 예약 → 부족 골드 → 원자적 반영**이다. 이 순서는 독립 구현 제안이며 원작 서버의 내부 호출 순서를 확인한 것이 아니다.

## 6. 텍스트와 수치의 결합

로케일은 표시 계층이다. 한국어 이름과 영어 식별자를 연결하되, 서로 다른 언어 파일에서 발견한 수치를 이유 없이 혼합하지 않는다. 양쪽 값이 다르면 수집 빌드와 원본 JSON 포인터를 비교하고 충돌로 남긴다.

공개 툴팁 변수는 일부 효과 배열 또는 계수 정보에 연결된다.[D01] 복원기는 해결 가능한 값만 연결한다. 의미가 남는 변수는 다음처럼 취급한다.

```json
{
  "field": "runtime.damage.formula",
  "value": null,
  "status": "unresolved",
  "reason": "public_static_data_does_not_define_complete_formula",
  "next_evidence": ["official_patch", "controlled_observation"]
}
```

이 JSON은 실행 모델 제안이다. `null`을 계산식에서 0으로 읽으면 오류를 숨기므로, 필수 값이 unresolved인 능력은 원작 일치 실행 대상으로 승인하지 않는다.

## 7. 수집·재생성·검증의 책임

1. 수집기는 고정된 공개 URL에서 응답을 읽고 응답 해시를 계산한다.
2. 보존본은 필요한 수치·식별자 중심의 projection이다. 긴 배경 이야기·툴팁 전문은 전달 테이블에서 제외한다. **응답 바이트의 해시와 projection 파일의 해시는 다를 수 있다.**
3. 정규화기는 보존본에서 CSV/JSON과 데이터 사전을 만든다. 원본의 숫자 정밀도를 무단으로 줄이지 않는다.
4. 검증기는 고유 키·부모 참조·필드 타입·허용 범위·배열 길이·소스 연결을 검사한다.
5. 검토자는 정규화의 성공과 실행 규칙의 완전성을 따로 승인한다.

`scripts/rebuild_data.py`의 기본 실행은 보존본으로 테이블을 재생성한다. `--download`는 고정된 공식 버전을 다시 수집한다. 재수집 날짜가 달라도 같은 버전의 파일이 수정될 수 있으므로 해시가 달라지면 변경을 기록해야 한다.

## 8. 후속 원작 관측이 필요한 영역

내부 시전 지연·입력 버퍼, 이동과 발사의 같은 틱 우선순위, 충돌체 반경, 투사체 소멸 예외, 감소 효과의 순서, 시야 상실 시 대상 처리, 전체 몬스터 리시·어그로 규칙, 비공개 MMR 계수는 정적 데이터만으로 완성할 수 없다. 해당 항목의 관측 조건과 수용 시나리오는 [검증 계획](11_qa_and_measurement_plan.md)에 연결한다.

단순히 빈칸이 적다는 이유로 더 좋은 복원본이 되는 것은 아니다. **같은 데이터로 같은 테이블을 만들고, 미확인 값이 실행 승인으로 넘어가지 않는 것**을 품질 기준으로 삼는다.

# 아르바이트 시스템
> 문서 성격: **역기획 분석 + 구현 명세 초안**. 원작의 정확한 내부 수치·우선순위·확률은 소스 검증 없이 확정할 수 없습니다. 아래 `확인 필요`는 원작 판본별 실측 대상이며 `제안`은 웹 프로토타입을 위한 독자적 설계입니다.

**분석 기준**: 1993년 원작 Princess Maker 2의 대표적인 육성 구조. 리파인/리제너레이션 및 지역판은 별도 검증 필요.

## 1. 목적과 책임
아르바이트 시스템은(는) 전체 육성 시뮬레이션의 독립 서브시스템이다. 입력 상태를 받아 규칙을 적용하고, 결과를 게임 상태와 로그에 반영한다. 원작 화면에서 관찰 가능한 행동과 내부 계산 추정치를 분리한다.

## 2. 주요 기능
### 2.1 직종과 해금 조건
- **플레이어 입력**: 직종과 해금 조건과 관련된 행동 선택 또는 자동 진행.
- **선행 조건**: 현재 연령·월·자금·능력치·이벤트 플래그에 의해 활성화 여부 결정.
- **상태 변화**: 직종과 해금 조건의 결과를 능력치, 자금, 관계, 평가, 상태 플래그 중 해당 항목에 적용.
- **표시/피드백**: 변경 전후 값, 비용/보상, 이벤트 문구 및 행동 로그 제공.
- **확인 필요**: 원작의 정확한 수치, 조건식, 예외, 우선순위, 판본별 차이.

### 2.2 수입 계산
- **플레이어 입력**: 수입 계산과 관련된 행동 선택 또는 자동 진행.
- **선행 조건**: 현재 연령·월·자금·능력치·이벤트 플래그에 의해 활성화 여부 결정.
- **상태 변화**: 수입 계산의 결과를 능력치, 자금, 관계, 평가, 상태 플래그 중 해당 항목에 적용.
- **표시/피드백**: 변경 전후 값, 비용/보상, 이벤트 문구 및 행동 로그 제공.
- **확인 필요**: 원작의 정확한 수치, 조건식, 예외, 우선순위, 판본별 차이.

### 2.3 직업별 능력 변화
- **플레이어 입력**: 직업별 능력 변화과 관련된 행동 선택 또는 자동 진행.

### 2.4 피로와 평판 리스크

- **선행 조건**: 현재 연령·월·자금·능력치·이벤트 플래그에 의해 활성화 여부 결정.

## 5. 경계 조건 및 테스트
- 자금이 0 미만이 되는 행동의 허용/거절 정책을 명시한다.
- 같은 날짜에 다수 이벤트가 발생할 때 결정적인 정렬을 보장한다.
- 저장 후 불러온 상태와 저장 전 상태의 행동 결과가 동일해야 한다.
- 능력치의 상한/하한과 미해금 행동의 처리를 검증한다.
- 월말/연말/18세 종료 경계에서 중복 실행을 방지한다.

## 8. 상세 역설계: 직업 해금과 임금

### 8.1 시스템 규칙 및 데이터 모델
아르바이트는 연령·능력치·이벤트 플래그에 따라 해금한다. 일당/슬롯 보수, 체력 소비, 스트레스, 도덕성 및 평가 변화는 직업별 데이터로 분리한다. 성공/실패/특수 사건의 가중치도 직업별로 둔다.

### 8.2 플레이어 경험과 처리 시퀀스
일 선택→자격 확인→작업 수행→임금 지급→평판/스트레스/능력치 변경

### 8.3 구현 시 고려사항
임금은 성공 일수×일당+보너스−벌금으로 계산하는 재구현 모델. 원작과 동일한 임금표라고 간주하지 않는다.

### 8.4 실패·예외 처리
- 요구 능력치·연령·재화가 부족하면 실행 전 차단하고 구체적 사유를 반환한다.
- 효과 적용 중 오류가 발생하면 트랜잭션 전체를 롤백한다.
- 이벤트 중 저장했다면 복원 후 선택지를 다시 제시하고 효과는 중복 적용하지 않는다.
- 정수 오버플로, 음수 자금, 중복 보상, 마지막 달 초과 진행을 검증한다.

### 8.5 테스트 시나리오
| ID | Given | When | Then |
|---|---|---|---|
| T01 | 정상적인 유효 상태 | 시스템 행동 실행 | 변경량과 로그가 정확히 일치 |
| T02 | 선행 조건 미충족 | 행동 요청 | 상태 불변 및 사유 반환 |

| T05 | 마지막 육성월 | 월 종료 | 엔딩 전이 한 번만 실행 |

### 8.6 원작 검증 프로토콜
1. 게임 판본, 플랫폼, 날짜, 행동 이전 수치와 난수 영향을 기록한다.
2. 한 번에 하나의 변수를 변경하여 전후 차이를 비교한다.
3. 최소 10회 반복 후 고정 효과와 확률 효과를 분리한다.
4. 확인된 규칙에 `VERIFIED`, 관찰 추정에 `INFERRED`, 구현 제안에 `PROPOSED` 태그를 붙인다.

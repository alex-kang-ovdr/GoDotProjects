# 37. 데이터 커버리지와 재현 구현의 완료 게이트

> **v4 추가 조사 안내:** 아래 본문과 개수는 해당 v2/v3 작성 당시의 범위를 설명한다. 현재 통합 자료, 추가 복원, 레벨 미기재 값의 처리와 실행 명령은 [39번 개요](39_research_reconstruction_v4_overview.md), [44번 근거 조정](44_sources_and_level_reconciliation.md), [최신 검증 보고서](reports/validation_report.md)를 기준으로 한다.

> v3 연구 도구 · 분석 기준일 2026-11-17 · 원작 클라이언트 관측 미실행
>
> 이 문서는 **자료를 얼마나 연결할 수 있는가**, **어떤 판단이 아직 막혀 있는가**, **다음 구현을 언제 완료로 볼 수 있는가**를 다룬다. 카드 수나 레코드 수를 재현율로 바꾸지 않는다. 수치는 제공된 원표에 대한 정적 분석 결과다.

## 1. 이번 고도화의 목적

v2의 공개 자료 복원에는 역사 카탈로그, 개체 정의, 개체 간 참조, 레벨별 배열, 최근 공식 패치의 일부 필드, 경제·모드 규칙, 자체 구현 대조가 함께 들어 있다. 모두 유용하지만 같은 종류의 완성도를 나타내지는 않는다. 예를 들어 기사 이름과 과거 HP 배열을 읽을 수 있다는 사실은 현재 기사 전체 프로필을 확보했다는 뜻이 아니다. 화염구의 최근 크라운 피해가 확인되어도 과거 데이터의 카드 루트 연결 누락이 사라지는 것은 아니다.

새 분석기는 이 차이를 카드별로 드러내고, 필요한 근거와 구현 조건을 후속 작업에 연결한다. 분석 결과를 정해진 파일로 재생성하므로 문서에 적힌 수치와 인터랙티브 화면이 별도로 집계되어 어긋나는 일을 줄인다. 분석기는 원표를 수정하지 않으며 네트워크에 접속하지 않는다.

원본 범위는 [16종 데이터표](data/dataset_manifest.json), 계보는 [재구축 개요](23_data_reconstruction_overview.md), 적용 한계는 [구현 차이](31_implementation_gap_matrix.md)와 [원작 관측 계획](33_observation_protocol_and_reconstruction_backlog.md)에 설명되어 있다.

## 2. 산출물과 데이터 계약

## 3. 커버리지의 분모를 고정하지 않는 이유

현재 합집합에는 **128개 카드 키**가 있다. 역사 공개 카탈로그 120개, 그 카탈로그에 없고 포함한 2026 패치에만 등장하는 키 6개, 독자 카드 2개가 합쳐진 결과다. 패치에 등장하는 카드 키 자체는 40개이며 이들에 대해 최종 필드 조회 60행이 있다. 이 값은 [자동 요약](data/analysis/quality_summary.json)의 계산 결과다.

이 집합에는 역사 이벤트·숨김 카드, 새로 발표된 형상과 관련된 부분 수치, 자체 프로토타입 카드가 함께 있다. 따라서 현재 원작의 카드 수나 정규 카드풀로 사용하면 안 된다. 또한 `damage` 하나를 확보한 카드와 소환·타겟팅·사망 효과까지 완성한 카드는 구현에 필요한 작업량이 다르다. 둘을 같은 한 장으로 계산해 복원율을 내면 중요한 차이가 지워진다.

분석기는 `reconstruction_percentage=null`을 반환한다. 이유는 아직 현재 전체 대상과 필요한 동작 범위를 확정하지 않았기 때문이다. 실제 진척을 관리하려면 프로젝트가 지원할 모드·카드·레벨·형상을 먼저 명시한 재현 프로필을 만들고, 그 프로필의 필수 필드와 상호작용을 분모로 삼아야 한다. 그때도 데이터 완성, 계약 테스트, 원작 관측 일치, 브라우저 검증을 각각 구분하는 편이 정확하다.

## 4. 카드별 커버리지를 읽는 방법

각 카드의 `archive`는 2023-10-18 공개 스냅샷에 대해서만 말한다. `latest_patch`는 제공된 패치 원장 안에서 가장 나중에 기록된 필드만 열거한다. `implementation`은 Crownfall v4.4.0의 독립 구현과 역할 참조를 연결한다. 세 객체의 수치를 합쳐 한 개의 실행 카드로 만드는 기능은 제공하지 않는다.

### 4.1 과거 연결

`archive.present`는 그 키가 역사 카탈로그에 있다는 뜻이다. `root_entity_ids`는 동일한 공개 `key`로 연결된 개체만 담는다. `reachable_entity_ids`는 이 루트에서 명시적 참조를 따라간 결과다. 이름이 비슷한 개체나 설명에 등장하는 개체를 유추해서 추가하지 않는다.

한 카드에 여러 exact-key 루트가 있을 수 있다. 카드 정의와 실제 병력 정의가 동시에 연결된 경우가 이에 해당한다. 이것은 `resolution=ambiguous`인 간선과 다른 상황이다. 전자는 모두 출발점으로 사용하고, 후자는 어느 후보가 정답인지 확인되지 않았으므로 탐색을 멈춘다.

현재 역사 카탈로그에는 정확한 공개 key로 연결되지 않는 카드가 10개 있다. 연결된 개체 사이의 428개 명시적 참조가 모두 resolved 상태라고 해도 이 10개 루트 누락이 해결되었다는 뜻은 아니다. 이름 없는 개체 6개도 별도로 격리되어 있다. [품질 보고서](reports/quality_report.md)는 이 세 상태를 따로 집계한다.

### 4.2 최근 부분 필드

패치 필드의 식별자는 다음 조합이다.

```text
card_key + form + component + key + reference_level
```

예를 들어 같은 카드의 기본형 피해, 진화형 보호막, 능력 지속시간을 한 필드로 덮어쓰면 안 된다. `fields`에는 각 조합과 원표 `record_id`, 이전 패치 원장을 가리키는 `lineage_patch_id`가 보존된다. 실제 수치와 근거는 해당 원표 행에서 읽는다.

`full_current_profile=false`는 현재 분석 범위에서 의도적으로 고정한 계약이다. 포함한 패치에서 변경되지 않은 HP·사거리·공격 간격을 과거 배열로 채우지 않는다. 원표가 부분 패치를 완전 프로필이라고 선언하거나 확인 범위를 임의로 넓히면 분석기가 오류를 발생시킨다. 새 데이터 체계를 만들 때는 이 계약과 스키마를 명시적으로 변경해야 한다.

### 4.3 자체 구현

`implementation.present=true`는 Crownfall에 대응하는 구현 카드가 있다는 뜻이다. 이 객체의 `custom_only=true`는 역할을 원작에서 참고하는 카드에도 적용된다. 수치·피해 단위·AI·모드 조건이 원작과 같다는 주장은 하지 않는다.

밀집보병과 강철 검사는 `independent_card=true`, 원작 카드 ID는 null이다. 독자 카드에 원작 ID를 주입하거나 향후 원작 키와 충돌하는 데이터를 넣으면 분석기가 중단된다. 원작 복원 작업이 사용자가 요청한 방진·돌격 동작을 자동으로 바꾸는 경로를 만들지 않는다. 해당 카드의 자체 계약은 [31번 문서](31_implementation_gap_matrix.md)에 설명되어 있다.

### 대표적인 읽기 예

| 키 | 관찰할 상태 | 올바른 판단 |
|---|---|---|
| `knight` | 과거 루트·개체가 있고, 제공된 최종 패치 필드는 없음 | 역사 자료를 조회할 수 있다. 현재 HP를 확인한 것은 아니다. |
| `fireball` | 역사 exact-key 루트는 누락, 부분 패치 필드는 있음 | 새 크라운 피해의 근거와 역사 연결 문제는 독립적이다. |
| `minion-giant` | 과거 카탈로그에 없고 부분 패치에 등장 | 새로운 카드 키에 관한 부분 자료다. 과거 ID를 만들어 넣지 않는다. |
| `super-lava-hound` | 여러 단계 뒤 Lava Pup 투사체까지 연결 | 연결 깊이를 3단계로 자르면 실제 참조 일부가 누락된다. |
| `phalanx` | 독자 구현만 존재, 원작 ID null | 사용자의 자체 카드로 유지하고 원작 통계에 포함하지 않는다. |

## 5. 그래프 탐색의 처리 규칙

카드에서 병력, 투사체, 사망 후 개체, 그 개체의 투사체로 연결되는 관계는 한두 번의 조인으로 끝나지 않을 수 있다. 분석기는 큐와 방문 집합을 사용하는 전체 탐색을 수행한다. 깊이 제한을 두지 않으며 순환 참조가 생겨도 같은 개체를 재방문하지 않는다.

탐색 가능한 간선은 `resolution=resolved`이고 대상이 정확히 하나인 경우다. 누락·모호 참조는 `blocked_links`에 남긴다. 참조 ID가 실제 정의에 없으면 `missing_entity_ids`로 기록한다. 격리된 정의는 실행 가능한 개체로 취급하지 않는다. 이 동작은 원작의 이동 경로 탐색 알고리즘이 아니라 공개 데이터의 참조 관계를 읽는 알고리즘이다.

방문한 개체 수는 전장에 생성될 병력 수와 다르다. 하나의 병력이 여러 투사체·효과 정의를 참조할 수 있고, 카드가 모든 참조를 매번 사용하지 않을 수 있기 때문이다. 해당 수치를 소환 수나 예상 피해 사건 수로 사용할 수 없다.

## 6. null·0·미기재 날짜를 구별하는 규칙

결측 분석은 단순히 null을 세는 것만으로 끝나지 않는다. 다음은 같은 JSON 표현이 서로 다른 의미를 갖는 사례다.

| 표현 | 문맥 | 해석 |
|---|---|---|
| `value=null`, `evidence_status=unverified` | 엘릭서 기본 생성 간격 | 이 자료에서 아직 확인하지 못한 값 |
| `unit=null` | 상태 이름·조건 규칙·시나리오 | 숫자 단위가 적용되지 않을 수 있음 |
| `card_cap=null`, `kind=owned_uncapped` | 모드 레벨 정책 | 모드가 별도의 상한을 적용하지 않는 정책값 |
| 해금 행의 `gold=null` | 최초 획득 레시피 | 해당 열의 비적용 표시와 원문 설명을 함께 읽음 |
| Epic 목표 7의 `gold=null` | 업그레이드 레시피 | 명시적 비용을 확보하기 전에는 총비용 완성 불가 |
| `damage=0` | 투사체를 사용하는 역사 개체 | 그대로 보존해야 하는 원시 값 |
| `attacks_air=false` | 대상 마스크 | 확인된 거짓이며 결측이 아님 |

분석기는 최상위 value null, value 안의 중첩 null, unit null, unverified 근거를 따로 집계한다. 이 개수들을 합쳐 미복원 필드 수라고 표시하지 않는다. 특히 역사 개체의 nullable 참조 필드가 많다는 이유만으로 모든 카드가 같은 정도로 미완성이라고 판단하지 않는다.

`effective_from=null`은 적용 시작을 확정하지 않았다는 뜻이다. `effective_to=null`은 종료일을 알지 못하거나 기재하지 않았다는 뜻이며 무기한 유효 판정이 아니다. 자료의 조회일, 공지일, 저장소 스냅샷 날짜와 실제 게임 적용일을 대체해 사용할 수 없다. 시점 해석의 기존 규칙은 [30번 문서](30_patch_history_and_version_boundaries.md)와 연결된다.

## 7. 출처 감사가 확인하는 것

출처 레지스트리에는 71개 ID와 서로 다른 URL 64개가 있다. 같은 공식 페이지를 전투 문서와 경제 문서가 각각 참조할 수 있으므로 source_id와 웹페이지 수는 다르다. `same_url_source_ids`는 이 관계를 보여준다.

URL 정규화는 HTTP(S)의 스킴·호스트 대소문자, 기본 포트, fragment만 다룬다. 경로 철자, 마지막 슬래시, 쿼리 순서는 보존한다. 다른 글을 같은 출처로 묶을 수 있는 공격적인 주소 정리는 하지 않는다. 로컬 구현 참조는 `local:` 내부 식별자로 구별하며 웹 주소처럼 검사하지 않는다.

`referenced_record_count`는 원표의 직접 참조 수다. 한 레벨 배열이 여러 행으로 정규화되면 출처 하나가 수천 행에서 참조될 수 있다. 이 값은 근거의 독립성이나 권위 점수가 아니다. 직접 원표 참조가 없는 배경 자료도 있을 수 있으며, 자동 삭제 대상으로 판단하지 않는다.

모든 출처의 `link_check_status`는 이번 분석에서 `not_checked`다. 분석기는 인터넷 접근, 인증 상태, 문서 변경, 링크 생존 여부를 검사하지 않았다. URL이 등록되어 있다는 사실을 현재 접근 성공으로 표시하거나, 공지에 나온 숫자를 실제 원작 클라이언트에서 측정했다고 바꾸지 않는다.

## 8. 후속 구현의 완료 게이트

후속 작업에는 과제 ID, 우선순위, 현재 상태, 선행 과제, 원표 근거, 구체적 완료 기준이 있다. 우선순위는 이 재현 프로젝트를 위한 제안이다. 원작 개발사의 일정이나 내부 개발 비용을 나타내지 않는다.

| 단계 | 통과 조건 | 통과 전 허용하는 작업 |
|---|---|---|
| 자료 경계 | 역사·부분 패치·자체 데이터의 출처와 네임스페이스가 구별됨 | 자료 탐색, 비교, 가정이 표시된 계산 |
| 필드 완성 | 지원할 카드·레벨·형상의 필수 수치와 단위가 같은 빌드로 확보됨 | 빠진 필드를 보여주는 연구용 프로필 |
| 동작 계약 | 타겟·피해·시간·사망·승패 경계에 입력과 기대 결과가 정의됨 | 명시적 가정에 따른 참조 코드 실행 |
| 원작 관측 | 같은 조건의 실제 관측과 오차가 기록되고 모순이 처리됨 | 미실행 명세와 관측 계획 유지 |
| 엔진 통합 | 프로필 누락 차단·중복 명령·리플레이·저장 호환이 검증됨 | 별도 테스트 프로필에서 제한적 실행 |
| 화면 검증 | 실제 브라우저·기기에서 조작·표시·성능·접근성 확인 | 코드 정적 검사와 순수 로직 테스트 |

현재 원표의 44개 상호작용은 모두 `observed=false`, `test_status=not_run`이다. 참조 JavaScript 함수의 단위 검사가 통과해도 이 값을 바꾸지 않는다. 가정한 방패 정책을 코드가 정확히 계산했다는 사실과 원작이 그 정책을 사용한다는 사실은 서로 다른 주장이다.

backlog의 16개 과제는 위 게이트를 구체화한다. `requires_original_client=true`인 과제는 현재 원작 관측 증거가 없다는 이유를 `blocked_reason`에 기록한다. 자료 기반으로 진행할 수 있는 입력 검증, 관측 원장 설계, 조건부 확률 계산, 가져오기 계약은 별도로 계속 작업할 수 있다.

특히 G01의 데이터 분리는 한 번 통과하면 끝나는 상태가 아니라 유지해야 하는 불변식이다. G03에서 현재 카드 프로필을 확보하고 G04에서 좌표를 교정한 다음 G09에서 엔진 가져오기 게이트를 적용하는 순서로 선행관계를 둔다. 의존 그래프의 순환과 없는 과제 참조는 테스트에서 검출한다.

## 9. 재생성과 검증

Python 표준 라이브러리만 사용한다. 프로젝트 루트에서 실행한다.

```bash
python scripts/analyze_quality.py
python scripts/analyze_quality.py --check
python -m unittest discover -s tests -p 'test_quality.py'
```

첫 명령은 분석 JSON 4개와 품질 보고서를 생성한다. `--check`는 현재 원표로 다시 계산한 결과가 저장된 분석 파일과 바이트 단위로 같은지 확인한다. 생성 시각을 매번 기록하지 않으므로 원표가 같으면 같은 출력이 나온다. 조사 기준일은 데이터 설정의 `AS_OF`를 사용한다.

테스트는 실제 위험이 있는 관계를 검증한다. 현재 기사 값에 과거 HP가 섞이지 않는지, 화염구를 유사한 이름의 정의에 임의 연결하지 않는지, 긴 사망 소환 체인의 투사체까지 도달하는지, 순환 그래프가 종료되는지, 모호 참조에서 탐색이 멈추는지, 자체 카드에 원작 ID가 주입되면 거부되는지, 출처 집계와 후속 과제 근거가 일치하는지를 확인한다.

이 검사는 원작의 비공개 데이터, 실제 네트워크 프로토콜, 현재 모든 카드의 정확한 수치, 숨은 매칭 규칙을 증명하지 않는다. 현재 파일에서 계산할 수 있는 사실과 다음 근거 확보가 필요한 영역을 명확히 연결하는 것이 이 분석기의 완료 범위다.

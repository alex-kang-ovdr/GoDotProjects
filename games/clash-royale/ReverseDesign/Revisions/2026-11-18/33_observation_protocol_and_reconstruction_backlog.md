# 33. 원작 관측 프로토콜과 후속 복원 작업

> **v4 추가 조사 안내:** 아래 본문과 개수는 해당 v2/v3 작성 당시의 범위를 설명한다. 현재 통합 자료, 추가 복원, 레벨 미기재 값의 처리와 실행 명령은 [39번 개요](39_research_reconstruction_v4_overview.md), [44번 근거 조정](44_sources_and_level_reconciliation.md), [최신 검증 보고서](reports/validation_report.md)를 기준으로 한다.

> 상태: 실험 설계 완료, 원작 직접 실험은 미실행. 이 문서는 공개 자료로 해결되지 않은 부분을 정확한 관측으로 좁히는 작업 계획이다.

## 1. 무엇을 더 확인해야 하는가

공식 규칙을 더 많이 읽는 것만으로 해결되지 않는 질문이 있다. 타겟 동률 처리, 보호막 초과 피해의 정확한 순서, 동일 프레임의 타워 파괴, 특수 레벨 증가와 모드 상한, 이동 중 충돌 같은 문제는 조건을 고정한 실제 관측이 필요하다.

역기획의 목표는 그럴듯한 내부 알고리즘을 만드는 것이 아니라, 어떤 입력에서 어떤 결과가 발생하는지 검증 가능한 계약을 만드는 것이다. 내부 소스가 없어도 특정 상호작용을 충분히 재현할 수 있지만, 같은 결과를 내는 여러 구현 가운데 원작이 어느 구현을 사용했는지는 별개의 질문이다.

## 2. 관측 기록의 최소 항목

| 항목 | 기록 내용 | 필요한 이유 |
|---|---|---|
| client_context | 버전·플랫폼·언어·실험 날짜 | 업데이트 전후 분리 |
| account_context | 해금 아레나·관련 레벨·형상 소유 | 사용 가능 기능과 보정 조건 |
| mode_context | 모드·시즌·레벨 정책·특수 배수 | 서로 다른 규칙의 비교 방지 |
| card_context | 카드·형상·레벨·타워 유닛·덱 | 공격자와 방어자의 정확한 조건 |
| initial_state | 타워 HP·활성화·현재 유닛·엘릭서 | 시작 상태 고정 |
| input_sequence | 배치 순서·좌표·시각·능력 입력 | 재실행 가능성 |
| observation | 화면 프레임·HP·타겟·상태 변화 | 예상과 실제의 분리 |
| uncertainty | 시간·좌표·HP 표시의 오차 | 측정 한계 명시 |
| result | 지지·반박·불충분·재현실패 | 단일실험으로 일반화 방지 |

계정 식별자나 개인 대화는 필요하지 않다. 동일 조건을 구별할 수 있는 익명 실험 ID로 충분하다. 화면 녹화는 타이머·카드 레벨·HP·배치 위치를 확인할 수 있는 범위가 중요하다.

## 3. 수치 계측 절차

### 3.1 HP와 단일 피해

공격자와 방어자의 레벨을 고정하고, 버프·보호막·중첩 피해·타워 지원이 없는 조건을 먼저 만든다. 피해 전후 HP 차이와 타격 횟수를 기록한다. 여러 개체가 동시에 공격했다면 총 피해를 한 개체 피해로 나누기 전에 실제 적중 수가 같았는지 확인한다.

보호막·관통·다중 파동은 별도 케이스로 만든다. 공격 한 번이 여러 피해 사건으로 이루어질 수 있으므로 애니메이션 한 번과 피해 한 번을 동일하게 세지 않는다. 주문의 본체 피해와 크라운 타워 피해도 각각 관측한다.

### 3.2 첫 타격과 반복 공격

배치 입력, 실제 개체 등장, 이동 시작, 사거리 진입, 공격 준비, 타격 또는 투사체 발사, 피해 적용 시점을 구분한다. 첫 피해까지의 시간을 그대로 공격 간격으로 저장하지 않는다. 첫 타격 이후 여러 주기의 차이를 측정하고 프레임 해상도에 따른 구간을 남긴다.

표시상0.1초 단위가 보인다고 내부 tick이0.1초라고 단정하지 않는다. 화면 출력 주기와 시뮬레이션 주기는 다를 수 있다. 네트워크 지연이 섞인 입력 시각은 클라이언트에서 보이는 배치 확정 시각과 구분한다.

### 3.3 거리와 배치

배치 타일 중심·타워 중심·실제 충돌 가장자리를 별도로 정의한다. 같은 겉보기 거리에서도 유닛 반경 때문에 공격 판정이 달라질 수 있다. 좌우·상하 반전, 강·다리, 큰 유닛과 작은 유닛, 군집 가운데와 가장자리 조건을 각각 테스트한다.

한 픽셀 차이로 결과가 달라지면 유효 배치점의 자동 보정 여부를 먼저 확인한다. 화면 회전이나3D 카메라 투영이 바뀌어도 논리 좌표가 같은지 기록해야 한다.

## 5. 44개 상호작용 명세의 활용

[interaction_cases.json](data/tables/interaction_cases.json)은 각 케이스의 조건·입력·예상·측정 항목·우선순위를 갖는다. 공식 문서가 예상 결과를 알려주는 경우와 결과 자체를 아직 모르는 경우가 모두 있다. 예상이null인 케이스는 실험을 통해 값을 얻는 탐색 과제다.

실행 기록을 추가할 때 원래 명세를 지우지 않고 별도의 `observation_id`로 저장한다. 한 명세에 여러 관측이 연결될 수 있어야 한다. 원작 관측과 Crownfall 재현 테스트도 다른 실행기 ID를 사용한다.

권장 결과 분류는 다음과 같다.

- `supported`: 기록한 조건에서 예상과 일치.
- `contradicted`: 명확한 조건에서 예상과 불일치.
- `inconclusive`: 효과 중첩·레벨·시각 등의 통제가 부족.
- `not_reproduced`: 실험의 초기 상황을 만들지 못함.

한 번의 supported는 모든 레벨·모드에서의 검증 완료가 아니다. 효과가 피해 임계에 의존하면 위·아래 레벨이나 HP 경계를 추가 관측한다. 반대로 결과에 영향을 주지 않는 조건을 무한히 반복해 숫자만 늘리지 않는다.

## 6. 관측 결과를 데이터에 반영하는 방법

관측으로 얻은 값을 `official_confirmed`로 올리지 않는다. 관측 출처 유형과 실험 ID를 추가하고, 확인한 빌드·레벨·반복 횟수·오차를 보존한다. 필요하면 공통 스키마의 근거 분류를 버전 올려 확장한다. 기존 출처의 주장과 관측이 다르면 둘 중 하나를 조용히 삭제하지 않는다.

고정 수치가 아닌 규칙을 확인했을 때는 결과를 조건식으로 저장한다. 예를 들어 ‘이 상황에서 피해가 없었다’는 관측을 ‘항상 면역’으로 일반화하지 않고, 대시 상태·상대 효과·타격 시점·레벨·모드를 함께 기록한다.

## 7. 재현 완료 판단

한 카드를 재현 완료로 표시하려면 해당 프로필의 필요한 수치가 모두 정의되어야 하고, 배치·이동·공격·사망·상태 예외의 대표 상호작용이 관측 결과와 맞아야 한다. 단순히 이름과 일러스트가 같거나 HP·피해 두 숫자가 같다는 이유로 완료 처리하지 않는다.

한 시스템의 완료는 더 넓은 조건을 필요로 한다. 예를 들어 성장 시스템은 단일 업그레이드 성공뿐 아니라 재화 부족, 중복 요청, 레벨 상한, 보상 변환, 미수령 보상 재접속 같은 경계를 포함한다. 이번 [26번](26_progression_economy_reconstruction.md)과 [27번](27_modes_matchmaking_social_contracts.md)의 거래·정산 계약을 실험 범위와 연결한다.

## 8. 현재 완료 상태

완료된 범위는 공개 자료 분석, 버전별 수치 재구축, 출처·결측·충돌 정리, 데이터 검증 도구, 실험 명세다. 전체 현재 원작 카드의 완전한 레벨별 수치, 숨은 매칭 알고리즘, 비공개 서버 구조, 실제44개 상호작용 실험은 미완료 범위로 남긴다. 이 경계를 유지하면 후속 작업에서 확보한 근거만큼 정확도를 단계적으로 높일 수 있다.

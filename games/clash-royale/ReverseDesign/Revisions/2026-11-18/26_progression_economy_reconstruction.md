# 26. 성장·경제·보상 데이터 재구축과 계산 계약

> **v4 추가 조사 안내:** 아래 본문과 개수는 해당 v2/v3 작성 당시의 범위를 설명한다. 현재 통합 자료, 추가 복원, 레벨 미기재 값의 처리와 실행 명령은 [39번 개요](39_research_reconstruction_v4_overview.md), [44번 근거 조정](44_sources_and_level_reconciliation.md), [최신 검증 보고서](reports/validation_report.md)를 기준으로 한다.

> 재조사 기준일: **2026-11-17**. 원작의 공개 지원 문서와 공식 공지를 재확인하고, 표를 JSON 레코드로 정규화했다. 실게임 계정에 접속해 재화를 소비하거나 내부 테이블을 추출한 결과가 아니다. 공개 표의 값, 계산으로 얻은 값, 구현 제안, 미확정값을 구분한다.

## 1. 이번 보강으로 추가된 것

기존 문서는 성장 구조와 주요 대표값을 설명했다. 이번에는 구현자가 실제로 조회할 수 있도록 다음 세 파일을 만들었다. 각 행은 출처·시점·적용 조건을 가진다. 현재 웹게임의 자체 밸런스나 밀집 보병 성장값으로 덮어쓰는 자료가 아니다.

| 파일 | 데이터 | 핵심 조회 키 |
|---|---|---|
| [progression_rules.json](data/tables/progression_rules.json) | 희귀도별 기본 레벨, 해금/업그레이드 비용, 킹 타워 조건, 컬렉션과 마스터리 | `system`, `key`, `value.rarity`, `value.target_level` |
| [economy_rules.json](data/tables/economy_rules.json) | 재화 한도·변환, 일일 보상·패스, 상자 수량, Crown Series 보상, 파생 계산 | `system`, `key`, `value.family`, `value.chest_level` |
| [reward_probability_tables.json](data/tables/reward_probability_tables.json) | 출발 등급→최종 등급, 최종 등급→종류의 조건부 확률, 이벤트 한정 표 | `probability_group`, `conditional_on` |
| [economy_sources.json](data/sources/economy_sources.json) | 원문 URL·발행일·열람일·근거 범위·결측 주의점 | `source_id` |

데이터를 읽을 때 먼저 `version_note`를 선택해야 한다. 2025년 경제 전환 공지의 **New** 표를 복원한 비용, 2026년 지원 문서의 성장 조건, 날짜가 없는 상자 확률 허브의 열람 스냅샷은 같은 의미의 버전이 아니다. 이 차이를 지우고 “2026년 전체 원본 데이터”라고 부르면 이후 수정 여부를 추적할 수 없다.

## 2. 복구의 범위와 원본의 의미

### 2.1 복구한 공개 사실

공식 문서의 숫자 표를 읽어 필요한 열만 정규화했다. 원문의 광고 문구·삽화·전체 문장을 데이터에 복제하지 않았다. `source_id`로 원문으로 돌아갈 수 있고, 일부 직접 받은 공개 HTML의 SHA-256을 출처 메타데이터에 남겨 어느 내용을 읽었는지 식별한다. HTML 전체는 산출물에 포함하지 않는다.

이 방식으로 복원되는 것은 **공개한 설계 수치와 계약**이다. 클라이언트의 원래 CSV 열 이름, 실제 서버 지급 순서, RNG 구현, DB 스키마까지 복원되는 것은 아니다. 다음 범위는 별도로 남긴다.

| 구분 | 처리 |
|---|---|
| 공지 표에 숫자가 있음 | 숫자와 조건을 그대로 기록 |
| 숫자 표의 빈칸 | `null`, 빈칸의 의미가 확인되면 별도 설명 |
| 공식 문구의 변환 계산 | `derived`, 사용한 수식·출처 기록 |
| 적용일 미표기 지원 페이지 | `effective_from: null`, 열람일과 버전 메모 기록 |
| 알려지지 않은 지급 순서 | 재현 설계로 제안, 원작 규칙으로 확정하지 않음 |
| 이전 공지와 현행 지원의 충돌 | 두 출처의 범위와 우선 적용 이유를 기록 |

**데이터의 빈칸을 0으로 채우는 것은 복원이 아니다.** “이 보상을 지급하지 않음”, “해금 단계라 업그레이드 비용이 적용되지 않음”, “표가 누락됨”은 서로 다른 상태다. 필요한 경우 `field_evidence`처럼 행 안에서도 근거 상태를 나눈다.

## 3. 카드 업그레이드: 획득과 강화 비용을 분리

### 3.1 희귀도와 레벨 범위

공식 새 비용표의 첫 복제본 행으로 확인되는 시작 레벨은 일반 1, 희귀 3, 영웅 6, 전설 9, 챔피언 11이다. 그 행의 복제본 1은 최초 획득이며, 이전 레벨에서 강화하는 비용이 아니다. 따라서 해금 행에는 `transaction_kind: unlock`, `from_level: null`을 사용했다. 그다음부터 `target_level - 1 → target_level` 거래다. [비용표 원문](https://supercell.com/en/games/clashroyale/blog/news/coming-in-the-next-update/)

예를 들어 전설 레벨 9를 해금하기 위해 “레벨 8 전설 카드”가 필요하다고 검증해서는 안 된다. 이 검증 오류는 레벨 스키마에 희귀도별 하한이 없을 때 발생한다. 전투의 임시 레벨 변경과 계정의 영구 성장 경로도 별도 계약으로 둔다.

### 3.2 비용을 조회하는 순서

재현 구현에서는 다음 순서로 비용을 조회한다.

1. 카드 ID가 소유 데이터의 기본 카드와 연결되는지 검사한다.
2. 영구 레벨과 희귀도를 읽는다. 부스트·모드 상한을 비용 기준으로 쓰지 않는다.
3. 대상 경제 버전에서 `(rarity, target_level)` 레코드를 찾는다.
4. 필수 값의 근거 상태를 확인한다. 골드 미확정 행이면 결제를 실행할 수 없도록 한다.
5. 복제본·사용할 와일드·골드의 부족분을 독립 계산한다.
6. 사용자 선택과 거래 ID를 확인한 뒤 자원 차감과 레벨 상승을 함께 확정한다.

이 순서는 **재현 설계**다. 원작의 서버 호출 순서를 공개 자료에서 알아냈다는 뜻이 아니다.

```text
cardsMissing = max(0, requiredCopies - ownedCopies - selectedWildCards)
goldMissing  = max(0, requiredGold - ownedGold)
canUpgrade   = recipeKnown AND cardsMissing == 0 AND goldMissing == 0
```

`max(0, ...)`를 적용하기 전에 `requiredGold`가 숫자인지 검사해야 한다. `null`을 언어의 암묵적 변환으로 0처럼 다루면 자료 누락이 무료 강화로 바뀐다. Gems 구매가 필요한 상황도 부족분 계산 결과일 뿐, Gems를 자동 소비할 권한이 생기는 것은 아니다.

### 3.3 발견한 빈칸

새 골드 표의 **영웅 목표 레벨 7** 칸은 비어 있다. 같은 페이지의 옛 표에는 400이 있지만, 그 값을 새 표에 복사할 근거가 되지는 않는다. 복구한 레시피에는 `gold: null`, `field_evidence.gold: unverified`를 넣었다. 과거값 400과 현재 누락을 같은 행의 확정값으로 합치지 않았다. [해당 원문 표](https://supercell.com/en/games/clashroyale/blog/news/coming-in-the-next-update/)

### 3.4 계산 사례와 실제 완주 시간

**[계산]** 이 발표 스냅샷의 레벨 11→16 비용을 더하면 골드는 희귀도 공통 335,000이다. 복제본 합은 일반 20,500, 희귀 4,100, 영웅 530, 전설 61, 챔피언 41이다. 최초 해금 비용이나 이미 보유한 카드는 제외한 계산이다. 이 합을 “현재 계정에서 반드시 그만큼 새로 얻어야 한다”는 요구량으로 표시하면 안 된다.

현 계정의 순수 부족분에는 현재 복제본, 배분 가능한 와일드, 이미 모은 골드, 다른 카드에 쓸 예정인 자원을 적용해야 한다. 카드별 평균 일일 유효 획득량도 전체 카드 획득량과 다르다. 같은 희귀도 100장을 받더라도 목표 카드에 사용할 수 있는 수량은 별도 분포다.

## 4. 계정 성장: 컬렉션과 킹 타워의 다른 목적

### 4.1 컬렉션은 합산, 킹 타워는 조건

컬렉션은 보유 카드 레벨과 해금 형태가 기여하는 합산 값이다. 타워 유닛은 포함하지만 Merge Tactics Rulers는 포함하지 않는다. 반면 킹 타워 조건의 카드 수에서는 타워 유닛과 Rulers를 제외한다. 두 시스템에서 같은 `allOwnedCards` 배열을 그대로 합산하면 오작동한다. [Collection Level](https://support.clashroyale.com/hc/en-us/articles/50815299122459-Collection-Level), [King Tower Level](https://support.clashroyale.com/hc/en-us/articles/50815997602715-King-Tower-Level)

```text
collection = sum(permanentLevels of eligible owned cards)
           + 5 * ownedEvolutionCount
           + 5 * ownedHeroCount

kingCandidate = highest target whose eligible-card count meets its rule
```

`permanentLevels` 및 영구 소유 상태를 사용하는 것은 재현 구현의 상태 정의다. 임시 전투 부스트가 계정 보상 획득→만료→재획득으로 연결되지 않게 한다. 마이그레이션에서는 기존 킹 타워 보존 상태가 추가되므로, 새 조건만 재계산해 기존 레벨을 내리면 안 된다.

### 4.2 데이터 기반 검증

킹 타워 조건은 2~16의 15개 목표 행으로 복구했다. `minimum_card_level`은 정확히 같은 레벨이 아니라 **이상** 조건이다. 레벨 15 카드가 레벨 13 조건에도 기여한다. 같은 카드의 진화와 히어로를 카드 수에 추가로 세지 않는다. 킹 타워 조건을 여러 개 한꺼번에 충족한 보상 묶음에서는 가장 높은 충족 레벨까지 일관되게 갱신해야 한다.

권장 검증 입력은 조건보다 한 장 적음, 정확히 충족, 한 장 많음, 타워 유닛만 추가, 기본 카드에 형태만 추가, 기존 레벨이 새 계산보다 높음이다. 이는 테스트 설계이며 원작 클라이언트에서 수행 완료한 시험은 아니다.

### 4.3 마스터리와 성장 자금

호그 라이더의 공개 9개 과제 전후 목표와 과제 세트별 골드 보상을 데이터화했다. 이 과제 표를 다른 카드로 복제하지 않는다. 모든 카드가 동일한 과제 수나 행동 지표를 가진다고 가정해서도 안 된다. [마스터리 개편](https://supercell.com/en/games/clashroyale/blog/news/new-collection-levels-and-mastery-changes/)

과제 보상은 한 번 얻는 자금이다. 과제를 끝낸 뒤에도 계속 반복 수입으로 계산하면 장기 골드 기대량이 부풀려진다. 경제 시뮬레이터에는 `repeatability`와 `claimed` 상태가 필요하다. 이미 완료한 과제는 미래 수입에서 제외하고, 목표 하향 패치에서는 과거 진행량을 보존한 채 수령 자격을 다시 판정한다.

## 5. 재화 초과: 하나의 clamp로 처리할 수 없음

공식 변환 안내는 절대 최대치와 인벤토리 한도를 다르게 취급한다. 골드처럼 초과분을 버리는 자원, 한도 미만에서 받은 묶음이 넘칠 수 있는 자원, 구매·거래 취소 예외가 있는 자원이 공존한다. [공식 변환 안내](https://support.clashroyale.com/hc/en-us/articles/49484891791771-Resource-Magic-Item-Conversion-Details)

### 5.1 지급 함수가 받아야 하는 상태

| 입력 | 필요한 이유 |
|---|---|
| 지급 전 잔액 | 묶음 초과 허용 여부의 기준 |
| 자원 종류·희귀도 | 한도와 전환 대상 선택 |
| 카드 영구 레벨 | 최대 레벨 복제본 전환 판단 |
| 해당 희귀도 전체 성장 상태 | 와일드 수동 전환 자격 |
| 현재 아레나 | 해금 자격·진화 조각 및 히어로 중복 수량 |
| 지급 출처 | 구매·일반 보상·취소 반환 구분 |
| 지급 묶음과 정산 순서 | 상태를 바꾸는 연속 항목 처리 |
| 규칙 버전·거래 ID | 패치 후 재시도·중복 지급 방지 |

같은 잔액이라도 출처와 수령 직전 상태가 다르면 결과가 달라질 수 있다. 화면에 보이는 잔액만으로 지급 결과를 재계산하지 말고, 서버가 확정한 원 보상·실제 지급·전환·손실을 하나의 영수증으로 제공하는 방식을 권장한다.

### 5.2 복제본과 최대 레벨 판정의 분리

**보상 필터**에서 최대 레벨에 준해 세는 조건과 **복제본을 Crystals로 바꾸는 조건**은 서로 다르다. 2026년 2월 중복 보정 공지는 강화에 충분한 복제본을 가진 카드도 60개 기준에 포함한다고 설명한다. 반면 변환 지원은 실제 레벨 16 도달 전 복제본을 보관한다고 설명한다. 따라서 `isMaxedForDropWeight`와 `isMaxedForOverflow`를 분리해야 한다. [중복 보정 공지](https://supercell.com/en/games/clashroyale/blog/release-notes/march-update-2026/), [변환 지원](https://support.clashroyale.com/hc/en-us/articles/49484891791771-Resource-Magic-Item-Conversion-Details)

이름이 비슷한 조건을 하나로 합치면 골드가 부족해 아직 강화하지 못한 카드의 복제본이 잘못 사라질 수 있다. 반대로 두 조건을 모두 실제 레벨만 보게 하면 원래 보정받아야 할 보상 풀을 잘못 만들 수 있다.

### 5.3 보존한 미확정 항목

- 진화 조각 전환표의 아레나 19~21 행이 누락되어 있다. 이웃 구간을 보간하지 않았다.
- 와일드 카드의 희귀도×킹 타워 레벨별 인벤토리 한도 전체 수량은 확보하지 못했다.
- 최대 카드 수가 정확히 60일 때의 드롭 가중치 규칙은 공지가 생략했다.
- 묶음 보상 중 어느 항목의 전환을 먼저 처리하는지는 공개 문서만으로 확정하지 않았다.

이 목록은 구현자에게 조사 우선순위를 주는 결측 목록이다. 테스트용 값을 넣고 싶다면 별도의 `reproduction_design` 규칙셋에서만 지정하고, 원작 데이터 파일을 조용히 덮어쓰지 않는다.

## 6. 상자 확률: 서로 다른 조건부 확률을 합치지 않기

### 6.1 세 단계 모델

상자 계산은 적어도 출발 등급, 최종 등급, 보상 종류, 보상 수량을 구분한다. 공개 표를 단순히 하나의 확률 열로 합치면 이미 5성으로 보장된 상자에 5성 도달 확률을 다시 곱하는 오류가 생긴다. [공식 확률 허브](https://supercell.com/en/games/clashroyale/blog/news/clash-royale-chest-info-2/)

```text
P(rewardType | startingStar, chestLevel, accountState)
 = sum_over_finalStar(
       P(finalStar | startingStar)
     * P(rewardType | finalStar, chestLevel, eligibility)
   )

Amount = quantity(rewardType, finalStar, chestLevel)
```

최종 카드 ID 선정과 초과 전환은 이 다음 단계다. 여기 제시한 식은 공개 표를 조합하기 위한 모델이다. 실제 내부 RNG가 같은 순서로 호출된다고 단정하지 않는다.

### 6.2 현재 파일의 적용 조건

Magic 상자의 출발 등급별 최종 확률과 Standard 상자의 1성 출발 확률을 분리했다. 보상 종류 표는 공개 조건에 따라 **Chest Level 13+**를 붙였다. Standard의 “골드/랜덤 카드” 큰 분류는 세부 희귀도 표와 다른 그룹이다. 둘을 합산하지 않는다.

144개 수량 레코드는 Magic 5등급×16레벨과 Standard 4등급×16레벨이다. 각 레코드의 `amounts`는 선택된 보상 종류별 지급 수량이다. 예를 들어 여러 열에 숫자가 있다는 이유로 골드·일반·희귀·영웅 카드를 한꺼번에 모두 지급하는 구조로 해석하면 안 된다.

낮은 상자 레벨에서는 일부 희귀도와 형태가 해금되지 않아 보상 분포가 달라진다. 해당 분포가 별도로 공개되지 않은 부분은 `REWARD_UNVERIFIED_LOW_LEVEL`로 남겼다. 높은 레벨 표에서 잠긴 희귀도만 제거하고 확률을 나머지에 비례 배분하는 것은 **가정**이며 원작 확정값이 아니다.

### 6.3 반올림과 합 검증

공식 표시 확률을 그대로 보존했기 때문에 일부 그룹은 1.0000이 아니라 0.9999 또는 1.0001이다. 2자리 퍼센트 표에는 합 검증 허용 오차를 0.0002로 기록했다. 2026년 10월 앨범 희귀도 표는 표시 합이 99.9%여서 별도 0.002 허용 오차를 사용한다.

검증기가 이를 맞추려고 마지막 행에 차이를 몰아넣으면 원문 복원값이 변한다. 샘플링을 위한 정규화가 필요하다면 별도의 파생 실행 표에 원시 합계와 정규화 방법을 기록한다. 배포용 보상 설정을 확정하는 단계에서는 실제 서버 확률이 몇 자리 정밀도인지 추가 확인해야 한다.

### 6.4 계산 예시

**[파생 계산]** 출발 1성 Magic 상자와 Chest Level 13+의 공개 보상 표를 조합하면 `0.0101 × 0.095 = 0.0009595`, 즉 **0.09595%**가 완성 진화 보상 종류의 확률이다. 이 값은 원하는 특정 진화를 새로 해금할 확률이 아니다. 이미 보유한 진화인지, 어떤 진화가 선택되는지, 전환될 수 있는지를 추가로 판단해야 한다.

**[파생 계산]** 출발 3성 진화 상자의 원시 조각 기대값은 `0.493×1 + 0.456×2 + 0.051×6 = 1.711`이다. 기대값은 특정 카드의 필요한 조각을 매번 그만큼 준다는 보장이 아니다. 목표 진화 완성 시간에는 카드별 선택 분포와 중복 전환을 추가해야 한다.

## 7. 히어로·패스·이벤트의 반복성

### 7.1 히어로 재화의 구버전 혼입 방지

현재 지원은 200 Hero Coins를 모아 원하는 히어로를 선택하는 구조다. 구 Hero Fragments를 모아 무작위 소환하던 설명이나 확률 허브에 남은 Hero Box 표를 현행 기본 획득 모델로 연결하지 않는다. 데이터에는 후자를 `legacy_hero_fragment_content_not_current_coin_acquisition`으로 보존했다. [현행 히어로 안내](https://support.clashroyale.com/hc/en-us/articles/49484957323163-Heroes), [전환 공지](https://supercell.com/en/games/clashroyale/blog/news/mid-march-update/)

시즌당 코인 수입을 가정해 해금 기간을 계산할 때도 첫 히어로 일회성 지급, 이미 보유한 코인, 유료 선택 보상, 이벤트 획득을 별도 항목으로 둔다. `200÷75`라는 나눗셈은 출발 재화 0·추가 수입 없음·발표된 무료 패스 완료라는 조건 아래의 분석일 뿐 모든 플레이어의 체감 기간이 아니다.

### 7.2 일일 보상과 패스의 데이터 계약

첫 N전 참여 보상과 첫 N승 보상을 별도 카운터로 저장한다. 전투에 진 후에도 참여 크라운을 받을 수 있는 조건을 승리 카운터로 묶으면 일일 보상이 달라진다. Catch-Up은 전체 미수령량 보전이 아니고 계정별 실험 조건이 붙을 수 있다. [일일 보상](https://support.supercell.com/clash-royale/en/articles/daily-battle-rewards-3.html)

패스는 다음 상태가 필요하다: 시즌, 진행량, 무료/유료 권한, 선택형 보상에서 선택한 항목, 이미 청구한 보상, Lucky Loop 해금 날짜, 과거 시즌 미수령 상태. 유료 구매로 진행량이 생긴 것과 진행량에 따라 새 권리가 열리는 것은 별도 사건이다. 클랜 이동으로 선물 수령 한도가 초기화되는 것으로 처리하지 않는다. [패스 지원](https://support.clashroyale.com/hc/en-us/articles/49484915388443-Pass-Royale)

실제 패스 가격·전체 단계별 보상량·개인화 상품은 지역·스토어·계정·시점에 따라 확인해야 하므로 가격을 임의로 복원하지 않았다. 가격 없는 상품에는 `null`을 사용한다. `0`은 무료 상품이라는 다른 계약이 된다.

## 8. Crown Series 보상 81개 계약

현재 공식 지원의 정규 주말 보상을 **9개 리그 그룹×0~8승**으로 분리했다. 그룹 9는 King's League의 9~13 리그다. 한 레코드는 종료 승수의 최종 보상 묶음이다. 8승이면 0~8승 레코드를 전부 더하는 구조로 구현하지 않는다. Grand Duel 보상은 이 표에 포함되지 않는다. [Crown Series 공식 표](https://support.clashroyale.com/hc/en-us/articles/58566501950107-Crown-Series)

재구축 과정에서 보상 문자열의 `4,800`처럼 천 단위 쉼표와 항목을 구분하는 쉼표를 구별했다. 문자열 전체를 모든 쉼표로 나누면 수량이 손상된다. 정규화 결과는 `gold`, `random_epic`, `wild_legendary`, `full_banner` 등의 명시적 키를 사용한다.

이 표를 경제 모델에 넣을 때는 참가 빈도, 최종 승수 분포, 리그 이동, 시즌별 주말 수를 입력해야 한다. 모든 참여자가 최대 승수 보상을 얻는 것으로 일일 환산하면 경제 공급량을 과대평가한다. 계정의 보유 카드 및 모드 레벨 상한도 결과에 영향을 주므로 모드별 분석과 연결한다.

## 9. 복원값을 사용하는 계산 도구의 최소 요건

다음 계산기는 구현 가능한 **재현 설계**이며 원작 내부 도구가 아니다.

| 도구 | 입력 | 출력 | 반드시 막을 오류 |
|---|---|---|---|
| 카드 성장 계산기 | 보유 레벨·복제본·와일드·골드·목표 | 단계별 부족분·합계·결측 목록 | 미확정 비용의 무료 처리 |
| 계정 성장 계산기 | 보유 기본 카드·형태·보존 타워 레벨 | 컬렉션·차기 킹 조건 | 형태를 기본 카드 수로 중복 집계 |
| 상자 기대량 계산기 | 가족·출발 등급·상자 레벨·자격 | 확률·수량·초과 후 기대량 | 조건부 확률 중복 곱셈 |
| 보상 영수증 재현기 | 지급 전 상태·묶음·출처·규칙 버전 | 지급·전환·손실·최종 잔액 | 여러 번 확정, 출처 예외 소실 |
| 시즌 수입 분석기 | 참여일·승률·패스·과제 완료 상태 | 수입 분포와 병목 | 일회성 보상을 영구 반복 수입으로 계산 |

평균만 반환하기보다 입력 가정과 사용할 수 없는 데이터도 함께 반환해야 한다. `complete: false`인 결과를 정확한 성장 기간처럼 표시하지 않는다. 충분한 데이터가 모이면 기대값 외에 완주 확률, 중간값, 장기 지연 구간을 몬테카를로 모델로 계산할 수 있지만, 미확정 카드 선택 분포를 임의 균등 분포로 둔 결과에는 반드시 가정 표시가 필요하다.

## 10. 검증 체크리스트와 완료 범위

이번 파일 생성에서는 공개 HTML 표의 열·행을 파싱하고 레코드 ID 고유성, 출처 참조, 확률 그룹 합과 반올림 허용 오차, 상자 수량 144행, Crown Series 81행을 검사했다. 이는 데이터 재구축 검증이며 실게임 계정 거래를 실행한 검증이 아니다.

추가 구현 검증은 다음 사례가 유효하다.

1. 영웅 목표 레벨 7 골드 결측 상태에서 강화 버튼을 누르면 확정하지 않음.
2. 목표 레벨과 현재 레벨을 뒤바꿔 직전 비용을 사용하는 오류를 탐지.
3. 같은 강화 거래 재전송 시 카드와 골드가 한 번만 소비됨.
4. 타워 유닛을 강화하면 컬렉션에는 반영하고 킹 조건 카드 수에는 추가하지 않음.
5. 상자 레벨 12 입력에 13+ 확률을 자동 적용하지 않음.
6. 보장 5성 상자에서 5성 도달 확률을 다시 곱하지 않음.
7. 초과 허용 자원은 수령 전 잔액과 지급 출처에 맞게 처리.
8. 최대 카드 수 59/60/61을 분리해 60은 추가 근거가 필요한 것으로 표시.
9. 상자 보상 수량 표의 여러 열을 동시에 지급하지 않음.
10. Crown Series의 정규 종료 보상을 Grand Duel 또는 단계 누적 보상으로 재사용하지 않음.
11. 구 Fragment Box를 Hero Coins 현재 획득 경로에 자동 포함하지 않음.
12. 개인화·복귀·연속 구매 실험을 전체 계정 기본값으로 활성화하지 않음.

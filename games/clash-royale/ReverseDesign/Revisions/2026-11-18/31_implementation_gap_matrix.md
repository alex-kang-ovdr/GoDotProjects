# 31. 원작 규칙과 Crownfall v4.4 구현 차이

> **v4 추가 조사 안내:** 아래 본문과 개수는 해당 v2/v3 작성 당시의 범위를 설명한다. 현재 통합 자료, 추가 복원, 레벨 미기재 값의 처리와 실행 명령은 [39번 개요](39_research_reconstruction_v4_overview.md), [44번 근거 조정](44_sources_and_level_reconciliation.md), [최신 검증 보고서](reports/validation_report.md)를 기준으로 한다.

> 확인 대상: 이 프로젝트의 Crownfall Arena v4.4.0 / rulesVersion4 카드 정의. 이 문서는 후속 원작 재현 작업의 차이 분석이며 이번 턴에서 웹게임을 수정한 변경 명세가 아니다.

## 1. 대조 기준

현재 웹게임은 원작의 카드 배치·자동 전투·엘릭서·손패 순환을 참고한 독립적인 프로토타입이다. [19개 카드 스냅샷](implementation_reference/crownfall_4_4_cards.json)을 읽어 [대조 JSON](data/tables/implementation_card_mapping.json)과 [CSV](data/tables/implementation_card_mapping.csv)를 생성했다. 카드의 역할이 비슷해도 수치·동작·그래픽·이름이 같다고 보지 않는다.

원작 공개 카탈로그와 개념상 대응되는17개 카드, 별도 독자 카드2개로 구분했다. 이것은 구현 완성도를17/120처럼 계산하기 위한 집계가 아니다. 120행의 아카이브에는 이벤트·숨김 카드가 포함되고 현재 원작의 전체 카드 수도 아니기 때문이다.

## 3. 밀집보병을 분리하는 이유

밀집보병은 사용자가 요청한 대형 유지·강한 방어·돌격 스킬을 구현한 카드다. 현재 정의는6명, 개체 HP340, 방진 피해 감소70%, 돌격 비용1, 지속5초, 재사용14초이며 게임 규칙4에서는 방진·집결·재정렬 상태에서 공격하지 않는다. 이러한 값은 기존 구현 문서와 코드에 속한 자체 밸런스다.

원작 Royal Recruits도 여러 방패 병사를 사용하지만, 두 카드가 같은 카드라는 근거는 없다. 원작의 실드 HP를 구현의 비율 피해 감소로 바꾸거나 원작 카드 레벨 배열에 밀집보병을 끼워 넣으면 다른 시스템이 된다. 재현 프로필에서는 독자 카드 네임스페이스와 허용 모드를 분리한다.

이번 데이터 조회에서 `compare phalanx`는 `original_archive_card_id=null`을 반환한다. 최신 원작 카드 조회에서 밀집보병을 발견했다고 표시하지 않는다.

## 4. 수치 적용 전에 해결할 차이

| 범위 | 현재 구현에서 확인할 것 | 원작 재현에 필요한 추가 계약 | 우선순위 |
|---|---|---|---|
| 좌표 | 480×640 논리 전장·픽셀 거리 | 원작 타일·충돌 반경·배치 격자 변환 | P0 |
| 레벨 | 카드별 자체 고정 수치 | 희귀도 시작 레벨, 모드 상한, 전체 수치 프로필 | P0 |
| 정의 | troop/building/spell 중심 | 카드→다중 개체→투사체→효과→사망 소환 그래프 | P0 |
| 시점 | 시뮬레이션 tick과 공격 예약 | 첫 타격·취소·동시 사건의 계측 기준 | P0 |
| 피해 | 자체 피해·범위·상태 처리 | 방패, 파동, 건물별 배율, 개별 면역 | P0 |
| 특수 형상 | 밀집보병의 자체 스킬 | 진화 카운터, Hero 슬롯, 능력 소유·1회 사용 | P1 |
| 타워 | 기존 킹·측면 타워 | Tower Troop 컬렉션·타워별 수치·레벨 계약 | P1 |
| 성장 | 싱글플레이 캠페인·진행 | 카드 복제본·골드·해금·킹 조건·확률 보상 | P1 |
| 모드 | 자체 싱글플레이·테스트·리플레이 | 원작 Ranked/Crown Series/클랜전별 상태·정산 | P2 |
| 통신 | 로컬 브라우저 전투 | 온라인 권위 서버·재접속·검증 설계 | 별도 범위 |

우선순위는 이번 분석의 구현 제안이다. 원작 개발사의 로드맵이나 실제 개발 비용을 추정한 값이 아니다.

## 5. 권장 프로필 구조 — 재현 설계

세 가지 프로필을 별도로 두면 비교 실험이 쉽다.

- `crownfall_custom_v4`: 지금의 플레이와 저장 호환을 유지하는 자체 규칙.
- `archive_2023_research`: 확보한 역사 수치와 그 시점의 규칙만 연구하는 프로필.
- `cr_current_observed_<build>`: 같은 원작 빌드에서 관측한 완전한 카드·모드 프로필.

프로필마다 카드 풀, 규칙 ID, 좌표 변환, 단위, 허용 레벨, 능력 정책, 데이터 해시가 필요하다. 현재 묶음의 부분 패치 테이블은 세 번째 프로필의 완성본으로 승격하지 않는다. 전투를 시작하기 전에 누락된 HP·피해·소환 참조를 검사하고 필요한 카드가 미완성이면 시작을 막거나 명시적인 자체 대체 프로필을 선택하도록 한다.

## 6. 개발자 테스트 모드의 활용

기존 양 팀 제어와 실시간 밸런스 입력은 상호작용을 실험하는 데 사용할 수 있다. 다만 조정한 숫자가 원작에서 관측된 값인지, 재현용 보정값인지 입력 출처를 구분해야 한다. 설정을 저장할 때 `base_profile`, `overrides`, `reason`, `source_ids`를 기록하는 방식이 적합하다.

배치 위치·레벨·초기 타워 상태·RNG·게임 속도를 고정하고, 수정 전후의 첫 타격 시각·생존 HP·타겟 변경 횟수를 비교한다. 무한 엘릭서는 배치 편의를 위한 실험 조건이므로 실제 원작 교환 효율을 평가할 때는 끈 조건도 별도로 측정한다. 수동으로 양 팀을 조종한 결과와 실제 AI 상대 승률을 혼동하지 않는다.

## 7. 이번 작업의 적용 상태

연구 데이터, MD, JSON/CSV, 검증·조회 스크립트를 추가했다. Crownfall 소스와 배포된 게임은 수정하지 않았다. 수치 차이를 확인했다고 기존 밸런스를 자동 수정하지 않았으며, 사용자 요청의 밀집보병 동작도 원작 복원 명목으로 삭제하거나 덮어쓰지 않았다.

후속 구현은 P0 계약을 먼저 해결한 뒤 대표 카드의 완전한 프로필을 추가하고, [44개 실험 명세](data/tables/interaction_cases.json)의 관측·재현 결과를 짝지어 확장하는 순서가 적합하다.

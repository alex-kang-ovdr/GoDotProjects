**데이터·기획 팩 r1 · 조사 기준일 2026-11-18 · 비교 대상 숨 4.0.0**

이 패키지는 Oxygen Not Included의 공개 자료를 분석해 원작 참조 데이터를 JSON·CSV로 재구성하고, 기존 JavaScript 웹 게임 **숨 · Breath Colony 4.0**의 차이와 개선 순서를 설계한 산출물이다. 시스템별 상세 문서, 필드별 근거, 현재 코드 감사, 재현 가능한 계산·검증 도구를 함께 제공한다.

**이번 완료 범위는 데이터와 고도화 기획이다.** 원작 설치 파일에서 내부 데이터를 추출한 결과나 새 게임 엔진의 구현 완료본은 아니다. 비교 대상 제품 코드를 수정·재배포하지 않았다. 기존 코드 기준 커밋은 `bb78805aef453cae4a79bed91daf88dfdf3535b3`이다.

## 3. 기획을 바꾼 주요 분석 결과

### 3.1 단위부터 분리해야 한다

숨 4.0은 120초 주기와 내부 산소·물·식량 단위를 사용한다. 원작 공개 참조의 600초 주기, kg/s, kcal, W, J, DTU를 숫자만 교체해서 넣으면 생산·소비·운반·발열의 상대 비율이 깨진다. 원작 주기값은 먼저 **sourceCycleSeconds=600**으로 초당 값에 정규화하고, 웹판의 시간·밸런스 조정은 별도 단계에서 처리하도록 설계를 바꿨다.

기존 세이브는 `breath_legacy_v4`, 원작 검증용은 `oni_reference_r1`, 웹 플레이 조정용은 `breath_balanced_v5`라는 별도 규칙 세트를 제안한다. 세 이름은 구현 명세이며 현재 게임에 추가된 기능을 뜻하지 않는다. 자세한 계약은 [10. 데이터·단위·프로필](docs/10_Data_Units_Profiles.md)에 있다.

### 3.2 질량 처리에는 원작의 명시적 예외가 있다

원작 장치의 입력·출력 질량이 항상 같은 것은 아니다. 무조건 부산물을 추가해 물리학적 질량 보존을 맞추면 원작 규칙과 달라진다. 따라서 초기량·유입·이동·생성·소멸·유출을 구분하는 원장을 설계했다. `intentional_sink`는 계산상 소멸을 기록하는 항목이며 새 원소나 아이템이 아니다.

18개 반응의 회계 검사 중 **17개는 명시된 소멸항을 포함해 잔차가 0**이다. 조류 배양기 1개는 선택적 CO₂·조명·반올림 조건 때문에 **조건부 항목으로 남겼다**. 원작 내부 구현과의 일치 인증은 아니다. [반응 자료](data/reactions.json) · [검사 결과](data/reaction-checks.json)

### 3.3 현재 코드에서 먼저 다룰 경계조건

| 인위적으로 구성한 진단 조건 | 관찰한 4.0 동작 | 새 규칙의 수용 기준 |
|---|---|---|
| 산소 수신 셀 2.999/최대 3, 전해기 0.1초 가동 | 명목 생산 0.03, 저장 증가 0.001, 차이 0.029 미기록 | 출력 공간 예약에 맞춘 가동 또는 명시적 방출·손실 기록 |
| 기체·물이 있는 셀에 타일 공사 완료 | 셀의 산소·CO₂·물을 0으로 처리 | 합법 위치로 변위하거나 공사 대기; 삭제는 원장에 명시 |
| 석탄 0.001, 정격 소비 0.025/s, 0.1초 틱 | 미량 연료로 정격 6J 생산 | 실제 가능한 0.04초에 대응하는 2.4J 또는 전량 대기 정책 |

앞의 산소 숫자는 **기존 내부 단위**이며 kg가 아니다. 진단은 메모리 안의 작은 상태를 구성한 검사이고 정상 플레이로 그 상황에 도달한 장기 검증이 아니다. 원본 게임 파일이나 저장 파일은 변경하지 않았다. [재현 결과](current-v4/audit_probe_results.json)

같은 0.1초 틱과 명령 순서의 리플레이, 저장·재개 비교는 일치했다. 서로 다른 외부 `Game.step` 분할에서는 차이가 있었지만, 현재 브라우저 경로는 이미 0.1초 누적기를 사용한다. 이를 기존 화면의 프레임레이트 의존 버그로 주장하지 않는다.

### 3.4 오래된 자료와 현재 변경을 분리했다

- Great Hall의 옛 +6과 현재 문서의 +4를 구분하고 Banquet Hall을 별도 다룬다.
- 물풀의 옛 표백석 요구와 2026 공식 변경을 같은 행에 합치지 않는다.
- 질식 무력화·동료 CPR의 존재는 공식 기록으로 확인하고 정확한 시간·회복량은 미확정으로 둔다.
- 관심 분야 기술은 **실제 사기 +1**이다. 필요 사기 비용을 낮추는 방식으로 저장하지 않는다.
- 기체 펌프의 처리량과 연결 배관의 용량, 설비의 현재 발열 표시와 기억에 의존한 옛 수치를 구별한다.

각 근거와 충돌 처리 방식은 [대원](docs/05_Duplicants_Morale_Schedules.md), [방](docs/07_Rooms_Progression.md), [충돌 목록](docs/15_Conflicts_Unknowns.md)에 연결했다.

## 4. 밸런스 기준선

표준 유기 대원, 특성 없음, 보통 배고픔, 정상 호흡 지속을 가정한 산술이다. 배달·수확·정전·식품 부패·냉각 비용까지 포함한 실제 기지 성능은 아니다.

| 인구 | 산소/600초 주기 | 열량/주기 | 전해조 등가 가동 수 | 해당 산소량의 이상적 물 소비/주기 |
|---:|---:|---:|---:|---:|
| 3명 | 180kg | 3,000kcal | 0.338대 | 202.70kg |
| 8명 | 480kg | 8,000kcal | 0.901대 | 540.54kg |
| 12명 | 720kg | 12,000kcal | 1.351대 | 810.81kg |

전해조 한 대의 공개 정격은 물 1kg/s에서 산소 0.888kg/s와 수소 0.112kg/s다. 이상적으로 8.88명분 산소이며, 8명을 담당하려면 약 90.09% 가동률을 유지해야 한다. 실제 계획에서는 출력 압력·펌프·급수·고장·온도 여유를 더 확인한다.

수소 전량 사용 시 이론 발전출력 896W를 발전기 한 대의 800W 상한과 혼동하지 않는다. 한 대만 연속 소비하면 전해조 정격 운전 기준으로 수소가 7.2kg/주기 남는다. 이상적 펌프 duty cycle을 포함한 부하는 624W이며, 단일 발전기의 순전력은 176W, 수소 전량을 처리하는 복수 발전기 구성의 이론 순전력은 272W다. 이 계산에는 냉각·필터·시동·손실 등이 빠져 있다.

Mealwood는 600kcal/3주기이므로 3명분 이론 최소가 15그루다. 웹판 설계 예시로 생산 가동률 85%를 가정하면 18그루가 된다. **85%는 원작 상수가 아니라 이번 계획의 가정**이다. 수세식 화장실은 입력 5kg/회, 오염수 출력 11.7kg/회로 6.7kg/회의 명시적 생성이 있으므로 재순환망의 넘침 처리가 필요하다.

계산식·입력 ID·13개 산술 검산은 [12. 밸런스](docs/12_Balance_Scenarios.md)와 [balance-math.json](reports/balance-math.json)에 있다.

| `reports/` | 범위 통계·검사 결과·패키지 파일 해시 |

압축을 풀고 패키지 루트에서 Node.js로 실행한다.

압축을 푼 직후 파일 무결성을 확인하려면 `python3 tools/manifest.py --verify`를 사용할 수 있다. 데이터를 편집하거나 보고서를 다시 생성하면 해시가 달라질 수 있다. 수정본의 새 목록은 `python3 tools/manifest.py`로 생성한다.

```sh
node tools/balance-math.mjs
node tools/validate.mjs
```

이 두 도구는 현재 게임 소스 없이 실행할 수 있다. 계산 결과를 먼저 갱신한 뒤 통합 검증을 실행한다. JSON 원자료를 편집했다면 Python 3로 정규화 파일과 CSV를 다시 만든다.

```sh
python3 tools/assemble.py
node tools/balance-math.mjs
node tools/validate.mjs
```

`tools/build-root-data.py`는 물질·시간·배관·루트 출처의 초기 조사표를 생성하는 도구다. 분야별 모든 자료를 웹에서 재수집하는 크롤러가 아니며, 수정된 자료를 덮어쓸 수 있으므로 일반 확인에는 실행하지 않아도 된다.

현재 게임 진단을 새로 실행하려면 이전에 제공한 **숨 4.0 전체 소스**가 별도로 필요하다. 이 패키지는 중복된 게임 소스를 포함하지 않는다. `GAME_SOURCE`와 `AUDIT_OUTPUT`에는 본인 환경의 절대 경로를 넣는다.

```sh
node current-v4/probe-current.mjs GAME_SOURCE AUDIT_OUTPUT
```

위의 두 경로는 설명용 자리표시자다. `source_manifest.json`에 기록된 버전·해시와 다른 코드를 쓰면 같은 조사 대상이라고 간주하지 않는다. 새 결과를 기존 감사 증거와 구분하려면 출력 폴더를 별도로 지정한다.

## 8. 검증 결과의 의미

- 통합 검증은 ID, 형식, 근거 연결, CSV 일치, 수지·산술, 문서 링크 등을 확인한다.
- 13개 수학 검산은 데이터로부터 계산한 산소·물·전력·식량·위생·열 기준선을 확인한다.
- 현재 4.0의 진단 6개는 작은 상태에서 수행한 소스 감사의 보조 증거다.
- 원작 내부 코드·전체 원본 테이블·실행 빌드의 완전 일치를 확인한 검증은 아니다.
- 새 고도화 엔진의 정상 진행·30주기 생존·성능 검증을 완료한 것으로 해석하지 않는다.

사용자가 처음 지정한 나무위키 페이지는 이번 직접 열람에 실패해 수치 근거로 사용하지 않았다. 실제로 확인한 Klei 공식 변경 기록과 공개 문서를 필드별로 연결했으며, 불확실한 값은 이유와 함께 남겼다. 남은 원작 데이터 수집과 게임 구현의 완료 조건은 각각 [복원 범위](docs/01_Scope_Sources_Versions.md), [결측 목록](docs/15_Conflicts_Unknowns.md), [QA](docs/13_Migration_QA.md)에 있다.

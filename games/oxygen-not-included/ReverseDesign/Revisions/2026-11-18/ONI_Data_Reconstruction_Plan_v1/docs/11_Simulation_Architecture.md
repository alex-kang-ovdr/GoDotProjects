# 11. JavaScript 시뮬레이션 구조 개선

## 1. 우선순위

현재 브라우저 게임의 기능을 유지하면서 원작 구조를 도입하려면, 한 파일에 특수 처리를 더하는 것보다 **결정론적 시계·물질 원장·공간 재고·작업 예약·명확한 데이터 단위**를 먼저 마련해야 한다. 아래는 구현 제안이며 현재 성능 측정 결과가 아니다.

## 2. 모듈 경계

| 모듈 제안 | 소유 상태 | 외부에 제공하는 계약 |
|---|---|---|
| `clock` | tick, accumulator, speed | 고정 dt의 tick 발행 |
| `catalog` | 승인된 정의와 참조 | ID 기반 읽기 전용 조회 |
| `world` | 주 환경 셀과 탐사 | 질량/열 교환, 지형 변경 이벤트 |
| `inventory` | 더미·화물·건물·저장 | 예약·이동·소비·반납 거래 |
| `networks` | 전력·기체·액체·신호 | 포트 연결, 용량, 전달 결과 |
| `production` | 설비 진행·버퍼 | 거래 가능한 만큼의 생산 |
| `jobs` | 작업 요청·예약·할당 | 안전·자격·접근을 만족하는 작업 |
| `colonists` | 욕구·상태·기술 | 생활·작업·구조 행동 |
| `rooms` | 공간 컴포넌트·가구 태그 | 방 판정과 효과 발생 조건 |
| `progression` | 연구·목표·기록 | 실제 이벤트 기반 진행 |
| `diagnostics` | 원장·최근 흐름·원인 | UI용 읽기 모델과 검증 |
| `renderer` | 카메라·표현 캐시 | 시뮬레이션 상태를 바꾸지 않는 그리기 |

초기 구현에서 파일 수를 무조건 늘릴 필요는 없다. 중요한 것은 누가 재고를 변경할 권한이 있는지와 모든 변경이 같은 거래 API를 통과하는지다.

## 3. 틱 처리 순서

1. tick 번호가 붙은 사용자 명령을 처리하고 topology 변경을 수집한다.
2. 변경된 전력·관·방·경로 캐시를 갱신한다.
3. 지난 확정 상태로 센서와 제어 신호를 평가한다.
4. 설비의 입력·출력 공간·전력 요청을 예약하고 공급을 배분한다.
5. 승인한 생산 거래와 환경 이동·열교환을 반영한다.
6. 대원 욕구와 작업을 진행하고 생활·구조 요청을 만든다.
7. 작업 할당, 실제 작업 결과, 연구·방 이용·목표 이벤트를 확정한다.
8. 원장 검사와 읽기 전용 UI 스냅샷을 만든다.

이 순서 자체는 웹판 제안이다. 순서가 달라졌을 때 같은 틱에 생성한 산소를 즉시 소비할 수 있는지 같은 경계 규칙을 명세한다. 같은 자원을 두 시스템이 먼저 가져가도록 암묵적인 배열 순서에 의존하지 않는다.

## 4. 외부 dt와 고정 시뮬레이션

렌더 프레임의 실제 경과 시간은 accumulator에 쌓고, 고정 tick을 필요한 횟수만 진행한다. 화면이 60Hz 또는 30Hz라고 대원이 다른 양의 산소를 소비하면 안 된다. 기본 tick은 검증을 통해 정하며, 원작 내부의 모든 시스템 tick을 복원했다고 표기하지 않는다.

프레임 하나에 처리할 tick 수를 제한할 때 **정상 동작 중 잔여 accumulator를 조용히 버리면 안 된다**. 백그라운드 탭은 현재처럼 일시정지하거나 별도의 오프라인 진행 정책을 명시한다. 배속을 바꿔도 생산률과 소비율의 상대 비율은 바뀌지 않아야 한다.

세이브에는 tick·accumulator·난수 상태·규칙 세트 버전·열려 있는 거래의 상태를 기록한다. 렌더 보간값은 저장 대상에서 제외한다. 동일 명령열 재생은 저장 후 재개와 비교한다.

## 5. 네트워크

전선은 부하·발전·저장·정격을 구분한다. 배터리의 잉여 전력 저장과 순간 부하 공급은 J를 기준으로 한다. 발전 설비를 연결해 두었다는 이유로 연료·운전자 없이 발전하지 않는다.

유체관은 원소 ID·질량·온도를 가진 패킷과 입력/출력 포트를 사용한다. 원작 공개 표의 기체 1kg/s, 액체 10kg/s를 기준 후보로 가져왔지만 분기 우선순위·브리지·정확한 갱신 순서는 추가 검증한다. [R09](https://onidb.wiki/buildings/gas-pipe) · [R10](https://onidb.wiki/buildings/liquid-pipe)

한 칸에 청수관과 오수관이라는 별개의 종류를 만드는 대신, 액체관 하나가 어떤 원소 패킷을 운반하는지로 상태를 표현한다. 더러운 물을 올바르지 않은 설비에 보냈을 때는 오류를 표시하고 손상/정지 정책을 데이터화한다. 배관 파괴는 저장된 내용물의 방출 거래와 같이 처리한다.

## 6. 데이터 배치와 캐시

셀마다 큰 객체를 만드는 대신 물질 ID, 질량, 온도, 세균 수 등을 TypedArray에 분리하는 방식을 제안한다. 초기에는 정확성을 확인하기 쉬운 단일 스레드로 시작하고, 시뮬레이션 시간을 측정한 뒤 Worker 도입을 판단한다.

변경이 없는 전선·방·관 연결을 매 틱 전체 flood fill 하지 않는다. 지형 변경 영역과 영향을 받은 컴포넌트만 dirty 처리한다. 분할이 발생하면 해당 연결 성분만 다시 계산한다. 렌더의 chunk 캐시는 시뮬레이션의 활성 chunk와 별개다. 보이지 않는 화면 밖의 기지는 정상적으로 운영되어야 한다.

## 7. 성능 목표와 측정 방법

제안 평가 장면은 128×64 셀, 대원 12명, 설비 100개, 활성 작업 500개다. 이 숫자는 원작 규격이나 이미 달성한 성능이 아니다. 기기·브라우저·배속·탭 상태와 함께 tick 시간 p50/p95/p99, 경로 재계산 횟수, 할당 횟수, GC 일시정지, 실제 장시간 총 진행량을 기록한다.

원장 검사는 개발 빌드에서 매 tick, 일반 플레이에서는 정해진 간격으로 실행할 수 있다. 성능 최적화를 위해 원장 오차를 숨기거나 어려운 장면을 일시정지시키지 않는다. 캐시를 끄고 계산한 기준 결과와 일부 장면을 대조해 캐시 누락을 찾는다.

## 8. 진단 UI

사용자는 구현 로그보다 원인을 알아야 한다. 생산하지 않는 전해장치를 선택했을 때 `청수 부족`, `출력 공간 부족`, `전력 미공급`, `과압`, `건물 비활성`, `과열 손상`을 구별한다. 각 원인은 해당 입력·출력·회로·환경 위치를 강조한다.

개발자용 창에는 물질 거래, 최근 질량/전기/열 원장 잔차, 규칙 세트 해시, 데이터 근거, 작업 대기 이유를 표시한다. 플레이어용 화면에는 최근 주기 순생산·비축으로 버티는 시간·현재 병목만 요약한다.

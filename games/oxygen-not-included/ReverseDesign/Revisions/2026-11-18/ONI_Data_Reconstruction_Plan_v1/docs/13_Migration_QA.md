# 13. 저장 이행과 검증 계획

## 1. 이번 작업과 실행 검증의 경계

이번 산출물은 원작 참조 데이터·현재 코드 감사·새 시스템 설계·검증 도구다. 숨 4.0의 제품 코드를 고치거나 새 엔진을 배포하지 않았다. 예전 4.0의 71개 테스트 통과를 새 규칙 세트의 통과 증거로 재사용하지 않는다.

감사의 경계조건 진단은 현재 소스를 직접 import하고 **작은 인위적 상태**를 만든 검사다. 정상 플레이로 해당 상태를 달성한 장기 진행과 구분한다. 이를 통해 새 계약의 필요성을 확인하고, 향후 수정이 끝나면 같은 재현 장면으로 회귀를 검사한다.

## 2. 새 저장 헤더 제안

```json
{
  "saveVersion": 5,
  "engineVersion": "planned-v5",
  "rulesetId": "breath_balanced_v5",
  "rulesetVersion": "pending",
  "catalogHash": "generated-on-build",
  "unitSchemaVersion": 1,
  "generatorVersion": "pending",
  "tick": 0,
  "rngState": null
}
```

예시 문자열 `pending`이 제품에서 허용된다는 뜻은 아니다. 정식 저장 전에 실제 승인값이 모두 채워져야 한다. 원작 카탈로그의 빌드 미고정 자료와 제품 규칙의 버전 해시를 별도로 관리한다.

## 3. 이전 저장 정책

v4의 산소·CO₂ 스칼라와 공용 수소는 kg로 해석되지 않는다. 따라서 기존 값을 아무 배율로 곱해 새 물질 세계로 자동 변환하는 것은 진행 보존이 아니다.

제안하는 기본 이행은 **이전 세이브를 legacy 규칙으로 열기**다. 새 원소·포트·사기·칼로리 규칙은 새 기지에서 시작한다. 사용자가 별도 전환을 선택하는 기능은 다음 조건을 갖춘 뒤 제공한다.

1. 원본 저장을 보존하고 새 파일로 변환한다.
2. 각 변환 항목을 정확·근사·변환불가로 분류한다.
3. 여러 칸 건물과 기존 한 칸 건물의 충돌을 사전 표시한다.
4. 산소·물·식량·재료의 임의 환산량을 명시한다.
5. 목표·숙련·사기 등의 재해석을 설명한다.
6. 로드 후 전체 유효성을 확인한 뒤에만 현재 기지로 채택한다.

v1–v3 저장은 기존의 검증된 v4 변환 경로를 거쳐 legacy 프로파일로 이어가는 방안을 우선한다. v5 신형 환경으로 자동 승격했다고 표시하지 않는다.

## 4. P0 경계조건 진단

| 위험 | 새 계약 | 검사 방식 |
|---|---|---|
| 출력 포화 때 투입 자원 소비/산소 손실 | 공간 예약만큼 부분 가동 또는 전량 대기 | 거의 가득 찬 셀과 전해기 1틱 |
| 타일 완공 시 기존 유체 제거 | 변위·방출·대기의 명시적 거래 | 공사 셀에 기체/물 존재 |
| 잔여 연료보다 긴 전력 생산 | 실제 연료량과 에너지에 동일 가동률 | 마지막 미량 연료 1틱 |
| 외부 step 분할 결과 차이 | 고정 tick의 단일 시계 API | 같은 명령·총시간의 여러 외부 dt 분할 |
| 공급이 끊긴 작업 경험치 | 생산적인 실제 작업만 인정 | 출력·전력·운반 막힘 반복 |

외부 dt 분할 검사는 앱의 일반 프레임레이트 문제와 구분해야 한다. 현 앱이 이미 0.1초 누적기를 사용한다면 단순 30/60FPS 차이를 고장 원인으로 주장하지 않는다. 정확한 현재 앱 판단은 감사 문서를 따른다.

## 5. 계층별 수용 게이트

| 계층 | 확인할 내용 | 통과의 의미 |
|---|---|---|
| 데이터 | 출처·단위·버전·ID·반응 참조·null | 근거와 형식이 추적 가능 |
| 원장 | 질량·전기·열 생성/소멸/이동 | 오차가 허용 범위이고 숨은 삭제 없음 |
| 단위 기능 | 방·레시피·배관·사기·경로 | 각 계약의 경계조건 만족 |
| 통합 | 운반→생산→식사→배출 연결 | 시스템 사이 자원/이벤트 일치 |
| 저장 | 동일 상태 왕복·재개·거부의 원자성 | 재고 복제와 상태 손상 없음 |
| 리플레이 | seed+명령+tick 재생 | 동일 순서에서 동일 결과 |
| 정상 진행 | 공개 명령만 사용한 새 기지 | 생성 자원/연구/상태 주입 없이 목표 가능 |
| 장애 복구 | 정전·출력 차단·문 잠금·침수 | 원인 표시와 복구 가능 |
| 브라우저 | 조작·저장·화면·백그라운드 | 실제 사용자 환경에서 동작 |
| 장시간 | 30주기 및 인구 증가 | 공급·열·노동·저장 추세 안정 |

새 구현의 통과 횟수는 실제 실행 후 기록한다. 이 문서의 테스트 ID나 기획 시나리오 개수를 “이미 통과한 테스트 수”로 쓰지 않는다.

## 6. 데이터 QA 도구 실행

Node.js가 준비된 환경에서 패키지 루트에서 실행한다.

```sh
node tools/validate.mjs
node tools/balance-math.mjs
```

외부 패키지 설치와 네트워크는 필요하지 않다. `reports/validation.json`과 `reports/balance-math.json`을 출력한다. raw 문서 데이터를 다시 정규화해야 하면 Python 3로 `python3 tools/assemble.py`를 실행한다. 도구가 숫자를 검산할 수 있다는 사실과 원작 값 자체를 실측했다는 주장을 구분한다.

## 7. 성능·운영 기록

CPU 시간은 시뮬레이션 tick과 렌더를 나눠 기록한다. 배속이 높아지면 실제 초당 처리해야 하는 tick이 늘어나므로 1배 결과만으로 4배 목표를 통과시키지 않는다. 저장 직전/직후·네트워크 재분할·대량 작업 예약 등 최악 구간을 함께 측정한다.

실제 플레이 검증은 시작 seed, 명령 로그, 규칙 해시, 시작/종료 저장, 지표 시계열을 보관한다. 플레이가 실패했다면 실패한 목표와 마지막 정상 상태를 기록하고, 임의 자원 주입으로 성공 결과를 대체하지 않는다.

# 08. 조립 UX·학습·미션 개선 설계

> 원작에서 확인한 UX 사실과 IRONWOOD의 다음 구현 제안을 분리한다. 아래 제안은 이번 조사에서 게임에 반영한 기능 목록이 아니다.

## 1. 설계 목표

플레이어가 ‘무슨 부품이 부족한가’뿐 아니라 **왜 원하는 운동이 발생하지 않는가**를 알아낼 수 있어야 한다. 제작 편의성은 클릭 수 감소와 물리 관계 가시화가 함께 개선될 때 효과가 크다. 부품 수를 늘리는 것보다 먼저 입력, 연결, 힘의 방향, 실패 원인을 읽는 흐름을 완성한다.

현재 V4에는 그룹 변형·8칸 설계 저장·일시정지 점검·시험 보고서가 있다. 다음 단계는 이 기능들을 부품별 입력과 명시적인 연결 데이터 위에서 작동시키는 것이다. 기존 기능의 출처는 `dist/main.js`, `dist/editor.js`, `dist/designs.js`, `dist/report.js`이며 정확한 기준 커밋은 [구현 감사](06_IRONWOOD_GAP_ANALYSIS.md)에 기록한다.

## 3. 제작 상태와 커밋 단위

편집 상태는 `inspect`, `place`, `transform`, `connect`, `bind`, `simulate`로 구분한다. 도구 전환은 미확정 작업의 취소/확정을 분명히 처리하고, 미리보기 데이터가 설계 원본에 섞이지 않게 한다.

| 작업 | 미리보기 | 확정 | 취소와 실패 |
|---|---|---|---|
| 일반 부품 배치 | 외형·충돌·후보 연결점 | 유효 클릭 한 번 | 원본 유지 |
| 이동/복사 | 전체 묶음과 예상 연결 | 전체 트랜잭션 한 번 | 부분 적용 금지 |
| 양 끝점 Brace | A 선택 후 B 후보와 길이 표시 | B가 유효하면 생성 | Esc는 A 선택부터 취소 |
| 키 설정 | 혼합값과 적용 가능한 부품 수 | 명시 편집을 완료할 때 | 포커스 이동만으로 값 복사 금지 |
| 모듈 추가 | ID 재매핑·연결 경계·비용 변화 | 승인한 위치에 일괄 삽입 | 기존 설계 불변 |
| 출격 | 연결·간섭·입력 진단 | 검증한 설계 스냅샷으로 시작 | 실행 실패 시 조립 상태 유지 |

모든 편집 트랜잭션은 부품·연결·바인딩·작전·선택 상태에 대한 전후 차이를 갖는다. 한 묶음 작업을 취소할 때 부품만 돌아오고 연결 ID는 새것으로 남는 상황을 방지한다. 실행 전 원본, 실행 중 상태, 보고서 스냅샷은 별도로 보관한다.

## 4. 연결점 중심 조립

### 4.1 보여줄 정보

고정측과 가동측을 서로 다른 기호로 표시한다. 후보 접점에는 포트 방향, 연결 종류, 가동축을 표시하고, 외형이 접촉했지만 허용 포트가 없으면 구체적 이유를 제공한다. ‘연결 실패’라는 단일 문구는 피한다.

| 진단 코드 제안 | 사용자에게 보여줄 내용 | 수정 행동 |
|---|---|---|
| `PORT_MISMATCH` | 이 면에는 맞는 연결점이 없음 | 부품 회전 또는 다른 포트 선택 |
| `ENDPOINT_MISSING` | 보강대의 다른 끝점이 필요함 | 두 번째 지점 지정 |
| `RIGID_BYPASS` | 고정 연결이 관절의 운동을 막음 | 가동부를 가로지르는 연결 제거 |
| `INITIAL_OVERLAP` | 시작 위치에서 충돌체가 겹침 | 위치·간격 수정 |
| `INPUT_UNBOUND` | 작동기를 조작할 입력이 없음 | 버튼/채널 지정 |
| `ACTUATOR_STALLED` | 출력 상한에서 목표 이동이 막힘 | 하중·기구·출력 검토 |

`RIGID_BYPASS`는 경고이며 모든 상황에서 자동 삭제하지 않는다. 플레이어가 의도한 잠금 구조일 수 있다. 구조적으로 불가능한 참조나 NaN처럼 실행을 망가뜨리는 데이터만 강제 차단한다.

### 4.2 조립 허용과 출격 허용

연결되지 않은 임시 부품은 편집·저장을 허용한다. 출격 시에는 선택한 플레이 규칙에 따라 판정한다. 기존 캠페인은 코어 연결 규칙을 유지하고, 물리 제작 프로필에서는 복수 분리 기체를 허용할 수 있다. 이 선택을 전역 코어 검사 하나에 숨기지 않고 `controlPolicy`와 `objectivePolicy`로 표현한다.

## 5. 부품별 입력과 다중 설정

각 작동기는 `drive`, `steer`, `extend`, `retract`, `fire`, `release` 등의 포트를 제공한다. 입력은 키 코드가 아니라 먼저 의미 있는 채널로 정규화한다. 키보드와 모바일 버튼은 같은 채널을 발생시키며, 센서·논리도 같은 경로를 사용한다.

| 입력 의미 | 권장 동작 | 예 |
|---|---|---|
| hold | 누르는 동안 활성, 해제 시 중립 | 바퀴 구동, 피스톤 수동 이동 |
| press | 눌림 전환의 상승 edge에서 한 번 발생 | 대포 발사, 분리 |
| toggle | 눌림마다 상태 반전 | 지속 회전, 자동 운전 |
| axis | 정규화된 연속값 | 조향 목표, 추력 |

두 대포에 서로 다른 발사 채널을 지정했을 때 한쪽만 발사되는 것이 첫 수용 기준이다. 반대로 동일 채널을 여러 작동기에 연결하는 것은 허용한다. 다중 선택의 공통 입력란을 바꿨을 때 해당 기능이 있는 부품에만 적용하고 적용/제외 개수를 표시한다.

혼합값은 숫자 0으로 표현하지 않는다. 예를 들어 피스톤 행정이 1m·1.5m이면 ‘여러 값’으로 표시하고, 사용자가 1.2m를 입력한 경우에만 일괄 변경한다. 마지막 선택은 표시 기준이지 자동 덮어쓰기 명령이 아니다. 허용 범위가 다른 부품을 선택하면 공통 구간을 표시하거나 부품별로 거부 이유를 보여준다. 조용한 임의 clamp는 피한다.

## 6. 모듈 저장·추가 로드

모듈에는 내부 부품과 연결, 바인딩, 외부로 노출할 포트를 저장한다. 전체 기체와 구분되는 `kind: module`을 사용하고, 기존 기체에 삽입할 때 모든 instance ID·connection ID를 새로 할당한다. 원본 ID는 이력용으로만 남긴다.

동일 채널명이 있는 경우 기본은 모듈 이름으로 범위를 분리한다. 사용자가 ‘기존 채널에 연결’을 선택하면 병합한다. 내부 연결만 복제하고 외부 연결은 노출 포트로 남긴다. 회전·대칭 후 방향 벡터와 입력 극성은 기구 유형별 규칙으로 변환한다. 카메라·포트·연료망까지 단순 이름 치환으로 처리하지 않는다.

첫 제공 모듈 제안은 조향 차축, 현가 바퀴, 두 포탑, 승강 집게, 꼬리날개, 수중 추진기다. 완성형 정답 설계만 제공하기보다 작동 원리가 보이는 최소 구성과 고장 예제를 짝으로 제공한다.

## 7. 시험과 재설계 연결

시험 화면에서 ‘입력 있음 → 출력 발생 → 구속/접촉 반응 → 운동’ 네 단계를 확인할 수 있게 한다. 피스톤이 정지한 이유가 미바인딩, 전원/제어 끊김, 끝단 도달, 과적, 관절 우회 중 무엇인지 분리한다. 다만 추정 원인은 확정 판정과 다르게 표시한다.

보고서에는 최초 사건뿐 아니라 설계 hash, physics profile, 입력 채널, 당시 힘/속도/잔량과 단위, 표본 주기를 함께 저장한다. 정기 샘플링만으로 충돌 최고값을 보장하지 않으므로 파단 직전 이벤트에는 별도 스냅샷을 남긴다. 재설계 화면의 강조는 원본 설계 hash가 맞을 때만 적용한다.

## 8. 조종 정책

V4의 직접 코어 제어 토크는 입문용 조종을 돕지만 조립한 조종면의 효과와 혼동될 수 있다. 다음 프로필을 명확히 분리한다.

| 프로필 제안 | 조종 명령 처리 | 기록 |
|---|---|---|
| `legacy_assisted` | 현재 거동과 코어 직접 토크를 보존 | 기존 기록 namespace 유지 |
| `assisted` | 목표 자세·속도를 실제 작동기의 제한 안에서 명령으로 변환 | 보조 명령·실제 출력을 기록 |
| `physical` | 설치한 작동기·조종면에 직접 명령, 숨은 코어 제어 토크 없음 | 프로필별 별도 기록 |

자세 보조 OFF의 의미를 문서와 코드에서 일치시킨다. OFF에서도 직접 회전 토크가 남는다면 이를 물리 전용 모드라고 부르지 않는다. 기존 비행기·배 프리셋은 해당 프로필과 함께 불러오고, 새 프로필 전환 시 필요한 조종 장치 추가를 안내한다.

## 9. 미션 목표 그래프

기존 표적 전부 파괴와 관문 순서 통과에 더해 회수, 운반, 작동, 제한 조건을 조합한다. 이것은 원작 레벨을 복제한 목록이 아니라 제작 선택을 늘리기 위한 독립 과제 설계다. 원작의 전체 맵·적 배치·스크립트는 확보하지 않았다.

`ObjectiveNode`는 상태(`inactive/active/completed/failed`), 선행 목표, 대상 집합, 조건, 누적값, 완료 시각을 가진다. 판정은 고정 물리 스텝 종료 후 사건을 모아 한 번 실행한다. 한번 완료한 목표가 늦게 도착한 충돌 이벤트로 중복 점수를 얻지 않게 `eventId`를 중복 제거한다.

| 목표 유형 | 판정 데이터 | 경계 조건 |
|---|---|---|
| destroy | 대상 ID 집합의 파괴 사건 | 같은 대상 중복 처리 금지 |
| reach | 지정 프레임의 영역/관문 통과 | 고속 swept 통과, 방향·순서 |
| deliver | 화물 ID가 지정 영역에 머문 시간 | 화물과 기체를 구분, 이탈 시 누적 정책 명시 |
| actuate | 레버·밸브의 실제 상태 | 화면 애니메이션으로 판정하지 않음 |
| preserve | 보호 대상 생존/손상 한도 | 승패 동시 발생 우선순위 고정 |
| budget | 설계 비용 또는 제한 부품 | 기록용 weighted score와 별개 |

관문은 전역 Z 평면에 종속시키지 않고 `position + orientation + shape + crossingDirection`을 가진다. 되돌아오는 경로, 경사·원형 항로에서도 동일 판정기를 사용할 수 있어야 한다.

정답 부품 조합을 강제하지 않는다. 과제에서 요구하는 결과와 금지 조건만 지정하고, 대체 해법은 허용한다. 튜토리얼이 원리를 보여주는 단계에서는 추천 부품을 표시하되 자유 제작에서는 숨길 수 있게 한다.

## 11. 평가와 기록

시간, 피해, 구조 비용을 각각 저장하고 종합 순위를 임의 가중합으로 먼저 합치지 않는다. 현재 V4 별 시스템은 유지 가능한 별도 규칙이다. 새 기록은 `missionRevision + physicsProfile + assistPolicy + designProvenance`에 묶는다. 프리셋·외부 가져오기·수정한 모듈을 기록에 남기되 개인 플레이를 금지하지 않는다. 온라인 리더보드는 이번 범위 밖이다.

시간은 시뮬레이션 시간을 기본으로 하고 사용자 체감용 실제 시간은 별도로 저장한다. 느린 기기에서 시간 배율이 바뀌어도 두 시계가 혼합되지 않아야 한다. 규칙 변경 전 기록을 새 프로필 최단 기록으로 자동 가져오지 않는다.

## 12. 모바일 및 접근성 수용 기준

터치에서는 다중 선택, 끝점 선택, 취소·확정, 카메라 회전이 같은 제스처에 겹치지 않아야 한다. 길게 누르기만을 유일한 기능 진입으로 쓰지 않고 화면 버튼도 제공한다. 연결 상태는 색뿐 아니라 기호와 텍스트로 구분한다.

세로 좁은 화면에서는 팔레트·상세 설정을 접을 수 있게 하고 출격/정지/조립 복귀는 항상 접근 가능하게 한다. 입력 캡처 중에는 게임 조작을 중지한다. 메뉴를 닫을 때 이전 키의 눌림 상태를 복원하지 않고 실제 입력 상태에서 다시 시작한다.

화면 해상도별 배치 검증, 실제 포인터·터치, WebGL 복구는 CPU 데이터 검사와 별도 게이트다. 이전 V4의 브라우저 QA 제약이 있으므로, 새 UI 완료 판정에 실제 화면 확인을 명시적으로 포함한다.

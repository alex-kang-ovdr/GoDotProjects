# 11. 공개 데이터 후보와 실제 복원 절차

## 1. 복원의 범위

이번 조사에서는 개발사 문서의 기능과 공개값을 원장으로 복원했고, 현재 웹 게임의 정의를 코드 스냅샷으로 분리했다. 정확한 원작의 질량·관성·콜라이더·내구도·접점·솔버 값은 설치본 또는 버전이 고정된 직접 관측 자료 없이는 채울 수 없다.

진행할 수 있는 다음 작업을 구체화하기 위해 공개 연구 도구의 **기하 후보 8행**, 원본 XML을 변형하지 않는 검사 도구, 측정 계획을 제공한다. 이들은 검증할 후보를 찾는 수단이다.

## 2. BesiegeField의 활용과 한계

[BesiegeField 연구 프로젝트](https://besiegefield.github.io/)는 부품 조합·시뮬레이션·과제 평가를 다루고 공개 코드와 데모를 연결한다. 연결된 MachineGenerator의 [기하 JSON](https://huggingface.co/spaces/Godheritage/BesiegeField-MachineGenerator/blob/main/Besiege_blocks_markov.json)에는 유형 키와 `bbox_size` 등의 데이터가 있다.

본 패키지의 [후보 표](../data/public_geometry_candidates.json)는 8개 항목의 외접 크기만 짧게 기록한다. `source_type_key`는 원문 키이며 `original_block_id`와 다르다. Starting Block과 작은 목재의 상자가 같더라도 기준점과 접점이 같다고 결론 내릴 수 없다. 피스톤의 확장·수축 변형 키도 개별 원작 블록 ID라고 가정하지 않는다.

**bbox는 충돌체가 아니다.** 렌더링 외형, 배치 허용 범위, collider, 부착점, 질량중심은 다를 수 있다. 연구 도구가 사용한 근사값을 게임용 실제 형상으로 자동 변환하지 않는다. 이 후보 표에는 질량을 추가하지 않았으며, 원문에 나온 생성 지시문·AI 프롬프트를 게임 규칙의 검증 근거로 사용하지 않았다.

## 3. 확보해야 하는 최소 자료

| 자료 | 알 수 있는 것 | 이것만으로 모르는 것 |
|---|---|---|
| 실행판 버전·changeset 화면 | 비교할 빌드 | 각 파트의 내부 상수 |
| 기본 부품 하나씩 배치한 저장 | 유형 식별·저장된 변환·명시 설정 | 저장되지 않는 기본값·실행 중 solver |
| 동일 부품의 설정 변경 전후 저장 | 어떤 필드가 변경되는지 | 그 값과 물리 출력의 비례 관계 |
| 툴팁·매퍼 화면 | 표시 이름·범위·UI 단위 | 실제 힘 제한·동역학 |
| 대조 실험 영상/로그 | 관측 운동·파손·입력 반응 | 직접 관측하지 않은 내부 알고리즘 |
| 원본/새로 배치/다시 저장한 동일 기체 | 저장 호환 차이 | 모든 역사 버전의 변화 |

자료는 사용자가 보유한 설치본·설계에서 얻을 수 있는 범위로 수집한다. 공개 자료의 조사와 원작 파일 추출을 같은 완료 상태로 표시하지 않는다. 현재 작업에서 설치본이나 사용자 저장 파일을 새로 확보했다고 주장하지 않는다.

## 4. 저장 비교를 통한 매퍼 복원

최소 기체를 만든 뒤 한 번에 한 설정만 바꾼다. 원본과 변경본의 파일 hash·빌드·부품 GUID를 기록한다. XML의 태그 순서나 UI 표시문구를 비교 키로 쓰지 않고, 같은 부품 GUID와 경로를 기준으로 변경 필드를 비교한다.

슬라이더를 최소·기본·최대로 저장하면 표시 범위와 직렬화값의 관계를 확인할 수 있다. 0.5 표시가 파일에 0.5로 저장된다고 미리 가정하지 않는다. 저장 당시 생략된 기본값은 explicit null과 구분한다. 새 기체를 다시 만들었을 때도 같은 결과가 나오는지 확인한다.

자동 실행이나 메모리 변경 없이도 저장 전후 비교로 조사할 수 있는 범위부터 시작한다. 파일에 없는 질량·마찰·파단력은 저장 파일 분석만으로 만들어내지 않는다.

## 5. 검사 도구

[inspect_bsg.py](../scripts/inspect_bsg.py)는 XML로 읽을 수 있는 파일의 태그·속성·말단 값·hash를 JSON으로 보고한다. 게임 실행, 파일 수정, 온라인 업로드, 원작 수치 자동 추정은 하지 않는다. 실제 게임 저장 파일이 제공되지 않았으므로 특정 Besiege 빌드와의 호환성이 확인된 importer가 아니다.

```bash
python scripts/inspect_bsg.py path/to/machine.bsg --out machine-inspection.json
```

제공된 `examples/xml_inspection_fixture.xml`은 검사 도구의 작동을 보여주는 합성 XML이다. 원작에서 추출한 저장본이 아니다. 도구는 UTF-8/UTF-16 등 XML 선언을 따르는 입력을 parser로 읽고, DTD·entity를 포함하거나 크기 제한을 넘는 입력은 처리하지 않는다. 출력도 기본적으로 기존 파일을 덮어쓰지 않는다.

검사 결과의 `block_like_elements`는 이름이 Block인 요소의 계수이며 실제 원작 부품 수라는 확정값이 아니다. XML schema가 다르면 블록 역할을 별도로 mapping해야 한다. `truncated=true`이면 표시 목록의 상한에 도달한 것이므로 전체 데이터를 다 추출했다고 해석하지 않는다.

## 6. 원작 측정과 독립 구현 보정

원작에서 측정한 운동과 현재 웹 엔진의 출력은 직접 상수를 복사하기보다 관측 목표로 비교한다. 예를 들어 상승 부하의 한계·확장 속도·중립 반응·파단 시점은 서로 다른 관측값이다. 힘 제한 하나를 맞췄다고 전체 피스톤이 원작과 같아지지 않는다.

허용 오차는 미리 정한 실험 목적과 측정 해상도에서 나온다. 원작 관측 오차, 독립 solver 오차, 입력/영상 시간 오차를 분리한다. 한 번의 실행에서 목표에 도달한 결과를 반복성이나 안정성의 증거로 확대하지 않는다. 반복 횟수·대조 조건·실패 사례를 [계측 프로토콜](09_MEASUREMENT_PROTOCOL.md)에 따라 기록한다.

## 7. 복원 완료의 단계

| 단계 | 완료 조건 |
|---|---|
| 이름 복원 | 식별 가능한 부품명과 출처 존재 |
| 기능 복원 | 입력·출력·연결·환경 반응의 문헌 또는 직접 관측 근거 |
| 설정 복원 | 범위·기본값·저장 의미·버전 경계 확인 |
| 물리 보정 | 대조 실험에서 관측 결과의 반복성과 오차 확인 |
| 구현 이행 | 기존 설계 보존·새 프로필 적용·상태 전환 검증 |
| 사용자 완료 | 실제 브라우저 화면·조작·성능을 확인 |

각 단계는 독립적으로 표시한다. 카탈로그가 많아졌다는 이유로 물리 보정이나 사용자 검증이 완료되지 않는다. R2의 가치는 다음 조사와 구현이 같은 불확실성을 반복해서 추측하지 않도록 만드는 데 있다.

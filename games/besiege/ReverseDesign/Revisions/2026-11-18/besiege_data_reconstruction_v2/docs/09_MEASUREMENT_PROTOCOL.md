# 09. 원작 수치 복원을 위한 계측 프로토콜

> 2026-11-18. **이 문서는 실행 계획이며 결과 보고서가 아니다.** 동봉된 40개 실험은 모두 `target=original_game`, `status=not_run`, `result=null`이다. IRONWOOD 자동 테스트·CPU 검사·프리셋 완주 수치를 원작 측정치로 재사용하지 않는다.

## 1. 복원 데이터의 세 층

| 층 | 얻는 내용 | 현재 상태 | 올바른 이름 |
|---|---|---|---|
| 공개 문헌 | 기능 존재, 발표 수치, 변경 시점 | 재조사 완료 범위에 출처 있음 | 문헌 확인값 |
| 원작 블랙박스 실험 | UI 설정, 실제 운동, 이벤트 시점 | 이 묶음에서는 미실행 | 측정값 |
| 독립 구현 튜닝 | 게임 목적에 맞춘 힘·제한·보조 | IRONWOOD 소스에 있음 | 설계값 |

세 층은 숫자가 같아도 하나로 합치지 않는다. `120N`이 웹 피스톤에서 검증됐다는 사실은 원작 피스톤의 힘을 알려 주지 않는다. 공개 도구가 표시한 연결 strength 숫자도 단위 교정 없이 N 또는 Pa가 되지 않는다. Colliderscope의 색 범위와 연결 관측은 계측 실마리이며 공식 현행 수치표가 아니다. [PHY-013](https://steamcommunity.com/sharedfiles/filedetails/?id=1865492589)

## 3. 단위와 오차

### 3.1 단위 보존

원작 UI에 출력 `1x`, 길이 `unit`, 질량 `mass`가 표시되면 우선 그대로 기록한다. 게임 격자 한 칸을 자동으로 1m, 질량 한 단위를 1kg으로 해석하지 않는다. 원작 내부 파라미터·화면 표시·게임 월드 좌표의 단위가 같은지도 확인한다.

SI 변환을 하려면 길이·시간·질량의 독립 교정 근거와 변환식을 별도 레코드로 남긴다. 그전에는 `normalizedForce`, `loadRatio`, `gridUnit/s` 같은 실제로 측정한 양을 사용한다. 상대 비교만 필요한 구동력 시험은 기준 하중에 대한 비율로도 유용하다.

### 3.2 시간과 샘플

녹화 프레임은 관측 간격이며 원작 물리 스텝이 아니다. 시간배율0.5에서 벽시계2초가 게임시간1초인지 먼저 확인한다. 고정 단계 입력이 불가능한 수동 실험은 시작/종료 오차 범위를 기록한다. 최소 두 관측 수단이 있으면 게임 타이머와 영상 타임코드를 비교한다.

긴 구간의 위치 차이로 평균 속도를 얻는 방식은 빠른 충돌 최고속도를 놓칠 수 있다. `peak_sampled`와 `peak_continuous`를 구분한다. 후자는 실제 전 단계 데이터가 없으면 null이다.

### 3.3 반복과 구간 추정

초기 탐색은 조건당3회, 최종 파라미터 채택은 경계 근처 조건당5회 이상을 권장한다. 이 횟수는 연구 프로토콜 제안이며 실행한 횟수가 아니다. 평균뿐 아니라 범위·중앙값·이상치를 보존한다.

파단 임계값은 한 점보다 구간으로 기록한다. 예를 들어 설정 A에서5회 모두 생존하고 바로 다음 하중B에서 파단이 관측되면 최초 결과는 `[A,B]`의 경계 구간이다. 부품 HP 파괴가 먼저 발생한 시행을 연결 파단력 추정에 섞지 않는다.

## 4. 공통 시행 절차

1. 원본 fixture를 읽고 사본으로 실행한다. fixture 해시·메타데이터를 먼저 기록한다.
2. 입력 없는 정착 구간을 둔다. 접속 실패나 초기 침투가 있으면 작동 실험과 구분하여 종료한다.
3. 독립변수를 하나 바꾼다. 하중과 출력, 각도와 속도를 동시에 바꾸지 않는다.
4. 미리 정한 입력 파형을 적용하고 관측을 저장한다.
5. 최초 파단·발사·결합·연료0·목표 도달 시각을 같은 시간축에 표시한다.
6. 원래 fixture로 완전히 초기화한 뒤 반복한다.
7. 가설과 다른 결과를 삭제하지 않고 원인 후보·추가 실험으로 남긴다.
8. 다른 fixture나 다른 빌드에 재현될 때 적용 범위를 확장한다.

물리 계수의 역추정은 모델 식별 문제다. 같은 상승 높이를 서로 다른 모터 상한·속도 설정·지지 마찰로 만들 수 있으므로 한 관측량만 맞췄다고 원작 계수를 복원했다고 선언하지 않는다.

## 6. 우선 실행할 최소 묶음

### A. 연결과 조작 범위

EXP-001~007을 먼저 수행한다. 포트 대상과 코어 분리 입력이 확정되지 않은 상태에서 부품을 대량 추가하면 모든 기체의 구조·제어 의미가 흔들린다. X+·배치 순서 가설은 EXP-002/003에서 실제 월드 회전과 함께 비교한다.

첫 연결 도구는 원작 화면만 관측하는 방식으로 시작한다. 필요하면 별도의 진단 도구 시행을 추가하되 모드 없는 시행과 섞지 않는다. 연결 시각화의 존재가 곧 렌더 메시와 동일한 충돌체를 뜻하지 않는다.

### B. 피스톤 모델 식별

EXP-008~011은 네 질문을 나눈다. 얼마나 움직이는가, 어떤 하중에서 멈추는가, 입력을 놓으면 무엇을 하는가, 지지가 끊기면 무엇이 남는가. 같은 결과를 얻기 위해 서로 다른 구속 모델을 무분별하게 튜닝하지 않도록 위 네 관측을 동시에 비교한다.

현재 IRONWOOD의 유한 힘/중립 hold는 비교 대상 구현이다. 원작이 같은 법칙을 쓰는지는 이 계획의 결과가 나온 뒤 판단한다. 정지한 피스톤은 모터 포화·기계 끝단·간섭·파단 중 어느 원인인지 별도로 확인한다.

### C. 추진·부력 대응

EXP-020/021은 Propeller·Flying Block·회전 구동원의 역할을 분리한다. EXP-023/025는 전용 부유체뿐인 모델과 객체별 부력 모델, 밀폐 선체 가설을 구분한다. 수면 위 외형이 같아도 잠긴 부품·질량 배치가 다르면 대조군이 아니다.

### D. 시간·자원 계약

EXP-029/030/036/037은 입력 파형·발사·신호의 시간을 확인한다. 이후 EXP-033~035에서 연료망과 공급 부족을 추가한다. 프레임률을 바꾸었는데 다른 결과가 나왔다면 관측 간격과 게임시간 차이부터 배제한다.

## 7. 원시 결과 기록 예시

다음은 **미실행 템플릿**이다. 숫자를 채운 예시 결과로 읽지 않는다.

```json
{
  "experiment_id": "EXP-009",
  "target": "original_game",
  "status": "not_run",
  "game_build": null,
  "save_origin_build": null,
  "fixture_hash": null,
  "trial_index": null,
  "independent_values": null,
  "units": {"length": "uncalibrated_game_unit", "mass": "uncalibrated_game_mass"},
  "samples": [],
  "events": [],
  "result": null,
  "uncertainty": null,
  "capture_paths": []
}
```

확정 레코드로 승격할 때에는 `measurement_id`, 실험 ID, 관측 원본 경로, 결과구간, 빌드, 작성자를 연결한다. 수동으로 보고 들은 값을 문헌 확인값으로 바꾸지 않는다. 숫자를 모르면0으로 채우지 않는다.

## 8. 독립 구현의 회귀 검사와 비교하는 방법

IRONWOOD는 동일한 목표 질문에 대해 별도의 테스트 ID를 만든다. 예를 들어 원작 EXP-009와 독립 구현의 피스톤 과적 테스트는 서로 대응하지만 동일 실험이 아니다. 테스트에서 상태를 강제로 바꿔 만든 파손 fixture는 자연 주행 검증과 분리한다.

비교 표는 `원작 문헌값 / 원작 측정값 / 독립 설정값 / 독립 측정값` 네 칸으로 유지한다. 원작 값이 null이면 독립 구현이 잘 동작해도 복원 일치율을 계산하지 않는다. 알려진 시나리오에서의 기능 일치와 알려지지 않은 내부 계수 일치를 분리한다.

## 9. 데이터 채택 기준

- 출처와 버전 범위가 연결돼 있다.
- 사용한 단위와 교정 상태가 명시돼 있다.
- 원시 관측 자료를 다시 읽을 수 있다.
- 독립변수 외의 차이를 설명할 수 있다.
- 최소 대조군과 반복 결과가 있다.
- 다른 설명 가능성을 남기거나 추가 실험으로 배제했다.
- 이전 값과 충돌하면 새 버전으로 추가하고 기존 근거를 보존한다.
- 실험을 실행하지 않았으면 결과·성공률·성능 숫자는 비워 둔다.

이 기준은 분석 데이터의 품질 기준이다. 원작의 버그나 복잡한 거동을 재현해야 할 제품 요구사항과는 별개이며, 어떤 규칙을 의도적으로 단순화할지는 시스템 개선 기획에서 결정한다.

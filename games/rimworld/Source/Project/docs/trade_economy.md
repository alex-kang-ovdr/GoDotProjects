# 교역과 물품 경제

이 문서는 `변방의 기록` v4의 실제 구현 규칙을 기록한다. 게임 안의 시간은 시뮬레이션 초이며, 모든 가격과 이동·방문 수치는 이 프로젝트의 독자적인 균형 값이다.

구현 근거는 [trade.js](../dist/trade.js), [economy-data.js](../dist/economy-data.js), [colony-systems.js](../dist/colony-systems.js), [engine.js](../dist/engine.js), [renderer.js](../dist/renderer.js)다. 제작과 장착 작업의 전체 절차는 별도 제작·장비 문서와 [v4 계약](v4_contract.md)을 함께 참고한다.

## 1. 자원과 소유권

기존 목재·강철·식재료·식사·약품에 은화 `silver`, 개량 소총 `rifle`, 방탄 조끼 `armor`, 작업 도구 `tool`을 추가한다. 새 게임은 은화 60개와 장비 재고 0개로 시작한다. v1·v2·v3 저장을 가져오면 새 자원 네 종류는 모두 0으로 시작하며, 기존 자원·지도·작업·난수·시계는 유지한다.

새 자원도 기존 바닥 물품, 운반, 창고 입출고 경로를 사용한다. 은화와 장비는 부패하지 않으며 식량 배치 장부에는 넣지 않는다. `colony-systems.js`의 허용 자원은 공용 `EXTRA_RESOURCE_LABELS`에서 가져오므로 엔진과 같은 ID를 사용한다.

| 보관 상태 | 교역에서 사용 가능한가? |
|---|---|
| 창고 `state.resources`의 은화 | 구매 대금으로 사용할 수 있다. |
| 창고의 판매 가능 물품 | 판매할 수 있다. |
| 바닥에 떨어진 물품·은화 | 운반해 입고하기 전에는 판매·구매 대금으로 사용할 수 없다. |
| 주민이 운반 중인 물품 | 거래 대상으로 계산하지 않는다. |
| 주민이 장착한 장비 | 판매하지 않는다. 해제·입고한 뒤 판매할 수 있다. |
| 건설에 선지급한 재료, 제작에 이미 전달한 재료 | 창고에서 빠진 물품이므로 거래에서 다시 사용하지 않는다. |

은화는 한 번에 최대 **100개**, 그 외 자원은 기존처럼 최대 **12개**를 운반한다. 판매 대금이 많으면 여러 번 나눠 운반할 수 있다. 거래는 주민의 기존 작업이나 소지품을 강제로 빼앗지 않는다.

## 2. 상인 방문과 이동

| 항목 | 구현 값 |
|---|---:|
| 새 게임 첫 방문 예정 | 80초 |
| 이전 저장 이동 후 첫 방문 예정 | 현재 시각 + 80초 |
| 실제 도착 후 체류 시간 | 100초 |
| 퇴장 완료 후 다음 방문 | 현재 시각 + 220초 |
| 방문 예정 때 습격 중이거나 유효 경로 없음 | 현재 시각 + 30초로 연기 |
| 이동 속도 | 1.8칸/초 |
| 막힌 경로 재탐색 간격 | 2초 |
| 연속 경로 막힘 허용 | 단계당 12초 |
| 도착·퇴장 이동 단계의 최대 시간 | 각각 120초 |

상인은 지도 동쪽 가장자리에서 출발한다. 씨앗과 다음 방문 횟수의 순수 해시로 선호 진입 행과 이름을 정한다. 재고와 가격은 고정되어 있으며 엔진의 `_rand()`를 호출하지 않는다. 상인 등장으로 기존 전투·환경의 난수 상태를 소비하지 않는다.

만남 지점은 안전한 창고 칸들의 평균 위치를 기준으로 고른다. 평균보다 동쪽 8칸인 위치에 가까운 후보를 우선하고, 창고 평균과 맨해튼 거리 4~14칸 범위의 지붕·건물·자원 개체·작물·구역이 없는 타일을 찾는다. 동쪽 진입점과 창고, 만남 지점이 모두 같은 안전한 연결 성분에 있어야 한다. 기본 지도에서는 기지 동쪽의 열린 공간이 우선된다. 지형이나 건축 상태가 다르면 다른 유효 후보를 선택한다.

이동은 상·우·하·좌 BFS 경로로 진행한다. 완성 벽, 물, 화력이 조금이라도 있는 칸은 통과하지 않는다. 문은 통과할 수 있다. 안전 경로가 없어도 불을 가로지르는 주민용 우회 규칙은 상인에게 적용하지 않는다.

방문자는 `arriving → trading → leaving` 순서로 진행한다. 습격이 시작되거나 만남 지점에 불·건물이 생겨 안전하지 않으면 거래를 즉시 중단하고 퇴장한다. 길이 막히면 2초 간격으로 다시 찾는다. 도착 경로가 12초 연속 막히면 철수로 전환하고, 퇴장 경로까지 12초 막히면 방문자를 회수해 방문을 종료한다. 이동 단계가 120초를 넘는 경우에도 같은 방향으로 정리한다. 이는 영구 봉쇄 때문에 방문자가 저장에 무한히 남지 않도록 한 제한이다.

구매품과 대금은 상인의 퇴장과 별개로 플레이어의 바닥 물품으로 남는다. 다음 방문은 새 상인 재고와 은화로 시작하며, 이는 지도 밖 시장에서 들어오는 공급이다.

## 3. 재고와 가격

가격은 **플레이어 관점**이다. `buy`는 플레이어가 지불하는 개당 은화, `sell`은 플레이어가 받는 개당 은화다. 방문 시작 시 상인의 은화는 **180개**다.

| 품목 | 시작 재고 | 구매가 | 판매가 |
|---|---:|---:|---:|
| 목재 | 30 | 2 | 1 |
| 강철 | 24 | 5 | 3 |
| 식재료 | 16 | 3 | 판매 불가 |
| 식사 | 10 | 8 | 판매 불가 |
| 약품 | 6 | 18 | 10 |
| 작업 도구 | 2 | 55 | 34 |
| 방탄 조끼 | 2 | 80 | 55 |
| 개량 소총 | 2 | 100 | 72 |

판매한 비식품은 상인의 재고에 실제로 추가된다. 상인에게 구매 대금으로 지급한 은화는 상인 잔고에 더해져 추가 매입에 사용할 수 있다. 상인에게 재고나 은화가 없으면 그 거래는 거절된다. 상인 재고와 가격은 UI 조회로 다시 생성되지 않는다.

식재료와 식사는 구매만 가능하다. 구매한 음식은 신선도 1로 배송되며 이후 바닥·운반·창고 위치에 따른 기존 부패 규칙을 따른다. 같은 타일의 기존 음식 묶음과 합쳐지면 `_dropItem`의 규칙대로 **더 낮은 신선도**를 유지한다. 오래된 식량을 판매하고 새 식량으로 되돌려 받는 경로는 없다. 상인 내부 재고의 식품 노화는 별도로 모사하지 않는다.

## 4. 거래 명령과 원자적 검증

```js
game.command('trade', {
  traderId: game.state.trade.visitor.id,
  side: 'buy', // 또는 'sell'
  type: 'medicine',
  count: 2
});
```

수량은 1~100의 정수다. 반환값은 `{ok, message}`이며 실패 사유를 사용자에게 알려준다. 계약·가격 검증부터 배송 준비까지 끝난 뒤 한 번만 재고를 차감한다.

거래 성공 조건은 다음과 같다.

1. 요청한 ID가 현재 방문자의 정확한 ID이며, 방문자가 `trading` 단계다.
2. 게임이 끝나지 않았고 활성 습격이 없으며 체류 종료 시각 전이다. 환경 갱신이 아직 퇴장 단계를 적용하지 않았더라도 종료 시각을 넘은 명령은 거절한다.
3. 방향·품목·정수 수량·가격이 유효하다. 은화 자체를 거래 품목으로 요청할 수 없다.
4. 구매라면 상인 물품과 창고 은화가 충분하다. 판매라면 창고 물품과 상인 은화가 충분하다.
5. 상인 현재 칸은 물·화재·건물에 막히지 않은 배송 위치다.
6. 상인과 안전한 창고 사이에 왕복 경로가 있고, 같은 안전 연결 성분에 거래를 담당할 수 있는 주민이 있다. 해당 주민은 생존·체력 15 이상·비징집 상태이며 운반되는 환자, 환자 운반자, 침상 안정 중인 환자가 아니다.
7. 배송될 물품의 묶음 수량과 전체 바닥 물품 개수가 저장 상한을 넘지 않는다.

경로는 대칭인 격자에서 확인하므로 같은 안전 연결 성분에 있으면 왕복 가능하다. 별도의 협상 작업이나 협상 대기 시간은 두지 않는다. 교환은 명령 시점에 성립하고, 배송 물품을 가져오는 일은 주민의 실제 운반 작업으로 남는다.

### 구매의 상태 변화

개당 가격 `p`, 수량 `q`인 거래는 다음을 한 번 적용한다.

```text
플레이어 창고 은화 -= p × q
상인 은화          += p × q
상인 해당 재고     -= q
상인 위치 바닥에 플레이어 물품 q개 생성
```

구매품은 창고로 자동 입고되지 않는다. 주민이 상인 옆까지 가서 물품을 수령하고 창고에 내려놓아야 건축·제작·장착 등에 사용할 창고 재고가 된다. 기존 음식 작업은 가능한 경우 바닥의 음식도 직접 찾아 먹을 수 있다.

### 판매의 상태 변화

```text
플레이어 창고 물품 -= q
상인 해당 재고     += q
상인 은화          -= p × q
상인 위치 바닥에 플레이어 은화 p × q개 생성
```

창고 은화는 판매 버튼을 누르는 순간 늘어나지 않는다. 운반자가 판매 대금을 창고에 입고해야 다음 구매에 쓸 수 있다. 창고 외 물품을 합산해 판매 수량을 맞추거나, 판매 대금을 아직 받지 않은 상태에서 순환 거래하는 행위는 허용하지 않는다. 매입·매각 가격 차이도 있으므로 동일품의 즉시 왕복 거래로 은화가 늘어나지 않는다.

## 5. 제작과 장비의 경제적 연결

작업대와 제작 주문은 재료를 실제 수령·전달하고 노동 시간을 들여 완성품을 만든다. 완성품은 작업대 바닥에 생긴 뒤 창고로 운반된다. 거래 역시 같은 물품 ID를 사용하므로 구매한 장비와 제작한 장비의 장착 효과는 같다.

| 제작품 | 투입 재료 | 재료를 그대로 팔 때 | 완성품 판매가 | 차이 |
|---|---|---:|---:|---:|
| 작업 도구 | 강철 8 + 목재 4 | 28 | 34 | +6 |
| 방탄 조끼 | 강철 16 | 48 | 55 | +7 |
| 개량 소총 | 강철 18 + 목재 8 | 62 | 72 | +10 |

위 차이는 재료의 **상인 매입가 기준**이며 작업 시간·운반 시간·상인 잔고의 제약을 공제한 수익률은 아니다. 모든 재료를 상인에게 구매해 제작한 뒤 되팔면 도구는 48을 써서 34, 조끼는 80을 써서 55, 소총은 106을 써서 72를 받으므로 즉시 차익을 만들 수 없다. 직접 확보한 재료에 제작 노동을 더해 부가가치를 만들거나, 판매하지 않고 주민의 생존·작업 능력에 투자하는 선택이다.

작업 도구는 지정된 생산 작업 속도 ×1.25, 방탄 조끼는 총탄 피해·총상 출혈 증가량 ×0.65, 개량 소총은 사거리 9칸·피해 ×1.35·명중률 +0.04·징집 사격 간격 1.2초를 제공한다. 장비의 능력은 실제 장착 슬롯을 기준으로 한 번만 적용한다. 장비를 보유하거나 구매했다는 사실만으로 효과가 생기지 않는다.

## 6. API와 저장 스키마

```js
initializeTrade(game, {migration=false}={});
updateTrade(game, dt);
executeTrade(game, payload); // {ok,message}
validateTrade(data, bad);

state.trade = {
  nextVisitAt: 80,
  visits: 0,
  visitor: null,
  stats: {bought: 0, sold: 0, earned: 0, spent: 0}
};
```

통계의 `bought/sold`는 거래한 **물품 개수**이며 거래 횟수가 아니다. `earned/spent`는 받은·지불한 은화의 누적 합이다. 판매 대금을 아직 입고하지 않았어도 정상 배송이 끝나면 `earned`에는 기록된다.

| 방문자 필드 | 의미 |
|---|---|
| `id` | 정확히 `trader_${state.trade.visits}`인 현재 방문 ID |
| `name` | 씨앗·방문 횟수로 정한 상인 표시명 |
| `x,y` | 이미 타일 중심을 나타내는 실수 좌표 |
| `phase` | `arriving`, `trading`, `leaving` |
| `path` | 남은 정수 타일 좌표 배열 |
| `destination` | 현재 단계의 정수 목적 셀 |
| `entry` | 최초 동쪽 지도 진입 셀 |
| `meeting` | 이번 방문의 만남 지점 |
| `arrivedAt/leavesAt` | 실제 도착 시각 / 그 시각 +100. 도착 전에는 둘 다 `null` |
| `nextPathAt` | 막힌 경로를 다시 검색할 수 있는 시각 |
| `blockedTime` | 현재 단계에서 연속으로 움직이지 못한 시간 |
| `travelElapsed` | 현재 이동 단계에서 지난 시간 |
| `stock` | 가격표의 8개 품목별 정수 재고 |
| `silver` | 상인 소유의 정수 은화 잔고 |

`updateTrade`는 엔진의 환경·화재 갱신 뒤 호출한다. 함수는 `state.time`을 직접 증가시키지 않는다. 이동을 최대 0.5초 단위로 나누며, 체류·재방문·재탐색의 기준 시각은 엔진 시각을 사용한다.

일반 초기화는 없는 필드만 채우고 기존 값을 보존한다. **구버전 이동 초기화 `migration:true`는 기존 payload에 교역 필드가 들어 있더라도 이를 승계하지 않는다.** 엔진이 복사한 상태에서 `nextVisitAt=현재 시각+80`, 방문 수 0, 방문자 없음, 통계 0으로 초기화한다. 구버전 저장에 임의로 끼워 넣은 미래 상인이나 교역 수익을 인정하지 않기 위해서다. v4 복원은 이 이동 초기화를 호출하지 않아 현재 방문과 경로를 그대로 보존한다.

## 7. 결정성과 검증

방문자의 이동 경로, 도착·출발·재탐색 시각, 재고, 은화, 통계가 모두 저장된다. 모듈 내부에 저장되지 않는 난수 상태나 벽시계 타이머를 두지 않는다. 방문 ID도 엔진의 새 개체 ID를 소모해서 만들지 않는다. 방문·거래 로그와 실제 배송 물품은 기존 엔진의 ID 경로를 사용한다.

`validateTrade`는 현재 방문 ID, 지도 안 좌표, 단계, 경로의 연속성과 목적지, 도착 전 `null` 시각, 정확한 100초 체류 기간, 8개 재고 키, 정수 잔고·통계를 검증한다. 경로 타일이 지금도 뚫려 있어야 한다고 강제하지는 않는다. 저장 직전에 새 벽이 완성되어 경로가 막히는 것은 정상 상태이며, 복원 후 재탐색이 처리해야 하기 때문이다.

상인 재고·잔고와 바닥 물품 묶음의 상한은 각각 100,000,000이다. 전체 바닥 물품이 10,000개에 도달한 경우 새 묶음을 만들 거래는 거절한다. 교역 통계·시간 상한은 10,000,000,000이다.

주요 검증 항목은 다음과 같다.

- 실제 지도 가장자리 진입·도착·퇴장과 방문 중 습격·화재 대응
- 상인 처리 전후 엔진 RNG의 불변
- 부족·잘못된 입력·기한 만료·이전 방문 ID·접근 불가 거래의 무변경
- 구매·판매 양쪽 재고와 은화 보존, 배송 전 창고 수량 불변
- 판매 대금의 실제 은화 운반, 식품 신선도와 판매 금지
- 상인 이동·우회·회전·교역·배송 운반 중 저장 이후 같은 미래
- 기존 생존·의료·화재·연구·전력·구조선 완주와 구버전 저장 이관

상인 우회·회전 중 실제 v4 엔진 상태 20개를 저장·복원하는 독립 검증에서 즉시 상태와 복원 이후 진행이 일치했다. 렌더러는 작업대·네 새 바닥 물품·소총/조끼/도구·세 단계 상인을 Canvas 대역으로 실행해 숫자 인수와 게임 상태 불변을 확인했다. 실제 브라우저 화면 검증은 별도 접근 가능 여부에 따라 구분한다.

교역 수용 검증은 [trade.test.mjs](../tests/trade.test.mjs), 제작·장비·교역의 연결 시나리오는 [economy-scenario.test.mjs](../tests/economy-scenario.test.mjs)에서 실행한다.

```bash
node --test tests/trade.test.mjs
node --test tests/*.test.mjs
```

## 8. 화면과 범위

작업대는 연구대와 구분되는 바이스·공구가 있는 작업대로, 제작 중에는 작업 상태를 반영한 움직임으로 표시한다. 은화·소총·조끼·도구에는 개별 바닥 아이콘을 사용한다. 장착한 조끼와 도구는 몸통·허리띠에, 소총은 징집 시 길어진 총과 조준경으로, 일상 중에는 등에 멘 모습으로 표시한다.

상인은 별도의 중립 방문자와 손수레로 그린다. 실제 중심 좌표를 사용하며, 거래 중에는 남은 체류 시간을 표시한다. 바닥 배송품은 기존 정수 물품 좌표를 `+0.5`해 그린다. 이러한 표현과 UI 조회는 재고·시간·난수를 바꾸지 않는다.

이번 범위에는 모집, 외교·호감도, 협상 능력, 동적 시세, 장비 품질·내구도·탄약, 상인 전투·약탈·호위 임무를 넣지 않는다. 기본 권총은 기존 전투 능력으로 유지하며 판매 가능한 물품이 아니다. 제작·장비·교역은 기존 핵심 목표를 확장하지만 기존 승리에 새 무역 필수 조건을 추가하지 않는다.

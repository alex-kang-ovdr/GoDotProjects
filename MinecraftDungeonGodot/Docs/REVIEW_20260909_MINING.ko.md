# M04 채굴·도구·물리 드롭 — 첫 구현 루프

## 구현 범위와 아직 남은 M04

실제 게임의 LMB는 즉시 회수가 아니라 누르고 채굴하기로 바뀌었다. 카메라의 6m 복셀 추적, 경도/도구별 누적 시간, 완료 전 진행 HUD, 버튼 해제·대상/지형 변경·도구 교체·커서/생성 패널·로드/생성에 따른 취소를 연결했다. 성공한 완료만 Builder 채굴 횟수와 내구도를 한 번 갱신한다. 물/나뭇잎은 기존 회수 불가 계약을 유지한다. 저장 v3는 도구와 미수거 드롭을 보존한다.

M04 전체 완료는 아니다. 면/수평 방향의 24가지 설치 상태·통나무 방향 렌더/이웃 갱신/저장, 단계별 3D 균열 표현은 다음 구현에 남아 있다. M05 제작/장비 이전의 테스트 가능한 프리뷰이므로 손과 나무·돌·철 곡괭이/도끼/삽 9개가 처음부터 제공되며 선택은 나무 곡괭이로 시작한다. `T` 다음/`Shift+T` 이전으로 선택한다. 이를 제작·획득·성장 시스템이 완성된 것으로 표시하지 않는다.

도구 내구도는 나무 59/돌 131/철 250, 선호 도구 속도는 2/4/6배다. 곡괭이 계열 블록은 사용 가능한 곡괭이가 있어야 수확된다. 수확 가능 시간은 경도×1.5÷속도, 수확 불가 시간은 경도×5다. 소진된 도구는 음수 내구도나 자동 무료 교체 없이 손 성능이 된다. 잘못된 도구로 돌을 부수면 아이템이 나오지 않는다. 블록 ID/9슬롯 의미/생성 v6와 결정론 기본 셀은 변경하지 않았다.

`VoxelWorld.finish_mining()`이 현재 재질·잠금·플레이어 소유권·드롭 수 한도를 검사하고 블록 제거/메시 갱신/드롭 생성/내구도 차감 후 이벤트를 보낸다. `remove_cell_for_inventory()`는 기존 저수준 원자 회수/편집 회귀 fixture로 남아 있지만 실제 플레이어 입력에서는 호출하지 않는다. 기존 직접 함수 테스트만으로 M04를 검증했다고 주장하지 않고 새 테스트는 viewport 누름/해제와 실제 W 이동을 사용한다.

## 물리와 저장 계약

드롭은 0.25m `RigidBody3D` 상자다. 지형 충돌은 유지하되 layer 2를 사용해 layer 1 블록 조준을 가리지 않고 플레이어 몸과는 충돌 예외를 둔다. 회전은 잠그고 중력/감쇠로 바닥에 떨어진다. 0.35초 지연, 플레이어 가까이 1.5m, 지형 차폐 검사와 전체 스택 용량 조건이 맞으면 한 번만 줍는다. 인벤토리가 가득 차면 드롭을 지우지 않는다. 인벤토리 changed 이벤트 전 드롭의 소유권을 제거해 동일 아이템이 양쪽 상태에 중복되지 않도록 한다.

최대 드롭은 2,048개이며 한도에 도달하면 수확 드롭을 만들 채굴을 블록/내구도 변경 전에 거부한다. 이 제한을 무한 규모 지원으로 표현하지 않는다. 제한 월드 바닥 아래 Y=-64 또는 저장 좌표 경계에 가까운 드롭은 삭제 대신 입구 위로 되돌리고 줍기 지연을 다시 준다. 이는 아이템 유실 방지를 위한 프리뷰 정책이며 마인크래프트와 동일한 소멸 정책은 아니다. 로드/생성 중 물리와 줍기를 멈추고 성공한 새 월드 publication에서 이전 드롭을 제거한다.

저장 포맷은 3, 생성 버전은 6이다. 같은 생성 버전의 포맷 2 파일은 기존 편집·플레이어를 읽고 기본 도구/빈 드롭으로 초기화한다. 포맷 3의 도구/드롭 누락·잘못된 선택/정수 내구도·스택/지연·비유한 좌표/속도·과도한 개수는 적용 전 거부한다. v2 런타임은 새 v3 파일을 읽을 수 없고 v5 이하 생성의 저장은 계속 거부된다. 자동 파일 삭제나 사용자 기본 저장 덮어쓰기는 테스트에서 하지 않는다. 기존 경로에 사용자가 직접 새 저장을 하면 v3로 기록되므로 이전 실행기로 돌아갈 필요가 있으면 별도 백업해야 한다.

도구 정수는 JSON 숫자에서 명시적으로 정규화한다. payload stringify에 full_precision을 적용한다. 실제 엔진에서 특정 atan2 카메라 각도는 여전히 약 7×10⁻¹⁸ 라디안의 1 ULP 차이가 관측돼 카메라 각도는 10⁻¹² 라디안 허용 오차로 따로 검사하고, 도구/드롭 fixture의 다른 상태는 정확 비교한다. 모든 물리 부동소수점 상태의 범용 비트 동일성이나 정전 중 파일 원자성을 보장하지 않는다.

## 실패·수정과 검증

`Saved/Verification/mining-dev`에서 초기 실행 이력을 보존한다. 첫 headless 입력 실행은 드롭 배열의 사전 조건 실패 뒤 테스트 자체가 인덱스 오류로 중단돼 소유 프로세스 60초 제한으로 정리됐다. 후속 진단은 실제 headless mouse mode=0, 렌더 mouse mode=2와 동일한 유효 조준 셀을 확인했다. 게임의 캡처 조건을 우회하지 않고 headless는 120개 도구/블록 조합의 수확/시간 240개 검사로 분리했다. 실제 조작/물리/저장은 렌더 실행에서 검사한다.

`render-v1`–`v4`는 카메라 각도의 JSON 반올림 차이를 정확 상태 비교가 검출했다. 내구도 정수 정규화와 payload 정밀도 보강 후 카메라 오차를 필드별로 분리했다. `render-v5`는 292개 단언/실패 0, 수정한 기존 viewport gameplay와 Builder 72개도 통과했다. 실제 첫 진행 PNG를 확인했고 이후 T/Shift+T·드롭 PNG를 추가했다. 임시 고정 위치를 사용하는 상태/저장 fixture와 실제 W로 접근해 줍는 검사를 구분한다.

새 OS 프로세스 재시작 fixture에는 두 모드의 기존 1,000편집/인벤토리/자세에 사용 중/소진 도구, 월드 격자 밖 드롭의 수량·위치·속도·남은 지연을 추가했다. 로드 완료 콜백의 상태를 기록해 이후 물리 진행을 저장 실패로 오인하지 않는다.

첫 전체 실행 `20260909-022243-895`는 실제 동굴 안내 경로 왕복의 180초 제한에서 중단됐다. 세 작은 월드와 185맵 마지막 방 도착까지 이동 기록은 있으나 전체 완료 표식이 없으므로 실패로 보존한다. 초기 49단계 성공 기록과 혼동하지 않는다. 이 실행의 새 두 모드 재시작 저장은 통과했지만 뒤의 M04 렌더 단계/성능 비교는 실행되지 않았다.

가속 경로 테스트의 `_hold()`에 `Input.flush_buffered_events()`를 추가했다. 한 렌더 프레임에 여러 물리 틱을 실행할 때 테스트가 보낸 키 전환을 다음 물리 틱 전에 전달하며 실제 입력/캐릭터 충돌/경로 허용 오차/물리 dt=1/60/180초 제한은 유지한다. [공식 Input 문서](https://docs.godotengine.org/en/stable/classes/class_input.html#class-input-method-flush-buffered-events)는 누적 입력 등으로 버퍼된 이벤트 전달 시점을 명시한다. 별도 `mining-dev/cave-flush.log`는 121개 단언/실패 0, 파일 생성–완료 약 132초로 확인했다. 전환 전달을 통제한 뒤 경로당 물리 틱 수가 줄었지만 최초 지연의 모든 OS/렌더 요인이 규명된 것으로 확대하지 않는다. 이 가속 하네스는 게임 성능 계측에 사용하지 않는다.

`mining-dev/render-v6.log`는 T/Shift+T, 가까운 벽 너머 줍기 거부/벽 제거 후 1회 전달, 낙하 아이템 구조/저장 가능성, 잘못된 도구 선택·필수 드롭 필드·비유한 좌표/속도·지연·최대 개수 거부까지 보강해 334개 단언/실패 0이다. 이 중 헤드리스는 도구×블록 240개+저장값 검증 34개, 총 274개다. 드롭 PNG 검토에서 테스트의 직접 인벤토리 설정이 HUD 변경 신호를 누락한 것을 발견해 fixture에도 changed 신호를 보냈다. 실제 인벤토리 API는 원래 신호를 보낸다. HUD 도움말은 Hold LMB로 명확히 했다. 전체 재실행 결과는 아래 최종 근거에 기록한다.

## 참고와 판정

독립 Godot 구현의 물리/쿼리 설계는 [RigidBody3D](https://docs.godotengine.org/en/4.7/classes/class_rigidbody3d.html), [PhysicsRayQueryParameters3D](https://docs.godotengine.org/en/4.7/classes/class_physicsrayqueryparameters3d.html), 숫자 기록은 [JSON stringify](https://docs.godotengine.org/en/4.7/classes/class_json.html#class-json-method-stringify)를 확인했다. Unreal의 로컬 `Docs/Milestones/M04_COMPLETION.ko.md`에서 취소·내구도·가득 찬 인벤토리·드롭의 조준 방해·영속 누락·실제 입력 우회 사례를 참고했다. 엔진 코드를 복사하거나 Unreal 작업트리를 수정하지 않았다.

수동 코드 검토는 채굴 완료의 재질/잠금/소유권 재검사, 인벤토리 신호 전 드롭 소유권 이전, 미수거 드롭의 저장 검증/복원, 월드 교체 수명과 입력 취소에 집중했다. 검증 최대 개수 거부는 순수 데이터 검사이며 실제 2,048개 물리 아이템의 프레임 비용/스트레스 검사가 아니다. Unreal의 10,000회 아이템 보존 검사에 대응하는 장기 반복도 아직 남아 있다. 테스트 수가 더 많다는 이유만으로 범위 동등성이나 더 높은 품질을 선언하지 않는다.

Unreal은 현행 문서상 M06 완료이며 현재 Godot은 M04 일부를 구현 중이다. 설치 방향과 균열을 포함한 M04 나머지, M05/M06 기능 격차와 기존 16.7ms 반복 지연/시각/동일 조건 비교 게이트가 남아 전체 목표를 완료하지 않는다.

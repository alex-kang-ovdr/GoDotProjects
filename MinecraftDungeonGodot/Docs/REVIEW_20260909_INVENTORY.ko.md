# M05 첫 루프 — 실제 36슬롯·커서·버전형 저장

## 범위와 현재 판정

Unreal `Docs/Milestones/M05_COMPLETION.ko.md`의 전체/절반 이동·병합·교환, 36슬롯/9핫바, 커서 소유권·저장, 배경 클릭과 작은 화면 사례를 참고해 Godot에서 독립 구현했다. 고정 슬롯별 수량 배열을 실제 위치를 바꿀 수 있는 36개 아이템 스택으로 전환하고 게임의 줍기·설치·HUD·저장까지 연결했다. 단독 데이터 모형이나 표시 칸만 추가한 구현이 아니다.

**M05 전체 완료는 아니다.** 이번 아이템 ID는 공유 블록/드롭 0–8만 지원한다. 4장비 슬롯, 재료/도구 아이템 레지스트리, 제작, 상자, 화로는 다음 구현이며 기존 9도구 프리뷰는 별도 `MiningTools`에 남아 있다. 이를 제작·획득·성장 완료로 세지 않는다. Unreal 재조회는 여전히 M06 완료/M07 후속·렌더 `20260909-022624-403`/Automation 42개/상위 62회 실패 0을 보고하며 이번 작업에서 Unreal을 실행하거나 수정하지 않았다. 전체 우위 목표는 계속 active다.

## 실제 게임 계약

- `BlockInventory`는 아이템 ID와 슬롯 위치를 분리한다. 초기 0–8번 슬롯에 해당 블록 8개, 9–35번에는 빈 스택을 두고 0–8번만 핫바로 선택한다. ID 0–8과 기존 블록 의미는 유지한다. 빈 스택은 정확히 `[-1,0]`이며 모든 스택은 최대 64개다.
- `add(item, amount)`는 같은 아이템의 기존 스택부터 채우고 남으면 번호가 낮은 빈 슬롯을 쓴다. 전체 수량이 들어갈 때만 변경/알림을 수행한다. 부분 용량밖에 없으면 물리 드롭 전체를 남기는 정책이며 부분 줍기는 아직 없다. 커서는 자동 줍기 용량에 포함하지 않는다.
- `consume(slot, amount)`는 지정 슬롯의 수량을 소비하고 빈 아이템 ID를 정리한다. 설치는 소비 전에 해당 슬롯의 실제 아이템을 조회한다. 1번 슬롯으로 옮긴 통나무가 조약돌이 되는 고정 매핑 오류를 실제 RMB로 검사한다. 물리 드롭의 저장 필드 `slot`은 역사적으로 안정 아이템 ID를 뜻하며 현재 가방 위치가 아니다.
- 왼쪽 클릭/Enter는 전체 집기·병합·교환, 오른쪽 클릭/Shift+Enter는 올림한 절반 집기/한 개 놓기다. 다른 종류 위의 오른쪽 클릭과 가득 찬 스택의 병합은 무변경이다. 모든 슬롯과 커서 소유권을 먼저 완료한 뒤 `changed`를 한 번 보낸다. 커서를 들고 패널을 닫아도 버리지 않으며 그대로 저장한다.
- E로 열고 E/Escape로 닫으며 방향키로 독립 선택한다. 배경 클릭은 스택을 버리거나 월드를 채굴하지 않는다. 이동/중력과 채굴을 정지하고 생성 패널과 중첩하지 않는다. 패널 내부 Ctrl+8/9 저장·복원을 지원하며 로드 중 스택 조작을 거부한다. 새 월드 생성은 전체 가방·커서를 초기화한다.
- 기존 개발용 Ctrl+1은 선택 스택을 채운다. 빈 핫바에서는 초기 해당 블록을 만들며 챌린지에는 포함하지 않는다. Ctrl+2는 선택 스택만 비운다. UI 조작은 채굴/설치 진행도를 올리지 않는다.

## 저장 v5 / 생성 v6

저장 포맷은 **5**, 생성 버전/기본 셀 해시는 **6/기존값**이다. `player.inventory`는 `{slots: [[item,count] ×36], cursor: [item,count]}`다. 새 포맷은 이 구조를 필수로 검증하며 9개 정수 배열을 조용히 허용하지 않는다. 잘못된 슬롯 수·타입·정수·범위·빈 스택·커서는 실제 플레이어/월드 변경 전에 거부한다. 스냅샷은 입력 배열과 분리되며 작업 스레드용 deep copy도 유지한다.

같은 생성 버전의 포맷 2–4는 당시의 9개 수량을 명시적으로 현재 스택으로 변환한다. 기존 핫바 종류/수량을 유지하고 빈 항목은 `[-1,0]`, 나머지 가방/커서는 비운다. v2는 기본 도구/빈 드롭, v3/4는 도구/드롭을 보존한다. v2/3는 방향을 초기화하며 v4는 방향을 유지한다. 생성 v5 이하 거부 정책은 그대로다. 이전 실행기는 새 포맷 5를 읽지 못하고 기본 체크포인트 경로는 같으므로 새 저장 전에 별도 사용자 백업이 필요하다. 테스트는 격리된 Saved 경로만 사용한다. Godot/Unreal의 같은 포맷 번호는 바이너리/JSON 호환을 뜻하지 않는다.

## 실패 → 수정 → 직접 확인

개발 근거는 `Saved/Verification/inventory-dev`에 보존한다.

1. 초기 인벤토리 데이터 10,058개/실패 0. 독립 `[item,count]` 참조 모델과 고정 시드 73051의 커서 조작 10,000회를 정확 대조하고, 매 변경 콜백에서 아이템 종류별 전체 수량과 저장 가능성을 검사했다. 절반 올림·한 개 놓기·오버플로·최대 2,304개 용량·부족 용량의 무변경·입력 배열 비별칭·손상 저장도 포함한다.
2. 첫 렌더 `render.log`와 진단 `render-v2`는 10,176개 중 21개 실패였다. 물리 창 크기와 1280×720 논리 화면 좌표를 혼용했다. 동시에 실제 작은 표시에서는 글자가 과도하게 축소됐다. 패널 CanvasLayer만 stretch 역배율로 보정하고 짧은 슬롯 문구/작은 화면 전용 간격을 적용했다. 게임 전체의 기존 stretch 정책이나 다른 HUD를 바꾸지는 않았다.
3. `render-v3`는 작은 패널 높이/레터박스 마우스 2개, `render-v4`는 잘못 뺀 OS 원점 때문에 마우스 5개가 실패했다. 창 클라이언트 좌표로 변환하는 `get_screen_transform()`에 실제 관측상 OS 원점이 들어 있지 않음을 확인했다. 레터박스 오프셋과 stretch를 함께 적용했고 `render-v5/v6`는 10,179개/실패 0이다. v6부터 테스트의 직접 `_layout()` 호출을 제거해 실제 창 크기 변경 신호로만 반응하는지도 검증했다.
4. 검사를 강화한 `render-v7`는 10,187개/실패 0. 실제 RMB의 옮긴 블록 설치, 패널 내 Ctrl+8/9 비동기 저장/커서 복원, W 유지 중 이동·중력 정지, 세 창 크기의 실제 오른쪽 절반 집기/왼쪽 놓기를 추가했다. 반복 마우스 검사는 매번 선택을 다른 칸으로 바꾸고 아이템 수량도 검사해 이전 선택이 남아서 통과하는 것을 막는다.

6. 동적 가방에서는 한 스택만 가득 찬 fixture가 전체 용량 거부를 뜻하지 않는다. ## 공유 참고와 다음 루프

공식 [Window](https://docs.godotengine.org/en/4.7/classes/class_window.html), [Viewport](https://docs.godotengine.org/en/4.7/classes/class_viewport.html)의 content scale/화면 변환 정의를 확인했다. 이 프로젝트의 1280×900 창은 1280×720 렌더 영역과 레터박스를, 640×480 창은 640×360 영역을 캡처한다. PNG 이름은 요청한 창 크기이며 원본 이미지 실제 크기는 별도로 기록한다. viewport 텍스처 캡처는 OS 창 테두리/레터박스 전체나 실제 모니터 표시를 캡처한 것이 아니다. 기존 작은 화면의 다른 HUD/생성 패널까지 개선했다고 주장하지 않는다.

다음은 같은 스택 모델의 재료·내구도 있는 도구·4장비 슬롯, 2×2/3×3 제작, 월드 셀에 결합된 다중 상자·고정 틱 화로와 저장이다. 슬롯을 물질 ID로 다시 사용하거나 임시 프리뷰 도구와 실제 소유 도구를 중복 집계하지 않아야 한다. Unreal의 M05는 상자/화로 각 1개 저장과 제작대 소유 기반 레시피 목록이라는 제한이 있으므로 해당 범위를 분명히 비교한다. M06 생존/시간/날씨, 16.7ms 반복 미달, 초기 준비/메모리/순간 지연, 지형·건축·HUD 시각 품질과 동등한 Unreal 계측도 전체 목표에 남아 있다.

# 저장·입력 구현 자체 검토

작성: 2026-09-08. 독립 리뷰어나 서브에이전트 검토가 아닌 구현 세션의 자체 코드 검토와 실행 검증 기록이다.

## 수정한 결함

- 저장 이후에 추가한 블록이 다시 불러온 화면에 남았다. 이전/새 저널의 합집합에서 유효 셀 값을 비교해 변경된 셀만 적용한다. 채굴 취소·설치 취소·같은 저장 반복 복원 0셀 갱신을 검사했다.
- 플레이어 정보가 잘못되어도 저널을 먼저 적용했다. 검증과 적용을 분리하고 잘못된 수량·위치·시점·선택 슬롯은 월드, 인벤토리, dirty 상태 모두 유지하며 거부한다.
- 숫자 문자열·소수 좌표·버전 소수값을 int로 강제 변환하여 잘못된 저장을 허용했다. 유한 숫자·정수 여부·범위·중복 셀·생성 기본 해시를 검사한다.
- 기존 파일을 직접 열어 덮어썼다. `.pending` 저장·flush·읽기 비교·기존 `.bak` 보존·rename 순서로 교체하며 실패 시 이전 파일 보존을 검사했다. 전원 차단/하드웨어 내구성 보장은 별도 검증 대상이다.
- 저장 I/O와 직렬화가 플레이 루프를 막았다. 편집과 플레이어의 독립 복사본을 작업 스레드에 전달한다. 저장 중 추가 편집이 저장 시점과 섞이지 않는지 검사했다.
- HUD의 기본 Control 입력 필터가 플레이 입력을 가로챌 수 있었다. 장식 UI를 마우스 입력 무시로 지정하고 렌더 창의 뷰포트 입력 경로를 검사했다. 테스트 자체도 입력 버퍼가 반영될 때까지 프레임을 기다리도록 보정했다.
- 검증 명령은 엔진이 오류를 출력하고 종료 코드 0을 반환해도 통과할 수 있었다. 로그 오류·필수 완료 표식·타임아웃 검사를 추가했다.

## 검증 근거

전체 `Verify.ps1`: `Saved/Verification/20260908-195304-170`, 종료 코드 0. 단위 48개·저장 통합 74개, 128시드 행렬, 렌더 뷰포트 입력 및 실제 PNG 확인을 포함한다. 저장 테스트는 별도의 사용자 실세이브를 사용하지 않고 증거 폴더에서 편집 1,000개와 이전 백업을 보존한다.

Godot 파일 API의 실패 코드와 경로 규칙은 [DirAccess 공식 문서](https://docs.godotengine.org/en/stable/classes/class_diraccess.html)와 [FileAccess 공식 문서](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html)를 확인했다.

## 남은 위험

- M02의 실제 데이터 저장과 렌더링은 아직 전역 Dictionary/GridMap이며 dirty 청크 큐가 자체 메시 재생성을 구동하지 않는다.
- 형식 검증은 저장 체크섬의 보안 서명이 아니다. 사용자 파일 조작 방지나 서버 권위는 이 단계의 기능이 아니다.
- M03 행렬은 비어 있지 않은 feature 집합과 스폰을 검사하며, 구조물 후처리 이후 모든 동굴 셀·높이맵·연결성 일관성을 증명하지 않는다.
- 씬 재생성 복원 테스트는 통과했으며, OS 프로세스 종료/재시작을 가로지르는 별도 실행 테스트와 전원 차단 주입은 후속 강화 대상이다.
- 프레임 지연 P95, 185 × 185 실제 렌더 메모리, Unreal 동등 깊이·콘텐츠 비교가 남아 있다. 목표는 계속 활성 상태다.

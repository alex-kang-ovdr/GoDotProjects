# M04 방향 상태·통나무 렌더·3D 균열·아이템 보존

## 구현과 계약

이전 채굴·도구·물리 드롭 위에 면×4회전의 24가지 설치 상태, 통나무 방향 렌더, 이웃 재표시/저장 복원, 10단계 3D 균열을 연결했다. Unreal M04 완료 보고서의 상태 전용 셀·구버전 잔존·벽면 회전 중복·실제 입력 우회 사례를 참고하되 Godot의 청크/greedy 메시 경로로 독립 구현한다. 생성 v6/기본 셀 해시는 그대로이며 시각적으로는 생성 통나무에도 새 단면이 보인다.

`BlockOrientation`의 상태는 Godot Y-up 기준 `face * 4 + quarter`다. face 순서는 +Y/-Y/+X/-X/+Z/-Z, quarter는 yaw를 90도로 반올림한 0–3이다. 0은 항등/수직 통나무다. 직교 정수 축으로 회전해 반사나 삼각함수의 셀 경계 오차를 피한다. 카메라 광선의 실제 면 법선과 플레이어 yaw를 RMB 설치 트랜잭션에 전달한다. 큐브 충돌은 방향에 따라 바뀌지 않는다. 방향 값은 고체 블록에서만 유효하며 물/공기에는 거부한다. 면 번호는 Godot 내부 저장 계약이며 Unreal의 축/바이너리 포맷과 직접 교환하는 프로토콜은 아니다.

`VoxelChunkStore.block_states`는 비기본 상태만 담는 희소 사전이다. 재질 편집이 없어도 생성 셀에 상태를 저장할 수 있고, 재질 교체/제거는 이전 상태를 지운다. 같은 재질 설정은 기존 상태를 보존하며 새 설치는 명시한 상태를 적용한다. 실제 상태 변화는 change_serial/셀/경계 이웃 dirty를 갱신하고 같은 값 설정은 무변경이다. 복원은 이전·입력 편집과 이전·입력 상태의 합집합을 비교해 방향만 달라진 셀도 다시 그린다.

통나무의 상태 비트를 면 병합 키에 포함해 방향이 다른 블록을 합치지 않는다. 노출 면/충돌 규칙과 기존 재질 ID는 유지한다. 회전 역변환으로 UV를 계산하며 두 단면은 별도의 UV 구간/단면 텍스처, 나머지 면은 껍질 텍스처를 사용한다. 단면의 비대칭 나이테·틈으로 분기 회전도 확인할 수 있다. UV 구간은 청크 안의 최대 16블록 greedy 사각형에서도 겹치지 않으며 ShaderMaterial은 nearest/repeat와 현재 게임 조명을 사용한다. GridMap 내부 기준과 통나무 드롭은 동일한 단위 통나무 메시/재질을 쓴다. 텍스처는 기존 방식처럼 코드로 생성한 독자 패턴이다.

`MiningCracks`는 채굴 대상의 여섯 면에 10단계 균열 메시를 미리 구성하고 진행 단계가 바뀔 때만 교체한다. 면 바깥 0.003m에 배치하고 depth test를 유지해 앞의 지형을 투시하지 않는다. 해제·완료·대상/월드 변경·패널/잠금은 표시를 끈다. 지형 메시/충돌/저장에는 균열을 기록하지 않는다. 깨진 도구나 잘못된 도구의 기존 채굴 규칙도 그대로다.

## 저장 호환성

현재 저장 포맷은 **4**, 생성 버전은 **6**이다. 직전 포맷 3이 방향 상태 없이 이미 기록될 수 있었으므로 의미를 조용히 바꾸지 않고 새 번호를 사용했다. v4의 `block_states`는 필수이며 정수 좌표/0–23 방향·중복·최종 고체 존재를 검증한 뒤 적용한다. 상태만 있는 생성 셀은 편집 사전에 없어도 허용한다. 사전 조회로 중복/셀 존재를 검사하며 행마다 전체 편집을 다시 검색하지 않는다.

같은 생성 버전의 v2/v3는 기존 방향을 모두 지우고 항등 상태로 읽는다. v3의 도구/드롭은 유지하며 v2는 기본 도구/빈 드롭을 준다. 작업 스레드 저장 스냅샷은 상태 사전을 복사해 이후 편집과 분리한다. 기존 생성 v5 이하 거부 정책은 유지한다. v2/v3 실행기는 새 v4 파일을 읽지 못하므로 구버전 복귀 가능성이 있다면 새 저장 전 사용자 체크포인트를 별도 백업해야 한다. 테스트는 격리된 Saved/Verification 경로만 사용한다.

## 실패·수정과 직접 검증

개발 근거는 `Saved/Verification/orientation-dev`에 보존했다.

- 초기 데이터/런타임 기본 검사 852개, 렌더 871개가 통과했다. NaN을 JSON으로 만드는 오류 주입 fixture는 엔진이 null로 치환하며 경고하므로 유효 JSON의 소수 좌표 거부로 바꿨다. 이는 비정수 좌표 검사이며 JSON이 NaN을 지원한다는 주장이 아니다.
- 실제 렌더 메시 비교를 추가한 `render-v2/v3`는 898개 중 2개 불일치였다. 저장/이웃 갱신 뒤 한 청크의 면 삽입 순서가 fresh build와 달랐다. 정점 배열 순서 대신 위치·법선·UV·삼각형 winding을 함께 정규화해 비교했다.
- 더 넓힌 `render-v4/v5`는 12개 불일치였다. 업로드한 ArrayMesh의 축 법선 0이 약 -0.000015로 읽히는 엔진 압축을 관측했다. 독립 fresh geometry도 동일한 업로드 경계를 통과시킨 뒤 정확 비교한다. UV 손상과 winding 반전을 주입해 비교기가 여전히 검출하는지 검증했고 `render-v6`는 900개/실패 0이다. 이를 런타임 텍스처 방향 손실을 수정한 것으로 과장하지 않는다.
- 방향 데이터/헤드리스 런타임은 878개다. 24회전의 정확 직교·determinant/고유성, yaw 부호/경계, 상태 전용 저장과 dirty, 구버전 초기화/손상 거부, packed/reference/cache 대조, 두 단면/UV 구간, 방향별 병합 분리, 실제 업로드 메시와 fresh geometry, 재생성 정리를 검사한다.
- 실제 렌더는 6면의 카메라 광선/RMB 설치·1개 소비·상태 기록과 24상태 갤러리/3축 근접 PNG를 추가한다. 24개 모든 face/yaw 조합을 실제 마우스로 설치했다고 주장하지 않는다. 갤러리는 테스트용 고정 배치·정사영이며 실제 플레이 카메라는 여전히 원근이다.
- 균열 후 채굴 데이터 294개/실제 렌더 360개. 10단계의 6면 기하/깊이 검사, 실제 대상 부착, 해제/완료 제거, 75% 진행 시점의 8단계와 PNG를 검증한다. 기존 120 도구×블록 조합·실제 유지 채굴·이동 줍기·저장·가득 참/벽 차폐/낙하 구조를 유지한다.
- 아이템 보존 검사 초기 스크립트의 Variant 내구도 타입 추론 오류를 명시적 정수로 고쳤다. `conservation-v2`는 525개/실패 0, 실제 물리 콜백으로 10,000개를 전달하고 인벤토리 changed 콜백 10,189회에서 소유 수량을 감사했다. 개발 실행은 약 5.453초다. 주기적 전체 스택/용량 해제와 2,048개 실제 RigidBody3D의 짧은 차단 줍기/채굴 한도 거부/저장 가능성을 포함한다. 반복 fixture는 지연 0으로 시작하며 일반 게임의 0.35초 지연은 별도 채굴 렌더가 검사한다. 장시간 2,048개 아이템의 FPS나 일반 사용자의 조작 지연 계측은 아니다.
- 기존 단위 48/메시 502/캐시 1,005/최적화 동등성 534/저장 74개 직접 회귀도 통과했다. 새 OS 프로세스 재시작 fixture에는 편집 없는 스폰 바닥 상태 17과 편집 통나무 상태 23을 추가했다.

## 전체 회귀

첫 전체 실행 `20260909-031805-271`은 방향/균열/보존·기존 데이터/두 모드 OS 재시작을 통과한 뒤 수동 리뷰에서 발견한 설치 알림 순서 결함을 수정하기 위해 중단했다. 당시 소유한 cave-network-input 엔진 PID 35912/출력 경로를 확인하고 종료해 stage exit -1/상위 exit 1이 남았다. 동굴 경로 실패나 시간 초과로 해석하지 않는다. 로그/캡처는 그대로 보존하며 완료 근거로 쓰지 않는다.

`placement-commit-before.log`는 인벤토리 changed 콜백 시점에 `material=-1, orientation=0, stock=7, placed=0`을 재현했다. 블록을 설치하기 전에 consume의 알림이 나가 그 순간 저장하면 소비만 남았다. `BlockInventory.consume()`에 트랜잭션용 알림 지연 옵션(기본값은 기존처럼 알림)을 추가하고, 실제 설치는 소비·블록·방향·플레이어 진행 기록 후 inventory.changed를 보낸다. `placement-commit-v2`는 콜백의 체크포인트를 실제 복원해 `material=8, orientation=23, stock=7, placed=1`을 확인했다. 점유/잘못된 방향/플레이어 겹침/빈 슬롯 거부에는 추가 소비나 변경 콜백이 없고 성공 알림은 한 번이다. 단위 48/Builder 53/물리 보존 525개도 다시 통과했다. 이는 현재 단일 플레이어 트랜잭션의 검증이며 임의 제3자 재진입 콜백이나 멀티플레이 권위를 보장하지 않는다.

최종 `Verify.ps1 -RenderComparison -BenchmarkScreen 0`은 `Saved/Verification/20260909-032728-408`에 55개 단계/상위 종료 코드 0으로 완료했다. 51개 프로세스는 exit 0, 잘못된 시작 옵션·헤드리스 표시 계측·화면 번호·FPS 상한 거부 4개는 의도한 exit 2다. 프로세스 실행 시간 합계는 792.604초이며 로그의 ERROR/WARNING/SCRIPT ERROR 행은 0개다. 검증 엔진은 모두 종료했고 Unreal 작업트리는 수정하지 않았다.

- 채굴 데이터 294/실제 렌더 360, 방향 데이터 878/실제 렌더 900, 물리 보존 525개와 설치 콜백 체크포인트의 실제 복원을 통과했다. 보존은 10,000개 전달/10,189회 콜백/루프 5.510초이며 프로세스 전체 시간은 6.471초다.
- 단위 48·저장 74·Builder 53/72·생성 패널 40/49·던전 408/32·웅크리기 24/25·메시 502·캐시 1,005·동등성 534·정리 25와 기존 생성/조명/인터페이스 검사를 유지했다. 동굴 안내 경로는 113/121개이며 엔진 실행 각각 130.295/131.720초로 기존 180초 제한 내다.
- 새 프로세스 Overworld 73916→77172, Dungeon 5592→12456에서 각각 1,000편집과 상태 전용 생성 바닥 17·편집 통나무 23·사용 중/소진 도구·미수거 드롭을 복원했다. 각 실패 0이다.
- 128시드 속성 행렬 33.205초. 헤드리스 185맵 시드 1337은 3.657916초/1,062,829셀/해시 392942167이며 세 시드 범위는 3.610686–4.160958초다. 생성 v6의 기존 셀 해시를 유지한다.

최종 1280×720 `orientation-gallery.png`, `orientation-axis-0/8/16.png`, `mining-cracks.png`를 직접 열어 확인했다. 24개 고정 배치와 세 축 단면/옆면을 식별할 수 있고 75% 진행의 균열이 대상 블록에 붙어 있다. 근접 캡처에서 주변 fixture 라벨/블록은 화면 밖으로 잘리고 기존 HUD와 겹치지만 중심 검증 블록의 단면은 보인다. 이는 방향 기능의 테스트 화면이지 완성된 갤러리 UI나 전체 게임 시각 품질 통과 판정은 아니다. 실제 플레이 HUD의 큰 채굴 패널이 대상 하단을 가리는 구성은 향후 UI 개선 대상으로 유지한다.

같은 185맵 내부 청크 준비 8.326161초/OS 최대 649.7422MiB/편집 CPU P95 3.091ms/viewport P95 6.562ms, GridMap 53.973788초/1,179.0039MiB/viewport 33.424ms다. 두 프로세스 모두 화면 0/60Hz/위치 1280,684/1280×720/VSync 1/FPS 상한 0/포커스 조건 검사가 유효하다. 유휴 중앙 간격은 청크 2.3175ms, GridMap 33.3335ms로 달라 설정값만으로 동일 실제 표시 페이싱이라고 가정하지 않는다. 통나무 재질은 양쪽에 적용했지만 플레이어/HUD/드롭/균열 없는 독립 카메라 벤치마크다. GridMap의 CPU 제출은 지연 업로드를 포함하지 않아 청크 CPU와 직접 비교하지 않는다. 이전 단일 결과보다 준비/viewport 시간이 늘었으나 한 회차만으로 새 통나무 셰이더의 비용으로 귀속하지 않는다. 반복 VSync ON 16.772–17.069ms의 16.7ms 미달과 native OS presentation 미계측은 그대로다.

실제 255맵 교체 20.21288초/P95 1.385ms/최대 18.045ms, controls 프로세스 최대 1,178.1094MiB다. Dungeon 255 교체는 1.02154초다. 이전 91.373ms/451.332ms 순간 지연이 이번에 재현되지 않았지만 원인 해결이나 프레임 상한 보장을 의미하지 않는다. 전체 기능·시각·성능 우위는 아직 판정하지 않는다.

## 참고와 다음 범위

회전/역변환과 메시 데이터 계약은 Godot 공식 [Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [Vector3](https://docs.godotengine.org/en/4.7/classes/class_vector3.html), [ArrayMesh 사용법](https://docs.godotengine.org/en/4.7/tutorials/3d/procedural_geometry/arraymesh.html)을 확인했다. 공유 입력은 Unreal 로컬 `Docs/Milestones/M04_COMPLETION.ko.md`이며 엔진 소스와 작업트리는 수정하지 않았다. 이번 재조회에서 Unreal의 HANDOFF는 여전히 M06 완료/M07 후속, 최신 렌더 `20260909-022624-403`/Automation 42개/상위 62회 실패 0을 보고한다. 이는 문서 확인이지 이 작업에서 Unreal을 재실행한 결과는 아니다.

M05의 36슬롯·제작·상자·화로와 M06 생존·시간·날씨가 아직 없다. 도구 전체 제공은 제작/획득/성장 시스템 완료가 아니다. 16.7ms 반복 viewport 게이트와 초기 준비/메모리/순간 지연 안정화, 자연 지형·건축·동굴 시각 품질, 동등한 기능·계측 조건의 Unreal 비교를 유지한다. 전체 목표는 active다.

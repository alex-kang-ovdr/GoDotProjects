# 자체 검토 — 월드 교체 시 데이터·노드 해제 지연

## 조사 출발점과 계측

직전 전체 실행 `20260908-233012-624`의 255맵 생성 루프 최대 간격은 451.332ms였다. 합계 로그만 있어 발생 단계를 알 수 없었으므로 `VoxelWorld`에 opt-in 단계 계측을 추가했다. 런타임 기본은 `generation_trace_enabled=false`다. 작업 스레드의 생성/검사/인덱싱, 메인 프레임의 입력·출력 상태/청크 진행, 각 청크의 마스크/geometry/upload, 이벤트 수신자, 기존 데이터 정리/인계/노드 이동/해제를 구분한다.

`tools/generation_profile.gd`는 실제 게임 씬·조명·HUD·생성 패널에서 시드 1337의 41→255→41 왕복을 3회 실행한다. 테스트에서는 플레이어 물리 이동만 비활성화하고 기존 생성 잠금과 실제 렌더·물리 노드는 유지한다. VSync=1/창 focus를 기록하고 각 프레임 간격과 직전 `_process`/단계 기록을 JSON으로 보존한다. process_frame 간격은 화면 표시 하드웨어 지연이나 GPU 실행 시간을 직접 측정한 것이 아니다. `controls_smoke.gd`도 같은 trace를 남겨 기존 451ms 사례와 같은 시나리오에서 이후 지연을 분류할 수 있다.

기준 3회에서는 41→255 최대 간격이 26.802–39.503ms여서 원래 451ms 사례를 재현하지 못했다. 대신 255→41 전환에서 **322.767/329.631/365.710ms** 지연이 반복됐다. 직전 프레임의 `clear_old` 100.173–107.877ms와 `adopt_data` 179.363–205.865ms가 대부분을 설명한다. 마지막 참조를 내릴 때 약 207만 셀의 Dictionary/청크 인덱스/평면 캐시가 메인 스레드에서 해제되는 경로다. 이 재현 가능한 병목을 고쳤지만, 과거 451ms도 반드시 같은 원인이었다고 주장하지 않는다.

## 구현과 안전 경계

[Godot 4.7 스레드 안전 API](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html)의 활성 씬 트리/GPU/물리 작업 제한과 공유 컨테이너·참조 처리 경계를 확인했다. 별도 렌더/물리 스레드 프로젝트 설정을 변경하지 않았다.

새 월드를 publication 할 때 기존 layout/순수 데이터 `VoxelChunkStore`/마스크/packed 평면 geometry의 참조를 전용 전달 Dictionary에 모은 뒤 메인의 필드를 새 것으로 바꾼다. 소유권을 넘긴 전달 컨테이너는 이후 메인에서 읽거나 수정하지 않는다. 정리 작업 스레드는 전달 컨테이너의 참조만 내리며 중첩된 기존 layout/배열/저장소를 `clear()`하거나 변경하지 않는다. 외부에서 보유한 이전 불변 스냅샷은 계속 유효하다. Node·ArrayMesh·Material·CollisionShape 같은 활성 엔진 객체는 전달하지 않는다. 현재 순수 데이터 클래스에 향후 엔진 자원을 추가할 경우 이 경계를 다시 검토해야 한다.

이전 청크 노드는 메인에서 숨기고 별도 `retired_bodies` 목록으로 옮긴다. 이후 SETTLING 중 약 2ms 예산으로 `remove_child`/`free`를 나눠 수행한다. 모든 노드를 한 프레임 끝의 queue_free에 몰아 GPU/충돌 자원 해제 비용을 다시 집중시키지 않도록 한다. 단일 노드의 실제 해제 비용은 예산을 넘을 수 있고 서버/드라이버의 후속 작업도 있어 엄격한 2ms 상한은 아니다.

새 데이터·메시가 보이더라도 이전 충돌 노드 제거, 그 후 물리 2틱, 정리 스레드 join이 모두 끝나기 전에는 gameplay/save/load/중복 생성 잠금을 풀지 않는다. 스레드 시작 실패는 `inline_fallback`으로 보고하고 동기 해제해 누수/영구 잠금 없이 완료한다. 이 예외 경로의 끊김을 숨기지 않는다. 월드 종료 때도 소유한 생성/정리 스레드를 join한다. 생성 버전 5/셀·해시·저장 포맷 2는 바꾸지 않는다.

## 단계별 실험 결과

근거는 `Saved/Verification/generation-profile-baseline-v1`, `generation-profile-retirement-v1`, `generation-profile-retirement-v2`의 JSON/PNG/log다. 세 실행 모두 3왕복·42개 단언·exit 0이며 마지막 v2가 현재 구현이다.

- 기준: 255→41 최대 간격 322.767–365.710ms, P95 12.700–14.589ms, 요청→완료 942.566–1,053.015ms.
- 데이터만 작업 스레드 해제(v1): 최대 38.577–40.395ms/P95 6.962–7.499ms. 메인 `adopt_data`는 0.007–0.008ms가 됐고 실제 데이터 해제 347.777–362.555ms는 작업 스레드에서 수행됐다. 기존 노드 전체의 한 프레임 자원 해제는 남았다.
- 노드 배치까지 적용(v2): 최대 26.771–33.936ms. 대응 회차의 최대 간격은 기준보다 약 89.5–91.9% 감소했다. 메인 `clear_old` 0.719–0.770ms/`adopt_data` 0.006–0.007ms, 노드 해제 배치의 사례별 최대 2.303–3.300ms다. 스냅샷을 복제하거나 지형을 줄이지 않았다.
- v2의 255→41 요청→완료는 1,120.271–1,188.288ms이고 P95 17.188–21.616ms다. v1/기준보다 평균적 간격과 전체 대기는 나빠진 실행도 있다. 최악의 한 번 끊김 감소를 모든 지표 개선으로 표현하지 않는다.
- 41→255 v2는 22.828–23.864초/P95 17.221–19.290ms/최대 33.745–43.561ms, 기준은 18.912–19.312초/P95 1.259–1.391ms다. 생성/검사/인덱싱 작업 시간은 비슷하거나 줄었지만 메인/표시 간격 양상은 크게 다르다. 고정 VSync/focus 기록만으로 외부 스케줄링·표시 동기화 영향을 제거했다고 볼 수 없고, 이 차이를 데이터 해제 CPU 시간과 섞지 않는다. 대형 월드 준비 시간 개선은 미완료다.

첫 255 사례의 상태별 분해에서 v1/v2 COMPUTING 간격 P95는 1.042/17.062ms지만 `VoxelWorld._process` P95는 0.002/0.004ms다. MESHING `_process`도 11.886/11.210ms로 느려지지 않았다. 정리 코드가 실행되기 전 COMPUTING부터 간격 양상이 달라졌다는 근거이며, 차이를 새 노드 정리 배치만의 회귀로 해석할 수 없다. 다만 이 자료만으로 VSync/OS/렌더링 중 정확한 원인을 확정하지는 않는다.

처음 프로파일러의 `_expect` 누락과 정리 검사 `WeakRef` 타입 추론 경고를 수정했다. 실패 로그는 각각 `generation-profile-baseline`과 `retirement-smoke/test.log`, `test.err`에 보존한다. 정리 검사 수정 후 `test2.log`는 25개 단언/0실패다.

## 회귀와 종료 조건

`retirement_smoke.gd`는 Semaphore로 정리 스레드를 붙잡은 상태의 gameplay/중복 생성 잠금, 실제 해제 후 join/해제 노드 목록/잠금 해제, 외부에서 보유한 이전 layout·store·마스크·geometry의 내용 보존, 스레드 생성 실패 fallback·최종 충돌·월드 종료 중 join을 25개 단언으로 검사한다. 기존 생성 조작 검사에는 프레임별 증거 파일 저장을 추가했다.

전체 회귀는 `Saved/Verification/20260908-235459-410`, `Verify.ps1 -RenderComparison` 종료 코드 0/39개 엔진 단계 완료다. 실행은 2026-09-08 밤에 시작해 09일 새벽에 끝났다. 의도한 CLI 거부만 exit 2이고 나머지 단계는 exit 0/오류 없음이다.

- 정리 수명 25·평면 캐시 1,005·메시 502·최적화 동등성 534·단위 48·기후 99·저장 74, Builder 53/72·웅크리기 24/25·생성 조작 40/49·Dungeon 408/32·인터페이스 48/50·조명 41개 단언이 통과했다.
- Overworld 128시드 33.977초/Dungeon 128시드+경계 2.299초, 랜드마크 독립 118/실제 왕복 41/42개·보호 동굴 3시드 왕복, 두 모드 OS 프로세스 1,000편집 복원도 통과했다. 쓰기/읽기 PID는 Overworld 86196/18848, Dungeon 85788/9560이다.
- 실제 controls 255맵 교체는 23.864초/P95 17.022ms/최대 33.721ms, 프로세스 최대 작업 집합 1,113.90MiB다. `render-generation-trace-4-255.json`의 최대 간격 직전은 MESHING이며 `VoxelWorld._process` 10.232ms, 청크 `(-4,1,-5)` 구성 10.170ms다. 차이 전체를 이 청크 CPU로 설명하거나 과거 451ms의 원인으로 소급하지 않는다.
- 185맵 생성 단독 3시드는 4.329–4.971초, Dungeon 255 교체는 1,949.28ms다. 생성기/버전/셀/해시는 바꾸지 않았다.
- 별도 게임 조명 렌더: 청크 준비 7.961초/637.95MiB/CPU 편집 P95 2.738ms/**화면 반영 17.091ms로 미달**이다. 같은 GridMap은 48.798초/1,133.45MiB/화면 반영 26.319ms다. Godot 내부 준비 약 83.7%·메모리 43.7% 감소이며 Unreal과 동등 기능 비교가 아니다.
- 최종 `controls-large.png`와 v2 큰→작은 전환 PNG를 직접 확인했다. 새 월드·PASS 상태·HUD/패널을 보존하며 이전 맵이 겹쳐 남지 않는다. 시각 검사가 모든 위치의 잔여 충돌 부재를 대신하지 않으므로 노드 목록/실제 물리 검사도 함께 수행했다.

추적 파일의 헤드리스/렌더 이름 충돌을 사전에 분리했다. 이 전체 실행의 초기 헤드리스 무접두사 trace는 그대로 보존했고, 수정 후 `controls-trace-headless.log`의 추가 40개 검사/exit 0으로 `headless-generation-trace-*`도 생성했다. 렌더는 `render-generation-trace-*`로 기록돼 서로 덮어쓰지 않는다. 기준 geometry 옵션도 `generation-profile-reference`에서 실제 255→41 왕복 14개 단언/exit 0으로 확인했다. 이는 단일 기능 검증이며 추가 A/B 성능 우위의 근거로 쓰지 않는다.

자연 동굴 전체 접근성, 기후 코어 고도·시각 품질, 편집 표시 P95 16.7ms, 동등 기능/같은 계측의 Unreal 비교는 여전히 별도 게이트다. 이번 근거는 재현된 월드 해제 지연의 감소이며 Unreal 대비 전체 우위나 모든 프레임의 상한 보장이 아니다.

# 동굴 방 식별과 실제 출구 안내

## 구현과 범위

이번 루프는 같은 회색 동굴에서 방과 귀환 방향을 알아보기 어려운 문제를 다룬다. 게임 HUD 하단에 `CAVE ATLAS`를 연결해 현재 방 이름, 보는 방위, 다음 출구 경로의 상대 방향·방위·남은 격자 이동 수, 상승 시 Space 점프/하강 시 Step down을 표시한다. 중앙/서쪽/동쪽/북쪽/남쪽 방을 구분하며 생성 패널·생성·로드 중에는 숨긴다. 지표나 지도 밖 자연 공동에 동굴 방 이름을 잘못 붙이지 않도록 보호 공기 셀과 발 높이를 함께 검사한다.

`CaveWayfinding`은 생성 당시 보호 동굴에서 지지 바닥과 몸 공간을 갖춘 후보만 작은 지도에 기록한다. 현재 `VoxelChunkStore.get_block()`으로 바닥·발·머리와 단차 점프 여유를 다시 검사하고, 표면 입구에서 역방향 BFS로 다음 한 칸을 고른다. 안내는 출구를 향한 직선 화살표가 아니다. 길 한 줄이 막히면 남은 어깨 경로로 우회하고, 전부 막히거나 지지 바닥이 없어지면 `No verified exit route`와 복구/R 복귀 안내를 표시한다.

후보 밖에 새로 판 지름길·새 계단은 자동으로 지도에 추가하지 않는다. 자연 동굴 전체 내비게이션이나 최적의 실제 이동 시간 경로를 보장하지 않는다. `grid steps`는 4방향 격자 간선 수이며 미터나 예상 시간과 다르다. 공중/원래 지도 바닥이 아닌 높이에서는 착지 후 재개 문구를 표시하고, 지도 공기 자체를 벗어나면 숨긴다. 보수적인 standing 공간 기준이라 웅크려 지나갈 수 있는 틈도 경로에서 제외할 수 있다. 노드 밖 점프/새 터널까지 완전한 동적 navmesh로 표현하지 않는다.

`VoxelChunkStore.change_serial`은 실제 set/초기화/체크포인트 복원 변경에만 증가하는 런타임 토큰이다. 같은 값 편집·같은 체크포인트 재적용은 유지하며, 서로 다른 store의 동일 serial은 객체 identity로 구별한다. 보는 방향/이동만으로 BFS를 반복하지 않는다. 지도는 전체 layout/store의 강한 참조를 보관하지 않아 이전 월드 데이터의 작업 스레드 정리를 지연시키지 않는다. HUD의 문자열·색도 바뀔 때만 갱신한다.

생성 v6, 저장 포맷 2, 기본 셀·골든 해시, 블록 ID와 저장 파일 경로는 변경하지 않았다. 사용자 기본 저장 파일과 Unreal 원본은 수정하지 않았다.

## 검증 근거

초기 독립 실행 `Saved/Verification/wayfinding-dev`:

- import 종료 0. 초기 데이터/실제 HUD 53개 단언 통과 후 상승·하강·추가 점프 여유·어깨 우회를 추가했다.
- 초기 4월드 지도 재계산은 후보 467/791개, 도달 467/791개, 1.844–2.901ms였다. 제한된 단일 실행 계측이며 일반 플레이 지연 P95나 성능 개선 판정으로 쓰지 않는다.
- 실제 렌더 `cave_network_smoke.gd --accelerated`는 121개 단언/실패 0. 1337/41, -7/41, int32 최대/41, 1337/185에서 모든 말단 방으로 걸어 들어가 안내 그래프를 따라 돌아왔다. 경로가 중앙 방을 우회하면 실제 표면까지 걸은 후 기존 입구/접근로로 중앙 방에 재진입했다. 테스트의 최초 월드별 위치 설정 외에 텔레포트/채굴/설치/지형 보정은 사용하지 않았다. 시험 가속만 적용하고 물리 dt=1/60을 유지한다.
- 네 방의 바깥 벽/입구 방향 PNG 8장을 생성했다. 서쪽·남쪽 입구 시점을 직접 확인해 이름/방위/안내와 핫바가 잘리지 않고 겹치지 않는 것을 확인했다. UI의 개선이지 방 지형의 다양성 개선은 아니다.
- 별도 `wayfinding_capture.gd` 실제 렌더 12개 단언/종료 0. 고정 시점으로 북쪽 방·출구 봉쇄·복원 PNG 3장을 저장했고 긴 이름/경고의 실제 글꼴 너비, 패널 열기, 실제 Overworld→Dungeon→Overworld 교체를 검사했다. `atlas-blocked.png`를 직접 검토해 경고 가독성/핫바 분리를 확인했다. 이 도구의 고정 위치 설정은 시각 fixture이며 보행 증거와 구분한다. 전체 회귀의 헤드리스 보행 단계 중 별도 실행했으며 성능 표본으로 사용하지 않는다.

최종 전체 회귀 명령은 `Verify.ps1 -RenderComparison -BenchmarkScreen 0`이며 실패/수정/재실행 결과를 아래에 기록한다.

전체 실행 중 북쪽 방 PNG에서 네 방향 반올림으로 `Facing S / LEFT (S)`가 함께 나타나는 혼동을 찾았다. 실제 시선은 남서쪽에 가까워 좌회전이 맞지만 표시만으로 알기 어려웠다. 현재 방위 표시를 8방향으로 보강하고 모든 8방향 기대값과 실제 140도 시선의 `Facing SW / LEFT (S)`를 추가 검사한다. 경로/이동/지형 변경은 없으며 해당 보강 뒤 별도 새 프로세스 재검증 결과를 구분해 기록한다.

첫 전체 실행 `20260909-012956-375`는 39번째 엔진 단계인 lighting-input에서 종료 1로 중단됐다. 앞의 동굴 이동은 113/121개 통과했지만 새 HUD 패널이 고정 조명 ROI 안에 들어가 세 동굴 시점의 어두운 면적이 약 6.286%로 집계됐다. 실패 로그/PNG를 삭제하지 않았다. 지형/조명 변경 없이 UI 배경이 분석에 섞인 회귀다.

조명 측정의 기존 ROI(570,279픽셀)·1% dark/near-white 임계값·10% 밝기 개선 기준은 유지했다. `lighting_audit.gd`의 별도 캡처에서 실제 씬의 CanvasLayer들을 숨긴 뒤 terrain-only viewport를 읽고 이전 표시 상태를 복원한다. 플레이어용 HUD 포함 PNG와 `*-scene.png`를 둘 다 보존하고 JSON에 측정 범위를 명시한다. 게임 HUD를 끄거나 조명을 밝게 바꿔 실패를 덮은 것이 아니다. UI 가독성은 별도 실제 안내 캡처로 검증한다.

수정 후 독립 실행: `final-data.log` 65개, `final-capture.log` 14개, `lighting-fixed.log` 53개 모두 실패 0/종료 0. `atlas-bearing.png`의 남서 시선/남쪽 좌회전과 `lighting-1337-cave-current-scene.png`의 UI 없는 동굴을 직접 검토했다. 세 동굴의 실제 지형 dark_fraction=0, current 표시 휘도 0.232052–0.238693, baseline 0.205322–0.211397로 기존 기준을 통과한다. 이는 정해진 카메라/표시 RGB 범위의 결과이지 모든 동굴 시점이나 실제 HDR 측정은 아니다. 두 수정과 새 시각 검사를 고정한 후 `20260909-014327-009`에서 전체 검증을 처음부터 재실행한다.

## 남은 판단

동굴 출구 안내를 구현했지만 반복 16.7ms 응답성 목표와 동일 기능·동일 계측 Unreal 비교는 여전히 미완료다. 방의 건축적 구분·보상·자연 공동 탐험성, 지도 밖 경로 확장, 표시 지연/초기 준비 비용과 지형·구조물 품질을 계속 개선한다. 목표 완료나 Unreal 우위로 판정하지 않는다.

이번 대기 중 Unreal의 현행 로컬 인수인계/마일스톤 보고서를 읽어 M06 완료 보고를 확인했다. 경쟁 구현은 M04 채굴·도구·드롭/방향 상태, M05 36슬롯·제작·상자·화로, M06 생존·시간·날씨까지 기술하고 있다. 이번에 해당 Unreal 실행을 독립 재검증한 것은 아니다. Godot M01–M03 수치만으로 전체 우위를 선언할 수 없으며 다음 기능 루프는 M04의 실제 채굴·드롭과 영속 상태에 착수한다. 현재 버전의 표시 지연·시각·정확성 게이트도 유지한다.

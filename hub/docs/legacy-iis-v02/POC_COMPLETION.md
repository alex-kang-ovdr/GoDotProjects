# PlayHub 0.2.0 — 1차 PoC 기능 구현 현황

기준일: 2026-11-16. 이 문서는 배포 패키지의 실제 코드와 실행한 검사 범위를 설명한다. 최초 기획 문서의 제품 목표와 구분하며, 현재 계약은 이 문서·`POC_API_CONTRACT.md`·`POC_GAMES.md`를 기준으로 한다. 최신 자동 검사 결과는 `../reports/acceptance.html`에 있다.

## 1. 이번 결과

사용자 사이트, 별도 관리자 사이트, 8개 경량 게임, 무가입 게스트 플레이, 선택 Google OAuth, 조건부 저장과 복원, 플랫폼 지표와 정확일 리텐션, 게임 목록 기반 빌드, IIS 설치·점검·백업·복원 도구를 구현했다. 0.2에서는 이전 패키지의 남은 사용자 복구 흐름과 운영 자동화를 연결했다.

코드와 API를 검증한 상태와 실제 Windows에 설치해 수용한 상태는 다르다. 작성 환경은 Linux/Node이며, 실제 Windows IIS·브라우저·Google 실계정·두 번째 LAN PC·재부팅 증거는 제공하지 않는다. 해당 환경에서 실행할 검사 도구와 수용 기준은 포함한다. 현재 환경에서 브라우저 실행 제한을 우회하지 않았다.

## 3. 사용자 사이트

### 바로 플레이

홈에서 목록을 보고 검색·장르로 좁힌 뒤 상세에서 조작법을 확인하고 플레이한다. iframe은 게임 실행 권한만 허용하고, 부모 포털이 서버 저장·이벤트를 중개한다. 게임 코드에 로그인 쿠키나 Google 토큰을 전달하지 않는다. 새로 시작·일시정지·재개·승패·재시작을 각 게임에 연결했다.

API가 연결되지 않는 경우에도 검증된 내장 게임의 로컬 플레이를 명시적으로 선택할 수 있다. 이 상태에서는 서버 저장과 이용 지표가 기록되지 않는다. 같은 탭의 임시 진행은 복구에 이용하지만 영구적인 계정 저장으로 표시하지 않는다.

D30 재방문을 세션 만료 때문에 놓치지 않도록 익명·게스트 식별은 90일을 사용한다. 첫 게스트 승격과 유효 게스트의 세션 재조회 때 서버 만료와 쿠키 기간을 함께 갱신한다. 이미 만료·로그아웃한 세션은 부활시키지 않는다. 쿠키 삭제·다른 브라우저·다른 주소에서는 같은 게스트로 자동 연결할 수 없다. Google 회원·관리자의 인증 수명은 별도로 유지한다.

### 저장 기록 화면

게임별 저장 기록에서 서버 현재 진행, 현재 탭 미반영 진행, 보관 슬롯, 교체·제거 전 복구 기록을 구분한다. 서버와 탭이 충돌하면 최신 탭 진행을 계속 보존한다. 다음 행동을 제공한다.

1. 서버 진행을 선택해 현재 게임을 다시 연다.
2. 현재 탭 진행을 별도 슬롯에 먼저 보관하고, 예상 revision을 확인한 뒤 main으로 적용한다.
3. 보관 슬롯이나 이전 main 백업을 선택해 복원한다. 교체 직전 main은 별도 백업에 남긴다.
4. 공간이 부족하면 보관 슬롯을 확인 후 제거한다. 원본은 복구 기록으로 남기고 main은 제거할 수 없다.
5. 서버 재연결·저장 재시도를 수행한다. 응답이 유실된 같은 쓰기는 동일한 멱등 키로 재시도한다.

다른 탭에서 계정이 바뀌면 이전 세션의 저장 응답을 적용하지 않는다. 이전 iframe의 추가 쓰기를 종료하고 계정별 임시 기록을 분리한다. 동시 변경으로 revision이 맞지 않으면 412로 멈추고 기존 데이터를 유지한다. 슬롯 이름을 제거했다가 다시 만들어도 이전 revision을 재사용하지 않아 오래된 요청이 새 기록을 바꾸지 못한다.

게임당 쓰기 슬롯은 main을 포함해 10개다. 복구 기록의 한도와 병합 원본 보존 규칙은 `POC_API_CONTRACT.md`에 있다. 모든 자동 저장을 무제한 영구 버전으로 보관하지는 않는다.

### Google 연결

Google 설정이 없으면 설정 필요 상태를 보여 주며 게스트 기능은 계속 쓸 수 있다. client ID/secret을 설정하면 실제 Google authorization code·PKCE·state·nonce와 서버의 ID token 검증을 사용한다. 가짜 로그인 성공 상태는 제공하지 않는다.

Google 연결 후 기존 게스트 저장을 계정에 옮길 때는 명시적인 선택을 거친다. 충돌하는 진행은 임의로 하나를 덮어쓰지 않는다. 구체적인 병합 정책과 응답은 API 계약에 있다. 로그인 성공·취소·콜백 오류·실계정 병합은 사용자 소유 OAuth client로 현장에서 확인해야 한다.

## 4. 관리자 사이트와 측정

관리자 화면은 사용자 사이트와 별도 주소·웹 루트다. 설치 중 정한 관리자 비밀번호로 로그인하며 public API는 관리자 경로를 제공하지 않는다. 관리자 API는 loopback에 바인딩한다. 같은 Node 프로세스와 DB를 사용하는 PoC이므로 별도 OS 서비스까지 분리된 구조는 아니다.

### 세 가지 데이터 영역

| 화면 | 의미 | 운영 변경 |
|---|---|---|
| 실제 이용 기록 | 기본 live 방문·플레이·저장·이벤트 | 게임 공개·비공개 변경 가능 |
| QA 실행 기록 | 서버에서 QA로 고정한 검증 세션의 이벤트 | 지표·오류 조회. 공개 상태 변경 버튼은 비활성 |
| 독립 가상 예제 | DB를 바꾸지 않는 고정 코호트 계산 예시 | 필터·변경 없음. 실제 성과가 아님 |

새 QA는 첫 화면 노출 전에 세션을 서버에서 분류한다. 클라이언트 이벤트 속성에 `qa`를 적는 방식으로 실제 이용자를 임의 전환하지 않는다. QA 인증은 관리자 권한을 주지 않으며 실제 Google 연결을 허용하지 않는다. 이전 0.1에서 QA 표식 없이 쌓은 데이터는 자동으로 추론해 재분류하지 못한다.

### 주요 지표와 해석

- 카드 가시 노출은 50% 이상이 1초 이상 보이는 조건으로 수집한다. 같은 노출 기회를 중복 분모로 세지 않는다.
- 카드 CTR은 유효 노출 기회에 연결된 클릭 / 해당 유효 노출이다. 분모가 없으면 0% 대신 대상 없음을 표시한다.
- 서버 play session, 게임 ready, 검증된 활성 10초/60초, 라운드 완료, 저장 성공을 구분한다.
- 숨김 탭·일시정지·중복 heartbeat·겹치는 탭 구간을 그대로 활성 시간에 더하지 않는다. 서버가 허용한 구간을 사용한다.
- D1/D7/D30은 최초 유효 플레이 날짜에서 각각 정확히 1·7·30일 뒤 돌아온 비율이다. 그 이후 아무 날에 돌아온 누적 리텐션과 다르다.
- Dn은 대상 날짜가 끝난 뒤 24시간의 확정 여유를 둔다. 아직 성숙하지 않은 코호트는 `집계 대기`/null이며 실패나 0%로 표시하지 않는다.
- 날짜 필터는 일반 지표에서는 그 기간의 활동, 리텐션에서는 전체 이력으로 구한 최초 활동일의 범위를 뜻한다. 기간 밖에 발생한 Dn 재방문도 해당 코호트의 재방문 판정에 사용한다.
- 세션 시작·ready·milestone은 발생 시점이 달라 기간별 집계가 같은 세션 집합을 뜻하지 않는다. 화면의 단계 수를 임의로 나누어 동일 코호트 전환율로 해석하지 않는다.

게임 선택 시 게임 자체의 최초 활동 코호트를 보여 준다. 기간·게임 조건은 오류 목록에도 적용한다. 게임 공개 상태 변경과 로그인을 감사 기록으로 남긴다. 실제 D30 성과는 실제 이용자와 코호트 성숙 시간이 있어야 확인할 수 있다.

## 5. 설치와 현장 수용

### 최초 설치

ZIP을 풀고 **64비트 관리자 Windows PowerShell 5.1** 또는 관리자 권한으로 `Install.cmd`를 실행한다. 기본 설치 경로는 `C:\PlayHubPoC`다. 공유 PC의 IP를 명시할 수 있다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-IIS.ps1 -ShareHost 192.168.0.10
```

예시 IP는 해당 PC의 LAN IP로 바꾼다. 설치 시 관리자 비밀번호를 직접 입력한다. 사용자 사이트는 `http://서버-IP:8080`, 관리자 사이트는 설치 PC의 `http://localhost:8081`이다. 사용자 API는 8090, 관리자 API는 127.0.0.1:8091을 사용한다. 관리자 포트는 다른 PC에 공유하지 않는다.

### 자동 현장 점검

```powershell
.\Validate.cmd -InstallRoot C:\PlayHubPoC -InstallTools
```

실제 IIS 사이트·웹 루트·바인딩·API 소켓·예약 작업·설정 ACL을 관측한다. 관리자 인증 HTTP 검사와 Edge 브라우저 검사를 별도 프로세스에서 실행해 `reports\poc-acceptance.html`에 모은다. 두 자식 도구가 각각 관리자 비밀번호를 요청할 수 있다. QA 도구 설치 후에는 `-InstallTools`를 생략한다.

`-SkipBrowser`는 부분 검증이다. 기존 성공 보고서를 새 결과로 재사용하지 않고, 실행 도구가 없거나 실패하면 pass로 바꾸지 않는다. 자동 검사만 통과하면 `automated_passed_manual_pending`이며 다음 항목은 직접 확인한다.

| 현장 행동 | 완료 증거 |
|---|---|
| 두 번째 LAN PC에서 사용자 주소 열기 | 검색·게임 실행·저장 가능, 관리자 주소·API 접근 불가 |
| 호스트 localhost에서 실제 Google 연결 | 계정 선택·동의·취소·기록 연결·로그아웃 결과 |
| Windows 재부팅 | 사이트·API 자동 시작, 기존 게스트 이어하기 |
| 백업·검증·명시 복원 | 복구 보고서, 원본 보존, 해당 시점 저장의 재개 |

Google localhost 시험은 사용자 사이트도 `http://localhost:8080`에서 연다. 다른 PC에서 호스트의 localhost callback을 사용할 수는 없다. LAN 밖을 포함한 공유 Google 로그인은 HTTPS와 등록된 도메인 구성이 필요하다. 기본 LAN PoC를 인터넷 공개 서비스로 간주하지 않는다.

## 6. 운영과 데이터 복원

`Backup-Data.ps1`은 SQLite 온라인 백업과 integrity check, SHA-256 메타데이터를 만든다. `Restore-Data.ps1 -VerifyOnly`는 서비스를 멈추지 않고 해당 백업을 검사한다. 실제 복원은 API를 멈춘 뒤 파일을 교체하고 다시 검증한다. 원본 DB와 관련 파일은 보호된 복구 폴더에 보존한다.

복원은 플랫폼 DB 전체를 과거 시점으로 돌리는 작업이다. 백업 이후 저장·지표는 복원된 현재 DB에 포함되지 않는다. 실패하면 원본을 되돌리고, 프로세스가 중간에 종료되면 maintenance lock을 유지해 반쯤 교체된 DB로 서비스를 시작하지 않는다. 중단 복구는 `-RecoverInterrupted`로 명시한다.

백업에 있던 로그인 세션을 그대로 부활시키지 않는다. 현재 유효한 일반 게스트는 현재 DB와 백업 모두 같은 미연결 게스트인 경우에만 쿠키를 유지할 수 있다. Google·관리자 세션, 이미 로그아웃한 세션은 복원 뒤 다시 인증해야 한다. 현재 DB가 손상되어 세션을 읽지 못하거나 게스트가 백업 시점에 존재하지 않았다면 기존 쿠키로 진행을 회수할 수 없다.

애플리케이션 release 복원과 데이터 복원은 별개다. 업데이트 시 지원 DB 스키마를 확인하고, 새 스키마를 읽지 못하는 과거 코드로 무조건 되돌리지 않는다. 실행 명령·자동 백업·중단 복구·ACL·실패 처리의 상세 절차는 `INSTALLATION_AND_RECOVERY.md`를 따른다.

## 7. 개발 검증과 패키지 구성

```text
node tools/acceptance.mjs
node tools/acceptance.mjs --with-python
```

새 빌드, Node 회귀, 전체 공개 상태 HTTP, 기존 비공개 게임 유지 HTTP, 선택 Python 검사를 실행한다. Node 회귀에는 인증·권한·Google 토큰 경계·저장 충돌·QA 분리·리텐션·슬롯 복원·실제 SQLite 데이터 복원·게임 규칙·포털 상태 전이가 포함된다. HTTP는 임시 DB와 실제 Node 소켓을 사용한다. 설치 서비스의 데이터를 수정하지 않는다.

검사를 시작하고 끝낼 때 코드 지문을 비교한다. 코드가 바뀌었으면 최종 소스로 재검증해야 한다. `acceptance.html`의 환경 확인 항목은 Windows·브라우저·Google을 미실행으로 유지한다. Node/VM 검사 결과를 브라우저 렌더링 통과로 바꾸지 않는다.

| 경로 | 용도 |
|---|---|
| `README.md`, `START_HERE.html` | 설치·기능·검증 진입점 |
| `web/user`, `web/admin` | 사용자/관리자 화면 소스 |
| `games`, `shared`, `catalog` | 8게임·SDK·게임 목록 |
| `server` | 인증·저장·이벤트·지표·SQLite |
| `dist/user`, `dist/admin` | 빌드된 분리 IIS 웹 루트 |
| `tools`, `scripts` | 빌드·수용 검사·IIS 설치·백업·복구 |
| `tests`, `qa`, `automation` | Node 회귀·선택 브라우저·Python 검증 |
| `reports` | 이번 실행의 검사 증거와 환경 미실행 표시 |
| `docs` | 현행 API·게임·운영·완료·검증 문서 |
| `planning` | 이전 28장 제품 기획 기준선 |
| `specs` | 제품 목표의 schema·OpenAPI·PostgreSQL 설계 예시 |

PoC 런타임에는 외부 npm 의존성이 없다. 선택 브라우저 QA는 별도 `qa` 개발 의존성을, Python 계약 검사는 별도 Python 라이브러리를 사용한다. 외부 제작자의 임의 게임 업로드·결제·광고·랭킹 경쟁·멀티플레이·다중 서버 운영은 이번 PoC 범위에 포함하지 않는다.

# PlayHub 사이트·서버 관리 운영 계획안

- 상태: 초안 (2026-11-20). 현재 구성은 단일 서버 기준이며, 분리 구성(Hub·Forge 별도 호스트)은 [hub-forge-decoupling-plan.md](hub-forge-decoupling-plan.md) 진행에 따라 적용한다.
- 범위: Hub(사용자·관리자), Forge(웹 에디터·Godot 런타임), 배포·백업·모니터링·장애 대응

## 1. 사례에서 가져온 운영 원칙 (Roblox)

| 원칙 | 출처 요약 | 적용 |
|---|---|---|
| 공유 의존성 하나가 전체 장애가 되지 않게 한다. Roblox는 단일 Consul 클러스터 의존으로 2021년 약 73시간 장애를 겪었고, 이후 클러스터 분리·독립 텔레메트리·이중 데이터센터로 보완했다. | [Roblox 사후 보고서](https://about.roblox.com/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021), [InfoWorld 분석](https://www.infoworld.com/article/3648414/robloxs-cloud-native-catastrophe-a-post-mortem.html) | 모니터링은 서비스와 독립된 경로로 둔다. Hub와 Forge는 서로의 장애가 전파되지 않게 분리한다. |
| 서버 간 자격 증명과 브라우저 세션을 분리한다. | Roblox Open Cloud는 API 키·OAuth(액세스 토큰 15분)를 쓴다. | 내부 호출은 공유 시크릿(32자 이상)을 쓰고 주기적으로 교체한다. |
| 비밀 관리는 전용 도구가 맡는다. | Roblox는 Vault를 사용한다. | 시크릿은 저장소와 로그에 두지 않고, 배포 환경의 시크릿 저장소에서 주입한다. |

다른 사례에서 가져온 원칙(출처와 한계는 [reference-cases-research.md](reference-cases-research.md)):

| 원칙 | 사례 | 적용 |
|---|---|---|
| 사용자 콘텐츠는 쿠키 없는 별도 origin에서 서빙하고, 접근은 60초 서명 토큰으로 준다. | Google, 쿠키 없는 origin 패턴 | §9 보안 점검, 분리 계획 P5 |
| 세션 폐기는 즉시 반영돼야 하고, 규모가 커지면 폐기 목록 배포로 전환할 수 있다. | Canva | §7 분리 트리거에 검증 지연 지표 추가 |
| COOP/COEP 에디터는 최상위 문서로 열고 팝업 로그인 흐름을 정기 점검한다. | StackBlitz | §9 정기 점검 |

한계: Roblox 규모의 운영 방식을 그대로 가져오지는 않는다. 규모에 맞게 아래에서 단순화한다.

## 2. 환경과 토폴로지

| 환경 | 구성 | 용도 |
|---|---|---|
| 로컬 | `tools/start-platform.ps1`, Hub + Forge(내부 포트 4177) | 개발·통합 테스트 |
| 스테이징 | 운영과 같은 구성, 별도 도메인·별도 시크릿·테스트 OAuth | 배포 전 검증 |
| 운영(1단계) | 단일 서버: Hub + Forge 프로세스 분리, 리버스 프록시가 `/forge/*` 분기 | 현재 목표 |
| 운영(2단계) | Hub와 Forge를 별도 호스트로 분리. Forge 검증은 HTTPS verify(`PLAYHUB_FORGE_REMOTE_VERIFY=1`) | 분리 리팩토링 이후 |

런타임은 Hub가 Node 24, Forge가 Node 22다. 통합 테스트는 Node 24로 실행한다.

## 3. 배포

- 배포 단위: Hub와 Forge를 각각 독립 배포한다. 같은 릴리스 태그로 묶되 롤백은 개별로 가능해야 한다.
- 절차: 스테이징 배포 → `hub-forge-integration` 통합 테스트와 스모크 → 운영 배포 → 헬스 확인(`GET /api/health`) → 이상 시 직전 버전으로 롤백.
- 변경 순서 원칙: 호환되지 않는 변경(예: 내부 API, 저장소 형식)은 "새 버전이 옛 버전도 읽는 상태로 먼저 배포 → 전환 → 정리"의 세 단계로 나눈다.
- Windows 패키징(`hub/portable`, `forge/Tools/package-windows-server.ps1`) 경로는 별도 검증 항목이다. `package-windows-server.ps1`은 아직 문법 검증을 하지 못했다.

## 4. 시크릿과 설정

| 항목 | 규칙 |
|---|---|
| `PLAYHUB_FORGE_INTERNAL_SECRET` | 32자 이상. 원격 verify에서는 필수(기동 시 검사됨). 분기별 교체하고, 교체 때는 Hub와 Forge가 이전·신규 값을 동시에 받는 전환 기간이 필요하다(현재 미지원, 구현 항목). |
| Google OAuth·Drive 자격 | 시크릿 저장소에서 주입. 저장소에 커밋하지 않는다. |
| 관리자 계정 | 관리 리스너는 루프백 전용을 유지한다. 외부에 노출하지 않는다. |

## 5. 백업과 복구

- 대상: Hub SQLite 데이터(`dataDir`), 계정별 프로젝트·릴리스(Forge `accounts`), 설정 파일.
- Hub에는 복구 도구(`hub/tools/restore-data.mjs`)와 관련 테스트가 있다. 정기 백업과 복구 리허설 주기는 아직 정해지지 않았다.
- 목표값(제안): RPO 24시간, RTO 4시간. 사용자 수와 수익 모델이 정해지면 조정한다.
- 저장소가 객체 스토리지로 이관되면(분리 계획 P3) 버전 관리와 보존 정책으로 대체한다.

## 6. 모니터링과 알림

- 외부에서 확인하는 헬스 체크: Hub `/api/health`, Forge `/api/health`(인증 없이 허용되는 경로).
- 핵심 지표(제안): 가용성, 로그인 성공률, Forge 세션 검증 실패율(503 `AUTH_SERVICE_UNAVAILABLE` 비율)과 검증 호출 p95 지연(§7 전환 기준용), 에디터 런타임 점유(전체 16개·계정당 4개 한도 대비), 빌드 큐 대기, 디스크 여유.
- Hub에는 `metrics.mjs`와 관리자 콘솔 지표가 이미 있다. Forge 쪽 지표는 추가가 필요하다.
- 알림은 서비스와 독립된 경로(외부 모니터)로 보낸다. 위 Roblox 사례처럼 감시가 감시 대상에 의존하면 장애 때 눈이 먼다.

## 7. 용량과 한도

- Forge 에디터 런타임은 전체 16개·계정당 4개로 제한되어 있다. 동시 에디터 사용자가 한도에 가까워지면 Forge를 별도 호스트로 분리하고 수평 확장하는 것이 분리 계획의 트리거다.
- 96MB 규모 에디터 wasm은 CDN 서빙 후보다(교차 출처 격리 헤더 검증 필요).
- 기준값(제안): 런타임 점유 70% 초과가 지속되거나 Forge CPU로 Hub 응답이 느려질 때 분리를 시작한다.
- 세션 검증 방식 전환 기준(제안): Forge가 요청마다 Hub에 보내는 검증의 p95 지연 또는 Hub의 verify 처리량이 병목 징후를 보이면, 분리 계획 P1 후속 선택지(서명 세션 + 폐기 목록 배포)를 검토한다. 그 전에는 현행 매 요청 검증을 유지한다. 지표는 §6에 추가한다.

## 8. 장애 대응

| 심각도 | 예 | 목표 |
|---|---|---|
| 1 | Hub 전체 불가, 로그인 불가, 데이터 손상 | 즉시 대응, 롤백 우선 |
| 2 | Forge 불가(Hub 정상), 빌드 큐 정지 | 당일 복구 |
| 3 | 일부 기능 저하 | 정기 일정 내 |

- 원칙: 먼저 복구하고 원인은 나중에 찾는다. Forge 인증은 fail-closed라서 Hub 검증이 막히면 Forge 사용이 차단된다. 이 동작은 의도된 것이므로, 복구 우선순위는 Hub 검증 경로 복구다.
- 장애 후 24시간 안에 사후 보고서(타임라인, 원인, 재발 방지)를 남긴다.

## 9. 보안 점검

- 사용자 게임이 세션과 같은 origin에서 서빙되는 점이 현재 가장 큰 구조적 약점이다(분리 계획 P5).
- 내부 verify 엔드포인트는 기본 비공개이며, 원격 모드는 시크릿·HTTPS·요청 제한이 모두 있을 때만 켠다.
- 외부에서 들어온 `X-PlayHub-*`·`X-Forwarded-*` 헤더는 프록시에서 제거하는 현재 규칙을 유지한다.
- 사용자 콘텐츠 origin을 도입하면(P5) iframe `sandbox`에 `allow-same-origin`이 포함되지 않았는지, 콘텐츠 origin이 쿠키를 설정하지 않는지 배포 때마다 자동 검사한다.
- 정기 점검: 의존성 취약점, 시크릿 교체 기록, 관리자 접근 로그, COOP 환경에서의 팝업 로그인 흐름.

## 10. 담당과 일정

담당자·일정은 아직 정해지지 않았다. 워크트리 소유권 기준(`tools/worktree-ownership/owners.json`)을 따라 Hub는 PlayHub-Admin·Platform, Forge는 Forge 브랜치 계열이 소유한다.

## 11. 열린 결정

1. 호스팅 대상(자체 서버 / Cloud Run 등)과 예산.
2. 백업 주기와 RPO·RTO 확정.
3. 모니터링 도구 선정(외부 모니터 + 로그 수집).
4. 시크릿 저장소 선정과 교체 전환 기간 구현.
5. 분리 시작 트리거 기준값 확정.

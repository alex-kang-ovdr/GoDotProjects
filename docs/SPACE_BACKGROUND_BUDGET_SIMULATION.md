# 우주 배경 메모리·배포 용량 예산 시뮬레이션

## 상태와 전제

이 문서는 독자적 Canvas 2D 우주 배경 생성기를 구현하기 전에, 배포 용량과 브라우저 메모리 예산별로 가능한 접근을 비교한 시뮬레이션이다. 수치는 2026-09-15에 현재 워크트리의 PNG 파일 크기와 RGBA8 메모리 공식을 사용해 계산했다. 실제 브라우저의 이미지 복제, GPU 백버퍼, 가비지 컬렉션, 드라이버 메모리는 포함하지 않았으므로 성능 보증 수치가 아니다.

## 계산 규칙

- 디코드 이미지·오프스크린 캔버스 메모리 후보: `너비 × 높이 × 4 bytes`.
- 1280×720 메인 Canvas 한 장: `1280 × 720 × 4 = 3.516MiB`.
- 1920×1080 메인 Canvas 한 장: `7.910MiB`.
- 3840×2160 메인 Canvas 한 장: `31.641MiB`.
- 성운 캐시: `타일 변 × 타일 변 × 4 × 타일 수`.
- 별 셀 수: `(ceil(화면 너비 / 72 + 2)) × (ceil(화면 높이 / 72 + 2))`. 1280×720에서는 240셀, 1920×1080에서는 493셀이다.
- 코드 gzip 크기는 JavaScript 미니파이·압축 결과를 아직 측정하지 않은 구현 후보값이다. PNG 전송 크기는 실제 로컬 파일을 측정한 값이다.

## 현재 PNG 기준선

현재 게임이 로드하는 `bg_1_1_cc0.png`와 `space003_cc0.png`는 전송 합계 **1.268MiB**, 디코드 이미지 메모리 후보 **11.597MiB**다. 메인 Canvas까지 단순 합산하면 약 **15.113MiB**이며, 이는 브라우저 내부 복제본을 제외한 하한 후보일 뿐이다.

레퍼런스 PNG 여섯 장을 모두 동시에 로드하는 방식은 전송 **7.655MiB**, 디코드 메모리 후보 **50.659MiB**가 된다. 이 방식은 전투 배경의 기본 구현으로 사용하지 않는다. 현재는 두 장만 로드하며, 나머지는 레퍼런스 보관용이다.

## 예산 A · 초경량 별밭

- **배포 추가 예산**: gzip 2–6KiB 후보, 이미지 자산 0 bytes.
- **추가 런타임 메모리 목표**: 0.25MiB 이하. 메인 Canvas는 기존 게임 비용이므로 별도 계산한다.
- **구현**: 시드·월드 좌표·72px 셀을 해시해 별 위치, 크기, 색, 반짝임 위상만 계산한다. 전역 별 배열과 오프스크린 캔버스를 만들지 않는다.
- **프레임 작업량**: 1280×720에서 최대 240셀 해시·소수의 `fillRect` 호출.
- **보이는 결과**: 어두운 심우주와 별 밀도 차이. 성운·은하수의 구역 정체성은 약하다.
- **적합한 경우**: 배포 파일이 수십 KiB 이하여야 하거나, 내장 그래픽·저사양 기기에서 배경을 거의 비용 없이 유지해야 할 때.
- **폴백**: 이 방식은 항상 사용 가능하며, 뒤 레이어를 모두 끄는 최종 폴백이다.

## 예산 B · 권장 경량 절차 배경

- **배포 추가 예산**: gzip 8–20KiB 후보, 이미지 자산 0 bytes.
- **추가 런타임 메모리 목표**: 약 1.75MiB. 256×256 성운 타일 6개는 1.500MiB, 생성용 타일 한 장은 0.250MiB다.
- **구현**: 예산 A의 별밭에 저알파 은하수 띠와 3옥타브 값 노이즈 성운 타일 캐시를 더한다. 화면에 필요한 성운 타일만 3×3 범위에서 선택하고, 캐시는 LRU 6개로 제한한다.
- **생성 작업량**: 2×2 블록 단위·3옥타브일 때 256px 타일 하나당 해시 샘플 후보 49,152회. 새 타일은 한 프레임에 한 장만 생성한다.
- **보이는 결과**: 별·은하수·낮은 대비 성운으로 구역별 색조 차이를 제공한다.
- **적합한 경우**: 현재 프로젝트의 무의존성 Canvas 2D 목표와 전투 가독성을 함께 유지하려는 기본 선택.
- **위험과 회복**: 첫 타일 진입에서 프레임 스파이크가 나면 캐시 수를 2개로 줄여 0.75MiB 목표로 낮추거나, 성운을 128×128로 내린다.

## 예산 C · 풍부한 절차 성운

- **배포 추가 예산**: gzip 20–45KiB 후보, 이미지 자산 0 bytes.
- **추가 런타임 메모리 목표**: 약 7MiB. 512×512 캐시 6개가 6MiB, 생성용 타일 한 장이 1MiB다.
- **구현**: 예산 B의 모든 레이어에 더 높은 해상도 성운, 구역별 팔레트, 먼지대 마스크를 추가한다. 캐시 정책과 프레임당 타일 한 장 생성 제한은 유지한다.
- **생성 작업량**: 2×2 블록 단위·3옥타브일 때 512px 타일 하나당 해시 샘플 후보 196,608회.
- **보이는 결과**: 확대 시 성운 블록감이 줄고 장거리 항로의 구역 구분이 강해진다.
- **적합한 경우**: 예산 B의 실제 프로파일이 통과하고, 1280×720 이상의 화면에서 성운 품질이 게임의 가독성을 해치지 않는다고 확인된 경우만.
- **위험과 회복**: 프레임 예산을 넘으면 즉시 예산 B의 256px 타일과 저알파 팔레트로 내린다. 512px 타일을 매 프레임 재계산하는 방식은 허용하지 않는다.

## 예산 D · 현재 CC0 하이브리드

- **배포 추가 예산**: 현재 로드 두 장 기준 PNG 1.268MiB.
- **추가 런타임 메모리 후보**: 디코드 이미지 11.597MiB. 메인 Canvas를 더한 단순 하한은 15.113MiB다.
- **구현**: CC0 별 타일과 1600px 성운 한 장을 저속 패럴랙스로 합성하고, 셀-해시 별을 전경에 더한다.
- **보이는 결과**: 즉시 풍부한 성운 질감. 구현 위험이 가장 낮다.
- **적합한 경우**: 첫 시각 품질 검증, 절차 생성기와의 A/B 비교, PC 메모리 여유가 충분한 배포.
- **제한**: 이미지 해상도·팔레트가 고정되고, 모바일·저사양에서 디코드 이미지 비용이 절차 예산 B보다 크다. 독자적 생성 방식의 최종 목표는 아니다.

## 선택 시뮬레이션

### 배포 증가를 16KiB 이하로 제한할 때

예산 A를 선택한다. 별 분포와 은하수 띠까지만 사용하고 성운 캐시는 넣지 않는다. 기대되는 추가 메모리는 0.25MiB 이하이며, 1280×720에서 240개 셀만 처리한다. 구역의 시각 차이는 색조와 띠 방향으로 보완한다.

### 추가 메모리를 2MiB 이하로 제한할 때

예산 B를 선택한다. 256px 성운 캐시 6개가 1.5MiB이므로 생성 캔버스 0.25MiB를 더해도 1.75MiB 후보에 머문다. 캐시 타일의 브라우저 내부 복제 때문에 실제 측정이 2MiB를 초과하면 캐시 수를 2개로 낮추고, 성운 타일을 128px로 낮춘다.

### 추가 메모리를 8MiB 이하로 제한할 때

예산 C를 실험할 수 있다. 512px 캐시 6개와 생성 타일을 단순 계산하면 7MiB다. 다만 1920×1080 메인 Canvas 자체가 7.91MiB이므로, 배경 추가 비용이 아니라 전체 렌더러 메모리를 제한해야 하는 저사양 목표에는 권장하지 않는다.

### 시각 품질 우선이고 추가 이미지가 허용될 때

예산 D를 사용한다. 현재 구현과 동일하며, 절차 생성기의 성능·가독성 검증 전까지의 안전한 비교 기준이다. 레퍼런스 PNG 여섯 장을 모두 런타임 로드하는 선택은 전송 7.655MiB와 디코드 후보 50.659MiB 때문에 제외한다.

## 권장 구현 경로

기본 목표는 **예산 B**다. PBG-1에서 결정론 시드·좌표 해시를 구현하고, PBG-2에서 예산 A의 별밭을 CC0 별 타일과 비교한다. PBG-3에서 은하수 띠를 추가한 뒤, PBG-4에서만 256px 성운 캐시를 도입한다. 평균 배경 비용과 최악 비용이 목표를 넘으면 예산 A로 되돌리고 CC0 하이브리드는 비교 폴백으로 유지한다.

512px 성운 캐시와 고품질 팔레트는 PBG-6의 실제 측정 후 선택한다. 이미지 파일 삭제는 절차 예산 B가 시각 가독성과 성능에서 통과한 뒤에만 검토한다.

## 측정 시나리오

각 예산 후보에서 같은 시드·경로로 다음을 기록한다.

1. 1280×720과 1920×1080에서 10분간 직선 이동한다.
2. 일반 적 상한, 부유 부품 상한, 파티클 상한이 동시에 존재하는 전투 3분을 기록한다.
3. 새 성운 타일 경계 통과 직전·직후의 프레임 시간을 따로 기록한다.
4. 보스·정거장·회수 부품·레이저가 배경보다 눈에 잘 띄는지 수동 확인한다.
5. 메모리 측정 도구에서 이미지, Canvas, JavaScript 힙을 가능한 범위로 분리해 기록한다.

통과 후보는 평균 배경 CPU 비용 2ms 이하, 최악 4ms 이하라는 계획 목표와 전경 가독성을 모두 만족해야 한다. 이는 통과 전까지 후보 기준이며, 최소 사양 실측 전에는 성능 보증으로 표기하지 않는다.

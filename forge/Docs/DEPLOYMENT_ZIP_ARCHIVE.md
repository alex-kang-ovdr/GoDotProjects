# Binary deployment ZIP archive

This is separate from the release-source JSON snapshot adapter. `DeploymentZipArchive({enabled:false, directory, drive, resolveOwnedPackage})` exposes async `archive({accountKey,projectId,releaseId})` and `status(...)`. Derive accountKey from a verified server session, enforce origin/CSRF in the route. The server-only resolver must verify project/release ownership and return the immutable built ZIP as Buffer. Client paths, owner overrides and content are not accepted. Pair with `DriveZipStore({enabled,folderId,getAccessToken,fetchImpl,timeoutMs})`; keep operator OAuth tokens and session URIs server-only. Use a dedicated package folder and private journal distinct from snapshots.

Validator: 64 MiB compressed, 128 MiB aggregate expanded, 2048 entries, root index.html required. STORE and DEFLATE supported; CRC, local/central matching, case/NFC collisions, file-parent collisions, overlapping/unindexed data, traversal, Windows device names, symlinks, encryption, executable extensions and compression amplification are rejected. The deliberately restricted format rejects ZIP64, comments, extra fields and data descriptors. Existing export-godot-project.cjs zipFiles output is tested. Validation inflates bounded content in memory to verify CRC; it never extracts to disk or runs game content. ZIP structure verification is NOT malware scanning, browser gameplay verification or a guarantee of safe code. Published content requires a separately isolated serving origin and approval workflow.

The journal stores immutable package.zip and atomic manifest.json under account/project/release. Persist reserved Drive ID before upload, retry with the same ID, never overwrite conflicting content. Single-process queues serialize concurrent requests; multi-process/distributed workers are unsupported. File fsync/rename is not a full database transaction or guaranteed directory durability across power loss. Local integrity and owner bindings fail closed. Restarts require the owned build resolver to still provide identical bytes.

Drive uses resumable initiation then one bounded PUT, not chunk resumption. It checks folder/owner/project/release metadata and downloads bounded ZIP bytes for SHA256 verification. The archive independently compares remote bytes before committed. Interrupted uploads retry using the durable ID; 409 verifies existing content without overwrite. Error text is redacted. A committed status is a historical verified receipt, not a fresh check against later remote deletion. No public links, permission changes, retention deletion or automatic publication. Quota reservation/admission must be supplied by the operator's existing policy before enabling. Larger packages require a reviewed streaming/chunked implementation.

Status separates localRecorded/cloudVerified and always published=false, publicationPending=true, runnableVerified=false. It returns no token, file ID, session URI, files or private server paths. Default disabled. Tests use in-memory fetch mocks; actual OAuth, uploads, quotas and browser runtime remain unverified.

References: https://developers.google.com/workspace/drive/api/guides/manage-uploads and https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT

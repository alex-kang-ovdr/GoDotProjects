# Submission release-source archive (disabled by default)

`SubmissionDriveArchive({enabled, directory, drive, resolveOwnedRelease})` exposes `archive({accountKey, projectId, releaseId})` and `status(...)`. The HTTP adapter must derive accountKey from a verified server session and enforce CSRF/origin checks, never trust a body owner. The resolver must open that account's private PlatformStore, locate the exact immutable release, and return `{accountKey, projectId, releaseId, revision, files}`; never substitute the current editable project files. Missing/foreign releases fail as not found. No server route is enabled by this module.

Use an operator-configured DriveSnapshotStore with server-only token provider and a dedicated private journal directory distinct from project synchronization. A durable reserved ID precedes upload. Upload receipt AND authenticated remote readback/hash verification are required before `cloudVerified=true`. Status reports local journal separately; it never returns operator token, Drive ID, public link or files. Retry archive with the same identity resumes a failed upload using the same reserved ID. A prior verified receipt is historical evidence, not a fresh guarantee against later remote deletion. Never serve or execute the stored content as trusted code.

This stores an immutable **release-source JSON package**, not a binary ZIP, compiled Godot web build, approved catalog publication or runnable deployment. Existing adapter cap: 4 MiB, at most 512 text entries including one reserved metadata file. Different releases with different metadata at the same project revision intentionally conflict. Set publicationPending=true and published=false until an independent authorized publication workflow succeeds. Binary deployment packages require a separate bounded binary adapter. Runtime dependencies and export verification are outside this implementation.

Journal atomicity and concurrency are single-process only. Explicit quota reservation is not implemented; enable only with the existing operator quota policy and storage limits. No delete, permission/public-link changes, OAuth activation, external network tests, or automatic retention is performed. Tests use mocks and temporary directories, not real credentials.

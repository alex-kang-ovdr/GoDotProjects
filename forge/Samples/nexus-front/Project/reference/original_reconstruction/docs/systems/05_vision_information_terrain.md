# 05. 시야·전장의 안개·정보 권한·지형

## 1. 문서의 범위와 판정 수준

기준일은 **2026-11-17**, 검토 기준은 **공개 패치 26.22 / Data Dragon 16.22.1**이다. 개별 규칙은 마지막으로 확인한 패치와 출처를 따로 적는다. 최신 버전 번호를 알고 있다는 사실만으로 모든 시야 수치와 챔피언 예외가 검증된 것은 아니다.

이 문서는 시야를 단순한 검은 화면 효과가 아니라 **관측, 대상 선택, 전투 단서, 서버가 전달하는 정보**의 결합으로 분석한다. 아래의 자료 구조와 처리 순서는 공개 자료를 바탕으로 작성한 **복원 구현안**이다. Riot의 실제 서버 코드, 네트워크 패킷 구조, 현재 시야 격자 원본을 회수했다는 의미가 아니다.

| 표시 | 의미 |
|---|---|
| 공식 확인 | 해당 공식 자료에 직접 적힌 규칙 또는 변경 |
| 역사 자료 | 당시에 공개된 설계. 현재 구현과 같다고 보증하지 않음 |
| 복원 구현안 | 관측 가능한 동작을 만들기 위한 본 문서의 설계 |
| 사용자 커스텀 확장 | 고저차, 공격 원점 공개, 건물 기억 등 사용자가 추가한 요구 |
| 미확인 | 정확한 수치·예외·서버 구현을 공식 자료만으로 결정할 수 없음 |

**연계 문서:** [전투 및 능력치](01_combat_stats_damage.md), [경제·경험치·아이템](02_economy_experience_items.md), [원문 출처 기록](../vision_meta_sources.json). 다른 문서의 세부 파일명이 바뀌면 패키지 색인을 우선한다.

## 2. 원작 근거를 다시 정리한 결과

| 항목 | 확인한 내용 | 적용 범위 |
|---|---|---|
| 전장의 안개 | 챔피언·능력·와드 등이 정보를 드러내는 시스템이며, 표시 경계를 부드럽게 만드는 일과 판정 정확도는 구별해야 한다. | Riot 기술 회고 [VM01] |
| 격자 크기 | 2016년 기술 글에 128×128 시야 격자와 해상도 증가 비용이 등장한다. | **역사 자료**. 2026년 내부 격자나 권장 UE 해상도로 확정하지 않음 |
| 은신 분류 | 위장과 투명은 별도 범주이며 제어 와드가 투명 챔피언까지 일괄 노출하지 않는다. | 2017 시즌 설명 및 11.24 수정 기록 [VM02][VM23] |
| Faelight | 26.1에 특정 와드 지점의 추가 시야가 도입되었다. | 도입 규칙 [VM03] |
| Faelight 후속 수정 | 26.3에서 강가 작은 수풀의 추가 영역을 축소하고 허수아비·와드 변장 효과와 실제 시야를 구별했다. | 마지막 확인 변경 [VM04] |
| 와드 재사용 대기시간 | 26.3 노란 장신구의 레벨별 구간은 210~90초로 조정되었다. | 26.1의 170~90초를 최신값으로 그대로 복사하면 안 됨 [VM04] |
| 고지대 우위·건물 기억 | 사용자 요구로 설계할 수 있지만, 이 조사에서 원작 전체에 적용되는 동일 규칙을 확정하지 않았다. | 아래 커스텀 프로필로 분리 |

역기획의 핵심은 **어떤 정보가 언제 플레이어의 의사결정을 바꾸는가**이다. 와드는 적의 존재를 알려 공격·회피·오브젝트 진입을 가능하게 한다. 반대로 적이 사라진 사실은 위치를 확정하지 않고 위험의 범위를 넓힌다. 이 해석은 원작 설계 의도에 대한 본 문서의 분석이며, Riot의 성과 지표나 내부 목표를 인용한 것은 아니다.

## 3. 하나의 visible 값으로 합치면 안 되는 상태

다음 표는 복원용 정보 모델이다. 한 대상이 여러 열에서 서로 다른 상태를 가질 수 있다.

| 계층 | 질문 | 예시·불변 조건 |
|---|---|---|
| 지형 탐색 | 이 지형을 과거에 본 적이 있는가? | 탐색한 바닥을 표시해도 현재 적 위치를 알 수 있는 것은 아님 |
| 현재 공간 시야 | 이 좌표를 지금 관측하는가? | 시야원 제거·벽·수풀·특수 실명 정책에 따라 변함 |
| 개체 식별 | 실제 개체의 모델·팀·상태를 현재 식별할 수 있는가? | 공간이 보여도 은신 규칙이 식별을 막을 수 있음 |
| 위치 단서 | 위치만 잠시 드러났는가? | 윤곽·타격 흔적·투사체와 완전 식별은 별도 |
| 대상 선택 | 이 행동의 대상으로 지정할 수 있는가? | 보이는 대상도 무적·대상 지정 불가 등 다른 조건으로 실패 가능 |
| 효과 적중 | 이미 발사된 효과나 범위 효과가 맞을 수 있는가? | 타깃 선택 권한과 충돌·피해 판정은 동일 함수가 아님 |
| 팀 기억 | 팀이 마지막으로 정당하게 관측한 상태는 무엇인가? | 커스텀 건물 기억에서는 숨은 실제 상태를 읽지 않음 |
| 서버 실제 상태 | 권위 서버가 알고 있는 현재 값은 무엇인가? | 플레이어에게 모두 전달하면 안 됨 |

따라서 **안개가 밝다 → 적이 보인다 → 클릭 가능하다 → 피해를 받는다**를 하나의 연쇄 조건으로 하드코딩하지 않는다. 각 능력은 선택 방식, 판정 시점, 은신 감지 종류, 투사체의 추적·취소 정책을 명시한다. 세부 예외를 확인하지 못한 능력은 미확인 항목으로 남긴다.

## 4. 시야원과 지형의 데이터 계약 — 복원 구현안

~~~ts
type Verification = "official" | "historical" | "inferred" | "custom" | "unknown";

interface VisionEmitter {
  id: string;
  ownerTeam: number;
  sourceEntityId: string | null;
  kind: "champion" | "minion" | "structure" | "ward" | "spell" | "faelight";
  origin: { x: number; y: number; z: number };
  shapeId: string;
  radius: number | null;             // 미확인 값을 0으로 치환하지 않음
  startsAtTick: number;
  expiresAtTick: number | null;
  occlusionProfileId: string;
  detectionProfileId: string;
  enabled: boolean;
  ruleVersion: string;
  verification: Verification;
}

interface VisionBlocker {
  id: string;
  geometryVersion: string;
  blocksMovement: boolean;
  blocksVision: boolean;
  brushRegionId: string | null;
  heightProfileId: string | null;     // 커스텀 고저차 프로필에만 사용 가능
}

interface VisibilityDecision {
  viewerTeam: number;
  entityId: string;
  terrainVisible: boolean;
  entityIdentified: boolean;
  locationCueOnly: boolean;
  allowedFieldMask: string[];
  reasonCodes: string[];
  observedAtTick: number;
  ruleVersion: string;
}
~~~

좌표계·거리 단위·반경의 기준점은 하나의 맵 매니페스트에서 정한다. Data Dragon의 수치, 현재 웹 게임의 1600 단위 지도, UE의 센티미터를 동일 단위라고 취급하지 않는다. 단위 변환은 콘텐츠 제작 단계에서 명시하고 실제 플레이 판정은 한 좌표계에서 수행한다.

시야원에 소유 개체를 직접 참조시키더라도 생명주기는 분리한다. 개체 삭제, 팀 변경, 와드 비활성화, 일시적 시야 제한, 지형 변화는 시야 기여분을 제거하거나 다시 계산하는 사건이다. 지형이 바뀌면 이동 캐시와 시야 캐시를 각각 무효화한다. 한쪽의 무효화가 다른 쪽에서 우연히 일어나도록 의존하지 않는다.

### 4.1 수풀과 벽

**복원 구현안:** 이동 차단 메시, 시야 차단 경계, 수풀 영역을 별도 데이터로 만든다. 하나의 벽 오브젝트에 모두 들어갈 수 있으나 판정 채널은 분리한다. 수풀은 단순히 어두운 원이 아니라 관측자·대상·시야원의 위치 관계를 사용하는 영역 정책으로 취급한다.

시야원과 대상 사이를 직선으로 검사하는 것만으로 모든 수풀 예외를 복원했다고 말할 수 없다. 같은 수풀 연결 영역, 수풀 경계, 다른 수풀로 넘어가는 선분, 벽과 수풀의 중첩, 원거리 공개 능력, 지형 변환 후 영역 번호 변경을 별도 사례로 검증해야 한다.

**미확인 원본:** 소환사의 협곡의 정확한 시야 차단 폴리곤, 지형별 예외, 현재 내부 높이 데이터, 가장자리 샘플링·보정 규칙. 공개 미니맵 이미지는 외관 자료이며 판정 충돌 메시가 아니다.

### 4.2 은신·위장·감지

공식 시즌 설명에서 제어 와드와 투명 상태를 구별하고, 11.24 패치에서도 투명 대상 주변에 잘못 표시되던 공개 시각 효과를 수정했다.[VM02][VM23] 따라서 제어 와드 하나를 모든 은신을 해제하는 만능 탐지기로 구현하면 분석 단계에서부터 잘못된다.

복원용 감지 정책은 다음 범주를 갖는다. 아래 이름은 구현 편의를 위한 분류이며 Riot 내부 enum이 아니다.

| 감지 정책 | 복원 계약 | 별도 검증할 사항 |
|---|---|---|
| 일반 시야 | 공간 관측과 일반 개체 표시를 판정 | 수풀·벽·시야 제한과의 우선순위 |
| 위장 감지 | 특정 위장 규칙에만 대응 | 근접 범위, 대상별 조건, LOS 필요 여부 |
| 완전 공개 | 특정 능력이 허용한 식별 정보를 제공 | 어떤 은신과 대상 지정 불가에 적용되는지 |
| 위치 단서 | 위치·윤곽만 제공하고 실제 타깃 ID를 공개하지 않을 수 있음 | 단서 지속시간, 클릭 가능 여부 |
| 와드 감지·무력화 | 와드의 표시와 시야 기여 중단을 독립 처리 | 제어 와드·장신구·특수 와드별 예외 |

감지 가능 범위와 모든 챔피언 예외는 이번 공식 정적 데이터만으로 완성되지 않는다. 수치가 없는 곳에 관행적으로 900, 1100 같은 값을 채우지 않는다. 실제 능력별 검증 기록에는 감지자, 대상 상태, 거리, 장애물, 시야원 종류, 결과 프레임을 함께 남긴다.

## 5. 2026 Faelight를 복원할 때의 주의점

**공식 확인:** 26.1은 Faelight에 설치한 와드의 기본 반경을 25% 늘리고, 45초간 지점별 별도 영역을 밝히는 기능을 설명한다. 추가 영역이 제어 와드의 감지 특성을 그대로 확대하지 않는다는 점도 구별한다.[VM03] 26.3은 일부 강가 지점의 영역을 좁혔으며, 피들스틱 허수아비·니코의 와드 변장이 시각적으로 흉내 낼 때 실제 시야를 획득하거나 기존 와드를 교체하지 않도록 설명한다.[VM04]

이를 **반경이 큰 단일 와드**로만 구현하면 형태·수풀·시각 효과·교체 예외가 섞인다. 다음은 복원 구조 제안이다.

~~~ts
interface FaelightBinding {
  spotId: string;
  actualWardId: string | null;
  bonusAreaGeometryId: string;
  bonusStartedAtTick: number;
  bonusExpiresAtTick: number;
  ordinaryRadiusModifier: number;
  effectsOnlyMimicIds: string[];
  sourcePatch: string;
}
~~~

1. 실제 와드와 장식용 모방 개체를 구분한다.
2. 일반 와드 시야와 Faelight의 추가 영역을 별도 기여분으로 등록한다.
3. 추가 영역의 모양은 좌표 데이터로 관리하고, 강가 지점만 수정하는 패치를 전체 반경 변경으로 번역하지 않는다.
4. 설치·교체·파괴·억제·만료 사건을 별도로 기록한다.
5. 추가 영역만 보이는 상황에서 어떤 적·수풀·와드가 드러나는지 검증한다.
6. 팀 전용 표시와 적이 정당하게 알 수 있는 표시를 나눈다.

억제 중 타이머가 흐르는지, 여러 와드의 교체 우선순위, 늦은 설치의 남은 시간 등 세부 사항은 원문과 관측 사례를 더 확보해 규칙표로 확정한다. 확인되지 않은 동작을 단순 구현 편의에 따라 원작 확정값으로 올리지 않는다.

## 6. 권위 판정과 렌더링 순서 — 복원 구현안

권장 서버 처리 순서는 **동일 논리 틱의 위치·지형 확정 → 시야 기여 갱신 → 은폐·감지 해석 → 팀별 정보 허용 → 행동별 유효성 판정 → 전송용 차이 계산**이다. 이 순서는 구현안이며 원작 틱 순서의 확인 자료가 아니다.

타깃 공격은 최소한 명령 접수, 발사 직전, 적중 시점을 구별한다. 접수 때 보였던 적이 발사 전에 수풀로 사라지면 해당 행동의 취소·추적 규칙을 적용한다. 이미 발사된 투사체가 시야 상실 때문에 사라지는지는 능력별 정책이다. 모든 투사체에 같은 취소 조건을 넣으면 원작 예외를 재현하기 어렵다.

비대상 지정 스킬의 좌표 입력은 위치가 어둡다는 이유만으로 일률적으로 차단하지 않는다. 서버는 사거리·벽 충돌·자원·재사용 대기시간·적중 대상 상태를 별도로 검사한다. 반대로 클라이언트가 숨은 적 ID를 전송했다고 해서 서버가 그 ID를 타깃 명령으로 받아들이면 안 된다.

~~~text
TargetCommand {
  actorId, requestedTargetId, clientSequence,
  actionDefinitionId, submittedAtClientTime
}

ServerDecision {
  accepted, rejectReason,
  authoritativeTick, resolvedActionId,
  visibilityEvidenceId, actionPolicyVersion
}
~~~

거절 사유도 정보가 될 수 있다. 보이지 않는 적의 생사·정확한 위치를 구별하는 상세 오류를 일반 클라이언트에 보내지 않는다. 개발자 로그에는 상세 이유를 남기되, 플레이어 응답은 허용된 정보만 포함한다.

렌더러는 판정 마스크를 보간해 부드러운 경계를 그릴 수 있다. 그러나 흐린 경계 픽셀이 밝아 보인다는 사실을 타깃 선택의 판정으로 사용하지 않는다. 전장의 안개 기술 회고는 시각적 품질과 판정 격자의 구분을 이해하는 역사 자료로만 사용한다.[VM01]

## 7. 팀별 정보 전송 계약 — 복원 구현안

전체 게임 상태를 보낸 뒤 화면에서 감추는 방식은 서버 권한 분리가 아니다. 실제 온라인 복원에서는 팀별로 허용한 필드와 사건만 내보내는 투영 계층이 필요하다.

| 데이터 | 기본 처리 | 주의점 |
|---|---|---|
| 아군 정보 | 팀 정책이 허용한 상태 전송 | 관전자·코치·재접속 권한은 별도 |
| 현재 관측한 적 | 허용한 위치·외관·전투 상태 전송 | 서버 내부 버프·결정 변수까지 자동 공개하지 않음 |
| 관측을 잃은 적 | 추적 중단과 허용된 마지막 단서만 제공 | 새로운 좌표를 계속 보내면 화면이 어두워도 누출 |
| 투사체·위험 영역 | 실제로 공개할 근거가 있는 부분만 전달 | 투사체에서 비공개 발사자의 현재 좌표를 역참조하지 않음 |
| 숨은 중립 몬스터 | 관측·공개 이벤트 정책에 따름 | AI도 같은 정보 계약을 사용하는지 구분 |
| 효과음·피해 숫자·핑 | 정보 채널별 공개 정책 적용 | 모델만 감추고 숫자·미니맵을 갱신하지 않음 |
| 개발 진단·리플레이 | 별도 권한·별도 스키마 | 전체 상태 저장을 플레이어 API로 재사용하지 않음 |

중요한 경계는 **서버는 알고 있지만 플레이어는 모르는 정보**이다. 렌더 가시성과 네트워크 관련성은 같은 개념이 아니다. 클라이언트가 수신하지 않은 적은 서버의 충돌·피해 판정에는 여전히 존재할 수 있다.

## 8. 사용자 커스텀 확장: 언리얼 고저차·벽·공격 원점·건물 기억

이 절은 이전 사용자 요구를 보존한다. **LoL 원작에 동일하게 존재한다고 확정한 기능이 아니다.** 별도 프로필 이름을 예를 들어 CUSTOM_HEIGHT_MEMORY_V1로 두고 원작 규칙 프로필과 함께 기록한다.

### 8.1 2.5D LOS와 구현 편의성

**권장 초기 구현안:** 정적 시야 차단 그리드, 지형 높이, 동적 차단 오버레이를 구성하고 시야원에서 대상 셀까지 DDA 또는 격자 선분 순회로 차폐를 검사한다. UE의 월드 지오메트리에 매 프레임 모든 시야원×모든 셀 Line Trace를 쏘는 방식은 제작 시작은 쉬워도 확장 시 비용이 커진다.

| 구성 | 역할 | 구현상의 이유 |
|---|---|---|
| WorldSubsystem | 팀별 시야·탐색·기억 관리 | 개별 Actor의 Tick 분산을 줄임 |
| VisionEmitterComponent | 위치·반경·팀·갱신 사유 등록 | 디자이너가 Actor에 부착 가능 |
| VisionOccluderComponent | 벽·문·다리 등 차단 정보 제공 | 이동 충돌과 시야 차단을 따로 편집 |
| 정적 베이크 데이터 | 셀 높이·차단 비트·수풀 영역 | 런타임 반복 지형 조회 감소 |
| 동적 차단 계층 | 열리는 문·파괴벽·임시 지형 | 관련 타일만 무효화 |
| GPU 텍스처 | 부드러운 안개 표현 | 논리 판정 결과를 시각화하는 역할 |
| 팀별 Knowledge 저장소 | 마지막 관측 상태 | 실제 Actor와 표시 프록시 분리 |

고지대에서 낮은 곳을 볼 수 있는지, 낮은 곳에서 높은 지형 표면이 가리는지, 눈높이·벽높이를 어떻게 조합하는지는 **사용자 게임의 명시적 규칙**으로 정한다. 높이 차이만으로 무조건 차단하거나, 물리 충돌 메시의 작은 장식이 시야를 막게 만들지 않는다. 중요한 모서리·큰 오브젝트는 다중 샘플로 보강하되 샘플 수와 갱신 빈도는 프로파일링 후 결정한다.

### 8.2 언덕 위에서 공격받으면 공격한 위치를 잠시 공개

공개하는 것은 **공격 당시의 고정 원점**이다. 이후 이동한 공격자를 계속 추적하는 공개 효과와 구분한다.

~~~ts
interface AttackOriginReveal {
  id: string;
  receiverTeam: number;
  originAtAttack: { x: number; y: number; z: number };
  createdAtTick: number;
  expiresAtTick: number;
  radius: number;
  causeEventId: string;
  followsAttacker: false;
  revealsIdentity: boolean;
  grantsTargetability: boolean;
}
~~~

공격 사건이 피해받는 팀에 정당하게 전달될 때 공개 토큰을 생성한다. 발사 순간과 적중 순간 중 어느 시점을 원점 기록 기준으로 삼을지 공격 정의에 명시한다. 발사 후 순간이동한 공격자를 원점 공개가 따라가면 요구에 어긋난다. 공격이 빗나간 경우, 지속 피해, 소환수, 반사 피해, 여러 팀이 맞는 광역기, 사망 후 효과는 별도 발동 조건으로 둔다.

이전 설계에서 제안한 **1.5초·250cm 같은 수치는 조정 가능한 커스텀 초기값**이다. 원작 수치나 검증된 성능 기준이 아니다. 공개가 벽을 무시하는지, 위치만 보여주는지, 타깃 지정까지 허용하는지를 데이터로 나눈다.

### 8.3 고정 건물의 LastObservedSnapshot

사용자 요구는 “탐색했던 건물은 현재 보이지 않아도 마지막 상태로 표시하고, 시야 밖에서 생긴 변경은 재탐색할 때 갱신한다”이다. 여기서는 건물 실제 상태와 관측 상태를 곱하여 관리한다.

~~~ts
interface StructureKnowledge {
  viewerTeam: number;
  structureSlotId: string;              // Actor가 파괴되어도 유지
  observation: "unknown" | "observed" | "remembered";
  lastObserved: null | {
    generation: number;                 // 같은 위치의 재건축 구분
    typeId: string | null;
    lifeState: "alive" | "destroyed" | "empty" | "construction";
    hp: number | null;
    maxHp: number | null;
    upgradeLevel: number | null;
    team: number | null;
    transform: number[];
    observedAtTick: number;
  };
}
~~~

| 실제 사건 | 현재 그 지점을 관측 중 | 관측하지 않음 |
|---|---|---|
| 피해·회복·강화 | 허용 필드를 새 스냅샷에 반영 | 이전 스냅샷 유지 |
| 파괴 | 파괴 상태 또는 빈 슬롯 관측 기록 | 기억 프록시 유지 |
| 재건축·다른 건물 생성 | 새 generation과 상태 기록 | 이전 generation 유지 |
| 다시 시야 확보 | 슬롯 자체를 조사하여 실제 상태로 교체 | 해당 없음 |
| 실제 Actor 없음 | 슬롯이 비었다는 관측으로 갱신 | 삭제 이벤트만으로 기억을 지우지 않음 |

기억 프록시는 마지막 외관·체력·소속만 사용한다. 실제 건물의 HP 바인딩, Destroyed 이벤트, 미니맵 갱신, 클릭 툴팁, 경로 미리보기에서도 숨은 변경이 새어 나오지 않게 한다. 기억 건물은 공격 가능한 실제 타깃이 아니다. 공격 명령은 관측과 서버 타깃 유효성을 다시 평가한다.

미탐색 지형에서 건물의 존재 자체를 보여줄지, 지도에 공개된 건물 위치만 보여줄지는 별도 공개 지도 정책이다. “위치는 원래 공개”와 “현재 체력까지 공개”를 같은 조건으로 처리하지 않는다.

## 9. 성능·정확성 우선순위 — 구현안

1. 시야원·차단체·관측 대상에 공간 인덱스를 적용하고 영향 타일만 재계산한다.
2. 여러 시야원의 기여를 합성할 때 단순 boolean 덮어쓰기를 피한다. 한 와드가 사라져도 다른 시야원의 기여는 유지되어야 한다.
3. 부드러운 안개 텍스처는 논리 갱신보다 높은 렌더 빈도로 보간할 수 있다.
4. 타깃 명령처럼 즉시 정확성이 필요한 경우에는 최신 위치를 사용하는 좁은 범위 판정을 보완한다.
5. 비동기 계산 결과에 지형 버전·시야원 버전을 붙여 오래된 작업 결과가 새 상태를 덮어쓰지 못하게 한다.
6. 고정 건물 기억은 변화가 관측될 때만 갱신하고 매 프레임 복제하지 않는다.
7. 지도 1·1.5·2배는 커스텀 지도 설정이다. 셀 크기 고정이면 면적 증가에 따라 셀 수가 증가하고, 셀 수 고정이면 판정 해상도가 거칠어진다. 어느 정책을 선택했는지 명시한다.

해상도·업데이트 주기·대역폭 목표는 대상 플랫폼과 최대 시야원 수를 놓고 측정한 뒤 확정한다. “128²이므로 몇 ms” 같은 성능 수치를 실측 없이 넣지 않는다.

## 10. 현재 웹 프로토타입과의 차이

다음은 이번 작업에서 읽은 로컬 코드의 상태이며, 이 문서가 해당 기능을 구현했다는 뜻이 아니다.

| 항목 | 현재 Nexus Front v7 | 복원·확장 시 필요한 작업 |
|---|---|---|
| 공간 시야 | visibilityAt의 팀별 원형 거리 검사 | 시야 차단 지형·정확한 시야원 정책 |
| 개체 시야 | isVisible에서 수풀·공개 상태 적용 | 은신·감지·타깃 권한 분리 |
| 건물 | 실제 구조물 상태 공개 | 커스텀 LastObservedSnapshot 도입 |
| 벽·고저차 | 벽은 이동 제약에 사용, 고저차 LOS 없음 | 별도 시야 차단 데이터 |
| 탐색 | 렌더러의 지형 탐색 마스크 | 개체 관측 기록과 분리 |
| AI | 일부 중립 목표 판단이 전체 상태를 사용 | 정보 제한 AI 프로필 또는 명시적 난이도 보조 |
| 저장·진단 | 전체 상태가 브라우저에 존재 | 온라인 권위 서버와 팀별 전송층 |
| 시야 원본 | 자체 단순 지도와 오브젝트 | 원작 지형·와드·능력 예외의 별도 검증 |

로컬 근거: 기존 프로젝트의 nexus_front/dist/game.js 중 visibilityAt, isVisible, getSnapshot 및 nexus_front/GAMEPLAY.md의 시야·진단 API 설명. 기존 FogOfWar_Unreal_Design_KR.md는 커스텀 UE 설계의 연속성 확인에만 사용했다.

## 12. 공개 자료로 복원되지 않는 필드

# 성능 및 장시간 진행 검증

측정일: **2026-11-20**. 엔진: **Godot 4.6.3 stable**.

이번 기록은 공유 실행 환경의 **헤드리스 CPU 시뮬레이션 측정**이다. 화면 렌더링·GPU·입력 지연·모니터 주사율을 측정하지 않았다. 아래 시간을 화면 FPS나 특정 사용자 기기의 보장 성능으로 해석해서는 안 된다. 같은 실행 환경에서도 다른 작업의 CPU 사용, 운영체제 스케줄링 및 캐시 상태에 따라 시간이 달라질 수 있다.

측정 대상 월드 소스의 SHA-256은 다음과 같다. 전체 배포물의 식별 정보와 무결성은 배포 검증 보고서도 함께 확인한다.

```text
scripts/sim_world.gd
3650c3d4a1943cdb1d72cdea726d2a32e8877807b402e9fd68ab11e18240d039
```

## 1. 공통 경기 구성

- 시드: `2601120`
- 선택 영웅: `lol_ezreal`
- 난이도: `standard`
- 팀 구성: 각 팀 미드·탑·정글·바텀·서포터 1명, 총 10명
- 정상적인 `setup()`으로 구성한 뒤 선택된 플레이어의 `is_player`를 `false`로 바꾸어 10명 모두 같은 봇 로직으로 진행
- 정상 웨이브 생성, 스킬 사용, 처치·성장, 귀환·구매, 구조물 보호 및 파괴 경로 사용
- 초기 데이터 읽기와 월드 생성 시간은 측정 구간에서 제외
- 승리가 먼저 확정되면 진행을 중단하고 실제 게임 시간·프레임 수를 기록

플레이어를 자동 조작으로 바꾸는 코드는 벤치마크 도구에만 있다. 실제 플레이에서는 선택한 영웅을 사용자가 조작한다. 원시 결과의 영웅별 `casts`는 현재 생존 구간의 능력 상태에 들어 있는 카운터이며, 사망·부활 과정에서 초기화될 수 있다. 경기 전체 스킬 사용량의 합계로 사용하지 않는다.

## 2. 세 맵에서 180초 진행 검증

[원시 결과: sustained_simulation.json](sustained_simulation.json)

이 검증의 목적은 크기가 다른 맵에서 웨이브·봇 전투·성장·구조물 공격이 계속 진행되는지와 좌표·체력이 유효한 범위를 유지하는지 확인하는 것이다. 각 맵에서 `step(0.1)`을 1,800회 호출했다. **10Hz의 검증용 시간 간격이며 실제 화면의 60Hz 물리 프레임 성능 측정과 구분한다.** 다른 시간 간격에서는 충돌·AI 판단 시점 때문에 전투 결과가 달라질 수 있다.

| 맵 | 게임 시간 | 웨이브 | 팀 킬 | 피해를 받은 구조물 | 파괴된 구조물 | 종료 시 개체 | 실제 처리 시간 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1배 | 180초 | 10 | 6 : 7 | 7 | 2 | 49 | 18.276초 |
| 1.5배 | 180초 | 10 | 4 : 7 | 4 | 3 | 57 | 19.901초 |
| 2배 | 180초 | 10 | 3 : 4 | 5 | 2 | 65 | 21.935초 |

세 맵 모두 마지막 검사에서 좌표가 유한하고 맵 안에 있었으며 체력이 0 이상, 최대 체력 이하를 유지했다. 세 경기 모두 180초에는 아직 승패가 확정되지 않았다. 넥서스까지의 보호 해제·파괴·승리·종료 후 시뮬레이션 정지는 별도의 월드 테스트에서 실제 `damage()`와 파괴 처리 경로를 호출하여 검증했다.

`damaged_structures`에는 파괴된 구조물도 포함되므로 `destroyed_structures`와 더해서 총 구조물 수를 계산하지 않는다.

## 3. 2배 맵에서 60Hz CPU 측정

[원시 결과: performance.json](performance.json)

| 항목 | 측정값 |
|---|---:|
| 맵 | 2배 |
| 프레임 수 | 3,600 |
| 프레임당 게임 시간 | `1.0 / 60.0`초 |
| 진행된 게임 시간 | 약 60초 |
| 실제 처리 시간 | **10.338초** |
| 실제 처리 시간 ÷ 프레임 수 | **2.872ms/프레임** |
| 종료 시 개체 수 | 85 |

실제 시간을 기다리지 않고 프레임을 연속 실행했다. 따라서 결과는 해당 조건의 시뮬레이션 CPU 처리 비용이며, 게임 화면이 몇 FPS로 보이는지를 측정한 값이 아니다. 이 원시 측정은 초기 병목을 확인하기 위한 함수별 시간 계측을 포함하며, 계측 자체의 작은 비용도 포함한다.

### 함수별 누적 시간 읽는 법

`performance.json`의 `profile_us` 값은 마이크로초 단위의 **포함 시간**이다. 상위 함수가 하위 함수의 시간을 포함하므로 다음 행들을 합산해서 총 시간을 구하면 중복 계산이 된다. 예를 들어 `_nearest_target` 안에서 `visible_to`가 호출되며, `abilities` 안에서도 이동과 시야 조회가 발생할 수 있다.

| 계측 구간 | 누적 시간 |
|---|---:|
| 시야 시스템 갱신 `vision` | 6.041532초 |
| 이동 `move_unit` | 1.065445초 |
| 새 대상 탐색 `_nearest_target` | 0.848692초 |
| 대상 가시성 조회 `visible_to` | 1.272399초 |
| 영웅 능력 갱신 `abilities` | 0.268887초 |
| 기본 공격 처리 `_attack` | 0.186082초 |

## 4. 개발 중 확인한 병목과 개선

초기 개발 단계의 2배 맵·3,600스텝 측정에서는 약 139.98초가 걸렸다. 이후 다음 처리를 바꿨다.

1. 팀과 거리를 먼저 검사하고, 가까운 후보에 대해서만 비싼 시야 검사를 수행한다.
2. 물리 스텝 안에서 같은 팀·대상의 시야 결과를 재사용한다. 대상 위치·생존·강제 노출 정보가 바뀌면 다시 검사하며 스텝 밖의 UI 조회와 저장에는 캐시를 사용하지 않는다.
3. 적이 없는 미니언과 포탑이 매 프레임 전체 목록을 다시 검색하지 않도록 새 대상 탐색 간격을 둔다.
4. 라인 경유점과 지형 우회점을 짧게 재사용하고, 목표가 이동하거나 가까워지면 갱신한다.
5. 구조물 보호 상태를 매 프레임 재계산하지 않고 생성·파괴·불러오기 시점에 갱신한다.

초기 139.98초와 최종 10.338초의 단순 비율은 약 **13.5배**다. 다만 개발 중 AI의 초기 스킬 학습·공용 회복 주문 등 동작도 보완되었고 공유 환경의 부하도 같다고 보장할 수 없다. 따라서 이 비율은 **개발 중 병목이 크게 줄었다는 참고 수치**이며 엄밀하게 동일한 실행 경로와 환경을 통제한 성능 비교가 아니다. 최종 결과 자체와 재현 가능한 실행 조건을 우선 사용한다.

## 5. 재현 방법

Godot 4.6.3 실행 파일을 `godot`으로 호출할 수 있는 환경에서 **이 프로젝트의 루트 디렉터리**를 작업 위치로 사용한다. 배포된 실행 파일이 아닌 수정 가능한 소스 프로젝트에서 실행한다.

세 맵의 180초 진행 검증:

```bash
godot --headless --path . --script tools/benchmark_world.gd -- --mode=stability
```

기본 결과 경로는 `docs/sustained_simulation.json`이며 재실행한 결과로 갱신한다. 기존 배포 측정 기록을 보존하려면 `--output=res://docs/sustained_simulation_rerun.json`을 추가한다.

2배 맵의 3,600프레임 / 게임 시간 60초 CPU 재측정:

```bash
godot --headless --path . --script tools/benchmark_world.gd -- --mode=performance
```

결과는 `docs/performance.json`에 저장되며 기존 기록을 갱신한다. 별도 기록이 필요하면 `--output=res://docs/performance_rerun.json`을 지정한다. 포함된 재현 도구는 전체 루프의 처리 시간과 스텝별 평균·95백분위·최대 시간, 최고 개체 수를 추가로 기록한다. 원래 개발 계측의 내부 함수 래퍼는 게임 소스에 넣지 않았으므로 재측정 파일에는 `profile_us`가 없다. 내부 함수 계측 유무와 타이밍 호출 자체의 비용 때문에 원래 수치와 정확히 일치해야 하는 것은 아니다.

시간 간격·기간·출력 위치를 바꿀 수 있다.

```bash
godot --headless --path . --script tools/benchmark_world.gd -- --mode=stability --dt=0.05 --seconds=120 --output=user://nexus_world_benchmark.json
```

`dt`는 0.001~0.1초, 기간은 0초 초과~3,600초를 허용한다. 월드가 큰 스텝을 최대 0.1초로 제한하기 때문에 도구도 같은 상한을 검사한다. `--help`로 옵션을 확인할 수 있다. 출력 디렉터리는 실행 전에 존재해야 한다. 종료 코드는 정상·유효 상태 0, 유효하지 않은 최종 상태 1, 잘못된 인자 2, 파일 쓰기 실패 3이다.

같은 시드와 같은 시간 간격으로 재실행하더라도 벽시계 처리 시간은 달라질 수 있다. 전투 재현을 비교할 때는 엔진 버전·소스 버전·시드·시간 간격을 함께 고정한다.

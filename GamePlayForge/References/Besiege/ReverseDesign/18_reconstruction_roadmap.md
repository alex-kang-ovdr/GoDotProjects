# 18. 유사 게임 재구성을 위한 구현 우선순위

> **이 문서는 독립적인 개발 제안이다.** Besiege 개발사의 실제 개발 일정·엔진 구조·우선순위를 서술하지 않는다. 앞의 역기획을 구현 가능한 범위로 나누기 위한 부록이다.

## 1. 첫 완성 목표

최초 목표는 ‘가능한 모든 탈것을 만드는 시스템’보다 **같은 설계를 반복 시험하고 원인을 이해하며 수정할 수 있는 작은 제작 게임**으로 잡는다.

첫 수직 단면은 다음 경험을 완결한다.

1. 구조 블록과 바퀴를 배치한다.
2. 좌우 구동 방향을 설정한다.
3. 짧은 코스를 주행한다.
4. 과부하로 연결이 끊어지는 모습을 본다.
5. 건설 상태로 돌아와 보강한다.
6. 같은 코스를 다시 통과하고 설계를 저장·불러온다.

## 2. 구현 단계와 종료 조건

| 단계 | 범위 | 완료 판단 |
|---|---|---|
| P0 규칙 실험 | 블록 두 개·힌지·모터·파단 | 자유도·접점·반력·복원 계약이 문서화됨 |
| P1 기본 편집 | 배치·회전·삭제·Undo·저장 | 설계 복구가 일관되고 손실이 없음 |
| P2 육상 기구 | 바퀴·조향·현가·Brace | 단순 차량이 제어 가능하고 실패 원인이 보임 |
| P3 과제와 파괴 | 목표·무기·충돌·파단 | 제작→시험→완료 루프가 성립 |
| P4 고급 제작 | 다중선택·대칭·부분 저장·표면 | 복잡한 기체도 편집 비용이 감당 가능 |
| P5 자동화 | 입력 채널·센서·타이머·논리 | 간단한 순차 동작과 상태 초기화 검증 |
| P6 환경 확장 | 비행·수상·수중 중 우선 분야 | 기본 기구와 결합해도 규칙이 일관됨 |
| P7 공유·멀티 | 의존성·권한·복제·로컬 시험 | 저장·실행·파손의 일관성이 유지됨 |

단계를 고정 일정으로 해석하지 않는다. 네트워크를 반드시 출시 범위에 포함한다면 P0부터 권한·이벤트·ID를 설계하고, 사용자가 플레이할 수 있는 UI 노출을 P7에서 완성하는 방식이 가능하다.

## 3. 부품 수보다 규칙 종류를 먼저 완성

| 대표 부품 | 검증하는 규칙 |
|---|---|
| 구조 블록 | 공간 배치·접점·고정 연결 |
| Brace | 두 끝점·보강·가동부 우회 고정 |
| Powered Wheel | 회전 구동·접지·반력 |
| Steering Hinge | 제한 각도·목표 추종·자동 복귀 |
| Suspension | 탄성·감쇠·한계 |
| Piston | 이동 구동·초기 전개·끼임 |
| Grabber | 실행 중 새 연결·해제 |
| Cannon | 발사·반동·탄약·피해 |
| Sensor/Timer | 조건 출력·시간 상태·복구 |

이 목록은 구현 순서 제안이다. 원작의 해금 순서나 필수 부품 목록이 아니다.

## 4. 고비용 기능을 결정할 때의 기준

### 4.1 완전한 재료 해석

연속체 변형·응력장을 사실적으로 계산할 필요가 있는지 먼저 묻는다. 연결 파단과 국소 파손만으로도 ‘보강하면 버티고 약한 곳이 부러진다’는 경험을 만들 수 있다. 정밀도보다 플레이어가 이해할 수 있는 실패와 재현성이 중요하다.

### 4.2 물과 공기

원하는 경험이 부품 조합에 따른 조종 성능이라면 부품별 힘 모델에서 시작할 수 있다. 선체 침수·유체 압력·복잡한 유동을 범위에 포함할 경우, 편집기의 밀폐 검사·구획 표시·디버그 도구까지 함께 비용에 포함한다. 외형만 닫으면 떠야 하는지부터 제품 규칙으로 확정한다.

### 4.3 임의 스케일

수치와 충돌 형상을 자유롭게 늘리는 기능은 콘텐츠 확장을 쉽게 하지만 접점·질량·관성·시각 일치·파손·네트워크 비용을 복잡하게 만든다. 이를 제공한다면 스케일에 따라 무엇이 바뀌는지 명시하고, 비균일 스케일의 지원 범위를 제한한다.

### 4.4 멀티플레이

정확한 상호 충돌을 공유하려면 권한 구조를 일찍 선택한다. 단순히 싱글플레이 위치를 복제하는 것으로는 파단·집기·분리·새 몸체 생성의 순서까지 일관되게 만들 수 없다. 물리 상태와 구조 이벤트를 함께 설계한다.

## 5. 편집기와 물리의 공동 완료 기준

| 기능 | 물리 완료 | UX 완료 |
|---|---|---|
| 힌지 | 한 축만 허용·제한 작동 | 축과 가동측을 이해할 수 있음 |
| 바퀴 | 구동·마찰·접지 안정 | 전진 방향과 좌우 대칭을 확인 가능 |
| 보강 | 의도한 연결 강화 | 가동부를 잠그는 경우 알 수 있음 |
| 무기 | 발사·반동·피해 발생 | 발사 가능·잔량·부착 방향이 명확 |
| 센서 | 조건과 출력이 일관 | 감지 범위·기준축·출력이 보임 |
| 저장 | 참조·설정 복원 | 이전 버전과 의존성 문제를 이해 가능 |

물리 테스트를 통과했더라도 사용자가 결과를 예측할 수 없다면 제작 기능으로는 미완성이다.

## 6. 필요한 도구

개발 도구는 사용자가 자주 겪는 실패를 설명하는 순서로 만든다.

- 연결·가동축·접점 표시.
- 입력 신호 송신·수신 표시.
- 힘의 방향·작용점·원인 표시.
- 최초 파손 위치와 사건 기록.
- 동일 초기조건 A/B 실행 비교.
- 신규 설계와 구형 저장본의 설정 차이.

모든 진단을 일반 플레이 중 상시 표시하지 않는다. 첫 화면은 제작에 필요한 조작을 제공하고, 원인 분석이 필요한 순간 상세 도구를 연다.

## 7. 테스트 자산의 역할

대형 멋진 기체 한 대보다 작은 기준 기체가 유용하다. 연결·관절·주행·사격·비행·부력·센서를 각각 분리한 시험 기체를 유지하면 엔진·부품 수정의 영향을 찾기 쉽다.

회귀 검사에서는 실행 결과를 비트 단위로 완전히 동일하게 요구하기보다, 목표 도달·최초 파단 부위·최대 자세 편차·완료 시간 범위처럼 제품에 중요한 조건을 정한다. 실제 수치 허용 범위는 측정 후 결정한다.

## 8. 우선순위 결론

1. **연결의 의미를 먼저 확정한다.** 가동측과 고정측, 접합과 접촉이 명확해야 한다.
2. **실험 복구를 완성한다.** 중단 후 원본 설계가 정확히 복원되어야 한다.
3. **힘의 원인을 보여 준다.** 움직임·반동·파단을 해석할 수 있어야 한다.
4. **반복 작업을 줄인다.** 다중 선택·대칭·부분 재사용이 제작 규모를 넓힌다.
5. **환경과 공유를 확장한다.** 기초 계약이 안정된 뒤 비행·해양·우주·멀티의 복잡성을 추가한다.

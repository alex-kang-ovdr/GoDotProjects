# 02. 목적별 데이터 정책 및 보안

## 1. 공식 확인과 설계 제안 구분

본 문서는 2026-11-17 확인한 공개 문서를 바탕으로 한 제품 설계안이다. 공급자별 실제 계약/승인, 적용 법률을 자동 판정하는 법률 자문이 아니다. Sources 문서의 공식 자료를 확인하고 출시 전 검토한다.

OpenAI App Developer Terms 1.2는 App Request 처리를 요청 수행 또는 법 준수에 필요한 범위 등으로 한정하고, 1.6은 경쟁 모델 개발 사용 등을 제한한다. Anthropic Commercial Terms D.4 역시 경쟁 제품·모델 등의 제한을 두며 출력 학습 안내에는 특정 비경쟁 활용 예외와 제한이 함께 있으므로 모델 종류·계약별 판단이 필요하다. '모든 외부 결과 학습 허용'으로 기본값을 설정하지 않는다.

SIWC Terms는 영속 인증정보의 로컬 사용자 통제 저장 및 다른 사용자 구독 사용 방지 등을 정한다. 사용료 부담 주체와 데이터 활용권은 별개의 문제다.

## 2. 목적을 분리하는 유한 목록

| 목적 | 기본 동작 | 별도 통제 |
|---|---|---|
| 서비스 기록 | 필요한 최소 실행·보안·무결성 기록 | 법적 근거, 고지, 접근·보관 제한 |
| 현재 프로젝트 지원 | 사용자가 요청한 읽기·수정·테스트·수정 반복 | 사용자/협업 권한, 작업 예산 |
| 공통 워크플로 개선 | 허용된 지표 또는 선별된 작업 데이터 | 공급자 계약, 프로젝트 정책, 필요한 동의 |
| 모델 학습 | 기본 차단 | 목적 특정 승인, 이용권한, 공급자 조건 |
| 마케팅 분석 | 제품 전환 분석에 한정해 별도 심사 | 별도 동의·고지·법적 검토 |
| 작품 공개 사례 | 스크린샷·게임명·성과 공개 | 내용·브랜드·제작자·협업 권한 |
| 홍보 메시지 | 수신 설정에 따름 | 별도 마케팅 수신 조건 |

선택 활용은 default off를 제안한다. 서비스 제공을 위한 기록의 법적 근거가 항상 '동의'라는 의미는 아니다. 선택 활용 동의와 필요한 서비스 기록을 섞지 않는다. 미성년자/나이 미확인자의 선택 학습·마케팅은 MVP에서 활성화하지 않는 보수적 정책을 제안하고, 서비스 가입 자체의 연령 규정은 별도 검토한다.

## 3. 세 번 검사한다

### 수신/기록 전

원문을 모두 영구 저장한 뒤 가리는 방식이 아니다. 허용된 필드·payload 종류만 로그에 기록한다. 편집 처리에 필요한 소스는 현재 프로젝트 저장소에서 처리한다.

### 데이터셋 구성/외부 전송 전

출처 profile, 목적, 기여물 권리, 수집 당시 조건, 현재 동의/조직/프로젝트 정책을 검사한다. 모든 원천 source를 flat manifest로 포함한다. 텍스트를 요약하거나 다른 사용자가 재업로드해도 provenance를 제거하지 않는다.

### 실제 실험/학습/캠페인 실행 전

정책 revision과 철회 상태를 재검사한다. 오래된 'allowed' 결과만 캐시해서 재사용하지 않는다. 실행 중 철회는 신규 배치·다운로드·모델 호출 중단점에 반영하고, 이미 처리한 결과에 대한 처리 범위를 기록한다.

### 판정 논리

```text
AllowPurpose = legal_review_ok
            AND provider_route_permission
            AND organization_policy
            AND project_policy
            AND contributor_rights
            AND applicable_consent_at_collection
            AND applicable_consent_now
            AND allowed_payload_class
```

동의 필요 여부는 목적과 법적 근거에 따라 결정한다. 모르는 조건은 UNKNOWN이며 선택 활용에는 DENY와 동일하게 처리한다. 이는 프로젝트 편집 실패로 전파하지 않는다.

## 4. 관측 지표도 정책에서 예외가 아님

메타데이터·집계·가명화는 정보량을 줄이는 방법이지 재사용 권한을 만드는 방법이 아니다. 모델 입력 요청에 파생된 통계까지 포함되는지 계약 해석이 필요한 경로는 미승인 상태로 두고, 필요한 경우 공급자 확인 또는 별도 계약을 확보한다.

독립적인 PlayForge 성능 실험에는 플랫폼 소유 예제와 허용된 실험 기록을 사용한다. 동의하지 않은 프로젝트의 화면을 보고 AI로 '새 예제'를 생성하는 식의 우회도 하지 않는다.

## 5. 철회·삭제·보관

제안 초기 보관값(확정 정책이나 법정 보관기간 아님): 운영 상세 메타데이터 30일, 선택 참여 원문 diff 후보 14일, 허용된 집계 지표 90일. 승인 데이터셋은 별도의 만료일·목적·삭제 대상 목록을 갖게 한다. 개발자의 수동 snapshot과 Release archive 보존은 별개다.

철회 시:

1. 데이터 사용 권한 epoch 증가, 신규 export/job dispatch 차단.
2. 기존 대기 Job을 취소하거나 새 정책으로 재평가.
3. dataset manifest와 source refs를 기준으로 원문·검색 인덱스·예제 저장소 등 파생 사본을 찾아 삭제/격리.
4. 외부 처리 업체의 삭제 절차와 백업 만료를 추적.
5. 복구된 백업에 삭제 원장을 다시 적용해 데이터가 부활하지 않게 함.

이미 학습한 모델에서 기여를 즉시 완전히 제거한다고 보장하지 않는다. 학습 전 배치별 provenance와 재학습·모델 폐기 경로를 마련한다. 법적 보존 의무가 있는 최소 기록과 선택 학습 데이터의 삭제 절차를 분리한다.

## 6. 마케팅 제한

workflow reuse 허용은 public showcase 허용이 아니다. '제작 시간이 단축된 사례'를 공개하려면 증거가 있는 지표, 허가된 화면·프로젝트명, 관련 권리, 공급자 이름 사용 조건을 별도로 확인한다.

개인 실패 로그·비공개 코드·대화 내용을 광고 타기팅 입력으로 기본 사용하지 않는다. 광고 목적 사용이 제한된 공급자 데이터는 사용자 동의만으로 전용하지 않는다. 마케팅 목적 데이터는 별도 allowlist와 목적용 저장 경로를 사용한다.

## 7. 위험과 방어

- Prompt injection: 코드·로그·에셋 설명은 자료이지 명령이 아님. 추출 Worker는 기본 네트워크 차단, 필요한 출구만 허용.
- 테스트 오염: private evaluation fixtures는 개선 Agent 읽기/수정 금지.
- 권한 상승: run/connection ID는 secret이 아니며 매 접근에 사용자/tenant/project 검사.
- 로그 유출: structured codes, redaction, field allowlist. SecretPayload enum만으로 실제 DLP가 구현된 것은 아님.
- 학습 오염: 실행 결과는 서버 확인과 로컬 self-report 구분, 반복 스팸은 승인 후보에서 제외.
- 재사용 정책 위조: model/tool 인자에 purpose/consent를 주더라도 판정은 서버 정책에서 수행.

## 8. 비용·자격증명

플랫폼 공통 실험은 PlatformResearch 예산만 사용한다. 개인 구독/개인 API/Free 체험권/Pro 주간 사용량에 자동 전가하지 않는다. 사용자 프로젝트 자동 수정은 사용자가 허용한 최대 반복·예산 범위에 한정한다.

SIWC 조건의 개인 사용 요청 원칙은 공유 Workspace에도 적용한다. B가 같은 프로젝트를 편집했다는 이유로 A의 개인 구독에서 추론이 시작되지 않는다. BYOK의 조직 공유는 MVP에서 제외하고 본인 계정 요청만 지원한다.

클라우드 서버의 암호화 금고가 모든 개인 구독 토큰 보관을 허용하는 해결책은 아니다. 각 경로의 보관·실행 조건을 먼저 만족해야 한다.

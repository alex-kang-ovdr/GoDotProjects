# 20. 밸런스 구조·QA 시나리오·재현 개발 계획

> 작성일: 2026-11-13 | 범위: PC 싱글플레이 DS/RoG | 문서 버전: 1.0  
> 이 문서의 수식·지표·실험·개발 순서는 [설계 해석] 및 [재구성 설계]다. 실제 게임 테스트 결과가 아니다. [목차](00_index.md)

## 1. 밸런싱의 대상

Don't Starve의 역기획에서 단일 아이템의 효율만 비교하면 중요한 비용이 빠진다. 식량 한 개를 얻기 위해 이동·전투·작업·보관·회복에 쓴 시간과 자원이 연결되기 때문이다. 본 문서는 앞선 규칙을 의사결정 비용으로 정리하고, 어떤 실험으로 실제 동작을 확인할지를 정의한다.

공식 플레이 안내는 탐색과 발견을 통한 학습을 강조한다. [S1] 따라서 재현 품질은 생존 시간을 늘리는 것만으로 판단하지 않는다. 실패의 원인과 다음 시도의 개선 방법을 플레이어가 이해하는지도 중요하다.

## 2. 다섯 가지 비용 장부

| 장부 | 소비 항목 | 확보 방법 | 다른 장부에 미치는 영향 |
|---|---|---|---|
| 시간 | 이동·작업·대기 | 동선 단축·설비·정보 | 긴 원정은 식량과 광원을 더 필요로 함 |
| 생존 상태 | 허기·체력·정신력 손실 | 섭취·휴식·회피 등 | 회복할수록 재료와 시간이 사용됨 |
| 물자 | 재료·연료·내구도 | 채집·가공·생산 | 더 많은 물자는 운반과 보관을 요구 |
| 공간 | 슬롯·배치·접근 경로 | 가방·상자·거점 선택 | 장비와 시설의 편의·위험 교환 |
| 정보 | 미탐색·미지의 규칙 | 관찰·실험·실패 | 알려진 안전 경로가 준비 비용을 줄임 |

이 표는 새로운 게임 내 게이지를 추가하라는 뜻이 아니다. 서로 다른 시스템을 비교할 때 빠뜨리기 쉬운 비용을 기록하는 분석 모형이다.

## 3. 식량 경제의 기본식

### 3.1 하루 평균 수지

```text
FoodMargin = RawNutritionInput + ProcessingNetGain
             - DailyConsumption
             - SpoilageLoss
             - UnrecoverableLoss
```

- `RawNutritionInput`: 해당 기간에 새로 얻은 원재료를 가공 전 기준 효과로 환산한 허기 회복량. 섭취 불가능한 재료의 직접 영양량은 0으로 둔다.
- `ProcessingNetGain`: 가공으로 생긴 영양량의 순증감. 가공 전 원재료와 결과물을 같은 기준으로 비교하여 한 번만 반영한다.
- `DailyConsumption`: 캐릭터·상태·행동에 따른 소모량. 정확한 값은 [03](03_survival_stats.md)의 제품별 기준을 사용한다.
- `SpoilageLoss`: 먹기 전에 상태가 변하거나 소실되어 잃은 가치.
- `UnrecoverableLoss`: 전투·화재·운반 실패 등으로 회수하지 못한 식량.

가공을 마친 식품의 가치로 유입을 집계하는 대체 회계에서는 `RawNutritionInput + ProcessingNetGain`을 그 완성 식품 유입량으로 치환한다. 완성 식품에 이미 반영된 가공 효과를 다시 더하거나 차감하지 않는다.

`FoodMargin > 0`이어도 언제든 안전한 것은 아니다. 하루 평균으로는 충분해도 긴 원정 중 음식이 떨어질 수 있고, 허기 회복만 충분한 식단은 체력·정신력 회복의 요구를 해결하지 못할 수 있다.

### 3.2 예시 계산 — 원작 수치가 아닌 모형 입력

**[재구성 설계·가정값]** 하루에 영양 가치 100을 확보하고 기본 소비 70, 부패 손실 10, 운반 손실 5가 발생한다고 가정하면 잉여는 15다. 그런데 수집 동선이 길어져 다음 날 생산이 80으로 줄면 수지는 -5가 된다.

이 예시는 숫자 자체보다 **생산 방식이 시간과 연결되어 있어 며칠의 평균 생산량이 중요하다**는 점을 보여준다. 원작 아이템의 조리값과 신선도 규칙은 [10번 문서](10_food_cooking_spoilage.md)를 사용한다.

## 4. 준비 여유와 병목

```text
FoodHorizon  = AvailableNutrition / ExpectedNutritionUsePerTime
LightHorizon = UsableLightDurationAlongPlannedRoute
GearHorizon  = ExpectedRemainingUsefulActions
SafeHorizon = min(comparable time-based horizons)
```

서로 다른 단위의 `GearHorizon`과 시간을 곧바로 `min`에 넣으면 안 된다. 예상 행동 횟수와 단위 시간당 행동 계획을 이용해 비교 가능한 단위로 바꾸거나, 별도 제약으로 유지한다. 온도·전투 위험을 단순 직선으로 환산하는 것도 실제 검증 전에는 피한다.

**[설계 해석]** 플레이어는 가장 짧은 준비 여유에 의해 행동 범위를 제한받는다. 식량이 많아도 광원이 끝나면 원정을 계속하기 어렵고, 방어구가 좋아도 회복과 운반 계획이 부족하면 이익을 회수하지 못한다.

## 5. 설비의 가치와 손익 분기

```text
InvestmentCost = BuildMaterials + BuildTime + RequiredResearch + RiskExposure
BenefitPerCycle = SavedTravel + SavedWork + ReducedLoss + AddedOptions
```

모든 항을 숫자로 더하는 대신 단위별로 비교한다. 시간만 평가할 경우 `BuildTime + MaterialAcquisitionTime`을 초기 비용으로 두고, 작업 주기마다 절약되는 시간으로 회수 기간을 계산할 수 있다. 화재·습격 위험과 새로운 선택지의 가치는 별도 항목으로 남긴다.

| 설비 유형 | 주요 편익 | 유지·숨은 비용 | 기획 검토 질문 |
|---|---|---|---|
| 조리 | 재료 조합의 효율·회복 선택 | 재료 분류·대기·회수 | 모든 재료를 한 요리로 몰아가는가? |
| 보존 | 소비 시점을 늦춤 | 제작·공간·손실 위험 | 생산 부족을 해결한 것처럼 착각하게 하는가? |
| 재생 자원 | 반복 탐색 감소 | 성장·보호·수확 시간 | 거점 밖 탐험의 이유를 전부 없애는가? |
| 방재·방어 | 자산 손실 감소 | 재료·배치·운용 | 준비의 대가가 위험 감소와 연결되는가? |
| 연구 | 새로운 선택지 | 초기 투자와 이동 | 기술 해금 이후에도 재료·상황 판단이 남는가? |

## 6. 전투의 총비용

```text
CombatCost = EncounterTime
           + HealingAcquisitionTime
           + GearReplacementTime
           + CollateralRecoveryTime
```

**[설계 해석]** 같은 적을 더 빨리 잡는 무기가 항상 원정 전체를 효율적으로 만들지는 않는다. 위험한 접근으로 피해가 늘거나 귀중한 장비를 많이 소비하면 총비용이 커진다. 생태 관계를 이용하는 전략은 직접 공격 비용을 줄이지만 이동·유인·예상 밖 피해를 발생시킬 수 있다.

**[재구성 설계]** 전투 실험은 초당 피해만 기록하지 않고, 처치까지의 시간·받은 피해·장비 사용량·주변 구조물 손실·안전 복귀 여부를 함께 기록한다. 원작의 방어구 중첩과 내구도 분배는 [13번 문서](13_combat_armor.md)의 범위와 검증 항목을 따른다.

## 7. 위험 곡선과 역전 가능성

| 단계 | 플레이어가 축적하는 것 | 새로 드러나는 비용 | 관찰할 문제 |
|---|---|---|---|
| 초기 생존 | 기본 자원과 환경 지식 | 밤·허기·탐색 | 실패 이유를 이해하기 전에 끝나는가? |
| 첫 정착 | 설비와 보관 재고 | 위치 선택·운영 | 더 이상 탐험할 필요가 없어지는가? |
| 계절 전환 | 대비 물자와 대응 지식 | 기존 생산 방식의 취약점 | 대비 방법이 지나치게 한 가지인가? |
| 장기 원정 | 장비·회복·위험 판단 | 휴대 용량과 귀환 | 보상 가치가 비용을 정당화하는가? |
| 반복 생존 | 안정적인 운영 | 반복 노동·목표 고갈 | 자동 루틴만 남고 선택이 사라지는가? |

난도가 높다는 이유만으로 설계가 성공한 것은 아니다. 준비하면 줄어드는 위험과 어떤 준비로도 예측하기 어려운 위험을 구분해 기록한다. 후자는 확인 가능한 신호나 사후 학습의 단서가 있는지 먼저 살핀다.

## 8. 대표 지표와 해석 제한

| 지표 | 수집 방식 | 읽을 수 있는 것 | 단독으로 판단하면 안 되는 이유 |
|---|---|---|---|
| 최초 사망 원인 | 사망 전 상태 변화 로그 | 초기 설명이 부족한 위험 | 적응한 플레이어와 초보자를 섞으면 왜곡 |
| 계절 도달률 | 동일 설정의 여러 시도 | 준비 루프의 난도 | 시작 계절·월드 편차 영향 |
| 채집·이동·전투 시간 비중 | 액션별 시간 기록 | 반복 노동과 위험의 비율 | 탐험 자체의 재미를 수치가 대표하지 않음 |
| 재고 폐기·부패율 | 획득과 소비의 차이 | 과잉 생산·보존 가치 | 의도적인 비축·가공을 손실로 오인 가능 |
| 사용한 제작법의 다양성 | 실제 제작과 장착 기록 | 선택지의 집중도 | 캐릭터 특성 때문에 집중될 수도 있음 |
| 거점 복구 시간 | 손상 전후 기능 비교 | 자산 손실의 회복 가능성 | 플레이어의 장기 목표마다 허용치 다름 |
| 동일 원인 재사망률 | 같은 플레이어의 반복 시도 | 학습 신호의 명료성 | 위험 감수 의도를 따로 확인해야 함 |

목표 수치와 합격선을 원작의 공식 KPI라고 쓰지 않는다. 재현 프로젝트에서 플레이테스트 후 합의할 관리 지표다.

## 9. 실험 환경 고정

### 9.1 실험 기록 헤더

```text
TestId:
Product: DS / DS+RoG
BuildOrBranch:
Platform:
DlcCompatibilityFlags:
WorldSettings:
Character:
Mods: disabled, or exact list
WorldSeedAndRegion:
StartingState:
InputSequence:
ExpectedRuleAndSource:
ObservedResult:
EvidenceFile:
Verdict: Pass / Fail / Inconclusive
```

실험 전후로 바뀐 변수를 하나씩 기록한다. 동일 시드라고 해도 빌드·월드 생성 규칙·DLC 설정이 다르면 동일한 세계라고 가정하지 않는다. 모드 없는 기본 실험과 계측 모드가 필요한 실험은 결과를 구분한다.

### 9.2 정확한 숫자를 확정하는 순서

1. 제품·DLC·플랫폼·패치를 특정한다.
2. 최신 공식 변경 공지와 공개 설명에서 적용 범위를 확인한다.
3. 같은 이름의 DS/DST 자료가 섞였는지 확인한다.
4. 단일 변수 실험으로 변화량과 발생 시점을 기록한다.
5. 경계값·저장 후 재개·지역 이동을 추가 검증한다.
6. 결과와 출처를 수치 레지스트리에 기록하고 관련 문서를 갱신한다.

## 12. 재현 개발 순서

| 단계 | 구현 범위 | 완성 판정 | 다음 단계가 필요한 이유 |
|---|---|---|---|
| P0: 첫 생존 루프 | 이동·채집·소지품·허기·빛·죽음 | 자원 확보와 시간 압력의 선택이 성립 | 제작 경제가 붙을 기반 |
| P1: 반복 생활 | 제작·시설·조리·부패·도구 내구도 | 같은 자원을 서로 다른 목적에 배분 | 정착과 원정의 교환 형성 |
| P2: 변화하는 위험 | 계절·환경·생태·습격·방재 | 장기 대비의 필요성과 회복 경로 존재 | 안정된 루틴을 흔드는 압력 |
| P3: 탐험과 진행 | 동굴·유적·보스·모험·부활 | 위험 대비와 보상이 연결 | 장기 목표와 다양한 플레이 |
| P4: 품질과 확장 | 캐릭터·설정·접근성·저장 안정성 | 규칙 일관성과 제품별 분리 | 콘텐츠 추가 때 회귀 방지 |

이는 인력·개발 기간을 추정한 일정표가 아니다. 최소한의 시스템 묶음으로 핵심 선택이 먼저 성립하도록 하는 의존 순서다. 실제 프로토타입에서 완성도를 확인한 뒤 범위를 조절한다.

## 13. 문서와 실제 재현의 완료 기준

**문서 검증:** 파일별 범위·출처·해석 표기, 서로 연결되는 이름, 수식의 단위, 알려진 버전 차이를 확인한다.

**행동 재현 검증:** 고정한 실제 빌드의 동일 조건에서 대표 행동과 경계 결과가 일치하는지 확인한다.

**경험 검증:** 새로운 플레이어가 압력을 인식하고, 대안을 비교하고, 실패의 이유를 설명하고, 다시 시도할 때 개선되는지 확인한다.

세 단계는 대체 관계가 아니다. 문서를 모두 작성해도 실제 재현 실험을 수행하지 않았다면 메커니즘을 실측 검증했다고 표현하지 않는다.

# 04. 구호 연락망·대피 준비·생활 안내 시스템

LAST LIGHT 4.0에 구현한 선택 목표와 안내 시스템의 상세 명세입니다. 구현 근거는 [engine.js](../dist/engine.js), 화면 연결은 [app.js](../dist/app.js), 회귀 검증은 [progression.test.js](../tests/progression.test.js)와 [campaign.test.js](../tests/campaign.test.js)입니다. 이 문서의 수치와 동작은 프로젝트 소스를 설명하며, 원작의 실제 수치로 취급하지 않습니다.

기존 규칙은 [은신처·경제](01-shelter-and-economy.md), [야간·주민](02-night-and-encounters.md), [캠페인·저장](03-campaign-and-saving.md)을 함께 참고하세요. 전체 검증 범위는 [VALIDATION.md](../VALIDATION.md)에 정리합니다.

## 1. 목적과 승리 조건

구호 연락망은 낮의 재료와 작업 시간을 장기 목표에 투자하는 선택입니다. 초반에는 생활 시설과 무전기에 같은 목재·부품을 배분하고, 중반에는 교신 비용과 난방 연료를 비교하며, 후반에는 오늘 먹을 식사와 대피 물자를 나누어 준비합니다.

캠페인의 기본 승리 조건은 그대로입니다. **12번째 밤의 결과를 확인한 뒤 한 명 이상 살아 있으면 승리**합니다. 무전기나 대피 물자 준비를 마치지 않았다는 이유만으로 패배하지 않습니다. 선택 목표는 사기, 한 번의 보급, 대피 경로와 후일담을 바꿉니다.

전원이 사망하면 기존 보고서·패배 흐름을 따릅니다. 연락망이 완성되어 있어도 사망자를 되살리거나 패배를 승리로 바꾸지 않습니다. 구조 차량을 직접 운전하는 별도 스테이지나 실시간 호위전은 포함하지 않습니다.

## 2. 단계별 규칙

| 단계 | 행동 ID | 시작 조건 | 비용 | 기본 시간 | 정상 상태의 윤 | 완료 효과 |
|---|---|---|---|---:|---:|---|
| 무전기 복구 | `buildRadio` | 낮, 무전기 미완성 | 목재 2·부품 5 | 100분 | 80분 | 무전기 설치, 생존자 사기 +3 |
| 구호팀과 교신 | `contactRelief` | 무전기, 4일 이상, 미교신 | 부품 2·연료 1 | 80분 | 80분 | 사기 +5, 다음 아침 보급 예약 |
| 대피 물자 봉인 | `prepareEvacuation` | 교신 완료, 9일 이상, 미준비 | 식사 3·물 4·붕대 1 | 100분 | 100분 | 사기 +8, 준비된 대피 경로 |

무전기 복구의 분류는 `build`, 작업 위치는 `radio`, 설치 시설은 `radio`입니다. 교신은 `survival` 분류·`radio` 위치, 물자 봉인은 `survival` 분류·`door` 위치를 사용합니다. 모두 기존 작업 시스템에 들어가는 유한 행동입니다.

윤의 제작·건설 시간 20% 단축은 무전기 복구에만 적용됩니다. 교신과 물자 봉인은 생활 행동이므로 기본 시간이 줄지 않습니다. 질병 60 이상이면 작업 시간이 1.2배, 사기 25 미만이면 1.15배가 적용되며 각 계산에서 올림합니다. 실제 화면에는 선택한 사람의 현재 조건을 반영한 시간이 나옵니다.

사기 보너스는 완료 순간 살아 있는 인물에게 적용하고 100에서 제한합니다. 세 단계를 모두 마친 동안 계속 생존한 인물의 명목 보너스 합계는 16이지만, 이미 사기가 높다면 실제 증가량은 그보다 작습니다. 작업을 시작하거나 예약한 시점에는 보너스를 주지 않습니다.

## 3. 날짜와 선행 조건

무전기는 첫날부터 복구할 수 있습니다. 이른 복구는 뒤의 교신 준비를 앞당기는 대신 난로·집수기·문 보강에 사용할 재료와 윤의 작업 시간을 차지합니다. 3일에 무전기를 완성해도 교신은 4일 낮부터 가능합니다.

교신 날짜는 고정되지 않습니다. 4~12일 중 선행 조건과 자원이 갖춰진 낮에 완료할 수 있으며, 완료한 날짜를 `contactDay`로 기록합니다. 보급 예정일은 항상 `contactDay + 1`입니다. 12일에 교신하면 마지막 밤을 정산한 13일 아침이 지급 시점입니다.

대피 준비는 9~12일에 가능합니다. 같은 9일 낮에 무전기 복구, 교신, 물자 봉인을 순서대로 마칠 수도 있습니다. 이 경우에도 재료와 시간이 실제로 필요합니다. 보급품의 수령은 물자 봉인의 선행 조건이 아니므로 교신 직후 준비하는 것도 허용합니다.

준비를 마친 후에는 무전기·교신·봉인을 반복할 수 없습니다. 무전기는 내구도나 재교신 횟수를 갖지 않으며, 기존 문 내구도·수리 시스템과 별개입니다.

## 4. 상태 데이터

새 게임에는 다음 값이 들어갑니다. 데이터는 직렬화 가능한 숫자·불리언·`null`만 사용합니다.

```js
state.facilities.radio = 0; // 0 또는 1
state.relief = {
  contacted: false,
  contactDay: null,
  deliveryDay: null,
  delivered: false,
  prepared: false,
  preparedDay: null
};
```

| 값 | 의미 | 갱신 시점 |
|---|---|---|
| `facilities.radio` | 무전기 복구 여부 | `buildRadio` 완료 |
| `contacted` | 구호팀과 연락을 마쳤는지 | `contactRelief` 완료 |
| `contactDay` | 실제 교신 완료 날짜 | 교신 완료 순간의 `state.day` |
| `deliveryDay` | 다음 아침 보급 예정일 | 교신 날짜 +1 |
| `delivered` | 보급을 이미 반영했는지 | 해당 아침의 밤 정산 |
| `prepared` | 대피 물자를 봉인했는지 | `prepareEvacuation` 완료 |
| `preparedDay` | 실제 준비 완료 날짜 | 봉인 완료 순간의 `state.day` |

봉인한 물자는 새로운 가방 아이템으로 만들지 않습니다. 시작 시 비용으로 예약되고 완료하면 대피 준비 상태가 남습니다. 이를 다시 식사나 붕대로 꺼내 쓰는 행동은 구현하지 않았습니다. 완료 전 취소는 일반 작업 환급 규칙을 따릅니다.

## 5. 작업·예약·중단

플레이어는 쉬고 있는 인물에게 바로 맡기거나 작업 중인 인물의 대기열에 예약합니다. 한 인물의 대기열은 기존과 같이 최대 3개입니다. **예약 버튼을 누를 때는 재료를 차감하지 않고, 실제 작업이 시작될 때 차감**합니다.

예약 가능 여부는 앞선 작업을 복사된 상태에서 진행해 예측합니다. 무전기를 만들고 있는 인물에게 교신을 예약하면 완성될 무전기를 고려합니다. 9일에는 그 교신 뒤에 물자 봉인을 예약할 수 있습니다. 미리보기는 실제 캠페인의 날짜·재고·사기·RNG를 바꾸지 않습니다.

예약 후 다른 인물이 재료를 쓰면 예상과 실제가 달라질 수 있습니다. 착수 시점에 재료·선행 단계·남은 시간을 다시 검사하며, 조건이 맞지 않는 작업은 로그를 남기고 건너뜁니다. 예약은 자원을 확보해 두는 보증이 아닙니다.

진행 중 작업을 취소하면 그 작업에 예약한 비용을 한 번 반환합니다. 대기 중 작업을 삭제하면 비용이 차감된 적이 없으므로 추가 환급도 없습니다. 취소만으로 무전기, 사기, 교신 상태나 보급 예약을 얻지 못합니다.

낮 종료에는 기존 스케줄러가 남은 시간을 처리합니다. 완료 가능한 작업은 끝나고, 끝내지 못한 작업의 예약 비용과 남은 대기열은 기존 낮 종료 규칙으로 정리합니다. 구호 작업만 다음 날까지 별도로 이어 붙이지 않습니다.

## 6. 중복 완료 방지

같은 시설의 동시 건설과 같은 교신·물자 봉인의 동시 실행을 거부합니다. 작업 시작에는 최신 완료 상태를 확인하므로 이미 끝난 목표를 다시 유료 작업으로 만들 수 없습니다.

여러 인물의 대기열이 같은 목표를 예상하는 경합도 정산 결과를 늘리지 않습니다. 먼저 시작하거나 끝낸 작업 때문에 뒤의 예약 조건이 달라지면 뒤의 예약은 건너뜁니다. 완료 함수에도 이미 끝난 목표를 다시 적용하지 않는 방어 처리가 있으며, 중복 작업 비용은 반환하고 사기·보급 효과는 반복하지 않습니다.

저장 검증은 동시에 실행 중인 구호 작업 ID의 중복을 거부합니다. 완료 플래그가 켜져 있는데 같은 목표의 작업이 진행 중인 상태, 무전기 없는 교신 작업, 날짜 조건을 어긴 준비 작업도 유효한 저장으로 받지 않습니다.

## 7. 아침 보급의 소유권과 정산 순서

교신에 성공하면 다음 아침에 아래 물자가 은신처 공용 재고로 한 번 들어옵니다. 별도의 방문자 선택이나 수령 버튼은 필요하지 않습니다.

| 보급품 | 수량 |
|---|---:|
| 식재료 | 2 |
| 약품 | 1 |
| 붕대 | 1 |
| 연료 | 2 |

`finishNight`는 습격·난방·생존자 상태 변화를 먼저 처리합니다. 그 뒤 귀환 물품과 구호 보급을 반영하고 재고 순증감을 계산합니다. 따라서 **다음 아침에 도착한 연료 2로 지난밤의 난방 부족을 소급해서 없앨 수 없습니다.** 보급품이 그날 밤 습격 방어에 이미 존재했던 물자로 계산되는 일도 없습니다.

지급에는 교신 완료, 미지급 상태, 예정 아침 도달, 생존자 존재가 필요합니다. 지급과 함께 `delivered=true`가 되며 같은 보고서를 다시 열거나 저장을 복원해도 추가 지급되지 않습니다. 전원이 사망한 밤에는 생존자를 위한 구호 보급을 지급하지 않습니다.

보고서의 항목과 로그에 예정 날짜·실제 물자 구성을 기록합니다. `report.supplyDelta`에는 전체 재고 변화의 일부로 포함됩니다. `report.loot`는 수색자가 가져온 가방이므로 구호품과 같은 값이 아닙니다.

보고서 단계는 지나온 밤의 날짜를 `state.day`에 유지합니다. 예를 들어 4일에 교신하고 4일 밤을 정산한 보고서는 `day=4`, `deliveryDay=5`, `delivered=true`일 수 있습니다. 화면상 아침 보고와 내부의 밤 번호를 혼동하지 않도록 저장 날짜 검증도 이 경계를 고려합니다.

## 8. 구호 목표 조회 API

```js
const status = Core.getReliefStatus(state);
// {
//   stages, completed, total: 3, next,
//   delivery: { scheduled, day, delivered, items },
//   contacted, prepared, routeLabel
// }
```

각 `stages` 항목은 `id`, `title`, `description`, `actionId`, `status`, `reason`, `cost`, `duration`, `unlockDay`, `workerId`를 제공합니다. 상태는 `locked`, `available`, `in-progress`, `complete` 네 종류입니다. `next`는 아직 완료하지 않은 첫 단계이며, 전부 끝나면 `null`입니다.

진행 가능한지의 전체 판단은 살아 있는 인물들을 확인합니다. 선택한 인물 하나가 작업 중이라는 이유만으로 전체 피난처의 목표를 막지 않습니다. 실제 실행 버튼은 `getActions(state, characterId)`의 `available` 또는 `queueable`을 사용해야 합니다.

조회 API의 `duration`은 단계의 기본 시간입니다. 윤의 시간 단축과 상태 보정, 앞선 작업 뒤의 `queueDuration`은 `getActions`에서 얻습니다. 비용과 보급품 조회 객체는 복사본이므로 화면에서 이를 변경해도 게임 재고가 바뀌지 않습니다.

`getReliefStatus`의 네 상태에는 별도의 `queued`가 없습니다. UI는 인물의 `queue`를 함께 확인해 예약자와 순서를 표시합니다. 데이터의 실행 상태와 화면의 예약 표시를 분리한 구조입니다.

## 9. 실제 화면 흐름

1. 낮 화면의 **구호 연락망** 또는 장면의 무전기를 누릅니다.
2. 담당할 살아 있는 인물을 선택합니다.
3. 단계별 비용, 해당 인물의 시간, 선행 조건을 확인합니다.
4. 쉬고 있으면 맡기기, 작업 중이면 다음 작업 예약을 누릅니다.
5. 창을 닫고 동료의 생활·시설 작업을 함께 진행합니다.
6. 교신 후에는 예정일, 이후에는 도착한 보급품 표시를 확인합니다.
7. 9일 이후 봉인을 마친 뒤에도 마지막 밤까지 생존을 관리합니다.

창을 여는 동안 게임 시간은 멈춥니다. 작업을 성공적으로 맡기면 창을 닫고 진행을 재개합니다. 작업 중에는 실제 담당자와 남은 시간, 대기열에 있으면 예약된 담당자와 순서를 표시합니다. 완료 단계에는 추가 실행 버튼이 없습니다.

모달의 담당자 선택은 현재 선택 인물과 연결됩니다. 생존자별 상태와 작업이 다르므로 같은 단계라도 표시되는 시간과 예약 가능 여부가 달라질 수 있습니다. 조언 카드나 목표 창을 읽는 것 자체로 작업이 자동 실행되지는 않습니다.

## 10. 생활 안내 우선순위

`getSurvivalAdvice(state)`는 최대 4개 항목을 반환합니다. 종료 상태에서는 빈 배열입니다. 현재 살아 있는 인물과 은신처 상태만 읽으며, 다음 난수나 숨은 수색 물자를 미리 알아내지 않습니다.

| 검사 순서 | 대상 조건 | 중요도와 제안 |
|---|---|---|
| 1 | 건강 45 미만 중 가장 낮은 인물 | `critical`, 붕대 또는 휴식·의료품 확보 |
| 2 | 질병 45 이상 중 가장 높은 인물 | 60 이상 `critical`, 그 아래 `warning`, 약품·동료 치료 |
| 3 | 허기 60 이상 중 가장 높은 인물 | 75 이상 `critical`, 그 아래 `warning`, 식사·식량 확보 |
| 4 | 난로 없음, 오늘 겨울 또는 3일 | 겨울 `critical`, 3일 `warning`, 난로 설치 |
| 4의 대안 | 겨울·난로 있음·연료 부족 | `critical`, 오늘 밤 필요한 연료 준비 |
| 5 | 피로 70 이상 중 가장 높은 인물 | 90 이상 `critical`, 그 아래 `warning`, 낮잠·밤 수면 |
| 6 | 문 보강 있음·내구도 65 이하 | 30 이하 `critical`, 그 아래 `warning`, 은신처 수리 |
| 7 | 준비된 식사가 생존자 수보다 적음 | 식사 0이면 `warning`, 그 외 `info`, 조리·수색 |
| 8 | 구호 연락망 미완료 | `info`, 다음 단계와 잠금·진행 이유 |

항목은 이 순서로 추가하다 4개에서 멈춥니다. 모든 항목을 중요도 숫자로 다시 정렬하는 방식은 아닙니다. 급한 생활 문제가 여러 개면 장기 목표가 안내 목록에서 잠시 빠지지만, 구호 연락망 버튼에서는 계속 확인할 수 있습니다.

내부의 허기·피로는 높을수록 나쁜 값입니다. 안내 문구는 `포만=100-hunger`, `기력=100-fatigue`로 번역해 낮 화면의 지표와 일치시킵니다. 해당 물자가 없으면 없는 물자를 사용하라고 실행 버튼만 내놓지 않고 확보가 필요하다고 설명합니다.

각 조언은 `id`, `title`, `description`, `severity`와 선택적인 `actionId`, `category`, `characterId`를 갖습니다. 안내 카드는 해당 인물·작업 탭·목표 화면으로 이동하는 데 사용합니다. 실제 착수 가능 여부는 작업 시스템이 다시 검사합니다. 긴급한 항목도 남은 구호 목표도 없으면 밤 역할과 귀환 준비를 확인하는 안내가 나옵니다.

## 11. 결말과 개인 후일담

| 조건 | `ending.route` | 표현 |
|---|---|---|
| 살아서 12일 완료, `relief.prepared=true` | `coordinated` | 합의한 경로와 봉인한 물자를 챙기는 준비된 대피 |
| 살아서 12일 완료, 준비 미완료 | `self` | 통로가 열린 뒤 스스로 길을 찾는 대피 |

교신만 마친 인물의 후일담은 위치를 전한 무전기와 미완성 대피 물자를 구분합니다. 무전기만 복구한 경우에는 구호 교신까지 마쳤다고 쓰지 않습니다. 봉인 완료 문구는 실제 준비 플래그가 있을 때만 붙입니다.

인물별 직업·부상·질병·사기·공동체 선택에 대한 기존 후일담은 유지합니다. 사망한 인물에게는 성공적으로 차량에 올랐다는 준비된 대피 문구를 추가하지 않습니다. 연락망의 공통 기록을 특정 인물이 혼자 수행했다고 꾸미지도 않습니다.

## 12. 저장 이행과 검증

새 시스템을 위해 저장 envelope 버전이나 브라우저 저장 키를 바꾸지 않습니다. `facilities.radio`가 없는 이전 기록은 0, `relief`가 없는 기록은 모두 미진행인 기본값으로 복원합니다. 기존 재고·건강·지도 자원·날짜를 초기화하지 않습니다.

현재 구호 상태에는 정해진 여섯 필드만 허용합니다. 교신 전에는 날짜가 `null`, 지급·준비 플래그가 `false`여야 합니다. 교신 후에는 무전기가 존재하고, 교신 날짜가 4~12일의 도달한 날짜이며, 지급 예정일이 정확히 그 다음 날이어야 합니다.

아직 도달하지 않은 아침의 지급 완료 플래그와, 살아 있는 상태로 이미 도달한 보급을 미지급으로 되돌린 기록을 거부합니다. 준비 완료 날짜는 9일 이상이고 교신 날짜보다 이르거나 현재보다 미래일 수 없습니다. 잘못된 값을 기본값으로 덮어 유효한 기록으로 위장하지 않습니다.

새 작업의 저장 데이터는 알려진 행동 ID, 위치·분류·시설, 정확한 비용을 확인합니다. 무전기 작업에 다른 시설이나 임의의 산출물을 넣은 기록, 비용을 바꿔 환급을 늘리려는 기록을 거부합니다. 승리 결말의 `route`도 실제 준비 상태와 일치해야 합니다.

## 13. 검증 사례와 관측한 선택 비용

전용 10개 테스트는 비용 차감·환급, 윤의 기본 80분, 날짜 잠금, 동시 실행 거부, 미래 선행 조건 예약, 큰 tick과 작은 tick의 동등성, 경합하는 예약의 일회성 완료, 지급 시점과 중복 방지, 결말, 저장 이행과 잘못된 데이터, 읽기 전용 안내를 확인합니다.

캠페인 검증은 표준·봉쇄 각각 시드 31·247에서 구호 목표를 포함한 12일을 실제 행동으로 완주했습니다. 경로는 3일 무전기, 4일 교신, 5일 아침 보급, 9일 봉인입니다. 해당 네 실행에서 세 인물은 건강 100으로 생존했고 절도·살해는 0회였습니다.

이 검증은 초기화 이후 재고·건강·좌표·시계·RNG를 주입하지 않습니다. 맵의 유한한 공용 물자를 실제 이동·조사·담기·귀환으로 얻고, 제작·교환·방문자 선택으로 운영합니다. 기존 목표 없는 캠페인 검증도 유지하여 선택 시스템이 기존 승리를 필수 목표로 바꾸지 않았는지 확인합니다.

봉쇄 정책에서는 무전기 지출 때문에 4일의 세 번째 문 보강에 목재가 1개 부족했습니다. 이를 무료 재료로 해결하지 않고 보강을 5일로 미루고 4일 경계를 늘려 통과했습니다. 무전기와 방어에 같은 재료를 쓰는 선택 비용이 실제 플레이 경로에 드러나는 사례입니다.

이 결과는 명시된 시드와 정책의 재현 가능한 사례이며 모든 선택·시드의 생존 보장이나 평균 난이도 측정은 아닙니다. 브라우저·모바일 검증과 전체 테스트 집계는 별도의 검증 문서에 기록합니다.

## 14. 구현 범위와 확장 후보

현재 구현은 고정된 세 단계와 한 번의 보급입니다. 난이도별 별도 교신 비용, 무작위 수신 실패, 여러 구호 세력, 보급 호위전, 봉인 물자 회수, 구조 경로 미니게임, 인물별 전용 의뢰는 없습니다.

확장 시에는 단계 정의를 데이터화하거나 선택 가능한 보급품·경로를 추가할 수 있습니다. 이러한 항목은 확장 후보이며 현재 보상이나 규칙이 아닙니다. 추가할 때에는 저장 이행, 날짜 경계, 일회성 지급, 재료 예약, 기존 선택 목표 없이도 승리하는 조건을 함께 검증해야 합니다.

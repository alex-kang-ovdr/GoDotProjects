# 26. 역기획 검증 시나리오와 재구현 순서

> **조사 기준일:** 2026-11-13  
> **검증 상태:** 문서 구조·참조·계산 검토와 **게임 플레이 실험**을 구분한다. 이 장의 게임 시험은 실행할 수 있도록 설계한 계획이며, 통과 결과를 보고하는 문서가 아니다.  
> [전체 목차](00_README.md)

## 1. 검증의 목표

역기획을 검증한다는 것은 문서의 모든 문장을 원작 코드와 일치시켰다는 뜻이 아니다. 플레이어가 관찰할 수 있는 입력·상태·출력의 관계를 재현할 수 있는지, 예외와 버전 차이를 누락하지 않았는지 확인하는 것이다.

다음 세 가지 결과를 각각 기록한다.

| 결과 유형 | 필요한 근거 | 이 문서 세트의 현재 상태 |
|---|---|---|
| 공개 자료 확인 | 공식 제품·개발자 업데이트의 명시적 내용 | 각 문서의 출처로 기록 |
| 분석 검토 | 식·인과관계·설계 제안의 논리 일관성 | 문서 작성 과정에서 검토 |
| 게임 실측 | 빌드·DLC·세이브·측정값·재현 절차 | 미수행, 아래 시험으로 확인 필요 |

## 2. 재현 가능한 실험의 공통 조건

모든 실험은 `빌드 번호 / Stable 또는 Public testing / Base 또는 Spaced Out! / 활성 DLC / 난이도 / 모드 / 월드 설정`을 남긴다. 숫자 하나가 다를 때 설정 차이인지 문서 오류인지 구분하기 위해서다.

공식 지원 문서는 테스트 브랜치가 개발 중이며 안정판과 다른 동작·성능·세이브 호환 제약이 있을 수 있다고 설명한다.[^testing] 따라서 안정판의 성능이나 규칙을 시험 빌드 결과로 대체하지 않는다.

### 실험 기록 양식

```yaml
test_id: SYS-EXAMPLE-001
purpose: 관찰할 관계 한 가지
build: 기록
branch: stable_or_public_testing
ruleset: base_or_spaced_out
content_packs: []
mods: []
setup: 재현 가능한 초기 상태
action: 변경하는 변수
observations: [가동시간, 실제 산출, 상태 메시지]
expected_relation: 문서에서 예측한 결과
actual_result: 미실행
evidence: [세이브, 화면, 측정기록]
conclusion: 미판정
```

## 4. 통합 시나리오

### 4.1 산소 공급의 단일 장애

**초기 상태:** 생존에 필요한 산소를 한 생산 계통이 공급하고 입력·전력·운송·저장이 각각 관찰 가능하다.

**변경:** 한 번에 한 요소만 차단한다. 입력 물, 발전 연료, 배관 출력, 자동화 신호를 차례대로 시험한다.

**관찰:** 생산 시설의 정지 이유, 저장 감소, 각 구역 산소 상태, 복제체의 행동 변화와 대응 가능 시간을 기록한다.

**판정:** 서로 다른 원인이 동일한 “산소 부족” 증상으로 나타나더라도 상태 정보로 구분할 수 있어야 한다. UI 설명과 실제 정지 조건이 어긋나면 규칙 또는 표시 모델을 수정한다.

### 4.2 산업화 이후의 지연된 농업 위기

**초기 상태:** 농업 구역과 산업 구역이 열적으로 연결되어 있고 식량 비축이 있다.

**변경:** 산업 가동 시간을 늘리고 다른 변수는 유지한다.

**관찰:** 온도 변화 → 작물 조건 → 수확 간격 → 이용 가능 식량 → 추가 노동의 순서를 추적한다.

**판정:** 온도 상승과 기근 사이의 지연을 설명할 수 있어야 한다. 단순히 “산업이 나쁘다”가 아니라 열 전달과 완충 재고가 얼마나 시간을 벌어 주는지 기록한다.

### 4.3 다중 거점의 독립성

**초기 상태:** Spaced Out!에서 본거지와 위성 거점 사이에 필수 보급 경로가 있다.

**변경:** 운송을 일시 중단하고 일부 인력을 본거지에서 파견한다.

**관찰:** 위성 거점의 버팀 시간뿐 아니라 본거지의 필수 유지 작업도 기록한다.

**판정:** 완충 재고와 현지 생산의 역할을 구별한다. 인력 파견이 공급과 수요를 양쪽에서 어떻게 바꾸는지 설명해야 한다.

## 6. 재구현의 권장 단계

이 절은 **[설계 제안]**이다. 원작의 실제 개발 순서나 일정이 아니다.

| 단계 | 구현할 경험 | 완료 기준 | 아직 범위에 넣지 않을 것 |
|---|---|---|---|
| A. 공간·명령 | 작은 맵에서 채굴·건설·이동 | 명령·도달·완료의 관계를 확인 | 대량 콘텐츠와 우주 |
| B. 생존 최소 루프 | 호흡·식량·생활 소비와 공급 | 인구 변화가 수지에 반영됨 | 복잡한 생태·고급 산업 |
| C. 운송·전력 | 입력과 출력이 연결된 생산 라인 | 막힘·부족·회로 문제를 구별 | 고온 상변화 대규모 설비 |
| D. 열·농업·부산물 | 산업의 부작용이 다른 시스템에 영향 | 시간 지연을 포함한 실패 연쇄 재현 | 모든 레시피와 생물 종 |
| E. 정책·자동화 | 반복 업무를 정책으로 안정화 | 신호·일정·저장 정책이 실제 상태와 일치 | 새 규칙 모드 |
| F. 성장·우주 | 기술 단계와 새 자원 확보 | 생존 기반과 확장 비용 연결 | 다중 월드 전체 |
| G. 다중 거점 | 여러 독립 생산망과 수송 | 단절·원격 관리·보급을 검증 | 콘텐츠 팩의 광범위 조합 |

각 단계는 다음 단계 없이도 작은 플레이 시나리오로 평가할 수 있어야 한다. 세부 건물 수를 늘리는 것보다 입력 부족·작업 지연·출력 정체·열 축적이 설명 가능한 상태로 동작하는지 먼저 확인한다.

## 7. 설계의 수용 기준

### 7.1 기능적 수용 기준

- 작업 명령, 선행 조건, 실제 실행 결과를 구분할 수 있다.
- 동일한 자원이 두 소비자에게 중복 배정되지 않는다.
- 생산 중단 이유가 상태 정보와 일치한다.
- 자원량·에너지량·유량의 단위가 혼용되지 않는다.
- 저장 후 불러오기에서 진행·정책·타이머가 일관되게 복원된다.
- 콘텐츠가 없는 조합에 전용 규칙이나 건물이 무조건 노출되지 않는다.

### 7.2 플레이 경험의 수용 기준

- 실패 이전에 원인을 추적할 수 있는 선행 정보가 있다.
- 같은 목표에 비용과 부작용이 다른 복수의 해결 방향이 있다.
- 확장할 때 기존 기지의 운영 안정성을 평가해야 한다.
- 자동화가 단순 편의뿐 아니라 변동성과 노동 비용을 다루는 선택이 된다.
- 환경과 자원이 달라지면 배치·기술 순서를 바꿀 이유가 있다.

## 9. 검증 결과의 기록 원칙

“통과”는 기대 관계와 실제 관측이 일치한 경우에만 쓴다. 출처가 설명하는 기능의 존재를 확인했다면 “문헌 확인”, 계산의 단위와 산술만 확인했다면 “분석 검토”라고 쓴다. 확인하지 않은 항목은 “미실행” 또는 “빌드 확인 필요”로 유지한다.

의도적으로 시험 결과를 비워 둔 이유는 불완전한 기능이 있어서가 아니라, 문서 조사와 게임 실행 시험이 서로 다른 근거이기 때문이다. 사용자가 특정 빌드와 세이브를 제공하면 이 계획을 실제 검증 기록으로 발전시킬 수 있다.

## 1. 먼저 읽을 핵심 해석

**[분석] 이 게임의 중심은 공개된 적 공격을 제한된 행동으로 수정하는 것이다.** 적을 제거하는 방법 외에도 위치 변경, 공격 취소, 사격 차폐, 적의 공격 유도, 지형과 스폰의 활용이 같은 방어 목표를 해결한다.

따라서 역기획에서는 `무기 피해량`, `누가 어디에 있는가`, `어떤 순서로 사건이 일어나는가`, `이번 전투에서 무엇을 지켜야 하는가`를 함께 보아야 한다. 전력망과 파일럿, 성장 보상이 서로 다른 시간 범위의 가치를 가지기 때문에 희생 선택이 생긴다.

공식 제품 설명과 개발자의 설계 회고는 [01번](01_게임구조와핵심루프.md)에, 모든 외부 근거의 접근 상태는 [19번](19_출처_버전_근거대장.md)에 모았다.

## 4. 문서 라벨 읽는 법

| 라벨 | 의미 | 사용할 때 주의할 점 |
| --- | --- | --- |
| **[확인]** | 인용한 공개 자료에서 확인한 기능·규칙 | 공식 자료인지 커뮤니티 자료인지 함께 확인 |
| **[분석]** | 확인 규칙에서 도출한 설계 해석 | 개발자의 발언으로 인용하지 않음 |
| **[제안]** | 재구현을 위한 데이터·알고리즘·QA | 원작의 내부 구현이라고 취급하지 않음 |
| **[미확인]** | 충돌·예외·버전 차이로 추가 검증 필요 | 확정 규칙표에 복사하지 않음 |
| **[자료 충돌]** | 외부 자료가 서로 다른 설명을 제공 | 어느 시점·상황인지 확인 후 판정 |

파일별 출처 ID는 `O` 공식·당사자 자료, `C` 전투 조사, `E` 적·콘텐츠 조사, `P` 캠페인 조사로 나눴다. 접두사는 신뢰도 등급이 아니다. 예를 들어 E 계열에도 공식 출시 공지가 있고, P 계열에는 위키와 사용자 사례가 함께 있다.

## 5. 조사와 확정의 경계

- 사용자 제공 [나무위키 Into the Breach 문서](https://namu.wiki/w/Into%20the%20Breach)는 직접 열기에 실패했다. 읽지 못한 내용을 근거로 인용하지 않았다.
- 개발사 제품 설명, AE 발표, 공식 패치, GDC 발표와 참여자 인터뷰를 우선했다.
- 구체적인 전투·상점·파일럿 규칙은 커뮤니티 위키의 세부 항목과 가이드를 대조했다.
- 일부 위키·공식 웹페이지는 직접 열기가 제한되어 검색 색인의 본문·발췌로 확인했다. 대장에 접근 수준을 기록했다.
- 정확한 적 AI 가중치, 생성기 내부 코드, 저장 포맷은 공개 규칙에서 확정할 수 없다. 관련 문서는 제안으로 표시했다.
- 자료에 없는 수치를 채우기 위해 그럴듯한 숫자를 만들어 넣지 않았다. 가상 예제의 숫자는 가상임을 표시했다.

## 8. 표·다이어그램·코드의 사용법

- 표는 규칙·조건·결과·예외를 비교하기 위한 것이다.
- Mermaid 다이어그램은 의사결정 흐름이나 상태 관계를 표현한다. 원작 함수 호출 관계가 아니다.
- YAML·텍스트 의사코드는 재구현에 필요한 필드를 제안한다. 원작 파일 형식이나 실행 가능한 완성 코드가 아니다.
- 가상 전투는 원작 리플레이가 아니다. [17번](17_대표전투_턴별분석.md)에 명시된 초기 상태와 가정을 기준으로 읽는다.
- Markdown 뷰어가 Mermaid를 지원하지 않으면 다이어그램 코드가 텍스트로 보일 수 있다. 핵심 규칙은 표와 본문으로도 설명했다.

## 9. 적용 시 우선순위

원작과 유사한 프로토타입을 만들 목적이라면, 먼저 한 장의 고정 보드에서 공격 예고·밀기·건물 보호·턴 제한·결과 미리보기를 완성한다. 이후 상태와 지형의 조합, 스쿼드와 성장, 캠페인 생성 순서로 확장한다.

콘텐츠가 많아도 미리보기와 실제 결과가 다르면 판단을 신뢰하기 어렵다. 반대로 작은 콘텐츠 집합이라도 위치와 사건 순서가 서로 영향을 주면 다양한 해법을 만들 수 있다. 이 기준으로 [16번 설계안](16_데이터모델_판정파이프라인.md)과 [18번 검증 목록](18_검증체크리스트_미확인항목.md)을 연결했다.

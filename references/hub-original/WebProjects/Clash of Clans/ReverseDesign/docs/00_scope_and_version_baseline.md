# 00. 분석 범위·버전 기준·문서 사용법

> 작성 기준: **2026-11-13, Asia/Seoul**. 공개 규칙을 설계 언어로 재구성한 독립 역기획서다. Supercell의 내부 기획서·소스 코드·운영 데이터가 아니다.

## 1. 이 문서 묶음의 목표

클래시 오브 클랜을 “건물을 짓고 상대 마을을 공격하는 게임” 수준에서 설명하는 데 그치지 않고, 각 시스템의 입력·상태·출력·제약·실패 처리를 연결한다. 기획자는 규칙과 성장 동기를, 클라이언트 개발자는 전투 및 편집 상태를, 서버 개발자는 자원·타이머·대회 정산의 경계를 검토할 수 있도록 구성했다.

분석 단위는 개별 캐릭터나 모든 레벨의 능력치가 아니라 **플레이어의 선택을 만드는 규칙**이다. 전투력 수치·가격·이벤트 일정처럼 자주 바뀌는 값은 출처가 있는 대표 사례와 설정 테이블 구조로 다룬다. 전체 레벨 도감이나 실제 클라이언트에서 추출한 데이터 덤프는 포함하지 않는다.

## 2. 사실·분석·제안의 구분

| 표기 | 의미 | 문서를 사용할 때의 원칙 |
|---|---|---|
| **[확인]** | 공식 공개 자료에서 해당 규칙을 확인 | 공개일·적용 범위까지 함께 읽는다 |
| **[과거]** | 이전 버전의 규칙 또는 이미 교체된 구조 | 현행 구현의 기본값으로 복사하지 않는다 |
| **[예고]** | 발표되었지만 기준일 현재 적용을 확인하지 못한 변경 | 별도 버전 또는 기능 플래그로 관리한다 |
| **[해석]** | 확인된 규칙이 유도하는 전략·동기·경제 효과 | 인과관계에 대한 가설이며 실제 운영 통계가 아니다 |
| **[제안]** | 같은 행동을 재현하기 위한 데이터·알고리즘·아키텍처 | 원작 내부 구현과 동일하다는 뜻이 아니다 |
| **[미확인]** | 공개 근거가 없거나 서로 충돌하는 세부 사항 | 인게임 관찰·리플레이·추가 공지로 검증한다 |

문단에 여러 성격이 섞이면 사실 부분에 출처를 달고 해석·제안을 별도로 시작한다. 의사코드, 스키마, 수치 예시, QA 수용 기준은 별도 언급이 없으면 **재구현을 위한 제안**이다.

## 3. 조사 방법과 한계

사용자가 지정한 [나무위키 문서](https://namu.wiki/w/%ED%81%B4%EB%9E%98%EC%8B%9C%20%EC%98%A4%EB%B8%8C%20%ED%81%B4%EB%9E%9C)는 직접 열람을 시도했으나 접근 오류로 본문을 확인하지 못했다. 따라서 그 문서를 읽거나 그 내용 전체를 검증했다고 주장하지 않는다. 실제 근거는 Supercell의 업데이트 공지·지원 문서를 우선 사용했다.

공식 자료도 시점이 다르다. 지원 페이지는 수정일이나 적용 버전을 표시하지 않는 경우가 있고, 신기능이 발표된 직후 설명이 미리 갱신되거나 이전 설명이 남을 수 있다. 다음 우선순위로 판정했다.

1. 적용일이 명시된 정식 업데이트에서 확인한 규칙.
2. 구체적 동작을 설명하는 현재 지원 문서.
3. 개발팀 발표·예고와 그 후 정식 적용 공지의 조합.
4. 서로 충돌하면 단정하지 않고 두 설명 및 확인 방법을 기록.

**미실시 항목:** 계정 접속을 통한 현행 빌드 전수 관찰, 패킷·바이너리 분석, 공식 비공개 API 사용, 실제 대전 표본 수집. 따라서 이 묶음은 공개 근거 기반의 상세 역기획이며 실측으로 내부 구현을 복원한 결과는 아니다.

## 5. 시스템 경계

| 영역 | 대표 상태 | 독립적으로 관리해야 하는 이유 |
|---|---|---|
| 본 마을 성장 | 건물·장벽·장인·연구·영웅 | 영구 계정 진행이며 전투 종료 후 파괴 상태와 다름 |
| 공격 편성 | 병력·마법·영웅·장비·펫·지원병 | 보유, 출전 가능, 선택, 실전 투입은 다른 상태 |
| 전투 인스턴스 | 타깃·HP·배치·시간·파괴·별 | 시작 시점 규칙과 배치를 고정해야 일관된 결과를 설명 가능 |
| 개인 경쟁 | 등록·그룹·배치 스냅샷·공격권·순위 | 일반 자원 약탈과 별도 정산 |
| 클랜 경쟁 | 명단·전쟁 배치·개별 공격·기지 최고 기록 | 개인의 가장 좋은 공격과 클랜 전체 성과를 연결 |
| 장인 기지 | 병력 능력·2단계 전투·방어 결과 | 본 마을과 승패·보상 루프가 다름 |
| 클랜 수도 | 공유 성장·구역 HP·공격권·주말 성과 | 여러 사람의 공격이 같은 파괴 진행도를 공유 |
| 이벤트·상품 | 시즌·권한·미션·보상 청구·만료 | 기간 종료와 보상 수령·소비 시점이 일치하지 않음 |

## 6. 공통 역기획 양식

각 시스템 문서는 다음 질문에 답하도록 작성했다.

- 이 시스템은 어떤 플레이어 결정을 만들며 어떤 반복 주기에 속하는가?
- 참가·해금·활성화 조건과 사용할 수 없는 조건은 무엇인가?
- 자원, 횟수, 슬롯, 시간은 언제 차감·고정·반환되는가?
- 결과는 공격 단위, 기지 단위, 계정 단위, 시즌 단위 중 어디에 저장되는가?
- 정상 흐름과 취소·접속 종료·중복 요청·마감 경계에서는 무엇이 달라지는가?
- 무엇을 관찰하면 밸런스 문제와 구현 오류를 구분할 수 있는가?

세부 정도는 시스템마다 다르다. 전투에는 타깃·충돌·효과 우선순위를, 경제에는 거래·용량·소모·시간을, 소셜에는 권한·명단·참가·정산을 더 자세히 기술했다.

## 7. 구현 검토 시 필수 원칙 [제안]

1. **콘텐츠와 규칙 버전을 함께 저장한다.** 레벨만 저장하면 같은 레벨의 과거 리플레이를 새 밸런스로 재생할 위험이 있다.
2. **배치 원본과 전투용 배치 사본을 나눈다.** 편집 즉시 현재 대회 방어가 바뀐다고 가정하지 않는다.
3. **시간과 사용 가능성을 분리한다.** 전투 후 회복 제거는 업그레이드 중 영웅 사용 제약의 제거를 뜻하지 않는다.
4. **보상 계산과 지급을 분리하되 지급은 한 번만 허용한다.** 결과 화면 재진입이 자원 복제로 연결되면 안 된다.
5. **해금 규칙을 하드코딩하지 않는다.** TH·건물·시즌·실험 대상에 따라 다른 조건을 자료로 관리한다.
6. **공식 미공개 값을 채워 넣지 않는다.** 확인이 필요한 슬롯은 `UNKNOWN`으로 남기고 관찰 계획을 붙인다.

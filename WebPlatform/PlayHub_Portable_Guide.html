01 / 실행·게임 추가·운영

PlayHub 0.3.0 — EXE 하나로 실행하는 웹 게임 플랫폼 PoC

이미 보유한 Rebex Tiny Web Server 옆에 PlayHub.exe를 복사하고 실행합니다. Node 런타임·SQLite·플랫폼 코드·기본 게임은 EXE 안에 포함되어 있습니다. 사용자 PC에 SQL Server, MySQL, PostgreSQL, Node.js, npm, IIS를 설치하지 않습니다.

사용자 사이트는 Rebex, 관리자 사이트는 별도 localhost 전용 worker가 제공합니다. 두 사이트는 물리 폴더·서버 프로세스·포트가 분리됩니다. 로그인 없이 탐색·플레이하고, 첫 플레이에서 게스트를 생성합니다. 관리자는 별도 화면에서 실제/QA 지표, 게임 공개 상태, 오류를 확인합니다.

1. 바로 실행

  1. 배포 ZIP을 풉니다.
  2. PlayHub.exe를 기존 RebexTinyWebServer.exe가 있는 폴더에 복사합니다.
  3. PlayHub.exe를 더블클릭합니다. 기존 파일을 못 찾으면 파일 선택 창에서 Rebex EXE를 한 번 선택합니다.
  4. 실행 창에 표시되는 최초 관리자 비밀번호를 보관합니다. 사용자 사이트는 준비 후 기본 브라우저에서 열립니다.

기존 Rebex 설치 파일·설정은 수정하지 않습니다. 사용자가 보유한 바이너리를 전용 실행 폴더로 복사하여 사용자 사이트용 인스턴스를 시작합니다. 이미 실행 중인 다른 Rebex 프로세스를 종료하지 않습니다. 실행 창을 유지하는 동안 서비스가 동작하며, Q를 입력해 종료합니다. A는 관리자 화면, U는 사용자 화면을 엽니다.

대상은 Windows 10/11 x64의 데스크톱 사용 환경입니다. 기존 Rebex가 요구하는 .NET Framework 4.6 이상과 Windows 기본 PowerShell 5.1이 있어야 합니다. 현재 제공한 Windows EXE는 서명되지 않았습니다. 시스템 정책에 따라 실행 파일 확인·방화벽 확인이 표시될 수 있습니다.

2. 단일 EXE와 데이터의 관계

단일 EXE는 실행 진입점입니다. 쓰기 가능한 게임·설정·데이터는 처음 실행할 때 자동 생성합니다. DB를 EXE 안에 덮어쓰는 방식이 아닙니다.

두 웹 루트 어디에도 서버 소스, 관리자 해시, Google client secret, SQLite DB를 넣지 않습니다. 관리자 화면과 사용자 화면은 각각 별도 서버 프로세스이며, 두 API listener는 하나의 별도 API worker에서 SQLite를 공유합니다. 이 PoC는 하나의 PC·Windows 사용자 계정 안에서 분리되며, 별도 VM·서버·OS 계정으로 격리된 구성은 아닙니다.

기본 데이터 폴더를 바꾸려면 PlayHub.exe --data-dir "D:\PlayHubData"를 사용합니다. 새 빈 경로는 별도 인스턴스를 만듭니다. 기존 데이터를 이동할 때는 종료 후 전체 데이터 폴더를 백업하고 절차를 계획해야 하며, 기존 절대 경로 설정을 무시하여 자동 이동하지 않습니다. EXE만 교체해도 같은 기본 폴더의 게임·설정·데이터는 유지합니다.

4. 게임 추가

  1. 실행 창에서 Q를 입력해 정상 종료합니다.
  2. %LOCALAPPDATA%\PlayHub\workspace\games\<id>\에 새 게임을 넣습니다. 기존 기본 게임의 game.manifest.json과 폴더 구조를 참고합니다.
  3. workspace\catalog\games.json의 entries 배열에 다음 항목을 추가합니다.
  4. PlayHub.exe를 다시 실행합니다. 검증·정적 사이트 생성 성공 후 카드·상세·게임 경로에 반영됩니다.
{"id":"new-puzzle","path":"games/new-puzzle","enabled":true}

실행 중 편집 파일을 감시하는 hot reload는 하지 않습니다. 재실행이 반영 시점이며, 실패한 검증을 건너뛰고 잘못된 게임을 서비스하지 않습니다. SDK 파일은 각 게임의 vendor 폴더로 배치됩니다. 추가 게임과 수정한 기본 게임은 다음 실행에도 유지합니다. 운영자가 DB에서 비공개로 지정한 게임은 목록을 다시 빌드해도 강제로 공개하지 않습니다.

5. Google 로그인과 관리자 비밀번호

Google 로그인 코드는 포함되어 있습니다. 실제 OAuth client ID·secret·redirect URI는 사용자가 발급한 값이 필요합니다. 값이 없으면 설정 필요 상태를 표시하며 게스트 플레이는 그대로 가능합니다.

종료한 상태에서 private\config\local.json의 google 객체의 clientId, clientSecret, redirectUri를 설정합니다. 로컬 검증의 redirect 예는 http://localhost:8090/api/auth/google/callback이며 실제 선택한 사용자 API 포트로 바꿉니다. 사용자 화면도 localhost 주소로 열어야 합니다. 정확한 필드 구조는 같은 파일의 google 객체와 config/example.json을 참고하세요. 설정 후 EXE를 다시 실행합니다.

LAN의 임의 IP를 localhost callback과 섞으면 다른 기기에서 올바르게 돌아오지 않습니다. 공유 Google 로그인은 Google이 허용하는 도메인·HTTPS redirect 구성이 추가로 필요합니다. Google 공식 웹 서버 OAuth 문서를 기준으로 등록합니다.

관리자 ID의 기본값은 admin입니다. 최초 비밀번호는 난수로 생성해 실행 창에만 표시하고 설정에는 scrypt 해시를 보관합니다. 잊었으면 종료 후 다음 명령으로 재발급합니다. 기존 관리자 세션도 무효화합니다.

.\PlayHub.exe --reset-admin-password

6. 실제 PC 자동 점검

서비스가 실행 중일 때 별도 PowerShell 창에서 배포 ZIP의 검사 스크립트를 실행합니다. 별도 npm 패키지나 SQL 설치가 필요하지 않습니다.

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\windows-acceptance.ps1 -WithHttpSmoke -WithAdmin

-WithAdmin은 비밀번호를 숨겨진 입력으로 받고 stdin으로만 검사 프로세스에 전달합니다. 비밀번호를 명령행·보고서에 기록하지 않습니다. 검사기는 실행 중인 프로세스·웹 루트·loopback 포트·비공개 경로를 관측하고, 선택 HTTP 검사에서 QA 전용 게스트·저장·이벤트를 생성합니다. 그 기록은 실제 이용 지표에서 제외됩니다. 공개 상태를 시험 변경하면 원래 상태로 복구합니다.

결과는 데이터 폴더의 reports\portable-acceptance.json, HTML 및 portable-http.json, HTML에 남습니다. 정확한 결과 파일명은 검사 출력도 함께 확인합니다. --self-test는 임시 DB·Node 정적 서버로 기능을 확인하는 검사이며 실제 Rebex 실행 증거를 대신하지 않습니다.

브라우저 입력·Google 실제 로그인·다른 PC의 LAN 접근은 자동 HTTP 검사와 구분합니다. 이 제작 환경은 Linux이므로 Windows/Rebex의 실실행은 not_run입니다. 실제 실행 전 확인할 항목과 관측 근거는 docs/PORTABLE_DESIGN.md에 정리했습니다.

02 / 사용자 흐름과 관리 화면

PlayHub Portable 빠른 시작

PlayHub Portable은 경량 게임 8종, 사용자 사이트, 관리자 사이트, 저장·이용 지표 API를 한 번의 실행으로 시작하는 Windows용 로컬 PoC다. 사용자는 SQL 서버·Node.js·IIS를 설치하지 않는다. SQLite와 Node 런타임은 PlayHub 쪽에 포함하며, 사용자 사이트의 정적 파일 서버는 사용자가 이미 보유한 Rebex Tiny Web Server를 연결한다.

이 문서의 실행 진입점은 PlayHub.exe다. 소스 저장소의 기존 Install.cmd, IIS 설치 스크립트, npm 명령은 이 포터블 사용 절차에 포함되지 않는다. 기존 IIS 버전과 동시에 같은 포트를 사용할 수 없으므로 먼저 해당 실행을 종료하거나 포트 충돌 안내를 해결한다.

1. 처음 실행하기

  1. 기존 RebexTinyWebServer.exe가 있는 폴더에 PlayHub.exe를 복사한다.
  2. PlayHub.exe를 더블클릭한다. 기존 Rebex 파일을 찾지 못하면 처음 한 번 표시되는 파일 선택 창에서 해당 EXE를 선택한다.
  3. PlayHub가 자체 실행 파일·정적 사이트·기본 설정·SQLite 데이터 폴더를 준비하고 서버 상태를 확인할 때까지 기다린다.
  4. 준비된 사용자 사이트를 브라우저에서 연다. 관리자 사이트 주소도 실행 안내에서 확인할 수 있다.

다음 실행부터는 저장한 경로 설정과 기존 데이터가 사용된다. 실행 파일이 있는 폴더에 데이터베이스를 만들거나 기존 Rebex 설정을 덮어쓰는 방식이 아니다. 실행 데이터는 기본적으로 %LOCALAPPDATA%\PlayHub 아래에 생성된다.

최초 준비 때 관리자 이름 admin과 무작위 초기 비밀번호를 실행 창에 표시한다. 비밀번호는 평문 파일이나 시작 보고서에 저장하지 않으므로 안전하게 보관한다. 재실행할 때 기존 비밀번호를 다시 표시하지 않는다. 잊었다면 실행 창에서 Q로 종료한 뒤 PlayHub.exe --reset-admin-password로 새 비밀번호를 만들 수 있다. 이 작업은 기존 관리자 세션을 폐기한다.

Windows의 실행 파일 보안 확인이나 방화벽 확인은 사용자의 시스템 정책에 따라 표시될 수 있다. 실패한 실행을 성공으로 표시하지 않으며, 포트 충돌·Rebex 파일 부재·데이터 폴더 쓰기 실패는 실행 안내와 보고서에서 확인해야 한다. Windows 로그인 없이 부팅 시 자동 서비스로 동작시키는 구성은 이번 포터블 범위가 아니다.

4. 저장과 복구

게임 상세의 저장 기록에서 서버 이어하기, 현재 탭의 임시 기록, 보관 슬롯, 교체 전 백업을 확인한다. 다른 탭에서 같은 기록이 바뀌면 자동으로 덮어쓰지 않고 충돌을 표시한다. 현재 탭 진행을 먼저 별도 보관한 뒤 이어하기로 적용하거나 서버 기록을 선택할 수 있다.

API가 일시적으로 연결되지 않거나 쿠키를 유지할 수 없는 경우에는 검증된 내장 게임을 로컬 모드로 실행할 수 있다. 이때는 현재 탭 임시 저장이며 서버 저장·서버 게임 통계·다른 기기 복구가 제공되지 않는다. 서버가 정상적으로 비활성·접근 거부한 게임을 로컬 모드로 우회하지 않는다.

게스트 저장의 연결 정보는 브라우저 쿠키에 의존한다. 쿠키 삭제·게스트 로그아웃·브라우저 데이터 제거 뒤 동일한 기록으로 자동 복귀하는 기능은 보장하지 않는다. Google 연결은 선택 기능이며, 연결 시 기존 게스트 기록을 어떻게 처리할지 명시적으로 선택한다.

데이터 폴더를 지우면 DB와 설정도 삭제될 수 있다. 프로그램 파일 교체와 데이터 폴더 삭제를 같은 작업으로 취급하지 않는다. 실행 중인 SQLite 파일을 탐색기로 복사하여 정상 백업이 끝났다고 판단하지 않는다. 포터블 데이터 백업·복구는 지원되는 절차와 실제 검증 범위를 확인한 뒤 수행한다.

5. 관리자 화면과 지표

관리자 화면은 실행한 PC의 브라우저에서 연다. 일반 게임 사용자의 쿠키로 관리자 로그인이 되지 않는다. 관리자 로그인 정보는 최초 준비 과정의 안내를 따르며, 고정 공용 비밀번호를 사용하지 않는다.

지표 화면에는 다음 세 가지 데이터가 분리되어 있다.

기간 필터는 KST 날짜 기준이며, 게임 필터로 개별 게임을 조회할 수 있다. 노출은 카드의 50% 이상이 문서가 보이는 상태로 1초 유지됐을 때 집계한다. 그 전에 누른 클릭은 별도 조건으로 기록한다. D1·D7·D30은 성숙한 코호트만 확정하며, 아직 시간이 지나지 않은 값은 0% 대신 집계 대기로 표시한다. 기획상의 32개 지표 전체가 이번 화면의 모든 카드로 구현되었다는 의미는 아니다.

6. 같은 네트워크에서 사용하기

게임을 제공하는 PC에서 실행한 뒤, 다른 PC·휴대전화는 해당 PC의 LAN 주소와 사용자 사이트 포트로 접근한다. 예를 들어 http://192.168.0.20:8080/ 같은 형식이다. 실제 IP와 포트는 실행 안내를 사용한다. 다른 기기에서 localhost를 열면 서버 PC가 아니라 그 기기 자신을 가리킨다.

사용자 사이트와 사용자 API의 포트가 Windows 방화벽에서 현재 네트워크에 허용되어야 한다. 방화벽 정책 변경이 필요한 환경에서는 관리자 권한이나 조직 정책 승인이 필요할 수 있다. 설치 없는 로컬 실행과 LAN 방화벽 설정이 필요 없는 것은 같은 의미가 아니다.

관리자 사이트와 관리자 API는 LAN에 공개하지 않는다. 사용자 사이트에 관리자 화면 링크를 추가하거나 사용자 포트를 열었다는 이유로 관리자 권한이 생기지 않는다. 인터넷 공개 서비스나 공유기 포트 전달을 이번 PoC의 검증된 운영 방식으로 간주하지 않는다.

7. Google 로그인은 별도 설정이 필요하다

게스트 플레이는 외부 인증 설정 없이 사용할 수 있다. 실제 Google 로그인에는 사용자의 Google OAuth client ID·client secret·정확한 redirect URI가 필요하다. 비밀 값은 사용자 사이트의 config.js나 정적 폴더에 넣지 않는다.

서버 설정 파일은 %LOCALAPPDATA%\PlayHub\private\config\local.json이다. 실행을 종료한 뒤 해당 파일의 google 항목을 설정하고 재실행한다. 다른 설정·관리자 해시·데이터 경로는 그대로 유지한다. callback은 현재 선택한 사용자 API 포트의 http://localhost:<API포트>/api/auth/google/callback과 Google Console의 등록값을 일치시킨다. 이 localhost 구성은 같은 PC 브라우저의 로컬 검증용이다.

설정이 없으면 화면은 설정이 필요하다고 알리고 게스트 플레이를 유지한다. 시험 계정으로 로그인된 것처럼 표시하지 않는다. HTTP LAN 주소와 localhost callback을 섞으면 다른 기기의 브라우저에서 인증 흐름을 완료할 수 없다. 이번 LAN PoC는 게스트 흐름을 기본으로 사용하고, Google은 올바른 호스트·HTTPS·OAuth 설정이 갖춰진 조건에서 별도로 검증한다.

8. 종료·재실행·문제 확인

브라우저 탭을 닫는 것과 서버 프로세스를 종료하는 것은 다르다. PlayHub 실행기의 종료 기능을 사용하여 해당 실행이 시작한 자식 프로세스를 정리한다. 사용자가 별도로 실행한 원본 Rebex를 이름만 보고 일괄 종료하는 방식은 사용하지 않는다.

실행 창에서 U를 입력하면 사용자 화면, A는 관리자 화면을 연다. Q는 이번 실행을 종료한다. 시작 보고서는 %LOCALAPPDATA%\PlayHub\reports\startup-report.json에 있다. 기본 위치 외에 --data-dir <폴더>를 사용한 경우에는 해당 폴더 아래의 같은 구조를 사용한다.

문제가 생기면 다음 순서로 확인한다.

  1. PlayHub가 준비 완료를 표시했는지, 시작 보고서에 실패 사유가 있는지 확인한다.
  2. 같은 PC의 사용자 사이트와 관리자 사이트가 각각 열리는지 확인한다.
  3. 게임에 로컬 모드 표시가 있다면 사용자 API와 쿠키 연결 상태를 확인한다.
  4. LAN 접속만 실패하면 서버 PC의 현재 IP·포트·방화벽을 확인한다.
  5. 포트가 사용 중이면 기존 PlayHub 또는 IIS 실행 여부를 먼저 확인한다. 다른 프로그램을 임의로 종료하지 않는다.

지원 자료로 보고서를 전달할 때도 관리자 비밀번호·Google secret·쿠키·CSRF 값을 함께 보내지 않는다. 정상 보고서는 이 비밀 값을 기록하지 않도록 구성한다.

9. 검증 상태를 읽는 방법

소스 자동 검사, EXE 패키징 검사, 실제 Windows 실행, 브라우저 조작, 다른 기기의 LAN 접속, Google 실인증은 서로 다른 검사다. 하나의 성공을 다른 검사의 성공으로 바꾸지 않는다.

현재 제작 환경에서는 실제 Windows·Rebex 실행과 브라우저 시험을 수행하지 않았으며 not_run으로 기록한다. portable/windows-acceptance.ps1은 사용자 PC에서 이미 실행 중인 인스턴스를 관측하여 실제 응답·프로세스·폴더 분리를 검사하기 위한 도구다. 선택 QA 검사는 별도 시험 방문과 저장 데이터를 만들며 실제 이용 지표와 분리한다. 상세 계약과 체크 목록은 PORTABLE_DESIGN.md를 참조한다.

실행 중인 기본 인스턴스를 관리자 인증을 포함해 검사하려면 Windows PowerShell에서 다음을 실행한다. 비밀번호는 숨겨진 입력창에서 받고 명령줄에 넣지 않는다.

$playhubRoot = Join-Path $env:LOCALAPPDATA 'PlayHub'
$playhubStartup = Get-Content (Join-Path $playhubRoot 'reports\startup-report.json') -Raw -Encoding UTF8 | ConvertFrom-Json
$playhubCheck = Join-Path $playhubStartup.paths.appRoot 'portable\windows-acceptance.ps1'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $playhubCheck -DataDir $playhubRoot -WithAdmin

-WithAdmin을 빼면 기본 관측만 수행한다. 관리자 인증 없이 QA HTTP만 확인하려면 -WithHttpSmoke를 사용한다. 이 경우 관리자 권한 검사는 미완료로 남을 수 있다. 결과는 reports\portable-acceptance.json과 .html, 선택 HTTP 상세 결과는 reports\portable-http.json에 기록된다. 종료 코드 0은 선택한 자동 검사 범위의 관측 통과이며, 브라우저·다른 기기 LAN·Google 실인증까지 완료했다는 의미는 아니다. 실패는 1, 미완료는 2다.

게임 폴더와 목록 변경

편집 가능한 게임 원본은 %LOCALAPPDATA%\PlayHub\workspace\games, 중앙 목록은 workspace\catalog\games.json이다. 게임을 추가할 때는 games/<id>/에 manifest·index.html·자산을 넣고 중앙 목록에 { "id": "<id>", "path": "games/<id>", "enabled": true } 항목을 추가한다. 종료 후 재실행하면 검증과 정적 페이지 생성을 거친다. 잘못된 manifest나 경로를 넣었다면 오류를 고친 뒤 다시 실행한다.

이 편집 영역의 게임·카탈로그는 다음 실행에서도 보존된다. workspace\web과 workspace\shared는 패키지의 앱 코드로 갱신되므로 사용자 콘텐츠의 영구 편집 위치로 사용하지 않는다. 현재 범위는 신뢰된 로컬 파일 카탈로그이며 외부 제작자 업로드·검수 시스템은 포함하지 않는다.

4. 시작·실패·종료

준비 과정은 자산 검증, 사용자 EXE 발견, 데이터·설정 준비, 포트 사용 가능 여부, worker 시작, health와 정적 응답 확인 순서로 진행한다. 성공 보고서는 필요한 구성 요소가 준비됐을 때만 작성한다. 시작 과정에서 실패하면 이번 실행이 만든 프로세스를 정리하고 원인과 failed 상태를 남긴다.

이미 사용자가 별도로 띄운 Rebex나 이름이 같은 다른 Node 프로세스를 종료하지 않는다. 종료는 실행기가 소유한 PID·실행 ID·경로를 기준으로 처리한다. 가능하면 정상 종료를 먼저 요청하고 제한 시간 뒤 필요한 자식만 정리한다. DB를 사용하는 API worker 종료와 파일 정리의 순서를 지킨다.

Rebex는 GUI 프로그램이고 autoStart=true는 프로세스 실행 후 서버 시작을 자동화한다. 실행 파일을 단일 진입점으로 만들더라도 자동 Windows 서비스 설치나 재부팅 후 무인 실행 기능을 제공한다는 의미는 아니다.

5. Rebex 설정과 버전

공식 확인 키는 webRootDir, httpPort, httpsPort, defaultFile, autoStart, minimizeOnStart, minimizeToTray, decodeUri, logLevel이다. root, httpPorts, httpBindings 같은 미확인 키를 사용하지 않는다. 설정 파일은 EXE와 같은 폴더의 RebexTinyWebServer.exe.config에 둔다.

HTTP portable 구성은 httpsPort를 빈 값으로 설정하여 기본 11443 listener를 만들지 않는다. defaultFile=index.html을 유지하고 이미 생성한 /play/<id>/index.html을 사용한다. SPA rewrite 지원을 추정하지 않는다. 상대 경로 기준은 공식 1.0.3부터 EXE 위치로 수정되었으며, 최소화 옵션은 1.0.6부터 추가되었다.

2026-11-16 조사에서 공식 latest ZIP의 PE 버전은 1.0.9.0이었으나 제품 페이지 이력 최상단은 1.0.8이었다. 설치된 사용자 EXE의 실제 버전과 SHA-256을 관측하여 보고서에 남긴다. ZIP의 모든 과거·미래 버전과 동작이 같다고 가정하지 않는다.

6. 정적 웹 보안과 게임 실행

관리자 Node 정적 worker는 loopback 바인딩과 응답 헤더를 직접 제어한다. Rebex의 커스텀 헤더 기능은 확인되지 않아 사용자 HTML에 필요한 meta CSP를 포함하는 방식을 사용한다. meta CSP는 HTTP CSP 헤더의 모든 기능을 대체하지 않는다. frame-ancestors, sandbox, report-only는 meta로 전달할 수 없다.

게임 iframe은 기존 sandbox="allow-scripts"를 유지한다. opaque origin의 초기 메시지는 source·nonce를 확인하고 MessageChannel을 전달하며, 저장·이벤트는 포털 broker가 API로 중계한다. Google token·세션 cookie·CSRF를 게임에 넘기지 않는다. 게임 코드가 서버 권한을 얻는 구조로 바꾸지 않는다.

.js, .css, .json, .svg, .html은 실제 응답 Content-Type을 확인한다. IIS용 web.config가 Rebex에서도 헤더·rewrite·MIME 설정으로 적용된다고 가정하지 않는다. 등록 게임은 빌드 카탈로그와 manifest로 확정하고 실행 시 API의 공개 상태를 우선한다.

7. API·저장·지표의 유지 범위

포터블 전환은 기존 API의 권한 모델을 완화하지 않는다. 게스트 저장은 주체·게임·슬롯·revision을 검사하며 충돌 시 412로 보존한다. 별도 슬롯·복원 전 백업·삭제 전 백업·멱등성 계약도 유지한다. 관리자 cookie와 사용자 cookie를 혼용하지 않는다.

실제·QA·예제 지표를 구분하고, QA는 새 익명 세션에서 전용 endpoint를 통해 서버가 분류한다. 검사 도구가 이벤트 body에 is_test를 넣는 방식으로 분류를 위조하지 않는다. 기간은 KST이며 리텐션의 최초일은 전체 이력을 기준으로 한다. 포장 방식 변경만으로 D30 실제 성과나 Google 실인증을 검증 완료로 기록하지 않는다.

Google 설정은 데이터 영역의 서버 설정에서 읽고 정적 파일에는 넣지 않는다. 미설정은 googleEnabled:false이며 게스트 플레이는 계속된다. Google OAuth 설정과 실제 계정 consent는 포터블 파일만으로 자동 완성할 수 있는 단계가 아니다.

8. Windows 실행 수용 검사 명세

portable/windows-acceptance.ps1은 이미 실행 중인 인스턴스를 검사한다. 설치·서비스 등록·방화벽 변경·재시작·DB 직접 수정·다른 프로세스 종료를 하지 않는다. 기본 검사는 관측 및 HTTP 읽기이며, 선택 QA 검사만 새 QA 세션과 게임 저장 데이터를 만든다.

입력과 증거

실행기가 작성한 startup-report.json을 입력받아 실제 origin·root·PID·실행 상태를 읽는다. 임의 보고서의 성공 플래그만 믿지 않고 OS 프로세스·listener·HTTP 응답을 다시 관측한다. 보고서 경로가 없거나 필수 필드가 누락되면 통과가 아니다. 실행 보고서의 정확한 필드 계약은 실행기와 같은 릴리스에서 고정한다.

현재 계약은 schemaVersion:1, version:0.3.0, mode:portable-rebex이며 runId, status, generatedAt, environment, mainPid, paths, ports, urls, children, rebex, security, checks를 포함한다. paths는 instanceRoot/appRoot/workspaceRoot/userRoot/adminRoot/configPath/dataDir/executable을, ports는 user/admin/publicApi/adminApi를 제공한다. 사용자 정적 root의 playhub-ready.json runId도 보고서와 대조하여 다른 실행의 페이지를 성공으로 인정하지 않는다.

출력은 JSON과 사람이 읽을 수 있는 HTML 또는 콘솔 요약이며, 각 항목에 pass, fail, not_run, 필요한 경우 skip을 유지한다. 검사 시각·실행 ID·호스트 OS·검사 도구 버전·관측 URL·비밀을 제외한 결과를 기록한다. 원본 보고서에 비밀이 있어도 이를 그대로 재직렬화하지 않는다.

04 / EXE 재현 빌드

PlayHub 0.3.0 단일 EXE 빌드

배포 대상 사용자는 PlayHub.exe를 실행합니다. Node.js, npm, Python, SQL 서버, IIS를 설치하지 않습니다. 이 문서는 실행 파일을 만드는 개발자용입니다. Rebex Tiny Web Server 실행 파일은 포함하지 않으며 사용자가 보유한 복사본을 런처에서 선택합니다.

1. 구조

launcher.cjs는 Node SEA의 CommonJS 진입점입니다. playhub.bundle.gz라는 asset 하나에 기존 ESM 서버와 웹·게임 소스를 담습니다. 실행 시 %LOCALAPPDATA%\PlayHub 아래 app/<payload SHA-256>에 검증해 풀고 다음 함수를 동적 import로 호출합니다.

await launch.run({
  appRoot, instanceRoot, args,
  executable: process.execPath,
  sea: true,
  launcherPath: null
});

Node 개발 실행은 sea:false, launcherPath:<launcher.cjs의 절대경로>를 전달합니다. --data-dir PATH는 기본 저장 폴더를 바꾸는 선택 사항입니다. 기본 실행에는 인수가 필요하지 않습니다. --worker=..., --self-test, --check-http 등 애플리케이션 인수는 launch.run으로 전달합니다.

--package-check는 추출·내장 ESM import·SQLite SELECT 42만 검사하고 서비스를 시작하지 않습니다. --bundle PATH는 Node 개발 실행에서만 사용할 수 있으며 완성된 SEA가 외부 payload로 바뀌는 것은 허용하지 않습니다.

3. Windows EXE 생성

아래 경로는 예시이며 실제로 검증해 풀어 둔 입력 위치를 지정합니다.

node portable/build-sea.mjs --target win-x64 --node-exe <build-inputs/node-v24.22.1-win-x64/node.exe> --node-license <build-inputs/node-v24.22.1-win-x64/LICENSE> --postject-api <build-inputs/postject/package/dist/api.js> --output <output/PlayHub_Portable/PlayHub.exe>

명령은 다음 순서로 수행합니다.

  1. 빌더 버전, Windows Node·LICENSE·postject API의 고정 체크섬을 확인합니다.
  2. 게임 catalog를 검사하고 런타임 파일의 SHA-256 목록을 만듭니다.
  3. {format:1,version:'0.3.0',files:[{path,sha256,data}]}를 UTF-8 JSON과 gzip으로 만듭니다.
  4. useSnapshot:false, useCodeCache:false, execArgvExtension:'none' 설정으로 SEA preparation blob을 생성합니다.
  5. 검증한 Node의 복사본에서 원래 Authenticode certificate directory를 제거하고 SEA blob을 주입합니다.
  6. 최종 PE32+ x64 구조, RT_RCDATA / NODE_SEA_BLOB, payload 일치, SEA fuse, 남은 서명 directory가 없는지를 검사합니다.
  7. EXE·bundle manifest·압축 payload·빌드 보고서를 기록합니다.

Node의 원래 서명은 수정한 애플리케이션의 서명이 될 수 없습니다. 결과물은 서명되지 않은 PlayHub 실행 파일입니다. 별도 코드 서명을 적용하려면 최종 주입·검사 후 발급받은 인증서로 서명하고, 서명 후 EXE 해시를 다시 기록합니다. 이 빌더는 인증서를 발급하거나 Windows 정책을 변경하지 않습니다.

산출물은 PlayHub.exe, PlayHub.exe.bundle.json, PlayHub.exe.bundle.gz, PlayHub.exe.build.json입니다. 뒤의 세 파일은 빌드·검증용 증거이며 실행 시 따로 필요하지 않습니다. 사용자가 다른 PC로 복사해야 하는 실행 파일은 PlayHub.exe 하나입니다. 개인 DB와 설정은 최초 실행 뒤 사용자 저장 폴더에 생성됩니다.

4. 포함·제외 범위

포함: server/, web/, shared/, games/, catalog/, package.json, config/example.json, 런타임 portable/*.mjs·portable/*.ps1, tools/build.mjs, setup.mjs, backup.mjs, restore-data.mjs, dev.mjs, smoke.mjs, check-stack.mjs, Node 전체 라이선스입니다.

제외: IIS 설치 스크립트, 기존 사용자 DB·비밀 설정, 테스트, 보고서, npm 패키지, 빌드 cache와 도구, Rebex 실행 파일입니다. 정적 dist는 원본 소스를 바탕으로 instance의 workspace에 생성합니다. 가변 게임·생성물과 앱 code cache를 구분하는 실제 동작은 prepare.mjs가 담당합니다.

launcher는 경로 이동, 절대경로, Windows 장치명·ADS, case 충돌, 파일/디렉터리 충돌, symlink·junction, 잘못된 base64와 SHA 불일치를 거부합니다. 압축 32 MiB, JSON 128 MiB, 파일 4,000개, 파일별 16 MiB, 실제 파일 합계 64 MiB의 제한이 있습니다. 현재 8종 기본 게임을 훨씬 넘는 크기이며 무제한 압축 해제를 허용하지 않습니다.

동일 payload를 다시 실행할 때도 필요한 code cache 파일의 SHA를 확인합니다. 파일이 달라져 있으면 사용자 DB를 지우거나 의심되는 코드를 실행하지 않고 중단합니다. Windows에서 EXE를 더블클릭해 시작 오류가 발생한 경우, 대화형 콘솔이면 Enter 입력을 기다려 오류 메시지를 읽을 수 있게 합니다. IPC worker·자동 검사·표준 입력 리디렉션에서는 입력 대기를 하지 않습니다.

5. Linux에서 동일 SEA payload 실행 검사

Linux x64·Node 24.22.1 환경에서는 다음과 같이 동일 원본의 SEA를 만들 수 있습니다.

node portable/build-sea.mjs --target linux-x64 --node-license <build-inputs/Node/LICENSE> --postject-api <build-inputs/postject/package/dist/api.js> --output <scratch/PlayHub-linux>

Linux 빌드는 생성한 ELF를 실제로 실행해 --package-check를 통과시켜야 성공합니다. 추가로 전체 격리 HTTP·SQLite 점검을 실행합니다.

<scratch/PlayHub-linux> --data-dir <scratch/portable-instance> --self-test

Windows와 Linux 빌드 보고서의 bundle.payloadSha256, sea.blobSha256, sea.launcherSha256을 비교하면 같은 소스·진입점·SEA blob을 사용했는지 확인할 수 있습니다. Linux의 통과는 Windows PE를 실제로 실행한 증거가 아닙니다. Windows 결과의 execution.windowsExecuted는 작성 환경에서 항상 false입니다. 실제 Rebex 기동, Windows 사용자 프로필 권한, 프로세스 종료, LAN, 브라우저·Google 인증은 Windows 대상 PC에서 따로 수행합니다.

개발용 bundle 실행 예시는 다음과 같습니다.

node portable/launcher.cjs --bundle <PlayHub.exe.bundle.gz> --data-dir <scratch/instance> --package-check
node --test tests/portable.packaging.test.mjs

SECTION 01

PlayHub 0.2.0 — 로컬 IIS 실행형 PoC

로그인 없이 가벼운 게임을 플레이하고, 게임 폴더와 목록 파일로 확장하며, 별도 관리자 사이트에서 노출·클릭·플레이·D1/D7/D30을 확인하는 1차 실행 패키지입니다. 실제 JavaScript 게임 8종, 사용자·관리자 화면, Node API, SQLite 저장, Windows IIS 설치·점검 도구를 포함합니다.

0.2.0에서는 저장 충돌 복구 화면, 보관 슬롯·이전 진행 복원, 실제/QA 지표 분리, 기간·게임별 분석, 데이터베이스 복원, 통합 수용 검사를 구현했습니다. 기능과 검사 증거는 docs/POC_COMPLETION.md, 실제 실행 결과는 reports/acceptance.html을 기준으로 합니다. planning/의 28장 기획서는 이전 기획 기준선이며 제품 목표와 당시 구현 상태를 함께 담습니다. 현재 구현 여부는 이 README와 docs/를 우선합니다.

1. 가장 빠른 설치

권장 대상은 IIS를 사용할 수 있는 Windows 11 Pro 또는 Windows Server, 64비트 Windows PowerShell 5.1입니다. IIS 기능 활성화·사이트·작업 스케줄러·방화벽 설정 때문에 설치 명령은 관리자 권한이 필요합니다. 기본 포트 8080·8081·8090·8091이 비어 있어야 합니다.

  1. ZIP을 풉니다. 소스 보관 위치의 예는 D:\Github\UnrealSamples\WebProjects\PlayHub입니다.
  2. Install.cmd를 우클릭하여 관리자 권한으로 실행합니다. 또는 관리자 Windows PowerShell에서 다음을 실행합니다.
  3. 설치 중 관리자 비밀번호를 직접 입력합니다. 12자 이상이며 공용 기본 비밀번호는 없습니다.
  4. 설치 결과에 표시된 사용자 주소를 다른 PC에 전달합니다. 같은 네트워크의 Private/Domain 프로필에서 사용자 포트만 공유됩니다.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-IIS.ps1 -ShareHost 192.168.0.10

192.168.0.10은 IIS를 설치한 PC의 실제 LAN 주소로 바꿉니다. -ShareHost를 생략하면 기본 게이트웨이가 있는 네트워크의 IPv4 주소를 찾아 사용합니다. VPN·네트워크 카드가 여러 개인 PC에서는 주소를 직접 지정하는 편이 명확합니다. 설치 경로 기본값은 C:\PlayHubPoC입니다.

화면·서비스 기본 주소 이용 범위
사용자 사이트 http://<서버-PC-IP>:8080 같은 네트워크에서 탐색·플레이
관리자 사이트 http://localhost:8081 설치한 PC에서 관리자 로그인
사용자 API http://<서버-PC-IP>:8090/api/health 사용자 기능용 API
관리자 API http://127.0.0.1:8091/api/health loopback 전용, 별도 인증

포트 번호를 지정할 수도 있습니다. 네 포트는 서로 달라야 합니다.

.\scripts\Install-IIS.ps1 -InstallRoot C:\PlayHubPoC -ShareHost 192.168.0.10 -UserPort 8080 -AdminUiPort 8081 -PublicApiPort 8090 -AdminApiPort 8091

한 PC에서만 확인하려면 -LocalOnly를 사용합니다. 이미 Node.js 24 이상이 있고 서비스 계정이 읽을 수 있다면 -NodePath 'C:\Program Files\nodejs\node.exe'를 지정할 수 있습니다. 기본 설치는 공식 nodejs.org의 Windows Node.js 24 ZIP과 SHA-256 목록을 받아 전용 runtime 폴더에 준비합니다. 최초 준비에 인터넷 연결이 필요할 수 있지만, 게임·화면·API 실행에 npm 패키지나 외부 CDN은 필요하지 않습니다.

설치 스크립트는 기존 Default Web Site를 바꾸지 않습니다. PlayHubPoC-8080-User, PlayHubPoC-8080-Admin 사이트와 앱 풀을 만들고, Node API는 Local Service 계정의 시작 작업으로 실행합니다. 관리자 사이트·API에는 LAN 방화벽 포트를 열지 않습니다.

3. 자동 점검

설치 끝에서 기본 HTTP 점검을 실행합니다. 설치 후 한 번에 확인하려면 관리자 권한 터미널에서 다음 명령을 실행합니다. 설치된 Microsoft Edge를 사용하며 -InstallTools를 지정한 최초 실행에만 QA용 Playwright 패키지를 설치합니다.

.\Validate.cmd -InstallRoot C:\PlayHubPoC -InstallTools

이 명령은 실제 IIS 사이트·관리자 loopback·API 작업·설정 ACL을 관측하고, 관리자 인증을 포함한 HTTP 및 브라우저 검사를 실행해 C:\PlayHubPoC\reports\poc-acceptance.html과 JSON으로 모읍니다. 독립 검증 프로세스가 각각 관리자 비밀번호를 요청할 수 있습니다. 브라우저 도구를 생략하려면 -SkipBrowser를 사용하되 결과는 부분 검증입니다. 실제 Google 로그인·두 번째 LAN PC·재부팅은 자동 통과로 표시하지 않습니다.

HTTP만 별도로 확인하려면 다음 명령으로 비밀번호를 입력합니다.

C:\PlayHubPoC\releases\<현재-release>\scripts\Test-IIS.ps1 -InstallRoot C:\PlayHubPoC -WithAdmin

정확한 현재 release 경로는 C:\PlayHubPoC\installation.json에 있습니다. 편하게 압축을 푼 소스의 같은 스크립트를 실행해도 됩니다.

.\scripts\Test-IIS.ps1 -InstallRoot C:\PlayHubPoC -WithAdmin

결과는 C:\PlayHubPoC\reports\iis-smoke.json과 같은 이름의 HTML에 기록됩니다. 점검은 서버에서 QA로 고정한 새 게스트의 저장·노출·플레이 이벤트를 만듭니다. 0.2 검증 트래픽은 실제 이용 지표에서 제외되며 관리자 QA 탭에서 조회합니다. 게임 공개 상태 변경은 원래 값으로 복원하고 검사 데이터는 남깁니다. 0.1에서 QA 표시 없이 생성된 과거 기록은 소급 분류하지 못합니다.

실제 브라우저 조작을 자동 확인하는 선택 도구도 있습니다. Microsoft Edge를 기본 사용하며, Playwright는 검증 도구에만 설치합니다.

.\scripts\Test-Browser.ps1 -InstallRoot C:\PlayHubPoC -InstallTools -WithAdmin

-WithAdmin은 관리자 기능까지 검사하며 비밀번호를 숨겨진 입력으로 받습니다. 이 옵션을 생략하면 관리자 검사는 skip이고 전체 결과는 partial입니다. 브라우저·IIS·실제 Google 계정 검증은 서로 다른 결과입니다. 어느 한 검사의 통과를 전체 출시 완료로 바꾸지 않습니다.

4. 개발 PC에서 설치 전에 검사

Node.js 24 이상에서 아래 명령을 실행합니다. check-stack은 임시 디렉터리·임시 DB·임시 포트를 사용하므로 설치된 서비스 데이터에 영향을 주지 않습니다.

node tools/acceptance.mjs
# Python 검증 도구도 설치된 개발 환경
node tools/acceptance.mjs --with-python

빌드 → 파일·구문·전체 Node 회귀 → 두 정적 사이트와 두 API의 실제 HTTP → 기존 비공개 게임이 있는 운영 상태 → 선택형 Python 검사 순서로 실행합니다. reports/acceptance.html에 새 결과만 모으며 검사 도중 코드가 바뀌면 실패 처리합니다. npm run check:all도 같은 Node 검사 진입점입니다. HTTP 검사는 Node 개발 서버 결과이며 Windows IIS 자체의 실행 증거는 아닙니다.

Python 전체 스키마·파일·ZIP 검증을 사용하려면 automation/README.md를 참고하세요. Python은 선택 검증 도구에만 필요하고 IIS PoC 실행에는 필요하지 않습니다. specs/openapi.yaml과 specs/retention_query.sql은 제품 목표용 계약·PostgreSQL 예시이며, 실제 PoC API는 docs/POC_API_CONTRACT.md를 기준으로 합니다.

5. 게임 추가

각 게임은 games/<id>/game.manifest.json, index.html, 실행 코드, assets/를 갖습니다. 중앙 catalog/games.json의 entries에 다음 형태로 추가합니다.

{"id":"new-puzzle","path":"games/new-puzzle","enabled":true}

manifest에는 한국어·영어 제목·소개·조작법, 태그, 입력, 화면 비율, 저장·SEO·미디어를 작성합니다. node tools/build.mjs가 검사하고, 공용 SDK는 게임별 vendor 폴더로 포함해 배포 게임을 독립 패키지로 만듭니다. 실제 카드·상세·사이트맵 반영은 빌드와 IIS 배포가 성공한 뒤입니다.

소스에서 폴더·목록을 바꾼 다음 Install-IIS.ps1을 같은 설치 경로·포트로 다시 실행하면 새 release로 배포합니다. 기존 설정·사용자 DB는 유지합니다. 새 release 전환이 실패하면 이전 release와 설정 복구를 시도합니다. 운영자 비공개 설정은 별도 DB에 남아 있으므로 catalog를 다시 빌드했다고 강제로 공개되지 않습니다.

현재 8개 게임의 실제 규칙·저장 범위는 docs/POC_GAMES.md에 있습니다. 여러 스테이지·상점·랭킹 등 제품 계획의 모든 확장 기능을 구현한 버전은 아닙니다.

6. Google 로그인

Google 로그인을 가장하려고 로컬 가짜 계정을 만들지 않습니다. OAuth client가 없으면 설정 필요 상태로 표시하고 게스트 플레이를 제공합니다.

  1. Google Cloud에서 웹 애플리케이션 OAuth client를 만듭니다.
  2. 호스트 PC의 localhost 검증을 위해 http://localhost:8090/api/auth/google/callback을 정확히 등록합니다.
  3. 아래 스크립트로 client ID를 지정하고 client secret은 숨겨진 입력으로 넣습니다.
  4. 사용자 화면도 http://localhost:8080에서 열어 로그인합니다.
.\scripts\Set-GoogleOAuth.ps1 -InstallRoot C:\PlayHubPoC -ClientId '<발급받은-client-id>'

client secret은 웹 루트 밖의 접근 제한된 config에 저장합니다. 다른 PC의 LAN IP 방문에서 localhost callback을 사용하면 다른 PC 자신으로 돌아가므로 지원하지 않습니다. LAN 밖을 포함한 실제 Google 공유 로그인은 HTTPS의 등록 가능한 도메인·인증서·정확한 redirect URI 구성을 별도로 해야 합니다. Google은 일반 웹 redirect에 HTTPS와 호스트 제한을 적용하며 localhost만 예외를 허용합니다.

공식 기준: https://developers.google.com/identity/protocols/oauth2/web-server

7. 관리자 사이트와 권한

관리자 화면은 사용자 사이트의 숨겨진 탭이 아니라 별도 물리 웹 루트·IIS 사이트·앱 풀입니다. API도 두 listener를 사용하며 public API에서 /api/admin/*는 제공하지 않습니다. 관리자 cookie와 CSRF, scrypt 비밀번호, Origin 검사, 로그인·공개 상태 변경 감사 기록을 사용합니다.

사용자와 관리자의 API는 같은 Node 프로세스와 SQLite를 사용합니다. 이것은 PoC의 운영 단순화를 위한 선택이며 독립된 OS 서비스나 별도 데이터베이스로 배포된 구조라는 뜻은 아닙니다. 런타임은 소규모 단일 호스트 검증용이고, 제품화 시 PostgreSQL·배포 작업자·운영 인증 체계로 확장합니다.

8. 데이터·복구·검색

  • C:\PlayHubPoC\data\platform.sqlite: 사용자·세션·저장·이벤트·운영 기록. 웹 루트 밖에 있습니다.
  • C:\PlayHubPoC\config\local.json: 비공개 서버 설정. client secret·관리자 해시는 사용자 사이트에 복사하지 않습니다.
  • scripts/Backup-Data.ps1: 실행 중 SQLite 온라인 백업과 integrity_check, SHA-256 기록.
  • scripts/Restore-Data.ps1: 백업 검증·API 중지·원본 별도 보존·DB 적용·실패 복구·재시작 점검. -VerifyOnly는 중지 없이 백업만 검사합니다.
  • scripts/Restart-API.ps1: 설정 변경 뒤 API 재시작.
  • scripts/Restore-PreviousRelease.ps1: 이전 애플리케이션과 설정 복원. DB를 과거 상태로 되돌리지는 않습니다.
  • scripts/Stop-IIS.ps1: 두 사이트·API 중지. 파일과 저장 데이터를 지우지 않습니다.

진행 복원에는 두 종류가 있습니다. 사용자 화면의 저장 관리에서는 한 게임의 보관 슬롯/이전 진행을 현재 저장으로 복원합니다. 관리자 PowerShell의 데이터 복원은 플랫폼 전체 DB를 선택한 백업 시점으로 되돌리므로 백업 이후의 저장과 지표가 현재 DB에서 사라집니다. 교체 전 원본 파일은 보호된 data\recovery에 보존합니다. 적용 예와 중단 복구 절차는 docs/INSTALLATION_AND_RECOVERY.md를 참고하세요.

데이터 복원 후 Google·관리자 계정은 다시 로그인합니다. 현재 유효한 일반 게스트 세션은 백업에도 같은 미연결 게스트가 있을 때만 유지합니다. 이미 로그아웃한 과거 세션은 백업에서 되살리지 않습니다. 백업 이후 처음 만들어진 게스트나 손상된 현재 DB의 세션까지 자동 복구하는 기능은 아닙니다.

PoC의 게임 상세는 정적 HTML에 고유 제목·설명·조작법·canonical·OG·링크를 포함합니다. 기본 robots와 응답 헤더는 내부 PoC가 외부 검색에 색인되지 않도록 설정합니다. 검색 구조 검사와 실제 Search Console·검색 유입 성과 확인은 별도입니다.

9. 이번 제공물의 검증 상태

실제 수행 결과는 reports/와 docs/VALIDATION_STATUS.md에서 확인합니다. Node HTTP·SQLite·게임 규칙·계약 검사를 실행했고, Windows PowerShell·실제 IIS·실제 Google 계정·실브라우저 결과는 수행 여부를 따로 표시합니다. 자동 점검 스크립트를 제공한 것과 대상 환경에서 그 점검이 통과한 것을 혼동하지 않습니다.

HTTP LAN은 내부 PoC 환경입니다. 외부 서비스 공개 전에는 HTTPS·도메인 격리·검색 설정·운영 정책·부하·복구 검증을 제품 계획의 별도 게이트로 진행합니다.

3. 사용자 사이트

바로 플레이

홈에서 목록을 보고 검색·장르로 좁힌 뒤 상세에서 조작법을 확인하고 플레이한다. iframe은 게임 실행 권한만 허용하고, 부모 포털이 서버 저장·이벤트를 중개한다. 게임 코드에 로그인 쿠키나 Google 토큰을 전달하지 않는다. 새로 시작·일시정지·재개·승패·재시작을 각 게임에 연결했다.

API가 연결되지 않는 경우에도 검증된 내장 게임의 로컬 플레이를 명시적으로 선택할 수 있다. 이 상태에서는 서버 저장과 이용 지표가 기록되지 않는다. 같은 탭의 임시 진행은 복구에 이용하지만 영구적인 계정 저장으로 표시하지 않는다.

D30 재방문을 세션 만료 때문에 놓치지 않도록 익명·게스트 식별은 90일을 사용한다. 첫 게스트 승격과 유효 게스트의 세션 재조회 때 서버 만료와 쿠키 기간을 함께 갱신한다. 이미 만료·로그아웃한 세션은 부활시키지 않는다. 쿠키 삭제·다른 브라우저·다른 주소에서는 같은 게스트로 자동 연결할 수 없다. Google 회원·관리자의 인증 수명은 별도로 유지한다.

저장 기록 화면

게임별 저장 기록에서 서버 현재 진행, 현재 탭 미반영 진행, 보관 슬롯, 교체·제거 전 복구 기록을 구분한다. 서버와 탭이 충돌하면 최신 탭 진행을 계속 보존한다. 다음 행동을 제공한다.

  1. 서버 진행을 선택해 현재 게임을 다시 연다.
  2. 현재 탭 진행을 별도 슬롯에 먼저 보관하고, 예상 revision을 확인한 뒤 main으로 적용한다.
  3. 보관 슬롯이나 이전 main 백업을 선택해 복원한다. 교체 직전 main은 별도 백업에 남긴다.
  4. 공간이 부족하면 보관 슬롯을 확인 후 제거한다. 원본은 복구 기록으로 남기고 main은 제거할 수 없다.
  5. 서버 재연결·저장 재시도를 수행한다. 응답이 유실된 같은 쓰기는 동일한 멱등 키로 재시도한다.

다른 탭에서 계정이 바뀌면 이전 세션의 저장 응답을 적용하지 않는다. 이전 iframe의 추가 쓰기를 종료하고 계정별 임시 기록을 분리한다. 동시 변경으로 revision이 맞지 않으면 412로 멈추고 기존 데이터를 유지한다. 슬롯 이름을 제거했다가 다시 만들어도 이전 revision을 재사용하지 않아 오래된 요청이 새 기록을 바꾸지 못한다.

게임당 쓰기 슬롯은 main을 포함해 10개다. 복구 기록의 한도와 병합 원본 보존 규칙은 POC_API_CONTRACT.md에 있다. 모든 자동 저장을 무제한 영구 버전으로 보관하지는 않는다.

Google 연결

Google 설정이 없으면 설정 필요 상태를 보여 주며 게스트 기능은 계속 쓸 수 있다. client ID/secret을 설정하면 실제 Google authorization code·PKCE·state·nonce와 서버의 ID token 검증을 사용한다. 가짜 로그인 성공 상태는 제공하지 않는다.

Google 연결 후 기존 게스트 저장을 계정에 옮길 때는 명시적인 선택을 거친다. 충돌하는 진행은 임의로 하나를 덮어쓰지 않는다. 구체적인 병합 정책과 응답은 API 계약에 있다. 로그인 성공·취소·콜백 오류·실계정 병합은 사용자 소유 OAuth client로 현장에서 확인해야 한다.

6. 운영과 데이터 복원

Backup-Data.ps1은 SQLite 온라인 백업과 integrity check, SHA-256 메타데이터를 만든다. Restore-Data.ps1 -VerifyOnly는 서비스를 멈추지 않고 해당 백업을 검사한다. 실제 복원은 API를 멈춘 뒤 파일을 교체하고 다시 검증한다. 원본 DB와 관련 파일은 보호된 복구 폴더에 보존한다.

복원은 플랫폼 DB 전체를 과거 시점으로 돌리는 작업이다. 백업 이후 저장·지표는 복원된 현재 DB에 포함되지 않는다. 실패하면 원본을 되돌리고, 프로세스가 중간에 종료되면 maintenance lock을 유지해 반쯤 교체된 DB로 서비스를 시작하지 않는다. 중단 복구는 -RecoverInterrupted로 명시한다.

백업에 있던 로그인 세션을 그대로 부활시키지 않는다. 현재 유효한 일반 게스트는 현재 DB와 백업 모두 같은 미연결 게스트인 경우에만 쿠키를 유지할 수 있다. Google·관리자 세션, 이미 로그아웃한 세션은 복원 뒤 다시 인증해야 한다. 현재 DB가 손상되어 세션을 읽지 못하거나 게스트가 백업 시점에 존재하지 않았다면 기존 쿠키로 진행을 회수할 수 없다.

애플리케이션 release 복원과 데이터 복원은 별개다. 업데이트 시 지원 DB 스키마를 확인하고, 새 스키마를 읽지 못하는 과거 코드로 무조건 되돌리지 않는다. 실행 명령·자동 백업·중단 복구·ACL·실패 처리의 상세 절차는 INSTALLATION_AND_RECOVERY.md를 따른다.

설치·업데이트·데이터 복구 운영 가이드 — 0.2.0

이 문서는 실제 제공된 Node 도구와 Windows IIS 스크립트의 사용 순서입니다. 목표 플랫폼의 대규모 운영 설계와 구분합니다. Node 복구·운영 회귀 18개는 임시 DB와 로컬 HTTP에서 실행하여 통과했습니다. Windows PowerShell 5.1, IIS, 작업 스케줄러, NTFS 권한과 재부팅은 이 작성 환경에서 실행하지 않았습니다. 대상 Windows PC의 결과는 직접 생성한 보고서로 판단합니다.

1. 운영 파일과 역할

파일·도구 실제 동작 데이터 영향
scripts/Install-IIS.ps1 별도 release 준비 → 빌드·검증 → 업데이트 전 DB 백업 → 설정·사이트·작업 전환 → HTTP 검사 기존 DB를 유지하며 새 코드 기동 시 지원되는 스키마 마이그레이션
scripts/Backup-Data.ps1 비공개 백업 폴더 권한을 설정하고 SQLite 온라인 백업 현재 DB는 그대로 두고 새 백업·해시 기록 생성
tools/restore-data.mjs 기본 모드 백업 체크섬·무결성·외래키·플랫폼 스키마 검사 실행 중 서비스와 현재 DB를 바꾸지 않음
scripts/Restore-Data.ps1 사전 검사 → API 작업 비활성화·중지 → IIS 사이트 중지 → DB 복구 → 권한·기동·HTTP 검사 선택한 백업 시점으로 데이터를 되돌림. 교체 전 원본은 보존
scripts/Restore-PreviousRelease.ps1 이전 코드·설정·자신이 만든 LAN 방화벽 정책 복원 DB를 과거 상태로 바꾸지 않음. 스키마 비호환이면 실행 전에 거부
scripts/Test-IIS.ps1 설치된 두 정적 사이트와 두 API의 HTTP 검사 서버가 QA로 분류한 테스트 저장·이벤트 생성
scripts/Test-PoC.ps1 설치 상태 관찰, HTTP 검사, 선택 브라우저 결과 종합 DB 복구는 수행하지 않음

기본 설치 경로는 C:\PlayHubPoC입니다. 현재 release·Node 실행 파일·포트는 installation.json, 서버 설정은 config\local.json, 현재 DB는 data\platform.sqlite에 있습니다. 사용자·관리자 웹 루트는 각 release의 dist\user, dist\admin입니다.

백업의 .sqlite와 같은 이름의 .sqlite.json은 한 쌍입니다. JSON에는 생성 시각·바이트 수·SHA-256·무결성·스키마 버전이 들어가며 세션·저장 내용은 출력하지 않습니다. 이 체크섬은 파일 손상·잘못된 짝을 찾는 수단입니다. 백업과 메타데이터를 모두 바꿀 수 있는 사람의 변조를 인증하는 전자서명은 아닙니다.

2. 최초 설치와 설정 재실행

관리자 권한의 64비트 Windows PowerShell 5.1에서 압축을 푼 소스 폴더를 기준으로 실행합니다.

.\scripts\Install-IIS.ps1 -InstallRoot C:\PlayHubPoC -ShareHost 192.168.0.10

ShareHost는 실제 서버 PC 주소로 바꿉니다. 한 PC에서만 검증하려면 -LocalOnly를 지정합니다. 네 포트는 서로 달라야 하며 기본값은 사용자 UI 8080, 관리자 UI 8081, 공개 API 8090, 관리자 API 8091입니다. 기존 사이트·앱 풀·작업·방화벽 이름과 충돌하는 신규 설치는 거부합니다. 같은 이름만 보고 타 애플리케이션 자원을 삭제하지 않습니다.

기존 설치에 다시 실행할 때 생략한 포트·공개 범위·공유 호스트는 기존 값을 사용합니다. 관리자 비밀번호는 -ResetAdminPassword를 선택했을 때 다시 입력합니다. 기존 관리자 이름, OAuth 설정, 색인 설정과 데이터 경로도 보존합니다. 설치 경로와 소스 폴더를 같게 하거나 설치 경로를 소스 아래에 두는 구성은 재귀 복사를 막기 위해 거부합니다.

tools/setup.mjs를 직접 사용하는 개발 환경도 있습니다. 설정 JSON은 표준 입력으로 전달하며 비밀번호를 명령줄 인수에 넣지 않습니다. 최초 직접 설정은 loopback 공개 API를 기본값으로 합니다. IIS 설치기는 공유 여부를 명시하여 LAN 또는 LocalOnly를 설정합니다. 이후 setup에 {}를 전달하면 기존 포트·Origin·비밀번호 해시·Google 설정을 보존합니다. 설정 재실행은 기존 DB를 다른 경로로 옮겨 주는 데이터 마이그레이션 도구가 아닙니다.

기존 HTTPS·프록시 배포의 주소를 HTTP 설치기로 다시 만드는 작업은 거부합니다. 인증서와 프록시 구성을 포함한 별도 배포 절차로 관리해야 합니다. 실제 maintenance.lock이 남아 있으면 설정 재생성이나 신규 release 기동보다 복구 상태를 먼저 해결합니다.

3. 안전한 업데이트 순서

  1. 소스의 코드·게임·manifest·중앙 catalog를 수정합니다.
  2. 개발 환경에서 node tools/build.mjs, node tools/verify.mjs --tests를 실행합니다.
  3. 동일한 InstallRoot로 Install-IIS.ps1을 다시 실행합니다. 기존과 같은 포트는 생략할 수 있습니다.
  4. 설치기는 새로운 release 폴더에서 빌드와 패키지 검사를 완료합니다. 이 단계의 실패는 기존 사이트를 전환하지 않습니다.
  5. 기존 DB가 있으면 온라인 백업을 먼저 생성합니다. 백업 실패 시 업데이트를 중단합니다.
  6. 이전 설정·설치 marker를 보관한 다음 자신의 사이트·API 작업을 새 release로 전환합니다. 새 작업은 비활성 상태로 등록하고, 새 release의 복구 도구를 가리키는 marker를 원자적으로 기록한 뒤 활성화·기동합니다. 이후 방화벽 단계가 실패해도 새로운 DB를 복구할 도구 위치가 남습니다.
  7. 공개 API health와 별도 PowerShell 프로세스의 IIS HTTP 검사가 모두 통과해야 설치 완료를 표시합니다.

업데이트가 실패하면 후보 API 작업을 비활성화·중지하고 포트 종료를 확인한 다음 이전 release 복원을 시도합니다. 실행 중인 마이그레이션과 지원 스키마 검사가 동시에 진행되지 않도록 순서를 고정합니다. 현재 DB가 이전 코드가 지원하는 스키마보다 새로우면 코드만 자동으로 되돌리지 않습니다. 이 경우 작업과 사이트를 중지하며 새 release의 복구 도구를 가리키는 marker, 원본, 백업을 남깁니다. 운영자가 아래의 명시적인 데이터 복구·코드 복원 순서를 사용합니다.

0.2.0은 package.json의 playhubDatabaseSchemaVersion: 1을 선언합니다. 0.1.x의 선언 없는 package는 스키마 0으로 해석합니다. 알려지지 않은 release의 지원 버전을 임의로 추측하지 않습니다.

4. 온라인 백업 만들기

설치된 서비스가 실행 중이어도 다음을 실행할 수 있습니다.

.\scripts\Backup-Data.ps1 -InstallRoot C:\PlayHubPoC

결과는 backups\platform-<UTC시각>-<임의식별자>.sqlite와 .sqlite.json입니다. Windows wrapper는 이 폴더에 Administrators와 SYSTEM만 허용하는 권한을 설정한 뒤 백업합니다. Node는 SQLite 온라인 backup API를 사용합니다. 현재 DB가 WAL을 쓰더라도 완료된 새 백업은 자체 포함된 DELETE journal 형식으로 정리하고 무결성·외래키 검사와 SHA-256을 기록합니다.

개발용 CLI 예시는 다음과 같습니다.

node tools/backup.mjs --config /private/config.json --out /private/backups/platform-new.sqlite

동일 경로의 기존 DB·메타데이터·journal sidecar가 있으면 덮어쓰지 않습니다. 데이터 복구가 진행 중인 maintenance.lock 상태에서는 새 백업을 시작하지 않습니다. 백업 빈도·외부 사본·보존 기간을 자동 관리하는 스케줄은 이 도구에 포함되지 않습니다. 실제 복구 가능 지점은 선택한 성공 백업의 생성 시각이며, Windows 복구 소요 시간은 대상 PC에서 측정해야 합니다.

5. 복구 전에 백업만 검사

.\scripts\Restore-Data.ps1 -InstallRoot C:\PlayHubPoC -BackupPath 'C:\PlayHubPoC\backups\platform-선택한백업.sqlite' -VerifyOnly

이 모드는 서비스를 중지하지 않습니다. 다음을 확인합니다.

  • .sqlite.json의 바이트 수와 SHA-256이 실제 파일과 일치하는지
  • SQLite 파일 헤더·integrity_check·foreign_key_check가 정상인지
  • 스키마 0 또는 1이며 필수 테이블·열이 있는지
  • 뷰·트리거·virtual table 등 이 PoC가 사용하지 않는 실행 가능한 DB 구조가 없는지
  • 백업이 비어 있지 않은 WAL·journal에 의존하지 않는지
  • 파일과 상위 경로가 symlink·junction을 사용하지 않는지

검사는 임시 사본에서 수행하여 백업 원본을 SQLite로 열거나 수정하지 않습니다. 예전 0.1 백업 메타데이터도 지원합니다. 최종 0.2 스키마 1은 save_slot_versions를 포함한 15개 플랫폼 테이블을 검사합니다. 백업 원본과 메타데이터가 없거나 손상됐다면 기존 DB는 건드리지 않습니다.

6. 일반 데이터 복구

다음 명령은 선택한 백업 시점으로 저장·사용자·통계·운영 데이터를 실제로 되돌립니다.

.\scripts\Restore-Data.ps1 -InstallRoot C:\PlayHubPoC -BackupPath 'C:\PlayHubPoC\backups\platform-선택한백업.sqlite'

wrapper는 설치 marker·작업 실행 경로·사이트 경로를 확인합니다. 그 뒤 시작 작업의 자동 재시작을 막고 API와 사이트를 중지한 다음 API 포트가 닫힐 때까지 기다립니다. 다른 프로그램이 포트를 사용하면 해당 프로그램을 강제로 종료하지 않고 복구를 거부합니다.

Node 복구는 data\maintenance.lock을 배타적으로 만들고 다시 포트를 확인합니다. 서버는 이 파일이 있으면 DB를 열거나 마이그레이션하기 전에 기동을 거부합니다. 현재 DB의 SQLite 잠금도 확인합니다. 이후 data\recovery\restore-<작업ID>에 원본·복구 상태 기록·검증된 후보를 준비하고 파일을 교체합니다.

원본 파일은 삭제하지 않습니다. 정상 복구의 original과 displaced, 실패한 시도의 failed-*에는 개인 저장과 인증 관련 데이터가 포함될 수 있습니다. Windows wrapper는 recovery 폴더를 Administrators·SYSTEM 전용으로 보호합니다. 복구된 현재 DB 파일에는 다시 비공개 data 폴더의 Local Service 권한을 적용한 뒤 기동합니다.

교체 후 SQLite 검사가 실패하면 보관한 원본으로 자동 롤백합니다. 롤백까지 실패하면 maintenance.lock을 유지하고 서비스를 중지 상태로 둡니다. 잠금 파일을 임의로 지워 자동 기동시키지 않습니다. 원본까지 손상된 경우 보관에 성공했다고 정상 서비스 기동을 보장하지 않습니다.

복구가 성공하고 이전 작업이 활성화되어 있었다면 API 기동과 공개·관리자 health를 확인합니다. 이전에 켜져 있던 IIS 사이트를 복원하고 두 사이트가 모두 활성 상태이면 Test-IIS.ps1을 별도 PowerShell에서 실행합니다. 원래 운영자가 비활성화한 작업은 임의로 활성화하지 않습니다.

플레이어 세션 처리

백업에 있던 모든 세션을 그대로 살리지 않습니다. 현재 DB에서 복구 직전에 유효했던 공개 guest 세션을 별도로 읽고, 다음 조건을 모두 만족하는 행만 복구본에 다시 넣습니다.

  • 현재 DB와 선택한 백업에 같은 principal의 kind=guest 사용자가 존재합니다.
  • 두 DB 모두 그 principal에 연결된 계정 identity가 없습니다.
  • 세션은 만료 전이며 관리자 세션이 아니고 실제 이용 live 세션입니다.

이에 따라 같은 브라우저의 기존 guest 쿠키는 백업에 남은 진행을 이어갈 수 있습니다. 백업에만 남아 있는 과거 로그아웃 세션, Google 세션, 관리자 세션, QA 세션은 재활성화하지 않습니다. OAuth 상태·저장 idempotency·미완료 merge는 폐기하고 미종료 플레이 세션은 종료 처리합니다. 완료된 merge 기록과 사용자·identity·저장·저장 백업·통계·슬롯 revision 이력은 선택한 백업 기준으로 보존합니다.

Google 사용자와 관리자는 다시 로그인해야 합니다. 백업 이후 처음 생긴 guest, 쿠키를 삭제한 guest, 현재 DB 손상으로 유효 세션을 읽을 수 없는 guest의 이어하기는 복구할 수 없습니다. 보고서에 보존 수·복구본에 없는 수·손상 경고를 남기며 세션 ID나 CSRF 값을 기록하지 않습니다. 게임 저장도 백업 이후 진행까지 자동으로 합치는 동작은 하지 않습니다.

7. 이전 코드로 돌아가야 할 때

DB가 현재 코드와 이전 코드 모두에서 지원되는 버전이면 다음을 실행합니다.

.\scripts\Restore-PreviousRelease.ps1 -InstallRoot C:\PlayHubPoC

0.2에서 스키마 1로 바뀐 뒤 0.1 코드로 돌아가는 경우에는 먼저 업데이트 전 스키마 0 백업을 적용해야 합니다.

.\scripts\Restore-Data.ps1 -InstallRoot C:\PlayHubPoC -BackupPath 'C:\PlayHubPoC\backups\platform-업데이트전백업.sqlite' -KeepStopped
.\scripts\Restore-PreviousRelease.ps1 -InstallRoot C:\PlayHubPoC
.\scripts\Test-IIS.ps1 -InstallRoot C:\PlayHubPoC -WithAdmin

-KeepStopped가 필요합니다. 구버전 DB 복구 직후 0.2 API를 다시 시작하면 그 DB를 다시 스키마 1로 마이그레이션하기 때문입니다. 이 옵션은 DB 복구 후 API 작업을 비활성·중지 상태로, 사이트를 중지 상태로 남겨 다음 코드 복원 단계를 준비합니다. 기존 데이터는 recovery에 보관됩니다. 최신 저장·이벤트를 오래된 백업과 자동 병합하지 않으므로 선택한 복구 시점을 확인해야 합니다.

8. 복구 프로세스가 중간에 종료된 경우

전원 종료나 복구 프로세스 중단 뒤 maintenance.lock이 남으면 서버 기동이 차단됩니다. 원래 복구 프로세스가 끝난 상태인지 먼저 확인한 뒤 다음을 실행합니다.

.\scripts\Restore-Data.ps1 -InstallRoot C:\PlayHubPoC -RecoverInterrupted

도구는 기록된 프로세스가 아직 존재하면 거부합니다. 기록된 경로가 이 설치의 recovery 아래인지 확인하고, 보관된 원본의 SHA-256을 다시 검사합니다. 파일 교체 전 중단이면 잠금만 해제하고, 교체가 시작된 뒤 중단이면 보관한 원본을 되돌립니다. 새로운 복구본과 실패한 파일도 별도로 남깁니다. 원본 복구를 마친 뒤 선택한 백업의 적용을 다시 시도할 수 있습니다.

필요하면 -KeepStopped를 함께 사용하여 코드 복원으로 이어갑니다. 잠금이나 recovery 기록이 다른 경로를 가리키거나 손상됐으면 자동으로 우회하지 않습니다. 보존된 DB·백업을 별도로 확보한 뒤 기록을 검토해야 합니다. 프로세스 강제 종료 시나리오는 자동 회귀로 재현했지만 물리 디스크 장애·전원 차단의 파일 시스템 내구성까지 증명한 검사는 아닙니다.

Node CLI를 직접 사용하는 경우의 대응 명령은 다음과 같습니다. API 작업을 먼저 중지해야 합니다.

기본 명령은 검증만 수행하고 --apply가 있어야 데이터를 바꿉니다. 보고서는 data 폴더 밖의 .json 경로로 지정합니다. 같은 이름의 HTML도 생성합니다. Windows의 계정 권한·서비스 재시작까지 처리하려면 위 PowerShell wrapper를 사용합니다.

IIS PoC API 계약

이 문서는 실제 PoC 백엔드와 사용자·관리자 UI 사이의 계약이다. public API는 기본 8090, admin API는 loopback 8091이며, 두 listener는 서로의 전용 경로를 제공하지 않는다. JSON 요청에는 Content-Type: application/json을 사용한다. 브라우저 fetch는 credentials: 'include'가 필요하다. 변경 요청은 해당 listener에서 받은 X-CSRF-Token과 허용된 Origin이 필수다.

게스트 식별자와 세션 수명

새 anonymous 방문 세션은 90일이고 첫 플레이에서 guest로 승격할 때 승격 시각부터 다시 90일을 부여한다. 아직 유효한 guest 세션으로 GET /api/session에 재방문하면 그 시각부터 90일 idle 만료로 갱신하며 서버 expires_at과 cookie Max-Age=7776000을 함께 맞춘다. 이 갱신은 기존 cookie 값·CSRF·게스트 principal·분석 subject를 바꾸지 않아 저장과 D30 코호트 연결을 유지한다. 이전 버전의 30일 guest 세션도 아직 만료되지 않았다면 같은 경로에서 90일로 갱신된다. anonymous 상태에서는 최초 발급 90일이며, 첫 guest 승격 전의 단순 조회만으로 계속 연장하지 않는다.

Google registered 세션은 로그인 시점부터 30일(Max-Age=2592000)이며 guest idle 갱신을 적용하지 않는다. 관리자 인증 세션은 기존 8시간(Max-Age=28800), 로그인 전 관리자 임시 세션은 10분이다. QA의 anonymous/guest도 일반 게스트와 같은 기간을 사용하지만 실제 지표와 계정 권한은 별도로 분리한다.

서버 만료 시각 이상인 세션은 갱신하지 않는다. 만료되거나 로그아웃으로 폐기된 cookie로는 기존 주체의 저장·플레이 API를 사용할 수 없고, 이후 session 조회는 새 anonymous 세션을 만든다. 첫 승격도 body 처리 후 세션이 여전히 유효한지 다시 확인하여 이미 폐기된 요청이 게스트를 되살리지 못하게 한다. cookie 삭제·브라우저 데이터 제거·90일 미방문·로그아웃 뒤의 게스트 기록 자동 재연결을 보장하는 정책은 아니며, DB 복구 작업이 폐기한 인증 세션도 이 갱신으로 복원되지 않는다.

QA 트래픽과 실제 이용 분리

자동 검사 도구는 새 cookie jar/browser context에서 GET /api/session → POST /api/qa/session {} 순서로 준비한 뒤 페이지를 열거나 이벤트·게임·저장 API를 사용한다. POST는 첫 GET의 CSRF를 보내야 하며, 응답으로 회전한 cookie·CSRF를 이후 요청에 사용한다. 이 기능은 관리자 인증이나 일반 저장 권한을 부여하지 않는다. 첫 플레이에서 정상 게스트 승격을 거치고 소유권·CSRF·Origin·revision 제한도 동일하게 적용한다.

서버가 traffic_type과 qa_run_id를 세션, 실행 세션, 이벤트, 실행 오류에 기록한다. raw event의 임의 is_test·traffic_type·qa_run_id로 지표 소속을 바꿀 수 없다. 이벤트 속성의 테스트 메모도 분류 근거로 신뢰하지 않는다. 로그아웃하거나 session이 만료되어도 이미 기록된 QA 분류는 남는다. QA 준비 세션에는 Google 연결을 제공하지 않으며 직접 호출도 403 QA_GOOGLE_DISABLED로 거부한다. QA 게스트의 저장은 실제 계정과 병합되지 않는다.

qaRunId는 계정·관리자 인증 토큰이 아니다. 관리자 지표에서 한 검사 실행을 필터링하는 서버 식별자이며, 이것만으로 다른 사용자의 저장이나 QA 지표에 접근할 수 없다. QA로 전환하기 전에 해당 방문이 이미 보낸 일반 노출 이벤트는 소급 변경하지 않는다. 기존 버전에서 QA 표시 없이 수집된 과거 행도 자동으로 판별할 수 없어 live로 유지한다. 새 검사 도구는 첫 이벤트 전에 QA 세션을 준비해야 한다.

저장 목록·충돌·복구

일반 저장 GET과 목록 GET에 X-CSRF-Token을 보내면 현재 cookie 세션의 CSRF와 비교한다. 다른 탭의 로그인·로그아웃으로 cookie가 바뀐 상태에서 이전 탭이 오래된 CSRF를 보내면 403 CSRF_INVALID가 되어 새 계정의 저장을 잘못 읽지 않는다. 기존 HTTP 도구의 무헤더 GET은 유지하지만, 사용자 UI는 헤더를 붙이고 신원 변경이 감지되면 실행 iframe을 정리한 뒤 session을 다시 확인한다.

목록 응답은 다음 구조다.

{
  "gameId": "slide-puzzle",
  "mainRevision": 3,
  "slotLimit": 10,
  "slots": [
    {"slot":"main","schemaVersion":1,"revision":3,"updatedAt":"2026-11-16T03:00:00.000Z","reason":"main"},
    {"slot":"recovery-tab","schemaVersion":1,"revision":1,"updatedAt":"2026-11-16T02:59:00.000Z","reason":"additional_slot"}
  ],
  "backups": [
    {"id":"서버가 발급한 백업 UUID","sourceSlot":"main","schemaVersion":1,"revision":2,"createdAt":"2026-11-16T03:00:00.000Z","reason":"restore_previous","source":"account"}
  ]
}

슬롯 reason은 main, merge_guest_copy, additional_slot이다. 백업 reason은 merge_conflict, restore_previous, slot_deleted이며 source는 현재 주체가 소유한 원본이면 account, 완료한 명시적 병합의 이전 게스트 원본이면 guest다. 여기서 account는 현재 소유 주체라는 의미로 일반 게스트도 포함한다. 목록은 본인 자료와 본인이 명시 병합을 완료한 원본에만 한정하며, 다른 계정·다른 게임의 ID를 넣어 접근할 수 없다.

별도 슬롯을 main으로 복구할 때:

{"sourceSlot":"recovery-tab","expectedSourceRevision":1,"expectedMainRevision":3}

불변 백업을 main으로 복구할 때:

{"backupId":"목록에서 받은 백업 UUID","expectedMainRevision":3}

sourceSlot과 backupId는 정확히 하나만 보낸다. sourceSlot=main은 허용하지 않으며, 슬롯 복구는 원본 revision도 검사한다. main이 없으면 expectedMainRevision:0을 사용한다. 이 body의 revision 조건은 복구의 필수 조건이며 일반 PUT의 If-Match 계약은 유지한다. 복구 POST에는 재시도 동안 유지하는 Idempotency-Key가 필요하다. 같은 key·같은 요청은 이전 성공 결과를 재사용하고, 같은 key로 다른 요청을 보내면 409 IDEMPOTENCY_CONFLICT다.

서버는 하나의 SQLite transaction 안에서 소유권, 원본 schema, 원본·대상 revision, 슬롯 한도를 확인한다. 검사를 통과하면 기존 main을 먼저 백업하고, 복구 원본을 복사해 main revision을 1 증가시킨다. 원본 슬롯·백업은 소모하지 않는다. 응답은 기존 save 객체에 restoredFrom:{type:'slot'|'backup',id}와 previousBackupId:null|UUID를 추가한다. 오래된 main 또는 source revision이면 412이며 기존 main과 원본을 모두 보존한다. 실패한 요청은 복구 백업도 만들지 않는다.

게임당 쓰기 가능한 슬롯은 10개다. 명시적 계정 병합도 이 한도를 지키며 초과 시 전체 병합을 취소한다. main이 이미 있으면 슬롯이 가득 차도 기존 main 복구는 가능하다. UI는 사용자가 확인한 보관 슬롯을 DELETE로 제거해 여유를 만들 수 있다. 서버는 해당 revision을 확인하고 원본을 slot_deleted 백업으로 남긴 후 슬롯을 비우며, main 삭제는 403 MAIN_SLOT_DELETE_FORBIDDEN으로 거부한다. 없거나 이미 바뀐 슬롯에 오래된 If-Match를 보내면 412다. 삭제 완료 후 목록을 다시 읽으며, 응답을 잃어 재시도했을 때도 목록으로 결과를 확인한다.

삭제한 이름으로 슬롯을 재생성해도 revision을 1로 되돌리지 않는다. 별도 save_slot_versions에 마지막 revision을 유지하므로 이전 탭의 오래된 삭제·수정 조건이 새 기록에 우연히 맞지 않는다. 삭제한 슬롯의 기존 PUT idempotency 결과는 제거하여 이전 성공 응답이 새 저장을 대신하지 않게 한다.

명시 복구와 슬롯 제거 때 만든 restore_previous, slot_deleted 백업은 합쳐서 사용자·게임별 최근 20개를 유지한다. merge_conflict 원본은 이 순환 보관으로 지우지 않는다. 매번 발생하는 자동 저장 전체를 영구 버전으로 보관하는 기능은 아니므로, 충돌한 현재 탭의 진행은 UI가 별도 recovery 슬롯에 먼저 보존한 뒤 main 복구를 요청한다.

metrics 응답은 {dataset,asOf,timezone:'Asia/Seoul',filters:{from,to,gameId,qaRunId},retentionScope:'platform'|'game',metricSemantics,summary,games,retention}이다. 필터를 생략한 값은 null이다. demo는 고정 예제이므로 날짜·게임·QA run 필터를 함께 보내면 400 DEMO_FILTERS_UNSUPPORTED다.

from과 to는 유효한 YYYY-MM-DD KST 날짜이며 양 끝 날짜를 포함한다. 생략한 하한·상한은 전체 이력·현재 수신 이력이다. 잘못된 달력 날짜나 뒤집힌 범위는 400이다. gameId는 비공개 게임도 조회할 수 있으나 존재하지 않는 ID는 404다. qaRunId는 dataset=qa에서만 사용할 수 있으며 다른 조합은 400 QA_RUN_FILTER_INVALID다. 예: /api/admin/metrics?dataset=qa&from=2026-11-01&to=2026-11-07&gameId=slide-puzzle&qaRunId=<UUID>.

summary에는 games, activeGames, visitors, playSessions, readySessions, active10sSessions, active60sSessions, activePlayers, totalActiveSeconds, roundsCompleted, saveWrites, impressions, clicks, ctr가 있다. CTR은 0~1 비율 또는 분모 없을 때 null이다. games는 {id,title,plays,ready,active10s,active60s,impressions,clicks,ctr} 배열이다.

retention은 {platform:{d1,d7,d30,cohorts:[]},games:[{gameId,d1,d7,d30,cohorts:[]}],selected:{d1,d7,d30,cohorts:[]}}다. selected는 게임 필터가 있으면 해당 게임 코호트, 없으면 platform과 같다. UI의 현재 필터 카드·표는 selected를 사용한다. platform 자체는 모든 게임을 기준으로 한 최초일 의미를 유지하며 게임 필터 때문에 최초일을 바꾸지 않는다. 각 d 값은 {eligible,cohortSize,retained,rate}이며 미성숙은 retained/rate가 null이다. cohort 행은 {cohortDate,day,cohortSize,eligible,retained,rate,matureAt}다. KST 정확일 D1/D7/D30이고 대상일 종료+24시간 뒤 확정한다. demo는 live 데이터에 삽입하지 않는 독립 가상 데이터다.

summary·게임 표의 방문, 노출, 클릭, ready, milestone, 저장 수는 해당 기간 서버 수신 활동을 센다. 실행 세션 수는 해당 기간 생성된 세션 수다. 각 단계의 발생 날짜가 다를 수 있어 기간 필터를 건 독립 카운터를 동일 세션 코호트 전환율로 해석하지 않는다. 활성 시간은 승인 구간을 날짜 범위에 맞춰 잘라 합집합으로 계산하므로 자정을 가로지른 heartbeat를 통째로 누락하지 않는다.

리텐션의 날짜 필터는 코호트 최초 날짜에 적용한다. 선택한 traffic dataset·QA run의 전체 이력으로 먼저 최초일을 찾고, 그 뒤 from/to 범위의 코호트만 표시한다. 재방문 판정에는 표시 기간 밖의 이후 이력도 사용하며 확정 시각은 응답 asOf다. 예를 들어 11월 1일에 시작한 사람이 11월 2일에 돌아와도 11월 2일 신규 코호트로 재분류하지 않는다. 11월 2일 코호트의 11월 3일 플레이는 화면의 to가 11월 2일이어도 성숙한 D1 분자에 반영한다.

최초 유효 세션의 서버 active_play_10s 날짜를 초기 코호트 근거로 보존한다. 이후 날짜 활동은 서버가 승인한 heartbeat의 시간 구간을 KST 자정으로 나눠, 사용자·게임·날짜마다 겹친 구간의 합집합이 10,000ms 이상일 때 추가한다. 여러 탭의 중복 시간은 두 번 세지 않는다. 따라서 같은 iframe에서 이미 최초 milestone을 만든 뒤 자정 이후 계속 플레이하거나 재개해도 다음 날짜 활동을 집계한다. 클라이언트 occurred_at을 활동 날짜로 신뢰하거나 원본 이벤트 날짜를 바꾸지 않는다. 전체 플레이 시간은 게임을 가로질러 사용자별 구간 합집합으로 집계한다.

설정과 실행

node server/index.mjs --config <absolute-config-path>로 실행한다. config는 publicPort/adminPort, publicHost/adminHost, userOrigins/adminOrigins, publicBaseUrl/userBaseUrl/adminBaseUrl, dataDir, secureCookies, google 및 admin을 사용한다. 프로젝트 root는 server의 상위 폴더다.

config는 Windows PowerShell이 작성한 UTF-8 BOM을 허용한다. config 파일이 외부 InstallRoot/config에 있어도 게임·catalog 경로는 config 위치가 아닌 실행 중인 server 폴더의 상위 release root에서 읽는다. dataDir는 별도의 절대경로다.

현재 SQLite PRAGMA user_version은 1이다. 기존 버전 0의 저장·identity·이벤트를 유지하면서 QA 분류 컬럼과 복구 백업 이유를 추가한다. 이미 버전 1인 DB 재기동은 같은 컬럼을 중복 생성하지 않는다. 버전 1보다 새로운 DB는 임의 변경 없이 기동을 거부한다. dataDir의 maintenance.lock가 있으면 DB를 열거나 마이그레이션하기 전에 기동을 거부하며, 오래된 marker도 자동으로 무시하지 않는다. 복구 작업이 중간에 멈춘 경우 운영 복구 절차로 확인해야 한다. 응답·오류에 marker 원문을 노출하지 않는다.

admin 설정은 {username,passwordHash,salt}이며 passwordHash = scryptSync(password, saltHex문자열, 64).toString('hex'), salt는 16바이트의 hex 문자열이다. Google 설정은 {clientId,clientSecret,redirectUri}다. LAN Google 로그인은 HTTPS의 실제 등록 도메인 구성이 필요하며, local HTTP는 별도 PoC 실행 조건이다. Google 미설정은 disabled 상태로 명확히 응답한다.

오류는 {error:{code,message},requestId} 형태다. 응답·로그에 cookie, 비밀번호, Google 토큰·code·clientSecret을 넣지 않는다. SQLite는 웹 루트 밖 dataDir에 저장한다.

3. 공통 실행과 저장 계약

각 게임의 폴더에는 index.html, game.js, game.manifest.json, assets/cover.svg가 있다. 별도 npm 패키지와 외부 자산 요청이 필요하지 않다. 소스 단계에서는 /shared/의 classic script와 CSS를 참조하고, 빌드는 그 파일을 각 게임의 vendor/로 복제해 상대 경로로 바꾼다. 게임 iframe의 스크립트는 fetch, 로그인 쿠키, CSRF 토큰, Google 토큰에 직접 접근하지 않는다.

부모 포털이 게임 URL의 fragment에 새 nonce를 넣는다. 포털은 event.source === 현재 iframe.contentWindow, origin === "null", 프로토콜 버전, nonce를 확인한 뒤 하나의 MessageChannel을 전달한다. 이후 저장·불러오기·이벤트는 이 포트에서만 받는다. 요청 큐 크기와 빈도를 제한하고 저장 대상 게임은 부모가 고정한다.

저장 데이터는 다음 공통 봉투를 사용한다.

{
  "gameId": "match3-garden",
  "schemaVersion": 1,
  "state": { "score": 0, "elapsed": 0, "status": "playing" },
  "runId": "라운드 식별자",
  "runStarted": true,
  "runEnded": false
}

state에는 위 게임별 필드가 추가된다. 불러올 때 게임별 배열 길이·숫자 범위·상태·구조를 검사하며, 형식이 다르면 실행에 사용하지 않는다. 저장 봉투의 최대 길이는 포털에서 65,536자이며, 서버에도 별도의 요청 크기 제한이 있다.

게임을 시작하기 전에는 복원된 상태로 대기하고 사용자 입력 후 진행한다. 게임 시간은 실제 게임이 실행 중일 때만 누적한다. 일시정지, 가려진 문서, 화면에서 벗어나 부모가 정지시킨 동안에는 시뮬레이션을 진행하지 않는다. 수초 동안 멈춘 프레임을 한 번에 큰 물리 이동으로 계산하지 않도록 프레임 단위를 제한한다.

퍼즐 입력 후에는 짧은 지연 뒤 저장하며, 실행 중에는 대략 10초마다 저장한다. 일시정지·완료·게임 닫기에서도 저장한다. 일반 화면 이동 시 부모는 마지막 스냅샷을 요청하고 저장 처리를 기다린 후 iframe을 제거한다. 브라우저 프로세스가 강제 종료되거나 탭이 즉시 폐기되는 경우 마지막 수초의 상태까지 보장하지는 않는다.

4. 온라인 게스트와 로컬 모드의 차이

상황 실행·저장 처리
API 정상, 세션 쿠키 사용 가능 플레이 시작 시 guest로 승격. 서버의 게임별 main 슬롯으로 저장
최초 서버 저장 If-None-Match: * 사용
기존 서버 저장 받은 revision에 대응하는 If-Match 사용
저장 재시도 동일 요청에 동일 Idempotency-Key 사용
다른 탭·기기와 저장 충돌 412 후 서버 쓰기를 중단하되 이후 진행도 같은 탭에 계속 보존. 저장 기록 화면에서 서버·현재 탭·보관 슬롯·백업을 선택
API 네트워크 실패 또는 502/503/504 빌드 카탈로그의 신뢰 게임은 로컬 모드로 시작 가능
플레이 세션 생성 401 쿠키를 사용할 수 없는 경우 로컬 모드 가능
API가 정상적으로 게임 404/403 반환 로컬 모드로 우회하지 않음
로컬 모드 같은 탭의 sessionStorage에 임시 저장. 서버 저장·계정 기록·서버 게임 통계 없음
로컬 모드 후 서버 연결 실행 중 로컬 게임을 유지하고 자동 병합하지 않음. 저장 기록 화면에서 직접 적용하거나 별도 슬롯 보관·파일 다운로드 선택
로그아웃 실행 iframe·포트·메모리와 임시 저장을 정리하고 새 익명 세션을 시작
다른 탭의 로그인·로그아웃 새 세션 문맥을 확인하면 이전 iframe을 쓰기 없이 닫고 이전 계정 임시 데이터를 정리. 늦게 도착한 이전 요청 결과는 적용하지 않음
쿠키 차단 중 재연결 두 번의 세션 조회가 같은 세션으로 유지되는지 확인. 유지되지 않으면 현재 로컬 게임과 임시 진행을 보존

서버 모드의 guest 기록은 서버에 남지만 복구 식별은 브라우저 쿠키에 의존한다. 쿠키 삭제 후 복구를 보장하지 않는다. 로컬 모드의 임시 데이터는 탭 단위이며 서버 백업·기기 간 복구를 제공하지 않는다. 사용자 UI에서 저장 상태를 구분해 표시한다. 현재 게임의 이어하기는 항상 main 슬롯을 읽으며, 다른 슬롯·백업을 선택하면 서버가 새 main revision으로 복원한 뒤 게임을 다시 연다.

저장 기록 화면

게임 상세의 저장 기록 버튼은 게임을 정지하고 최신 스냅샷을 확보한다. 현재 계정의 이어하기, 계정 연결 때 별도 보관한 게스트 기록, 사용자가 보관한 기록, 교체 전 백업을 구분해 표시한다. 목록에는 저장 시각과 revision이 표시되고, 이 탭의 기록에는 점수·경과 시간·라운드 상태를 추가로 보여 준다. 원본 슬롯 목록 API는 전체 payload를 노출하지 않는다.

선택 처리
서버 이어하기 사용 마지막 확인한 revision과 현재 main을 비교. 일치하면 게임을 다시 열며, 미반영 탭 진행은 별도 임시 백업으로 유지
이 탭 진행으로 이어하기 먼저 새로운 recovery-… 슬롯에 조건부 최초 저장. 그 슬롯의 revision과 현재 main revision을 함께 제시해 복원
이 탭 진행 별도 보관 recovery 슬롯만 만들고 main은 그대로 유지. 목록에서 이후에 복원 가능
보관 슬롯 복원 원본 슬롯 revision과 대상 main revision을 모두 검사. main 변경 전 상태는 서버 백업으로 보관
교체 전 백업 복원 접근 가능한 backup ID와 main revision으로 복원. 현재 main도 다시 백업
보관 슬롯 제거 사용자 확인과 해당 슬롯의 If-Match revision으로 제거. main은 유지하고 제거한 원본은 복구 기록으로 보관. main 제거는 금지
적용 중 다른 탭이 변경 412 표시, 기존 main과 원본·임시 진행 유지. 목록을 새로 읽은 뒤 다시 선택
네트워크가 응답을 끊음 같은 idempotency key로 한 번 재시도. 확인할 수 없는 결과를 성공으로 표시하지 않음

슬롯은 게임·계정별 최대 10개이며 main도 포함된다. 복원 전 main과 제거한 슬롯의 백업을 합쳐 최근 20개를 순환 보관하며 계정 병합 충돌 원본은 별도로 유지한다. 슬롯이 모두 차면 사용하지 않는 보관 슬롯을 제거해 한 칸을 비울 수 있고, 제거한 원본을 복구 기록에서 main으로 적용할 수 있다. 임시 기록 파일은 진행 봉투를 내려받는 백업이며, 임의 JSON 파일 업로드·가져오기 기능은 이번 UI에 없다. 계정 연결 중 충돌 목록이 바뀌면 최신 목록을 읽고 다시 선택하도록 한다.

서버 재연결은 페이지를 강제 새로고침하지 않는다. 동일 세션이면 기존 실행과 임시 진행을 유지하고 조건부 저장을 다시 시도할 수 있게 한다. 서버 저장과 별도로 시작한 로컬 모드 기록은 사용자의 명시 선택을 거쳐야 서버 기록으로 들어간다. 로그아웃 시 미반영 임시 진행이 있으면 삭제 전에 확인한다. 로그아웃 성공 후 새 세션 조회에 실패하더라도 이전 계정으로 표시하지 않고 로컬 모드로 전환한다.

게임 공개 중단은 API 목록과 새 플레이 생성에 적용된다. 이 PoC의 정적 내장 파일은 내려받은 소프트웨어이므로, 운영자의 공개 설정을 복사본 실행 방지나 DRM으로 설명하면 안 된다.

5. 포털과 이용 지표의 현재 동작

사용자 사이트는 홈 카드, 장르, 검색, 최근 게임, 개별 소개·조작법·규칙, 실행 iframe, 저장 상태와 오류 안내를 제공한다. 새 게임은 카탈로그와 manifest를 통해 목록에 반영한다. /play/<id>/와 ?game=<id>의 진입을 지원하며, 빌드는 각 게임의 정적 제목·설명·본문·canonical·Open Graph 메타데이터와 sitemap을 생성한다. 내부 LAN 배포의 기본 검색 색인은 빌드 설정에서 차단된다.

카드는 같은 노출 기회에서 면적 50% 이상이 문서가 보이는 상태로 연속 1초 유지됐을 때 노출 이벤트를 보낸다. 그 전에 누른 클릭은 viewability_met:false로 구분한다. 문서를 숨기면 진행 중인 노출 타이머를 초기화한다. 검색·다른 목록 렌더링은 새 노출 기회다.

게임 활성 시간은 부모 포털에서 계산한다. 게임 준비 완료, 실행 중 상태, iframe 가시 면적 50% 이상, 부모 문서 visible, 최근 게임 업데이트 신호가 모두 있어야 한다. 게임은 실행 중 1초 주기의 업데이트 신호를 보내고, 부모는 대략 15초마다 누적 heartbeat를 보낸다. 정지·종료 전에 남은 활성 구간을 전송한다. 10초·60초 milestone과 D1/D7/D30 집계는 서버 책임이며 게임 코드가 직접 확정하지 않는다. 이것은 이용 품질 측정이며 경쟁 점수용 부정행위 방지 체계가 아니다.

사용자 이용에서 관리자 지표까지

관리자 화면은 실제 이용 live, 자동 도구의 별도 세션으로 남긴 qa, 고정 가상 예제 demo를 각각 조회한다. 일반 사용자 화면에는 QA 전환 버튼을 노출하지 않는다. 도구가 시작한 QA 세션은 사용자 헤더에 QA 기록으로 표시하며 Google 계정 연결을 제공하지 않는다. 이 표시 자체가 실제 브라우저 검증의 실행 증거는 아니고 실행 보고서를 함께 확인해야 한다.

관리자는 시작일·종료일을 KST 날짜로 지정하고 전체 게임 또는 특정 게임을 선택한다. 화면은 서버가 반환한 실제 적용 필터와 최신 집계 시각을 표시한다. 노출·가시 클릭·CTR·준비·10초·60초·유효 사용자·활성 시간과 함께 라운드 완료·서버 저장 성공을 보여 준다. 클릭 분모가 없으면 분모 없음, 성숙한 리텐션 코호트가 없으면 집계 대기로 구분한다.

기간 요약은 해당 기간의 활동이다. 세션 생성 수는 기간에 발급된 세션이며 ready·10초·60초는 기간의 실제 발생 수이므로 날짜 경계를 넘는 세션에서는 서로 같은 코호트의 전환율이 아니다. 리텐션은 전체 이력의 최초 유효 플레이일을 유지하고 코호트 최초일에 기간 필터를 적용한다. 게임을 선택하면 retention.selected로 해당 게임의 코호트·D1/D7/D30을 표시한다. 실행 오류도 같은 데이터·기간·게임 범위로 조회하고 운영 변경 기록은 전체 이력으로 제공한다.

고정 가상 예제에서는 날짜·게임 필터와 게임 공개 변경을 비활성화한다. QA 탭에서도 실제 공개 상태를 변경하지 못하게 하고, 공개 전환은 실제 이용 기록 탭에서 확인 후 실행한다. 지표 조회가 실패하면 이전 자료를 다른 범위로 잘못 읽지 않도록 통계 표시를 지우고 오류를 알린다. 관리자 인증이 만료되면 로그인 상태와 이전 화면 자료를 정리한다.

6. 현재 자동 검증과 남아 있는 검증

node --test tests/games*.mjs로 게임 규칙과 포털 계약·저장 흐름을 검사한다. 작성 시점의 37개 테스트는 모두 통과했다. 게임 규칙 15개, 포털·관리자 순수 계약 8개, 실제 포털 코드의 저장·세션 흐름 14개다.

# Git 작업 브랜치 최신화

요청된 저장소의 기존 작업 브랜치에서 rebase와 충돌 해결을 끝낸다. 스킬을 만들거나 고치라는 요청만으로 실제 브랜치를 재배치하지 않는다.

## 실행 원칙

- 현재 worktree에서 브랜치가 체크아웃되어 있으면 그 자리에서 진행한다. 일반 checkout도 동일하게 취급한다. 새 worktree, 임시 clone, 백업 브랜치·태그·ref·파일 복사본을 만들지 않는다.
- 빌드, 테스트, 쿠킹, 리뷰 봇, 별도 검증용 checkout, range-diff 등의 사후 검증은 생략한다. Git 작업에 필요한 현재 상태, 충돌 유무, 명령 성공 여부와 결과 HEAD 확인만 수행한다.
- merge 대신 rebase를 사용한다. 기존 merge를 재생성하는 `--rebase-merges`도 별도 요청 없이 사용하지 않는다.
- 사용자가 승인하기 전에는 force push를 실행하지 않는다. rebase 요청은 force push 승인이 아니다.

## 대상과 base 결정

1. 현재 경로의 저장소 지침을 읽는다. 요청된 커밋·브랜치·PR이 속한 저장소, 현재 브랜치, upstream, 작업 상태를 필요한 범위에서 확인한다. submodule은 `.gitmodules`와 gitlink를 기준으로 찾는다.
2. 요청되지 않은 다른 루트로 자동으로 작업 범위를 넓히지 않는다. 다른 체크아웃의 ref나 파일을 몰래 이동하지 않는다.
3. 기본 base는 **각 대상 저장소 서버의 최신 기본 브랜치(master/main/PlayHub-Platform)**다. 실제 원격을 확인하고 명시적 refspec으로 fetch해 remote-tracking ref를 갱신한 뒤 SHA를 고정한다.
4. 지정 SHA는 그 커밋이 존재하는 저장소에서만 사용한다. 루트 저장소의 특정 커밋 스냅샷을 base로 지정한 경우 서브모듈 base는 그 트리에 기록된 gitlink로 정한다.
5. 다른 브랜치 checkout이 필요하면 필요한 범위만 이동한다. 대규모 checkout이 요구되는 경우 사용자 승인 규칙을 따른다. detached HEAD에서 임의의 기존 브랜치를 덮어쓰지 않는다.

## 미커밋 변경 처리

- 관련 저장소의 일반 파일 변경, staged 변경, 미추적 파일, 서브모듈 내부 변경, 상위 gitlink와 실제 서브모듈 HEAD 차이를 구분한다. 서로 다른 값이라는 이유만으로 서브모듈 HEAD를 되돌리지 않는다.
- 현재 checkout에서 바로 rebase할 수 있으면 진행한다. 미커밋 변경이 막으면 충돌하는 경로와 필요한 조치만 설명하고 임시 stash 허용 여부를 묻는다.
- 허용된 stash는 필요한 경로만 다루고 rebase 후 복원한다. 대용량 미추적 콘텐츠까지 일괄 stash하거나 사용자 변경을 임의로 커밋·폐기하지 않는다.
- 기존 rebase/merge가 진행 중이면 그 상태부터 처리한다. 임의 abort나 `reset --hard`로 현재 작업을 지우지 않는다.

## 재배치와 충돌 해결

1. 의존 서브모듈의 작업 브랜치를 먼저 각 base 위에 rebase하고, 루트 작업 브랜치를 나중에 rebase한다. 무관한 서브모듈은 건드리지 않는다.
2. 루트 rebase에서 서브모듈을 재귀 checkout하지 않는다. submodule update나 LFS 자산의 대량 전개를 재배치의 기본 단계로 넣지 않는다.
3. gitlink 충돌에서 한쪽 SHA를 기계적으로 고르지 않는다. base의 수정과 작업 브랜치의 기능 커밋을 함께 유지하도록 서브모듈 브랜치를 재배치한 결과를 연결한다.
4. 텍스트 충돌은 양쪽 변경 의도를 유지해 해결한다. 선택에 따라 기능이 달라지고 요청 맥락으로 결정할 수 없을 때만 사용자에게 묻는다.

## 루트 커밋 정리 및 원격 반영

- 새 base 이후의 서브모듈 포인터 갱신은 마지막 커밋 하나에만 남긴다. 일반 코드·문서 커밋까지 모두 squash하지 않는다.
- 대화형 에디터 입력에 의존하지 않는다.
- 진행 상황, 승인 요청, 완료 보고에서 커밋 정보를 표시할 때는 항상 해당 저장소의 **브랜치명과 절대 폴더 경로**를 함께 표시한다.
- force push가 필요하면 대상 원격·브랜치와 재작성 결과를 제시하고 사용자 승인을 받은 뒤 `--force-with-lease=<ref>:<expected-sha>`를 사용한다. 서브모듈을 먼저 푸시하고 루트를 나중에 푸시한다.

# 8종 기본 게임의 실제 PoC 구현 범위

이 문서는 이 저장소의 `games/*/game.js`, `shared/game-logic.js`, `shared/game-engine.js`, `shared/sdk.js`, 사용자 포털 코드를 기준으로 작성했다. 기존 플랫폼 기획 문서는 출시 목표이며, 아래 내용이 이번 로컬 IIS PoC에 포함된 구현이다. 게임을 만드는 초기 구조와 단일 완결 라운드, 저장·실행·측정을 연결하는 데 범위를 두었다. 콘텐츠 볼륨, 경쟁 점수 검증, 다양한 기기에서의 품질 검증까지 완료했다는 의미는 아니다.

## 1. 기획 목표와 이번 구현의 경계

| 항목 | 기존 플랫폼 기획의 방향 | 이번 PoC 구현 |
|---|---|---|
| 기본 게임 | 8종 경량 게임과 후속 콘텐츠 확장 | 8종 모두 입력·점수·승패·다시 시작이 있는 단일 라운드 |
| 매치3 콘텐츠 | 단계별 목표·여러 레벨로 확장 | 8×8, 25회 이동, 1,200점의 한 가지 목표 |
| 낙하 블록 | 완성도 높은 블록 게임 프로필 | 10×18, 무작위 7종 블록, 20줄 목표; 표준 회전 규격 전체를 재현하지 않음 |
| 슬라이드 퍼즐 | 보드·난이도 확장 | 3×3, 숫자 1~8과 빈칸 |
| 게임 배포 | 폴더·manifest·중앙 목록 기반 자동화 | 동일한 소스 계약과 게임별 정적 산출물. 공통 코드는 빌드 시 각 게임의 `vendor/`에 복제 |
| 게임 저장 | guest principal 서버 저장과 계정 연결 | 서버 `main` 조건부 쓰기, 충돌 비교·해결, 보관 슬롯·교체 전 백업의 명시 복원, 같은 탭 임시 기록 |
| 서버 없이 실행 | 기본 플레이를 막지 않는 복구 경로 | 검증된 내장 카탈로그에 한해 명시적인 로컬 모드. `sessionStorage` 기록, 서버 저장·게임 통계 없음 |
| Google 로그인 | 선택 로그인·게스트 기록 연결 | 실제 설정된 OAuth 경로를 연결. 미설정·HTTP LAN 조건에서 가짜 로그인이나 로그인 완료 상태를 만들지 않음 |
| 이용 지표 | 노출→클릭→활성 플레이·리텐션 | 부모 포털의 가시성·활성 시간 신호와 서버 판정. 로컬 모드 게임 이벤트는 서버에 전송하지 않음 |
| 보안 | 장기적으로 외부 제작자도 수용 | 현재 신뢰된 저장소 내장 게임만 대상. 포털의 iframe은 `sandbox="allow-scripts"`; 외부 게임 업로드 기능은 없음 |

## 2. 게임별 규칙과 현재 조작

### 2.1 매치 가든 — `match3-garden`

| 항목 | 구현 |
|---|---|
| 보드 | 8×8, 여섯 종류의 색·모양 조각 |
| 시작 상태 | 자동 매치가 없고 가능한 교환이 있는 보드 생성 |
| 목표 | 25번의 유효 교환 안에 1,200점 달성 |
| 입력 | 인접한 두 조각을 차례로 클릭·터치. 버튼은 Tab과 Enter/Space로도 선택 가능 |
| 유효 교환 | 가로 또는 세로로 같은 조각 세 개 이상이 생기는 교환만 이동 횟수 차감 |
| 연쇄 | 제거 → 위 조각 낙하 → 빈칸 생성 → 재매치. 한 번의 교환에서 연쇄 반복 |
| 점수 | 제거 조각 수 × 10 × 해당 연쇄 차수 |
| 종료 | 목표 이상이면 성공. 목표 미달 상태로 이동을 소진하면 실패 |
| 막힌 보드 | 더 이상 가능한 교환이 없으면 새 유효 보드 생성 |
| 현재 저장 | 64칸 배열, 남은 이동, 목표, 점수, 경과 시간, 라운드 상태 |

연쇄 결과는 즉시 계산해 보드에 반영한다. 드래그 교환, 특수 조각, 폭탄, 장애물, 20개 이상의 레벨, 단계 선택, 복잡한 연출은 이번 구현에 없다. 기획상의 장기 콘텐츠 목표와 구분해야 한다.

### 2.2 블록 드롭 — `falling-blocks`

| 항목 | 구현 |
|---|---|
| 보드 | 가로 10칸 × 세로 18칸 |
| 블록 | 7종 네 칸 블록 중 다음 조각을 무작위 선택 |
| 목표 | 총 20줄 제거 |
| 입력 | ←/→ 이동, ↑ 또는 Z 회전, ↓ 한 칸 내리기, Space 즉시 낙하 |
| 모바일 | 좌·우·회전·아래·즉시 낙하 버튼 |
| 줄 제거 | 가득 찬 가로줄을 동시에 제거하고 윗줄을 내림 |
| 점수 | 한 번에 1/2/3/4줄 제거 시 100/300/500/800 × 현재 레벨. 즉시 낙하 한 칸당 2점 |
| 속도 | 5줄마다 레벨 증가. 자동 낙하 간격은 점점 짧아짐 |
| 종료 | 20줄 이상이면 성공. 새 블록을 놓을 수 없으면 실패 |
| 현재 저장 | 180칸 고정 블록, 현재 블록 형태·위치·회전, 줄 수, 레벨, 점수, 경과 시간 |

화면에는 착지 예상 위치를 옅게 표시한다. 회전 시 좌우의 제한된 보정을 시도한다. 보드 10×20, 홀드, 다음 블록 미리보기, 7-bag, 표준 SRS 전체, 벽·바닥 회전 규칙의 완전한 재현, T-spin, 대전은 미구현이다. 이름과 아트는 자체 표현이며 특정 상표의 공식 게임이라고 표시하지 않는다.

### 2.3 버블 스플릿 — `bubble-split`

| 항목 | 구현 |
|---|---|
| 장르 해석 | 튀는 공을 세로 공격으로 분할하는 액션 게임 |
| 논리 화면 | 640×440. 화면 크기에 맞추어 Canvas를 표시 |
| 시작 | 큰 공 두 개, 기회 세 번, 활성 시뮬레이션 시간 90초 |
| 입력 | ←/→ 이동, Space 발사. 모바일 좌·우·발사 버튼 |
| 공격 | 위로 뻗는 줄 하나. 다음 발사는 기존 줄이 사라지고 대기 시간이 지난 뒤 가능 |
| 분할 | 큰 공 → 중간 공 두 개 → 작은 공 두 개. 가장 작은 공은 제거 |
| 점수 | 맞힌 공 하나당 100점 |
| 피격 | 플레이어와 공이 닿으면 기회 하나 차감. 1.8초 동안 연속 피격 보호 |
| 종료 | 공이 모두 사라지면 성공. 기회 소진 또는 90초 종료 시 실패 |
| 현재 저장 | 플레이어 위치, 각 공의 위치·속도·크기, 공격 상태, 기회, 남은 시간, 피격 보호·발사 대기 시간 |

여러 맵, 장애물, 사다리, 보스, 아이템, 무기 종류, 사운드 연출은 없다. 이 문서에서 ‘팡’ 요구를 버블 분할형으로 해석했으며, 버블 슈터와는 다른 규칙이다.

### 2.4 브릭 브레이크 — `brick-breaker`

| 항목 | 구현 |
|---|---|
| 논리 화면 | 640×440 |
| 시작 | 8열 × 5행의 벽돌 40개, 기회 세 번 |
| 입력 | 마우스·터치로 패들 이동, ←/→ 이동, Space 또는 화면 버튼으로 공 발사 |
| 공 | 처음과 기회를 잃은 뒤에는 패들에 붙어 대기 |
| 반사 | 좌·우·상단과 벽돌에서 반사. 패들에 맞는 위치에 따라 출사 각도 변경 |
| 점수 | 벽돌 하나당 25점 |
| 종료 | 40개 벽돌을 모두 지우면 성공. 공을 세 번 놓치면 실패 |
| 현재 저장 | 40개 벽돌의 잔존 상태, 패들 위치, 공 위치·속도·대기 상태, 기회, 점수, 경과 시간 |

벽돌의 내구도, 여러 공, 아이템, 단계 구성, 곡선 패들, 정교한 연속 충돌 검출 엔진은 이번 범위에 없다. 프레임 이동을 작은 단위로 나누고 이전 좌표를 사용해 기본 충돌을 처리한다. 극단적인 저사양·비정상 프레임 정지에서의 모든 물리 품질을 보장한 상태는 아니다.

### 2.5 슬라이드 나인 — `slide-puzzle`

| 항목 | 구현 |
|---|---|
| 보드 | 3×3, 숫자 1~8과 빈칸 |
| 시작 | 완성된 보드에서 유효 이동을 반복하여 항상 풀 수 있게 섞음 |
| 입력 | 빈칸에 인접한 숫자를 클릭·터치. 방향키는 빈칸을 이동 |
| 목표 | 위에서부터 `1 2 3 / 4 5 6 / 7 8 빈칸` |
| 점수 | `max(100, 2000 - 이동 횟수 × 10)` |
| 종료 | 정렬되면 성공. 시간 제한과 실패 횟수 제한 없음 |
| 현재 저장 | 아홉 칸 순열, 이동 횟수, 점수, 경과 시간 |

4×4·5×5 보드, 사진 퍼즐, 최단 경로 힌트, 최적해 검증, 난이도 선택은 미구현이다. 자동 검증은 여러 난수 시드의 풀 수 있음과 완료 판정을 확인한다.

### 2.6 마인 그리드 — `mines-grid`

| 항목 | 구현 |
|---|---|
| 보드 | 9×9, 지뢰 10개 |
| 첫 클릭 | 처음 여는 칸과 인접한 여덟 칸에는 지뢰를 놓지 않음 |
| 숫자 | 주변 여덟 칸의 지뢰 수 |
| 빈 영역 | 주변 지뢰 수가 0인 칸은 연결된 안전 영역을 자동으로 엶 |
| 입력 | 클릭·터치로 열기. 우클릭 또는 ‘깃발 모드’로 표시 |
| 깃발 | 사용자의 추측 표시. 깃발이 있는 칸은 바로 열리지 않음 |
| 점수 | 열린 안전 칸당 10점, 완료 보너스 500점 |
| 종료 | 안전한 71칸을 모두 열면 성공. 지뢰를 열면 실패 |
| 현재 저장 | 지뢰 위치, 열린 칸, 깃발, 첫 클릭 여부, 이동 횟수, 점수, 경과 시간 |

첫 클릭 이후 무추측 해결 가능성을 보장하는 생성기, 숫자 양쪽 클릭, 난이도 선택, 서버에서 숨긴 지뢰 상태, 경쟁 기록 검증은 없다. 지뢰 배열이 저장 JSON 안에 있으므로 클라이언트에서 열람할 수 있다. 이 구현의 점수를 경쟁 결과로 취급하면 안 된다.

### 2.7 메모리 페어 — `memory-pairs`

| 항목 | 구현 |
|---|---|
| 보드 | 4×4 카드, 여덟 그림의 두 장씩 |
| 입력 | 클릭·터치 또는 버튼의 키보드 활성화 |
| 한 차례 | 두 장을 선택. 같은 카드를 두 번 고를 수 없음 |
| 일치 | 열린 상태로 남음 |
| 불일치 | 약 0.8초 뒤 다시 닫힘. 이 사이에는 세 번째 선택 차단 |
| 점수 | 진행 중 찾은 쌍당 100점. 완료 시 `max(100, 2000 - max(0, 시도 수 - 8) × 65)` |
| 종료 | 여덟 쌍을 모두 찾으면 성공. 시간 제한 없음 |
| 현재 저장 | 카드 배치, 찾은 카드, 현재 열린 카드, 시도 횟수, 점수, 경과 시간 |

그림 테마 선택, 카드 수 조절, 단계별 콘텐츠, 음성·사운드, 멀티플레이는 없다. 중간 저장에서 다른 두 카드가 열린 경우, 이어서 시작한 뒤 닫기 대기를 적용한다.

### 2.8 머지 타일 — `merge-tiles`

| 항목 | 구현 |
|---|---|
| 보드 | 4×4 |
| 시작 | 무작위 빈칸 두 곳에 2 또는 4 생성 |
| 입력 | 방향키, 화면 방향 버튼, 보드 위 스와이프 |
| 이동 | 모든 타일을 지정 방향으로 밀고 같은 숫자를 합침 |
| 합치기 제한 | 하나의 타일은 한 번의 이동에서 한 번만 합쳐짐 |
| 새 타일 | 보드가 실제로 변한 이동 뒤 하나 생성. 2가 90%, 4가 10% |
| 점수 | 합쳐져 만들어진 숫자의 합 |
| 종료 | 2048을 만들면 성공. 빈칸도 없고 합칠 이웃도 없으면 실패 |
| 현재 저장 | 16칸 숫자 배열, 이동 횟수, 점수, 경과 시간 |

되돌리기, 2048 이후 계속하기, 힌트, 난이도·보드 선택, 서버 검증 경쟁 기록은 없다. 자동 검증은 `[2,2,2,2] → [4,4,0,0]`이며 한 번에 8로 연속 합쳐지지 않는 규칙을 포함한다.

## 3. 공통 실행과 저장 계약

각 게임의 폴더에는 `index.html`, `game.js`, `game.manifest.json`, `assets/cover.svg`가 있다. 별도 npm 패키지와 외부 자산 요청이 필요하지 않다. 소스 단계에서는 `/shared/`의 classic script와 CSS를 참조하고, 빌드는 그 파일을 각 게임의 `vendor/`로 복제해 상대 경로로 바꾼다. 게임 iframe의 스크립트는 `fetch`, 로그인 쿠키, CSRF 토큰, Google 토큰에 직접 접근하지 않는다.

부모 포털이 게임 URL의 fragment에 새 nonce를 넣는다. 포털은 `event.source === 현재 iframe.contentWindow`, `origin === "null"`, 프로토콜 버전, nonce를 확인한 뒤 하나의 `MessageChannel`을 전달한다. 이후 저장·불러오기·이벤트는 이 포트에서만 받는다. 요청 큐 크기와 빈도를 제한하고 저장 대상 게임은 부모가 고정한다.

저장 데이터는 다음 공통 봉투를 사용한다.

```json
{
  "gameId": "match3-garden",
  "schemaVersion": 1,
  "state": { "score": 0, "elapsed": 0, "status": "playing" },
  "runId": "라운드 식별자",
  "runStarted": true,
  "runEnded": false
}
```

`state`에는 위 게임별 필드가 추가된다. 불러올 때 게임별 배열 길이·숫자 범위·상태·구조를 검사하며, 형식이 다르면 실행에 사용하지 않는다. 저장 봉투의 최대 길이는 포털에서 65,536자이며, 서버에도 별도의 요청 크기 제한이 있다.

게임을 시작하기 전에는 복원된 상태로 대기하고 사용자 입력 후 진행한다. 게임 시간은 실제 게임이 실행 중일 때만 누적한다. 일시정지, 가려진 문서, 화면에서 벗어나 부모가 정지시킨 동안에는 시뮬레이션을 진행하지 않는다. 수초 동안 멈춘 프레임을 한 번에 큰 물리 이동으로 계산하지 않도록 프레임 단위를 제한한다.

퍼즐 입력 후에는 짧은 지연 뒤 저장하며, 실행 중에는 대략 10초마다 저장한다. 일시정지·완료·게임 닫기에서도 저장한다. 일반 화면 이동 시 부모는 마지막 스냅샷을 요청하고 저장 처리를 기다린 후 iframe을 제거한다. 브라우저 프로세스가 강제 종료되거나 탭이 즉시 폐기되는 경우 마지막 수초의 상태까지 보장하지는 않는다.

## 4. 온라인 게스트와 로컬 모드의 차이

| 상황 | 실행·저장 처리 |
|---|---|
| API 정상, 세션 쿠키 사용 가능 | 플레이 시작 시 guest로 승격. 서버의 게임별 `main` 슬롯으로 저장 |
| 최초 서버 저장 | `If-None-Match: *` 사용 |
| 기존 서버 저장 | 받은 revision에 대응하는 `If-Match` 사용 |
| 저장 재시도 | 동일 요청에 동일 `Idempotency-Key` 사용 |
| 다른 탭·기기와 저장 충돌 | 412 후 서버 쓰기를 중단하되 이후 진행도 같은 탭에 계속 보존. 저장 기록 화면에서 서버·현재 탭·보관 슬롯·백업을 선택 |
| API 네트워크 실패 또는 502/503/504 | 빌드 카탈로그의 신뢰 게임은 로컬 모드로 시작 가능 |
| 플레이 세션 생성 401 | 쿠키를 사용할 수 없는 경우 로컬 모드 가능 |
| API가 정상적으로 게임 404/403 반환 | 로컬 모드로 우회하지 않음 |
| 로컬 모드 | 같은 탭의 `sessionStorage`에 임시 저장. 서버 저장·계정 기록·서버 게임 통계 없음 |
| 로컬 모드 후 서버 연결 | 실행 중 로컬 게임을 유지하고 자동 병합하지 않음. 저장 기록 화면에서 직접 적용하거나 별도 슬롯 보관·파일 다운로드 선택 |
| 로그아웃 | 실행 iframe·포트·메모리와 임시 저장을 정리하고 새 익명 세션을 시작 |
| 다른 탭의 로그인·로그아웃 | 새 세션 문맥을 확인하면 이전 iframe을 쓰기 없이 닫고 이전 계정 임시 데이터를 정리. 늦게 도착한 이전 요청 결과는 적용하지 않음 |
| 쿠키 차단 중 재연결 | 두 번의 세션 조회가 같은 세션으로 유지되는지 확인. 유지되지 않으면 현재 로컬 게임과 임시 진행을 보존 |

서버 모드의 guest 기록은 서버에 남지만 복구 식별은 브라우저 쿠키에 의존한다. 쿠키 삭제 후 복구를 보장하지 않는다. 로컬 모드의 임시 데이터는 탭 단위이며 서버 백업·기기 간 복구를 제공하지 않는다. 사용자 UI에서 저장 상태를 구분해 표시한다. 현재 게임의 이어하기는 항상 `main` 슬롯을 읽으며, 다른 슬롯·백업을 선택하면 서버가 새 `main` revision으로 복원한 뒤 게임을 다시 연다.

### 저장 기록 화면

게임 상세의 **저장 기록** 버튼은 게임을 정지하고 최신 스냅샷을 확보한다. 현재 계정의 이어하기, 계정 연결 때 별도 보관한 게스트 기록, 사용자가 보관한 기록, 교체 전 백업을 구분해 표시한다. 목록에는 저장 시각과 revision이 표시되고, 이 탭의 기록에는 점수·경과 시간·라운드 상태를 추가로 보여 준다. 원본 슬롯 목록 API는 전체 payload를 노출하지 않는다.

| 선택 | 처리 |
|---|---|
| 서버 이어하기 사용 | 마지막 확인한 revision과 현재 main을 비교. 일치하면 게임을 다시 열며, 미반영 탭 진행은 별도 임시 백업으로 유지 |
| 이 탭 진행으로 이어하기 | 먼저 새로운 `recovery-…` 슬롯에 조건부 최초 저장. 그 슬롯의 revision과 현재 main revision을 함께 제시해 복원 |
| 이 탭 진행 별도 보관 | recovery 슬롯만 만들고 main은 그대로 유지. 목록에서 이후에 복원 가능 |
| 보관 슬롯 복원 | 원본 슬롯 revision과 대상 main revision을 모두 검사. main 변경 전 상태는 서버 백업으로 보관 |
| 교체 전 백업 복원 | 접근 가능한 backup ID와 main revision으로 복원. 현재 main도 다시 백업 |
| 보관 슬롯 제거 | 사용자 확인과 해당 슬롯의 If-Match revision으로 제거. main은 유지하고 제거한 원본은 복구 기록으로 보관. main 제거는 금지 |
| 적용 중 다른 탭이 변경 | 412 표시, 기존 main과 원본·임시 진행 유지. 목록을 새로 읽은 뒤 다시 선택 |
| 네트워크가 응답을 끊음 | 같은 idempotency key로 한 번 재시도. 확인할 수 없는 결과를 성공으로 표시하지 않음 |

슬롯은 게임·계정별 최대 10개이며 `main`도 포함된다. 복원 전 main과 제거한 슬롯의 백업을 합쳐 최근 20개를 순환 보관하며 계정 병합 충돌 원본은 별도로 유지한다. 슬롯이 모두 차면 사용하지 않는 보관 슬롯을 제거해 한 칸을 비울 수 있고, 제거한 원본을 복구 기록에서 main으로 적용할 수 있다. 임시 기록 파일은 진행 봉투를 내려받는 백업이며, 임의 JSON 파일 업로드·가져오기 기능은 이번 UI에 없다. 계정 연결 중 충돌 목록이 바뀌면 최신 목록을 읽고 다시 선택하도록 한다.

서버 재연결은 페이지를 강제 새로고침하지 않는다. 동일 세션이면 기존 실행과 임시 진행을 유지하고 조건부 저장을 다시 시도할 수 있게 한다. 서버 저장과 별도로 시작한 로컬 모드 기록은 사용자의 명시 선택을 거쳐야 서버 기록으로 들어간다. 로그아웃 시 미반영 임시 진행이 있으면 삭제 전에 확인한다. 로그아웃 성공 후 새 세션 조회에 실패하더라도 이전 계정으로 표시하지 않고 로컬 모드로 전환한다.

게임 공개 중단은 API 목록과 새 플레이 생성에 적용된다. 이 PoC의 정적 내장 파일은 내려받은 소프트웨어이므로, 운영자의 공개 설정을 복사본 실행 방지나 DRM으로 설명하면 안 된다.

## 5. 포털과 이용 지표의 현재 동작

사용자 사이트는 홈 카드, 장르, 검색, 최근 게임, 개별 소개·조작법·규칙, 실행 iframe, 저장 상태와 오류 안내를 제공한다. 새 게임은 카탈로그와 manifest를 통해 목록에 반영한다. `/play/<id>/`와 `?game=<id>`의 진입을 지원하며, 빌드는 각 게임의 정적 제목·설명·본문·canonical·Open Graph 메타데이터와 sitemap을 생성한다. 내부 LAN 배포의 기본 검색 색인은 빌드 설정에서 차단된다.

카드는 같은 노출 기회에서 면적 50% 이상이 문서가 보이는 상태로 연속 1초 유지됐을 때 노출 이벤트를 보낸다. 그 전에 누른 클릭은 `viewability_met:false`로 구분한다. 문서를 숨기면 진행 중인 노출 타이머를 초기화한다. 검색·다른 목록 렌더링은 새 노출 기회다.

게임 활성 시간은 부모 포털에서 계산한다. 게임 준비 완료, 실행 중 상태, iframe 가시 면적 50% 이상, 부모 문서 visible, 최근 게임 업데이트 신호가 모두 있어야 한다. 게임은 실행 중 1초 주기의 업데이트 신호를 보내고, 부모는 대략 15초마다 누적 heartbeat를 보낸다. 정지·종료 전에 남은 활성 구간을 전송한다. 10초·60초 milestone과 D1/D7/D30 집계는 서버 책임이며 게임 코드가 직접 확정하지 않는다. 이것은 이용 품질 측정이며 경쟁 점수용 부정행위 방지 체계가 아니다.

### 사용자 이용에서 관리자 지표까지

관리자 화면은 실제 이용 `live`, 자동 도구의 별도 세션으로 남긴 `qa`, 고정 가상 예제 `demo`를 각각 조회한다. 일반 사용자 화면에는 QA 전환 버튼을 노출하지 않는다. 도구가 시작한 QA 세션은 사용자 헤더에 **QA 기록**으로 표시하며 Google 계정 연결을 제공하지 않는다. 이 표시 자체가 실제 브라우저 검증의 실행 증거는 아니고 실행 보고서를 함께 확인해야 한다.

관리자는 시작일·종료일을 KST 날짜로 지정하고 전체 게임 또는 특정 게임을 선택한다. 화면은 서버가 반환한 실제 적용 필터와 최신 집계 시각을 표시한다. 노출·가시 클릭·CTR·준비·10초·60초·유효 사용자·활성 시간과 함께 라운드 완료·서버 저장 성공을 보여 준다. 클릭 분모가 없으면 **분모 없음**, 성숙한 리텐션 코호트가 없으면 **집계 대기**로 구분한다.

기간 요약은 해당 기간의 활동이다. 세션 생성 수는 기간에 발급된 세션이며 ready·10초·60초는 기간의 실제 발생 수이므로 날짜 경계를 넘는 세션에서는 서로 같은 코호트의 전환율이 아니다. 리텐션은 전체 이력의 최초 유효 플레이일을 유지하고 코호트 최초일에 기간 필터를 적용한다. 게임을 선택하면 `retention.selected`로 해당 게임의 코호트·D1/D7/D30을 표시한다. 실행 오류도 같은 데이터·기간·게임 범위로 조회하고 운영 변경 기록은 전체 이력으로 제공한다.

고정 가상 예제에서는 날짜·게임 필터와 게임 공개 변경을 비활성화한다. QA 탭에서도 실제 공개 상태를 변경하지 못하게 하고, 공개 전환은 실제 이용 기록 탭에서 확인 후 실행한다. 지표 조회가 실패하면 이전 자료를 다른 범위로 잘못 읽지 않도록 통계 표시를 지우고 오류를 알린다. 관리자 인증이 만료되면 로그인 상태와 이전 화면 자료를 정리한다.

## 6. 현재 자동 검증과 남아 있는 검증

`node --test tests/games*.mjs`로 게임 규칙과 포털 계약·저장 흐름을 검사한다. 작성 시점의 37개 테스트는 모두 통과했다. 게임 규칙 15개, 포털·관리자 순수 계약 8개, 실제 포털 코드의 저장·세션 흐름 14개다.

- 초기 상태와 저장 구조: 8종 게임, 여러 난수 시드.
- 매치3: 초기 자동 매치 부재, 교환 가능성, 유효 교환의 이동 차감·연쇄.
- 낙하 블록: 연속 가득 찬 줄 제거, 회전의 칸 수 보존, 즉시 낙하·경계.
- 버블: 크기별 분할·최소 공 제거·연속 피격 보호.
- 벽돌: 놓친 공의 기회 차감·마지막 벽돌 완료.
- 슬라이드: 풀 수 있는 섞기와 완료.
- 지뢰: 첫 칸·주변 보호, 정확한 지뢰 수, 깃발·완료.
- 메모리: 같은 카드 재선택 방지, 불일치 대기, 8쌍 완료.
- 머지: 한 이동의 중복 합치기 금지, 무변경 이동의 새 타일 방지, 막힌 보드.
- 포털: iframe source·origin·nonce·프로토콜, 로컬 모드 허용/거부, 노출 1초 조건, 숨김·정지·가림·오래된 업데이트의 활성 시간 제외.
- 저장: 412 이후 최신 진행 보존, 같은 키의 조건부 재시도, 충돌한 캐시 복원, 보관→main 복원→게임 재시작, 복원 충돌 시 양쪽 보존, 서버 선택 시 임시 백업 유지, 보관 슬롯 제거의 revision·CSRF와 main 제거 금지.
- 세션: 계정 변경 중 늦은 응답의 캐시 재생성 차단, 이전 게임의 쓰기 없는 종료, 로컬 모드의 서버 무요청 저장, 쿠키 차단 중 재연결의 진행 보존.
- 관리자: live/qa 분리, 날짜 유효성·역전 범위 거부, demo 필터 제외, 선택 게임 리텐션과 0%·분모 없음 구분.

저장 흐름 검사는 배포에 사용하는 `web/user/app.js`의 실제 함수를 VM에서 실행하고 전송·최소 DOM 어댑터를 제공한다. 구현 함수를 복사해 만든 테스트가 아니지만, Canvas 렌더링·실제 iframe·브라우저 쿠키·네이티브 dialog를 검증하는 도구도 아니다. 그 항목은 Windows 브라우저 E2E의 실행 증거와 분리한다.

위 검증은 실제 Windows IIS 설치, 터치 기기의 전체 조작, 브라우저 렌더링, 장시간 물리 동작, 접근성 보조기기, 계정별 OAuth 설정을 실행했다고 주장하지 않는다. 현재 작업 환경에서는 브라우저 프로세스의 소켓 생성이 차단되어 실제 UI 실행을 완료하지 못했다. 별도의 Windows/IIS 브라우저 검증 절차와 선택형 Playwright QA를 실행하고 결과를 기록해야 한다. 설치·API·정적 파일·배포 검증은 프로젝트의 다른 도구와 보고서를 함께 확인한다.

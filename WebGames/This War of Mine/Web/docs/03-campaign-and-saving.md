# 03. 캠페인·결말·저장 시스템

Campaign Edition 4.0의 캠페인 운영과 저장 호환 명세입니다. [engine.js](../dist/engine.js), [saves.js](../dist/saves.js), [campaign.test.js](../tests/campaign.test.js), [saves.test.js](../tests/saves.test.js)를 기준으로 합니다.

## 캠페인 계약

캠페인은 고정 세 인물, 장소 5곳, 12번의 밤으로 구성합니다. 12번째 밤을 정산하고 다음 장으로 진행할 때 한 사람 이상 살아 있으면 승리입니다. 살아 있는 사람이 없으면 밤 보고서를 거쳐 패배 화면으로 이동합니다. 최대 날짜는 결말 상태의 13일입니다.

상태 단계는 `day`, `planning`, `expedition`, `report`, `ended`입니다. 수색하지 않는 밤에도 `beginNight`와 `finishNight`를 거쳐 같은 경계·수면·습격·난방을 정산합니다. UI가 별도 결과를 계산하지 않습니다.

## 난이도와 생존기 번호

새 게임에서 표준·봉쇄를 선택합니다. 진행 중 난이도를 변경하지 않습니다. 생존기 번호는 0~4294967295의 정수이며, 빈 입력은 새 번호를 만듭니다. 같은 번호와 난이도, 같은 입력과 진행 순서를 사용하면 같은 난수 흐름을 재현할 수 있습니다. 다른 선택으로 난수 소비 순서가 바뀌면 같은 번호라도 결과가 달라질 수 있습니다.

| 항목 | 표준 | 봉쇄 |
|---|---:|---:|
| 초기 목재 | 12 | 10 |
| 초기 부품 | 14 | 12 |
| 초기 물 | 8 | 6 |
| 초기 식재료 | 4 | 3 |
| 초기 식사 | 3 | 3 |
| 초기 연료 | 4 | 3 |
| 초기 천 | 3 | 2 |
| 초기 약품·붕대 | 각 1 | 각 1 |
| 초기 쇠지레·칼 | 각 0 | 각 0 |
| 밤마다 추가되는 허기 | 18 | 21 |
| 습격 확률 배수 | 1 | 1.35 |
| 습격 강도 보정 | 0 | +4 |
| 문 마모 배수 | 1 | 1.6 |

날씨·시설 상한·지도 자원·가방 크기·인물 특성과 승리 날짜는 같습니다. 표준의 기존 출발 물자와 기본 생존 압박을 유지하면서, 봉쇄에서는 더 적은 자원과 강한 습격을 관리하게 합니다. 난이도는 `state.difficulty`, 캠페인 소개는 `state.campaign`, 공통 날짜는 `CAMPAIGN_PROFILE`에 기록합니다.

## 생존 압박과 예측 가능성

4~8일은 추우며 6~7일은 혹한입니다. 난로와 연료를 미리 준비해야 합니다. 경비·수색은 피로를 쌓고, 침대 수와 수면 배정은 회복량을 바꿉니다. 배고픔·중병·극심한 피로는 건강과 사기를 해칩니다. 습격 이후에는 내구도와 재고 변화가 다음 낮의 준비 목표가 됩니다.

플레이어가 모든 결과를 예견할 수는 없지만, 출발 전 화면은 위험 범위와 부족한 준비를 알려 줍니다. 보고 화면은 실제 난수 결과를 포함한 내구도 손상, 물자와 인물 상태 변화를 보여 줍니다. 새 불확실성을 추가하기보다 예측·행동·결과 사이의 인과를 읽을 수 있게 합니다.

## 개인별 결말

`getEpilogues(state)`는 세 인물 각각에 대해 `{id,name,alive,title,body}`를 반환합니다. 생존·건강·질병·사기, 공동체의 도움·수색·절도·치명적 충돌 기록에 따라 문구를 고릅니다.

미라는 돌봄, 윤은 다시 세울 집과 완성한 시설, 레오는 돌아올 길이라는 직업별 주제를 갖습니다. 부상과 낮은 사기는 무조건적인 낙관적 결말로 덮지 않습니다. 공동체 통계만 있는 사건을 특정 인물이 했다고 단정하지 않으며, 사망한 인물의 이름과 기록도 남깁니다.

종료 시 `ending.epilogues`에 결과를 저장합니다. 구 저장에 후일담이 없으면 기존 상태로 생성합니다. 결말 화면에서도 기록을 JSON으로 내보내거나 난이도를 골라 새 생존기를 시작할 수 있습니다.

## 저장 계층

서버 저장과 계정 동기화 없이 현재 브라우저의 저장소를 사용합니다. 자동 저장과 수동 내보내기는 같은 검증을 거칩니다.

| 키 | 내용 | 용도 |
|---|---|---|
| `last-light-campaign-v1` | 현재 캠페인과 진행 중 수색 | 일반 재개 |
| `last-light-backup-v1` | 직전 정상 스냅샷 | 기본 기록 손상 복구 |
| `last-light-dawn-v1` | 현재 생존기의 하루 시작 | 아침부터 다시 준비 |

envelope는 `{schema:1,state,expedition,savedAt}`입니다. 내부 규칙이 추가되어도 기존 버전 1 기록을 읽을 수 있도록 새 필드는 보완 가능한 형태로 추가합니다. 파일 크기, 알려진 품목, 정수 재고, 날짜·단계, 인물 ID, 좌표·경로, 가방 크기와 수색자·장소의 일치를 검사합니다.

## 이전 저장의 이행

| 누락 필드 | 복원값 또는 처리 |
|---|---|
| `difficulty` | `standard` |
| `campaign` | 표준 캠페인 메타데이터 |
| `shelterIntegrity` | 100 |
| 인물 대기열 | 빈 배열 |
| 진행 중 현장의 스태미나·회피·공격 예고 | 안정된 기본 상태 |
| 장소의 대화·허락·적대 기록 | 빈 기록 |
| 구 버전 진행 중 수색의 문 | 진행 경로를 막지 않도록 열린 상태로 추가 |
| 상인의 유한 재고 | 이전에 거래한 꾸러미를 반영하여 재구성 |
| 개인별 후일담 | 기록된 최종 상태로 생성 |

이행은 확인되지 않은 물자를 새로 만들거나 이미 획득한 지역 물자를 보충하지 않습니다. 데이터에 있던 잘못된 값은 기본값으로 덮어 무조건 통과시키지 않습니다.

## 아침 기록의 범위

아침 기록은 같은 날짜의 반복 저장으로 덮어쓰지 않습니다. 확인은 생존기 번호와 난이도를 함께 비교하므로 같은 번호의 표준·봉쇄를 섞어 복원하지 않습니다.

플레이어가 명시적으로 새 게임을 시작하면 `startCampaign`이 현재·백업·아침을 새 첫날로 바꿉니다. 같은 번호로 다시 시작해도 지난 실행의 아침이 남지 않습니다. 새 게임 화면은 현재 자동 저장이 대체됨을 알리고 먼저 내보낼 수 있는 버튼을 제공합니다.

기본 기록이 손상되면 정상 백업, 아침 기록 순서로 복구합니다. 저장소를 사용할 수 없으면 UI에 자동 저장 제한을 알리고 파일 내보내기를 제공합니다. 파일을 가져올 때는 새 상태 전체를 검증한 뒤 현재 생존기를 교체합니다.

## 단일 HTML과 소스의 관계

기준 소스는 `dist`의 ES 모듈입니다. `scripts/package-offline.mjs`는 로컬 import/export의 알려진 구문만 묶고, 지원하지 않는 구문이면 실패합니다. CSS·아이콘·모든 모듈을 `dist/last-light.html`에 내장합니다. 두 실행 방식 모두 같은 UI 통합 테스트를 수행합니다.

소스 ZIP은 문서·모듈·테스트·포장 스크립트와 단일 HTML을 포함합니다. 사이트 식별자나 Git 자격증명은 담지 않습니다. 새 문서를 추가하거나 소스를 수정하면 단일 HTML과 ZIP도 최종 검증 후 다시 만듭니다.

## 검증 해석

단위 테스트는 경계 조건과 자원·저장 일관성을 확인합니다. 캠페인 테스트는 실제 공개 행동 API, 실제 지도 이동·조사·회수·귀환, 유한 물자만으로 12일을 수행합니다. 재고·건강·좌표·날짜를 덮어써서 승리하지 않습니다.

UI 인터페이스 테스트는 실제 앱 컨트롤러와 생성 HTML을 검사하지만 브라우저의 배치를 대신하지 않습니다. 실제 브라우저 확인과 Canvas 이미지 확인은 [VALIDATION.md](../VALIDATION.md)에 별도로 범위를 기록합니다. 특정 생존 정책의 성공은 모든 임의 선택의 성공을 보장하지 않습니다.

## 4.0의 추가 상태

선택형 구호 연락망은 `facilities.radio`, `relief`에 기록합니다. 교신 날짜·보급 도착 날짜·지급 완료·대피 준비를 서로 검증하며, 이전 기록에는 미진행 상태를 보완합니다. 승리의 `ending.route`는 `coordinated` 또는 `self`이며 12일 생존 판정은 같습니다. `stats.distractions`는 실제 투척 사용 횟수를 누적하며 NPC 유인 성공률을 뜻하지 않습니다. 현장에는 유인 소리·재사용 시간과 조사 상태를 저장합니다. 상세 스키마는 [구호 연락망](04-relief-and-objectives.md)과 [소음 유인](05-stealth-and-navigation.md)에 있습니다.

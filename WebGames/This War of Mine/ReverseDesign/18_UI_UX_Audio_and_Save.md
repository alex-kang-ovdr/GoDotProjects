## 1. 시스템 역할

**[분석]** 이 게임의 인터페이스는 효율적인 명령 입력과 불완전한 상황 이해를 함께 다룬다. 플레이어는 재고와 인물 상태를 알아야 선택할 수 있지만, 모든 미래 결과와 숨은 확률을 정확히 알지는 못한다.

따라서 다음 두 질문을 분리해야 한다.

- 무엇을 할 수 있고 무엇이 부족한지는 명확한가.
- 그 선택의 장기 결과에는 어떤 불확실성이 남는가.

첫 질문의 혼란은 조작 실패를 만들고, 두 번째의 불확실성은 경험의 긴장을 만들 수 있다. 둘을 같은 “어려움”으로 취급하면 정보 누락이 선택의 무게를 대신하게 된다.

## 3. 화면별 의사결정 구조

아래 표는 **[분석] 기능 기준 분해**다. 특정 해상도의 실제 UI 명세를 복원한 표가 아니다.

| 화면·표현 영역 | 사용자가 알아야 하는 것 | 내리는 결정 | 피드백 실패의 결과 |
|---|---|---|---|
| 은신처 전경 | 인물 위치, 접근 경로, 상호작용 대상 | 누가 어디서 무엇을 할지 | 잘못된 인물 이동·시간 손실 |
| 인물 초상·상태 | 현재 상태와 행동 가능성 | 회복·노동·밤 역할 | 회복이 필요한 인물을 무리하게 배정 |
| 공동 재고 | 현재 물자와 사용할 수량 | 소비·제작·거래 | 다른 용도의 필수재를 소모 |
| 제작 화면 | 비용, 조건, 생산 결과 | 지금 만들거나 보류 | 부족 이유를 오해 |
| 밤 계획 | 인물별 역할, 지역, 반출품 | 기회와 방어 배분 | 중복 배정 또는 도구 미지참 |
| 지역 지도 | 방문 가능성과 알려진 지역 정보 | 수색 목적지 | 정보 없는 선택 또는 정보 과신 |
| 현장 상호작용 | 탐색·개방·거래·공격 의도 | 행동 실행 | 원치 않는 적대화 |
| 루팅·가방 | 품목, 스택, 남은 공간 | 가져갈 것과 버릴 것 | 가치 높은 물자를 실수로 포기 |
| 거래 | 서로 제시한 물건과 수락 가능성 | 교환 확정 | 최종 교환 내역 오인 |
| 아침 보고·일지 | 지난밤 사건과 결과 | 원인 학습·다음 계획 | 손실 이유를 이해하지 못함 |

## 4. 상태를 텍스트로 보여 주는 효과

**[분석]** 상태명이 행동 판단의 단서가 되면 사람을 세밀한 수치 막대로만 읽지 않게 할 수 있다. 그러나 상태 단계가 실제로 무엇을 바꾸는지 전혀 드러나지 않으면 플레이어는 추측만 반복하게 된다.

**[재구성안]** 상태 UI는 다음 세 층을 분리해 검토한다.

| 층 | 예시 표현의 역할 | 제공하면 좋은 정보 |
|---|---|---|
| 현재 상태 | 피로·부상·심리적 어려움의 정도 | 무엇이 문제인지 |
| 조치 가능성 | 수면·치료·대화 등의 선택 | 지금 할 수 있는 행동 |
| 변화 피드백 | 호전·유지·악화 | 조치가 효과를 냈는지 |

정확한 내부 확률을 모두 공개하지 않더라도, 조치가 불가능한 이유와 행동의 진행 상태는 명확하게 설명할 수 있다. 반대로 모든 결과를 퍼센트로 노출하면 인물을 확률 계산의 대상으로만 보게 할 가능성도 있다.

## 5. 정보의 신뢰도 구분

**[재구성안]** 화면과 메시지의 정보 상태를 다음처럼 구분하면 잘못된 확신을 줄일 수 있다.

| 정보 상태 | 예 | 표현 원칙 |
|---|---|---|
| 현재 확정 사실 | 소지품, 이미 관찰한 부상 | 단정형으로 명확히 |
| 관찰된 현장 정보 | 이전 방문 때 본 장애물·인물 | 관찰 시점과 변화 가능성 |
| 제3자의 전달 | 뉴스·도움 요청 | 전달한 사람·채널 유지 |
| 미래 전망 | 날씨·전쟁 동향 | 예상과 확정의 차이 |
| 내부 계산 | 습격·질병·감정 가중치 | 필요 이상의 정답 노출 주의 |

이 분류는 원작 UI가 모두 이런 메타데이터를 표시한다는 설명이 아니다. 역기획 검토에서 어떤 정보가 플레이어에게 어떤 수준의 확신으로 전달되는지 기록하기 위한 도구다.

## 6. 소리·애니메이션·시각 효과의 기능

**[분석]** 시청각 연출은 감정과 행동 판단을 함께 지원해야 한다.

| 표현 채널 | 게임플레이 정보 | 정서적 역할 | 검증 관점 |
|---|---|---|---|
| 작업 애니메이션 | 행동 수행·완료 여부 | 일상을 유지하는 노력 | 멈춘 행동을 작업 중으로 오해하는가 |
| 이동과 자세 | 이동·휴식·전투 상태 | 피로·취약성의 인상 | 실제 판정과 자세가 맞는가 |
| 상호작용 아이콘 | 가능한 동작·대상 | 최소한의 조작 안내 | 수색과 절도·공격을 구분할 수 있는가 |
| 환경음 | 공간과 위협의 단서 | 은신처와 외부의 분위기 | 소리를 끄면 필수 정보를 잃는가 |
| 라디오 | 외부 변화의 정보 | 도시가 살아 있다는 감각 | 핵심 정보를 다시 읽을 수 있는가 |
| 색·명암·스케치 | 시선 유도와 분위기 | 불안과 생활 흔적 | 중요한 대상의 가독성 저하 여부 |
| 인물 독백·대화 | 행동에 대한 반응 | 선택의 개인적 의미 | 반복 문구가 맥락을 어긋나게 하는가 |

밤의 소음 시각화와 NPC 인지의 관계는 [13번 문서](13_Stealth_Perception_and_NPC_AI.md)를 따른다. 화면에 보이는 소음 표현과 실제 AI의 내부 판정 범위를 같은 것으로 확정하지 않는다.

## 7. 의도하지 않은 행동을 줄이는 입력 계약

**[재구성안]** 재현할 때 다음을 분리한다.

1. 현재 선택 인물.
2. 현재 탐색/전투 등 입력 맥락.
3. 선택한 대상.
4. 대상에 가능한 행동 목록.
5. 실행 직전의 경로·재료·상태 조건.
6. 실행 결과와 취소 가능 범위.

탐색 중 문을 열려던 클릭이 NPC 공격으로 해석된다면 그 손실은 전략 실패와 다르다. 포인터, 아이콘, 입력 모드가 현재 수행할 행동을 일관되게 알려 주어야 한다.

상호작용을 무조건 확인창으로 감싸는 방식도 비용이 있다. 자주 하는 작업의 속도와 흐름을 끊기 때문이다. 행동의 빈도, 결과의 되돌리기 어려움, 대상 밀집도를 함께 고려해 직접 실행·길게 누르기·확인창 중 정책을 선택한다.

## 8. 시간과 UI

**[검증 필요]** 특정 창을 열면 게임이 멈추는지, 일시정지 상태에서 명령을 예약할 수 있는지, 대화와 거래 중 NPC가 계속 이동하는지는 플랫폼별 실측 항목이다.

**[재구성안]** 다음 항목을 화면별로 표준화해 두면 불일치를 찾기 쉽다.

```yaml
ui_time_contract:
  screen_id: example_trade
  world_clock_policy: to_be_verified
  npc_update_policy: to_be_verified
  pending_command_policy: to_be_verified
  transaction_commit_point: explicit_accept
  cancel_behavior: restore_uncommitted_offer
```

거래창에서 물자를 옮겼다는 이유만으로 실제 재고를 확정 변경하지 않도록, 편집 중 제안과 확정 거래를 분리한다. 같은 원칙을 밤의 가방 편성과 제작 수량 선택에 적용할 수 있다.

## 9. 저장의 확인 범위

**[확인·커뮤니티]** Day log 문서는 임의 시점의 일반적인 수동 저장/불러오기 대신 아침 자동 저장을 설명한다. 현재 PC 빌드의 사망·귀환·종전 등 특수 저장 시점과 플랫폼 종료 동작은 별도 확인이 필요하다. [W05](https://this-war-of-mine.fandom.com/wiki/Day_log)

**[분석]** 하루 단위로 결과가 굳어지는 저장 구조는 작은 선택들의 연속에 무게를 준다. 동시에 종료 시 진행이 어디까지 보존되는지 명확하지 않으면 사용자는 전략적 손실과 프로그램 종료로 인한 손실을 구분하기 어렵다.

저장을 “결정을 되돌릴 수 없게 하는 장치”로만 이해하면 안 된다. 안전한 지속성, 손상 복구, DLC·모드 호환성도 별도 기술 요구다.

## 10. 저장 데이터 계약

다음은 **[재구성안]**이며 원작 저장 포맷이 아니다.

| 저장 대상 | 필요한 이유 | 빠지면 발생하는 현상 |
|---|---|---|
| 캠페인·페이즈·시간 | 진행 위치 복구 | 다른 날짜로 복귀 |
| 인물 상태·부재·역할 | 생존과 노동 일관성 | 죽은 인물의 재등장, 부재 무시 |
| 재고·가방·시설 | 물자와 제작 결과 보존 | 복제·소실 |
| 지역 지속 상태 | 루팅·문·장애물 변화 보존 | 재방문 시 자원 재생성 |
| 사건·선택 이력 | 후속 요청과 결말 | 이미 끝난 사건 반복 |
| 난수 상태 | 재현 가능한 결과 | 로드마다 무관한 사건 변경 |
| 적용된 결과 ID | 정산 중복 방지 | 같은 습격·감정 반응 두 번 반영 |
| 콘텐츠 버전 | DLC·데이터 변경 대응 | 존재하지 않는 인물·시설 참조 |

저장 완료와 아침 보고의 데이터 기준이 다르면 사용자가 본 결과와 다시 시작했을 때의 결과가 달라질 수 있다. 저장 스냅샷과 보고를 같은 확정 결과에서 생성하는 설계를 권한다.

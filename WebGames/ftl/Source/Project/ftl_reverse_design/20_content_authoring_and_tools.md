# 20. 콘텐츠 데이터 작성·검증·제작 도구

> 조사 기준일: 2026-11-13. 범위: 원작과 Advanced Edition의 콘텐츠를 체계적으로 재구성하기 위한 제작 설계.\
> **이 문서의 스키마, 편집기, 작업 절차와 예시 이벤트는 모두 [재구성안]이다.** 원작 개발팀의 내부 도구나 실제 배포 데이터 구조를 확인한 문서가 아니다. 예시 문장·수치는 설명을 위해 새로 작성했다.

관련 문서: [이벤트](03_events_quests_and_choices.md), [경제](04_economy_shops_and_progression.md), [함선](14_ships_loadouts_and_unlocks.md), [데이터·저장](19_data_architecture_and_save.md), [QA](21_qa_and_acceptance_tests.md).

## 1. 제작 도구의 목표

FTL형 콘텐츠는 아이템 하나보다 상호작용이 어렵다. 장비는 전력·슬롯·상점·이벤트 조건에 연결되고, 종족은 전투·산소·수리·특수 선택지에 연결된다. 함선은 시스템 위치만 달라도 침투 방어와 수리 동선이 달라진다.

따라서 제작 도구는 데이터를 입력하는 표에 그치지 않고 다음 질문에 답해야 한다.

- 이 콘텐츠는 어느 난이도·섹터·AE 설정에서 등장하는가?
- 현재 함선이 이 선택지를 실제로 이용할 수 있는가?
- 보상을 받을 공간이 없으면 어떤 결과가 발생하는가?
- 선택 이후의 참조 이벤트와 퀘스트 비콘이 존재하는가?
- 전투·대화·저장·재개를 거쳐도 결과가 중복되지 않는가?

**[확인]** Subset Games는 공식 사이트에서 팬 제작 모드와 도구 생태계를 안내한다. 그러나 공개 모드가 있다는 사실만으로 특정 편집기나 스키마가 원작 개발 과정에서 사용되었다고 결론 낼 수는 없다. [C1]

## 2. 정의 데이터의 분류

| 정의 | 중요한 필드 | 검증할 연결 |
|---|---|---|
| 종족 | 체력·이동·수리·전투·환경 특성, 능력 | 승무원 생성, 고용, 이벤트 조건 |
| 함선 | 방·문·타일, 시스템 배치, 장비·승무원, 슬롯 | 해금, 적 생성, 텔레포트 공간 |
| 무기 | 발사 방식·충전·전력·피해 채널·부가효과 | 상점, 전투 판정, UI 조준 방식 |
| 드론 | 배치 방식·전력·AI 유형·부품 소비 | 드론 제어, 표적 탐지, 파괴·재구성 |
| 증강 | 적용 조건·수정 규칙·중복 정책 | 전투, 이벤트, 수입, 회수 |
| 시스템 | 수준별 능력·전력·가격·방 필요 조건 | 구매, 교체, 업그레이드, 해킹 |
| 섹터 | 종류·등장 제한·이벤트 풀·상점 설정 | 경로 생성, 보상, 추격 |
| 이벤트 | 본문·조건·선택·결과·후속 단계 | 자원, 전투, 퀘스트, 승무원 |
| 적 조합 | 기본 함선·수준·장비 후보·제약 | 난이도, 섹터, 특수 이벤트 |
| 해금·업적 | 관찰 조건·판정 시점·기록 | 런 이벤트, 프로필, 격납고 |

정의와 인스턴스를 분리한다. 예를 들어 같은 무기 정의를 쓰는 두 무기는 충전량과 표적이 다를 수 있다. 편집기에서 정의를 수정했다고 실행 중 개별 무기의 남은 충전 시간이 예기치 않게 재설정되면 안 된다.

## 3. 공통 메타데이터

```json
{
  "id": "example_weapon_precision_01",
  "revision": 1,
  "contentFlags": ["example_only"],
  "displayNameKey": "weapon.example_precision.name",
  "descriptionKey": "weapon.example_precision.description",
  "sourceConfidence": "reconstruction",
  "verificationNote": "설명용 신규 콘텐츠이며 원작 장비가 아님"
}
```

- `id`는 번역명과 무관한 고정 키로 둔다.
- `revision`은 데이터 변경을 추적하되, 원작 게임 버전 숫자를 흉내 내지 않는다.
- `contentFlags`는 AE 여부와 별도 실험 콘텐츠 여부를 구분한다.
- `sourceConfidence`는 원작 확인 데이터, 추정 데이터, 신규 설계 데이터를 나눈다.
- 수치에 출처와 확인일을 연결하여, 나중에 하나의 값을 바꾸는 이유를 추적할 수 있게 한다.

## 4. 이벤트를 조건·선택·결과로 분리

### 4.1 조건 평가

이벤트의 출현 조건과 선택지의 이용 조건은 다르다.

| 조건 위치 | 평가 시점 | 실패 시 처리 예 |
|---|---|---|
| 섹터 풀 필터 | 섹터 또는 비콘 생성 | 후보 목록에서 제외 |
| 이벤트 진입 조건 | 조우 시작 | 대체 이벤트 또는 무사건 |
| 선택지 표시 조건 | 대화 표시 | 숨김 또는 사용할 수 없음 표시 |
| 선택 확정 조건 | 플레이어 입력 처리 | 상태 재검사 후 거절 |
| 결과 적용 조건 | 선택 결과 처리 | 규정된 대체 보상·실패 처리 |

예를 들어 특정 종족이 있다는 사실, 해당 승무원이 생존한다는 사실, 현재 임무에 투입할 수 있다는 사실은 같은 조건이 아니다. 원작 이벤트마다의 실제 요구는 [03번 문서](03_events_quests_and_choices.md)와 콘텐츠별 원문 검증을 따른다.

### 4.2 자체 작성 예시 이벤트

아래는 **원작에 존재한다고 주장하지 않는 예시**다. 숫자도 밸런스 확정값이 아니다.

```json
{
  "id": "example_relay_repair",
  "textKey": "event.example_relay_repair.intro",
  "choices": [
    {
      "id": "use_repair_team",
      "textKey": "event.example_relay_repair.repair",
      "requirement": {
        "type": "all",
        "items": [
          {"type": "resource", "resource": "scrap", "atLeast": 5},
          {"type": "crewTrait", "trait": "repair_specialist"}
        ]
      },
      "presentation": {"kind": "special_option"},
      "effects": [
        {"type": "consume", "resource": "scrap", "amount": 5},
        {"type": "grant", "resource": "fuel", "amount": 3}
      ],
      "next": "example_relay_repair.completed"
    },
    {
      "id": "leave",
      "textKey": "event.example_relay_repair.leave",
      "effects": [],
      "next": "end"
    }
  ]
}
```

이 예시는 요구 조건을 문자열 스크립트 하나로 숨기지 않고, 편집기와 검증기가 읽을 수 있는 구조로 만드는 방법을 설명한다. 실제 종족 이름이나 원작 이벤트 확률을 가상의 값에 연결하지 않는다.

### 4.3 선택 확정의 원자성

1. 이벤트와 선택 ID를 확인한다.
2. 선택 조건을 다시 평가한다.
3. 비용을 지불할 수 있는지 확인한다.
4. 결과를 추첨하거나 이미 확정된 결과를 사용한다.
5. 비용·보상·승무원·퀘스트 변화를 한 묶음으로 적용한다.
6. 처리 ID를 기록한다.
7. 다음 화면을 표시한다.

결과 표시가 실패해도 비용만 소모되고 보상은 사라지는 상태를 만들지 않는다. 저장이나 동일 클릭의 재전송으로 같은 선택이 두 번 적용되지 않게 한다.

## 5. 확률과 가중치를 다루는 규칙

- 확률과 가중치를 다른 타입으로 둔다. `weight: 3`을 3%로 표시하지 않는다.
- 조건으로 후보가 제거되면 남은 후보를 어떤 방식으로 재정규화하는지 정의한다.
- 후보가 0개일 때 사용할 명시적 대안을 둔다.
- 한 섹터 내 유일 등장과 런 전체 유일 등장을 구별한다.
- 퀘스트·해금 같은 중요한 콘텐츠가 일반 풀의 중복 방지와 충돌하지 않게 한다.
- 이미 생성된 비콘의 결과가 저장·재개 때 다시 추첨되는지 여부를 상태로 남긴다.

**[검증 필요]** 원작이 모든 이벤트 풀에 같은 중복 정책과 같은 생성 시점을 사용하는지는 확인되지 않았다. 위 정책을 원작의 실제 알고리즘으로 오인해서는 안 된다.

## 6. 함선 레이아웃 편집기의 요구사항

| 편집 기능 | 즉시 보여줄 결과 | 막아야 할 오류 |
|---|---|---|
| 방·타일 배치 | 실내 면적과 슬롯 | 중복 타일, 음수 면적 |
| 문·에어록 연결 | 내부 그래프와 외부 연결 | 연결되지 않은 문, 잘못된 외부 참조 |
| 시스템 배치 | 방별 시스템 아이콘 | 한 방의 비허용 중복 설치 |
| 승무원 초기 위치 | 점유 슬롯과 이동 경로 | 존재하지 않는 슬롯, 중복 점유 |
| 이동 거리 표시 | 주요 시스템 간 경로 길이 | 수리 불가능한 고립 구조 |
| 산소 연결 미리보기 | 문 개폐별 진공 전파 | 실제 그래프와 다른 시각 배치 |
| 침투 시뮬레이션 | 진입 위치, 병목, 방어 도달 시간 | 도달 불가능한 핵심 방 |
| UI 안전 영역 | 장비·드론·함선 표시 | 플레이 가능한 부분의 화면 밖 배치 |

의도적으로 고립된 방은 오류와 다르다. 기함처럼 특수한 설계에서는 고립이 게임 규칙일 수 있으므로 `intentionalIsolation` 같은 명시적 면제 사유를 둔다. 모든 함선을 하나의 연결 그래프로 자동 수정하면 원작의 전술 차이를 없애게 된다.

## 7. 무기·시스템 비교 도구

장비 편집기는 단일 DPS 순위표보다 조건별 결과를 보여줘야 한다.

| 테스트 환경 | 관찰 지표 |
|---|---|
| 실드 없음·회피 없음 | 최소 충전 이후 순수 피해 처리 |
| 여러 실드 층 | 첫 유효 피해까지 시간과 발사 소모 |
| 일정 회피율 | 평균·분산·무효 일제사격 비율 |
| 방 크기 변화 | 표적 방식·산탄·빔 경로의 영향 |
| 전력 부족 | 가능한 활성 조합과 충전 손실 |
| 시스템 손상 | 장비 정지 우선순위와 복구 시간 |
| 소모품 부족 | 실행 가능한 공격 횟수 |
| 해킹·은폐 등 결합 | 피해 시간창과 재사용 공백 |

모든 수치를 자동으로 하나의 점수로 합치면 전술 역할이 가려진다. 적 시스템을 멈추는 무기, 승무원을 공격하는 무기, 선체만 빠르게 줄이는 무기를 같은 순위 기준에 억지로 맞추지 않는다.

## 8. 콘텐츠 정적 검증 규칙

| 오류 코드 | 검출 내용 | 기본 처리 |
|---|---|---|
| `REF_NOT_FOUND` | 후속 이벤트·아이템·종족 ID가 없음 | 빌드 실패 |
| `NO_VALID_CHOICE` | 진입 가능하지만 모든 선택 불가 | 빌드 실패 또는 필수 검토 |
| `IMPOSSIBLE_REQUIREMENT` | 상호배타 조건을 동시에 요구 | 빌드 실패 |
| `WEIGHT_SUM_ZERO` | 가중 선택의 유효 후보 없음 | 빌드 실패 |
| `NEGATIVE_RESOURCE_PATH` | 비용 이후 불법 음수 상태 | 빌드 실패 |
| `AE_REFERENCE_LEAK` | AE 꺼짐 경로가 AE 전용 정의 참조 | 빌드 실패 |
| `UNREACHABLE_QUEST` | 퀘스트 목표가 가능한 경로에 없음 | 경고 후 생성 검증 |
| `DUPLICATE_REWARD_ID` | 서로 다른 결과가 같은 처리 ID 공유 | 빌드 실패 |
| `MISSING_LOCALIZATION` | 선택지·경고·아이템 이름 키 없음 | 빌드 실패 |
| `UNVERIFIED_NUMBER` | 원작 데이터로 표시했지만 근거 없음 | 검토 경고 |
| `LAYOUT_ISOLATION` | 의도 설명 없는 고립 방 | 검토 경고 |
| `CAPACITY_UNHANDLED` | 장비·승무원 초과 보상 처리 없음 | 빌드 실패 |

조건 검증의 정확도가 부족하면 가능한 콘텐츠까지 잘못 제거할 수 있다. 복잡한 조건은 정적 분석만으로 결론 내리지 않고 대표 상태를 넣는 실행 검증으로 보완한다.

## 9. 동적 재생 도구

제작자가 이벤트를 시험하려고 매번 새 게임을 시작할 필요는 없다. 다음 기능을 개발 전용 도구로 제공한다.

1. 함선·섹터·자원·종족·시스템 수준을 가진 테스트 상태를 불러온다.
2. 이벤트 또는 적 함선 생성 정의를 선택한다.
3. 사용 가능한 선택지와 숨겨진 선택지의 조건 실패 이유를 표시한다.
4. RNG 결과를 지정하거나 여러 결과를 순회한다.
5. 비용·보상·승무원·퀘스트 변경 전후를 비교한다.
6. 결과 직전과 직후 저장·재개를 실행한다.
7. 같은 테스트를 AE 켜짐·꺼짐, 각 난이도에서 반복한다.

디버그 UI는 숨은 적 상태와 추첨 결과를 표시할 수 있지만, 일반 플레이 UI에 그 정보가 섞이지 않도록 별도 권한 또는 빌드 플래그로 묶는다.

## 10. 로컬라이제이션과 표현 검증

- 표시 문자열과 판정 조건을 분리한다. 번역 문장 안의 숫자를 파싱해 실제 비용으로 쓰지 않는다.
- 비용·보상 수치는 데이터에서 삽입하여 본문과 실제 적용값이 어긋나지 않게 한다.
- 특수 선택지의 색만으로 이용 조건을 전달하지 않는다.
- 긴 한국어 문장이 선택 버튼, 자원 아이콘, 취소 영역을 덮지 않게 한다.
- 이름이 같은 두 승무원도 ID로 구별하고, 손실·복제·해고 메시지는 대상 확인이 가능해야 한다.
- 기함·해금·퀘스트 고유명은 용어집의 표기를 사용한다.

## 11. 제작과 검수 책임

| 산출물 | 작성 책임 | 검수 관점 |
|---|---|---|
| 규칙 정의 | 시스템 기획 | 실제 원작 근거와 제안의 구분 |
| 콘텐츠 데이터 | 콘텐츠 기획 | 조건·보상·연결의 완결성 |
| 레이아웃 | 함선·레벨 기획 | 이동, 산소, 침투, 가독성 |
| 실행 코드 | 프로그래밍 | 상태 일관성, 저장, 결정론 |
| 표현·텍스트 | UI·아트·현지화 | 정보 정확도와 조작 맥락 |
| 회귀 패키지 | QA | 경계 조건·복합 상황·재개 안정성 |

수치 변경 요청에는 변경 이유, 영향을 받는 조합, 기대 결과와 비교 테스트를 함께 남긴다. 단순히 “체감상 약함”만 기록하면 이후에 같은 문제가 반복된다.

# 15. 적 함선 생성·전투 AI

> 범위: 본편 + AE. 확인일: 2026-11-13. 원작의 전체 생성 알고리즘이나 AI 소스 코드를 확인하지 않았다. [확인]은 공개 자료의 관찰 가능한 규칙, [해석]은 분석, [재구성안]은 독립 설계다. 내부 점수·가중치를 원작의 확정값처럼 사용하지 않는다.

## 1. 역할과 경계

적 생성은 플레이어가 가진 도구를 다양한 조합으로 시험한다. AI는 생성된 함선을 운용하여 무기 사격, 수리, 인원 이동, 특수 시스템, 도주·항복을 실행한다. 두 기능은 같은 적을 구성하지만 수명 주기가 다르다.

**[해석]** 생성은 전투가 시작되기 전의 문제이고 AI는 전투 도중의 문제다. 둘을 분리하면 같은 적 조합으로 전투 AI만 비교하거나, 같은 AI로 장비 구성의 난이도만 측정할 수 있다.

| 계층 | 입력 | 출력 |
|---|---|---|
| 조우 선택 | 이벤트, 섹터, 세력, 콘텐츠 옵션 | 적 템플릿 |
| 생성 | 템플릿, 진행도, 난이도, 난수 | 선체·설비·장비·승무원 구성 |
| 전략 제어 | 항복·도주 조건, 목표 | 교전 유지·탈출 준비·결과 제안 |
| 전술 제어 | 사격·설비·인원 상태 | 표적·전력·작업 명령 |
| 공간 행동 | 경로·문·위험·슬롯 | 이동·수리·교전 |

## 2. 확인된 생성 원리

**[확인]** 적 함선은 섹터 진행과 난이도에 따라 강해지며, 함종별로 허용되는 설비·무기·드론·승무원의 범위가 있다. 같은 외형이 항상 같은 내부 구성이나 전투력을 의미하지 않는다. 보상과 행동은 해당 조우 이벤트의 영향을 받을 수 있다. [A01]

**[해석]** 이 구성은 완전 무작위보다 읽을 수 있는 무작위다. 외형과 세력에서 대략적인 위험을 예상하고, 실제 실드 수·무기·드론·특수 기능을 보고 판단을 수정한다. 알 수 없는 요소가 남아 있으므로 센서·정찰·첫 공격까지의 관찰 시간이 의미를 가진다.

**확인되지 않은 주장:** 현재 플레이어 장비를 보고 항상 상대 장비를 맞춰 주는 동적 상성 생성, 승률을 일정하게 유지하는 숨은 난이도 보정, 모든 생성값이 단일 섹터 배율로 결정된다는 설명은 본 문서에서 원작 규칙으로 채택하지 않는다.

## 3. 적 유형의 기능적 분류

아래의 분류명과 위험 해석은 **[해석]**이다. 실제 생성 가능한 모든 조합을 열거하는 테이블은 아니다.

| 기능적 유형 | 관찰할 특징 | 시험하는 플레이어 능력 |
|---|---|---|
| 단순 포격형 | 투사체 수·실드·무기 충전 | 일제사격과 방어 투자의 효율 |
| 미사일 압박형 | 일반 실드를 우회하는 위협 | 회피·방어 드론·선제 무력화 |
| 드론 운용형 | 지속 사격·빔·방어 드론 | 순간 화력과 지속 화력의 구분 |
| 침투형 | 텔레포터·강한 전투 종족 | 선내 방어와 수리 인력 배분 |
| 제어형 [AE] | 해킹·정신 지배 | 기능 장애와 일시 적대 관계 대응 |
| 무인함선 | 승무원 부재·진공·자동 수리 | 승무원 제거 이외의 승리 수단 |
| 특수 실드형 | 전투 시작 보호층 | 제어 기능 사용 전 방어층 제거 |
| 보스 | 고정 페이즈·지속 상태·특수 공격 | 장기 빌드의 종합 완성도 |

Lanius 적은 산소 없는 내부와 특수 시스템 조합 때문에 일반적인 생물 승무원 침투와 다른 대응을 요구한다. Slug 계열에서는 인원 정보·정신 지배 면역·문이 침투 판단에 영향을 준다. [A02, A03]

## 4. 재구성 생성 파이프라인

다음은 재현 프로젝트용 **[재구성안]**이다. 실제 FTL의 코드 호출 순서나 예산 공식을 뜻하지 않는다.

1. 이벤트가 요구한 적 세력·함종·특수 조건을 고정한다.
2. AE 옵션과 섹터 범위를 만족하는 템플릿을 후보로 모은다.
3. 템플릿의 필수 설비와 최소 기능을 설치한다.
4. 섹터·난이도 테이블에서 선체와 설비 수준을 결정한다.
5. 슬롯·전력 조건 안에서 장비를 뽑는다.
6. 승무원 구성과 초기 위치를 배치한다.
7. 항복·도주·승리 후 이벤트 참조를 연결한다.
8. 모든 제약을 검증한 뒤 하나의 스냅샷으로 전투에 전달한다.

```json
{
  "archetypeId": "example_raider",
  "contentSet": "base",
  "allowedSectorRange": [1, 7],
  "mandatorySystems": ["piloting", "engines", "weapons"],
  "optionalSystemPool": ["shields", "drones"],
  "weaponPoolId": "example_raider_weapons",
  "crewPoolId": "example_mixed_crew",
  "scalingTableId": "example_sector_difficulty",
  "outcomePolicyId": "example_encounter"
}
```

`example_` 데이터는 설명용이며 원작 ID나 수치가 아니다. 생성 과정에서 계속 실패하여 장비를 재추첨할 때는 실패 원인을 기록한다. 무제한 재추첨은 특정 장비가 비정상적으로 자주 나오는 편향을 숨긴다.

### 4.1 검증 규칙

**[재구성안]** 생성기의 필수 검사와 밸런스 경고를 분리한다.

| 필수 무결성 검사 | 별도 밸런스 검토 |
|---|---|
| 설치된 무기를 담을 슬롯이 존재 | 해당 섹터에서 제어 효과가 과도하게 겹치는가 |
| 필요한 설비·방 참조가 유효 | 상대가 피해를 줄 기회가 지나치게 일방적인가 |
| 승무원 배치가 유효한 방을 가리킴 | 방어·공격·회복이 동시에 극단값인가 |
| AE 비활성에서 AE 전용 데이터 미노출 | 어려운 조합이 의도된 변동성인가 |
| 결과 이벤트와 도주 경로가 존재 | 여러 조우 누적 시 자원 소모가 적정한가 |

밸런스 경고가 있다는 이유로 반드시 적을 약화시키지는 않는다. 이는 원작의 실제 생성 필터로 주장하지 않는 제작·검수 도구다.

## 5. AI의 서로 다른 의사결정 주기

**[해석]** 모든 판단을 매 프레임 최적화하면 적은 불필요하게 완벽해질 뿐 아니라 시각적으로 계속 표적을 바꿀 수 있다. 장비 운용, 승무원 작업, 도주 의사결정은 서로 다른 시간 단위가 적합하다.

**[재구성안]** AI를 다음 모듈로 나눈다.

- `EncounterDirector`: 이벤트 명령·항복·도주 상태를 관리한다.
- `WeaponController`: 발사 가능성과 표적 정책을 관리한다.
- `SystemController`: 해킹·은폐·정신 지배·드론 등 발동을 관리한다.
- `CrewCoordinator`: 수리·방어·의료·조작 업무를 배정한다.
- `CrewAgent`: 배정된 방으로 이동하고 로컬 작업을 실행한다.

모듈은 명령을 제안하고 공통 규칙 계층이 실행 가능성을 최종 검사한다. AI만 냉각·실드·문 규칙을 우회하는 것은 명시적으로 확인한 예외에 한정한다.

## 6. 표적 선택

**[확인 범위]** 커뮤니티의 분석과 고난도 플레이 자료는 난이도에 따라 적 사격 표적 선정이 달라지고, Hard에서는 현재 중요 시스템을 우선하는 선택이 포함된다고 보고한다. 단순히 모든 방을 항상 균등 추첨하는 모델은 이 관찰과 맞지 않는다. 다만 본 작업에서 원작 코드를 확인한 것은 아니다. [A04, A05]

**[재구성안]** 표적 정책을 아래처럼 교체 가능한 전략으로 둔다.

```text
candidateRooms = visible_or_rule_allowed_rooms()
policy = choose_target_policy(difficultyProfile, encounterRng)
target = policy.select(candidateRooms, observedCombatState)
submit_fire_order(target)
```

무기 충전이 끝난 순간의 목표, 발사 시작 순간의 목표, 연사 중 각 투사체의 목표가 같다고 가정하지 않는다. 빔·범위 무기·다연발은 각자의 표적 표현이 필요하다.

**[검증 필요]** 알려진 난이도별 확률과 우선 시스템의 정확한 조건은 동일 버전의 반복 관측으로 확정한다. 이 문서에는 임의 점수표를 원작 수치로 넣지 않는다.

## 7. 승무원 AI

**[확인 범위]** 적은 의료실 이용, 실드 복구, 침입 대응, 위험 회피 등을 수행하고, 방을 오가게 만드는 플레이어의 조작에 반응한다. 공개 침투 자료에는 특정 우선순위를 이용한 유인 전술이 기록되어 있다. 이것만으로 모든 상황을 포괄하는 고정 우선순위 목록이 확정되지는 않는다. [A06]

**[재구성안]** 각 작업은 대상·필요 인원·중요도·중단 조건을 가진다.

```text
TaskRequest
  id, kind, targetRoom
  minWorkers, maxWorkers
  priorityBand
  assignedCrew
  interruptRules
  validityPredicate
```

같은 작업에 모든 인원이 몰리는 문제를 막기 위해 슬롯·경로·이미 배정된 인원을 고려한다. 위험한 방에 이동 중인 인원의 생존 가능성도 평가하되, 원작보다 현명하게 개선한 정책은 별도 모드로 명시한다.

### 작업 지속성

**[해석]** 이미 시작한 회복·수리·이동을 얼마나 오래 유지하는지가 AI의 개성이다. 판단 점수가 매 순간 조금 바뀔 때마다 전체 인원이 역방향으로 움직이면 안정적인 대응 패턴이 없다. 작업 종료 또는 긴급 사건에서만 재배정하거나, 전환 비용을 주는 방식이 재현 작업에 유용하다.

## 8. 무인함선 특례

**[확인]** 무인 적은 산소·승무원 없이 작동하고 시스템을 자동 수리한다. Mike Hopley의 Hard 기준 자료는 시스템 한 칸의 자동 수리를 37.5초로 정리하며, 균열이 있는 시스템은 수리하지 못한다고 설명한다. 동일 자료는 적 무인함선이 일반적으로 항복하지 않으며 특정 이벤트의 시작부터 도주하는 경우를 구별한다. [A07]

**[해석]** 무인함선의 약점은 생명체 제거가 아니라 설비 상태와 공간 분절이다. 승무원을 교란하는 빌드는 일부 효용이 낮아지고, 균열·산소 저항·직접 시설 파괴의 상대 가치가 달라진다.

**[재구성안]** 자동 수리를 “보이지 않는 승무원”으로 구현하지 않는다. 무인 제어 효과와 실제 승무원 존재를 분리해야 정신 지배·생명체 감지·승무원 제거 판정이 올바르게 작동한다.

## 9. 항복·도주·전투 종료

**[해석]** 항복은 플레이어가 남은 위험과 제안 보상을 교환하는 선택이다. 도주는 적을 빨리 파괴하거나 추진·조종 기능을 막도록 목표를 바꾼다. 둘을 단순히 “적 HP가 낮으면 종료”로 합치면 선택의 의미가 사라진다.

**[재구성안]** 전투 상태를 `Fighting`, `SurrenderOffered`, `Fleeing`, `Resolved`로 분리한다. 항복을 거절한 상태에서 동일 프롬프트가 무한히 열리지 않게 제안 사용 여부를 기록한다. 도주는 이벤트 타이머인지 시스템 충전인지 종류를 명시하고, 기함의 페이즈 이탈은 일반 도주와 다른 결과로 보낸다.

적 도주 시간이 플레이어 FTL 충전 공식과 완전히 같다는 가정은 하지 않는다. 공개 자료에서도 이벤트별 타이머와 시스템 기능 정지의 관계를 구별한다. [A01, A07]

## 10. QA·분석 로그

| ID | 검사 | 합격 기준 |
|---|---|---|
| AI-01 | 같은 생성 seed·조건으로 재생성 | 같은 적 스냅샷 |
| AI-02 | AE off 대량 생성 | 전용 시스템·인종·장비가 잘못 혼입되지 않음 |
| AI-03 | 동일 조우를 난이도만 변경 | 의도한 표에서만 변경 발생 |
| AI-04 | 의료실·실드·화재 동시 위기 | 작업 배정의 이유와 중단 이유 추적 가능 |
| AI-05 | 마지막 생물 적 사망, 자동함선 | 생물 인원수만으로 보상 지급하지 않음 |
| AI-06 | 도주 중 조종·엔진 정지 | 정책에 맞춰 타이머 정지·재개 |
| AI-07 | 전투 결과 프레임에 마지막 사격 | 결과 중복·새로운 AI 명령 발행 없음 |
| AI-08 | 적의 표적 분포를 반복 수집 | 설정 정책과 통계적으로 부합 |
| AI-09 | 문·봉쇄로 목표 접근 불가 | 무한 이동·빈번한 작업 진동 없음 |

**[재구성안]** 로그는 `time, ship, decisionType, candidates, chosenTarget, reason, rngDrawIndex`를 남긴다. 적이 왜 그 방을 공격했는지 설명 가능한 로그는 생성 버그와 체감 난이도 문제를 분리하는 데 필요하다.

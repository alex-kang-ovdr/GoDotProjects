# 03. 이벤트·선택지·퀘스트·서사

> 역할: 제한된 텍스트와 선택으로 전투·자원·승무원·지도 상태를 연결한다.  
> 범위: 원작과 AE 이벤트 구조. 원문 대사나 전체 이벤트 목록의 복제가 아니라 조건과 결과의 역기획이다.

## 1. 이벤트가 담당하는 게임플레이

**[확인]** FTL은 다수의 텍스트 조우를 통해 선택을 요구하며, 같은 런에서도 적·이벤트·결과가 달라질 수 있다. [O1]

**[해석]** 이벤트의 목적은 전투 사이에 이야기를 붙이는 데 그치지 않는다. 장비와 승무원의 가치를 전투 밖으로 확장하고, 지도 경로에 목적지를 만들며, 현재 자원을 다른 종류의 기회로 바꾼다. 전투용으로 구매한 장비가 구조 상황을 해결하면 빌드의 의미가 달라진다.

## 2. 구성 요소

| 요소 | 설명 | 대표 연동 |
|---|---|---|
| 상황 텍스트 | 의사결정에 필요한 맥락 | 서사·정보 불확실성 |
| 선택지 | 플레이어의 명시적 행동 | 입력·조건 검사 |
| 요구 조건 | 종족·장비·설비·자원·플래그 | 함선·승무원·경제 |
| 결과 분기 | 확정 결과 또는 확률 결과 | RNG·위험 |
| 효과 | 보상·손상·승무원·추격·전투 | 거의 모든 시스템 |
| 후속 이벤트 | 결과를 다시 선택으로 연결 | 연속 조우 |
| 퀘스트 목적지 | 이후 비콘에 배치하는 콘텐츠 | 지도·추격 |
| 해결 상태 | 중복 처리 방지와 저장 | 런 지속성 |

### 정보와 효과의 구분

**[재구성안]** “당신은 연료를 얻었다”라는 문자열을 해석해서 실제 연료를 추가하는 구조를 피한다. 텍스트는 표현이고 `ResourceDelta`는 규칙이다. 그래야 번역, UI 수정, 자동 검증과 저장이 서로 영향을 덜 준다.

## 3. 선택지의 유형

| 유형 | 특징 | 설계상 주의점 |
|---|---|---|
| 보편 선택지 | 대부분의 함선이 선택 가능 | 거절·무시가 항상 있어야 하는 것은 아님 |
| 조건 선택지 | 특정 장비·종족·설비가 있어야 함 | 조건 충족과 결과의 안전성을 혼동하지 않음 |
| 비용 선택지 | 자원을 내고 결과를 얻음 | 지급 전 자원 검사, 중복 차감 방지 |
| 위험 선택지 | 일부 분기에서 손실 발생 | 확률을 문맥 없이 임의로 균등화하지 않음 |
| 전투 선택지 | 함선 또는 선내 전투 생성 | 시작 상태·환경·항복 정책을 함께 설정 |
| 퀘스트 선택지 | 현재 보상보다 미래 기회를 생성 | 목적지가 없을 때의 처리 필요 |

## 4. 청색 선택지(Blue Options)

**[확인]** 특정 승무원·장비·설비 조건에 따라 추가 선택지가 제공된다. 청색 선택지는 그 조건을 사용할 수 있다는 뜻이며, 반드시 최고 보상이나 무위험 결과를 뜻하지 않는다. 일부는 비용을 요구하거나 다른 선택보다 보상이 낮을 수 있다. [E1][E2]

### 조건은 한 종류가 아니다

| 조건 축 | 예시로 표현할 수 있는 검사 | 구현 시 질문 |
|---|---|---|
| 승무원 종족 | Engi가 있는가 | 사망 대기·원격 파견 상태도 포함하는가? |
| 시스템 설치 | 텔레포터가 있는가 | 설치만 필요한가, 정상 작동도 필요한가? |
| 시스템 레벨 | 의료 설비가 지정 수준 이상인가 | 손상 후 유효 레벨과 설치 레벨 중 무엇을 검사하는가? |
| 장비 보유 | 특정 드론 설계도가 있는가 | 화물칸 보유도 허용되는가? |
| 자원 | 드론 부품을 지급할 수 있는가 | 보상과 비용의 순서가 결과에 영향을 주는가? |
| 런 플래그 | 앞선 이벤트를 해결했는가 | 섹터를 넘어 보존해야 하는가? |

위 질문의 정답은 이벤트마다 다를 수 있다. **[재구성안]** 모든 조건을 `hasItem()` 하나로 축약하지 말고 `InstalledSystemLevel`, `CargoContains`, `AliveCrewSpecies`, `ConsumableAtLeast`처럼 명시한다. 원작과 일치해야 하는 조건은 이벤트 단위로 확인한다.

## 5. 대표 사례: 거대 외계 거미

아래는 이벤트 원문을 옮기지 않고 **기계적 구조만 요약**한 것이다. [E3]

| 접근 | 규칙상 차이 | 설계 해석 |
|---|---|---|
| 일반 승무원 파견 | 성공 보상과 승무원 손실 가능성이 공존 | 인적 자원을 걸고 기회를 얻음 |
| 관여하지 않음 | 이벤트 해결 보상 없이 떠남 | 위험을 거절하는 기본 선택 |
| 대인 드론 사용 | 조건을 만족하면 별도 해결 경로 | 전투 장비에 비전투 가치를 부여 |
| 강습 드론 사용 | 다른 보상 경로 | 같은 문제를 해결해도 수단에 따라 결과가 다름 |
| 대인 빔 사용 | 또 다른 장비 기반 해결 | 드문 장비를 이벤트 열쇠로 사용 |
| 클론실 보유 | 일부 사망 결과의 손실 양상이 달라짐 | 사전 투자로 위험 비용을 바꿈 |

**[해석]** 중요한 것은 “최선의 버튼 하나를 외우는 것”보다 같은 이벤트가 함선 상태에 따라 다른 위험이 된다는 점이다. 동시에 조건 선택지가 여러 개여도 보상을 동일하게 만들면 장비별 특징이 줄어든다.

**[검증 필요]** 이 이벤트의 드론 부품 비용에 관한 문헌에는 보상과 겹칠 때의 버그가 기록되어 있다. 재구현에서는 비용 차감의 명확한 계약을 정하고, 원본 버그 호환 여부를 별도 정책으로 둔다.

## 6. 확률 결과와 불확실성

### 6.1 서로 다른 무작위 층

1. 이 섹터에 이벤트 풀이 선택되는 단계.
2. 비콘에 특정 이벤트가 배치되는 단계.
3. 플레이어가 선택한 후 결과 분기가 결정되는 단계.
4. 보상 유형 안에서 수량·장비가 결정되는 단계.

**[해석]** 모든 난수를 한 번의 성공률로 묶으면 “이벤트를 만날 가능성”과 “만난 뒤 실패할 가능성”을 구분할 수 없다. 밸런싱과 QA 역시 두 확률을 따로 봐야 한다.

**[재구성안]** 결과 분기는 정수 가중치로 정의하고, 총합 0·음수·도달 불가능 분기를 제작 도구에서 거부한다. 이는 원작 XML 형식의 재현이 아닌 제안이다.

```text
WeightedOutcome
  weight
  predicates[]
  effects[]
  nextEvent?
```

각 선택지가 항상 50:50이라는 가정은 하지 않는다. 특정 이벤트의 실제 확률을 모르면 임의값을 원작 규칙으로 표기하지 않는다.

## 7. 효과의 유형

| 효과 | 저장할 값 | 예외 |
|---|---|---|
| 자원 변경 | 종류·증감량·상한 정책 | 부족한 자원 비용, 음수 방지 |
| 선체/시스템 손상 | 대상·양·원인 | 선체 손상과 균열의 구분 |
| 장비 지급/제거 | 장비 ID·인스턴스 ID | 화물칸·장착 슬롯 초과 |
| 승무원 합류/손실 | 종족·숙련·개체 ID | 정원 초과, 클론 적용 여부 |
| 전투 시작 | 적 프리셋·환경·목표 | 도주·항복·정찰선 플래그 |
| 퀘스트 생성 | 후속 콘텐츠·배치 조건 | 현재 섹터에 유효 목적지가 없음 |
| 추격 변경 | 지연/증가·유효 횟수 | 다른 변경 효과와의 중첩 |
| 상점 제공 | 재고·거래 상태 | 대화창 종료 후의 지속성 |
| 해금 기록 | 해금 조건·대상 | 현재 런과 프로필의 저장 시점 |

**[재구성안]** 사망과 실종·납치·이탈을 `removeCrew` 하나로 처리하지 않는다. `lossCause`와 `clonePolicy`를 분리해야 클론실이 모든 인적 손실을 되돌리는 오류를 막을 수 있다. 실제 이벤트별 복제 가능 범위는 [13번](13_advanced_edition_systems.md)과 원본 이벤트 확인이 필요하다.

## 8. 퀘스트 목적지

**[확인]** 퀘스트는 지도에 별도 목적지를 추가할 수 있다. 현재 섹터에서 적절한 목적지를 확보하기 어렵다면 다음 섹터로 넘어가기도 하며, 마지막 섹터는 일반 퀘스트 배치에 예외가 있다. [M1]

### 배치 알고리즘 제안

```text
createQuest(quest):
  candidates = collectEligibleUnvisitedBeacons(currentSector)
  candidates = removeProtectedBeacons(candidates)
  candidates = applyQuestEnvironmentConstraints(candidates)
  if not empty(candidates):
      assignQuest(selectCandidate(candidates))
  else if nextSectorAcceptsQuests():
      enqueueForNextSector(quest)
  else:
      resolveQuestUnavailable(quest)
```

이는 **[재구성안]**이다. 원작의 무작위 선택 순서나 가중치를 뜻하지 않는다. 목적지 없이 퀘스트 텍스트만 성공으로 표시되거나, 이미 사용한 상점·출구를 의도치 않게 덮어쓰는 문제가 없어야 한다.

## 9. 완결된 이벤트 데이터 예시

다음은 **문서 전용 가상 이벤트**다. ID·대사·수치·분기 모두 원본 데이터가 아니며, 조건과 효과를 분리하는 방법을 보여준다.

```json
{
  "id": "demo_disabled_observatory",
  "origin": "reconstruction_example",
  "uniqueScope": "sector",
  "textKey": "demo.observatory.intro",
  "choices": [
    {
      "id": "leave",
      "labelKey": "demo.leave",
      "requirements": [],
      "effects": []
    },
    {
      "id": "engineering_assist",
      "style": "conditional",
      "requirements": [
        {"kind": "alive_crew_species", "species": "engi"}
      ],
      "effects": [
        {"kind": "reward_table", "table": "demo_engineering_reward"},
        {"kind": "set_flag", "flag": "demo_observatory_helped"}
      ]
    }
  ]
}
```

`style=conditional`은 색상만 의미한다. 실제 선택 가능 여부는 `requirements`가 결정한다. UI가 선택지를 표시한 뒤 조건이 바뀔 수 있는 구조라면 실행 순간에도 다시 검증한다.

## 10. 결과 확정과 저장

**[재구성안]** 선택 처리에는 `eventInstanceId + choiceId + resolutionIndex` 같은 식별자를 부여한다. 한 번 확정한 선택은 저장 후 다시 열어도 비용·보상이 중복되지 않아야 한다.

```text
ResolveChoice:
  validate current event and requirements
  select outcome once
  construct effects transaction
  apply costs and effects exactly once
  persist resolved outcome identity
  show resulting text or begin encounter
```

개발자 패치노트에는 이벤트가 다른 결과로 복원되는 저장 문제가 수정된 이력이 있다. [O2] 이는 저장 설계에서 이벤트의 표시 텍스트만 남기면 부족하다는 점을 보여주는 과거 사례이며, 현재 버그라고 주장하는 것은 아니다.

## 11. 콘텐츠 설계 해석

### 11.1 도덕 선택과 경제 선택이 겹친다

도움을 줄 것인가라는 질문은 동시에 선체·승무원·연료를 얼마나 걸 것인가라는 질문이 된다. 도덕적으로 우호적인 선택이 항상 보상을 보장하면 생존 상황의 긴장이 약해진다. 반대로 정보 없이 손실만 반복되면 플레이어는 모든 위험 선택을 거절하게 된다.

### 11.2 장비의 잠재 가치

즉시 전투 성능이 낮은 장비라도 특정 이벤트의 안전장치가 될 수 있다. 다만 플레이어가 아직 만나지 못한 이벤트의 정확한 빈도를 알기 어렵기 때문에, 장비 가격 전체를 이벤트 기대값으로 정당화하기는 어렵다.

### 11.3 반복 플레이와 학습

첫 런에서는 텍스트와 보유 능력으로 판단하고, 반복 플레이에서는 사건의 패턴과 결과를 학습한다. 이 때문에 명확한 선택 조건, 일관된 효과, 장비별 차이를 유지하는 것이 중요하다.

## 12. 검증 시나리오

| ID | 전제·행동 | 기대 또는 관찰 항목 |
|---|---|---|
| EVT-01 | 요구 종족이 있는 상태와 없는 상태 | 조건 선택지의 등장/활성화 차이 |
| EVT-02 | 비용에 해당하는 부품 수량이 0 | 지급이 필요한 선택을 실행하지 못함 |
| EVT-03 | 선택 확정 직후 중단·복원 | 동일 결과 유지, 비용·보상 중복 없음 — 재구성안 |
| EVT-04 | 정원 가득 찬 상태에서 승무원 보상 | 초과 인원 처리 UI와 상태 일관성 |
| EVT-05 | 장비 지급 시 모든 보관 슬롯 사용 중 | 지급 보류/교체/폐기 중 명시적 정책 적용 |
| EVT-06 | 현재 섹터에 퀘스트 대상 없음 | 다음 섹터 이월 또는 불가 결과 |
| EVT-07 | 클론실이 있지만 복제 불가 손실 사건 | 무조건 복구하지 않음 |
| EVT-08 | 여러 청색 선택지가 동시에 충족 | 모두 동일 보상이라고 가정하지 않음 |
| EVT-09 | 유일 이벤트를 같은 섹터에서 재추첨 | 정해진 유일성 범위 준수 — 재구성안 |
| EVT-10 | 재고 있는 상점을 이벤트가 열어 줌 | UI 재진입으로 재고가 초기화되지 않음 — 재구성안 |
